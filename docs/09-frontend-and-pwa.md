# 09 - Frontend and PWA

## Shape (Decided)

A React single-page application built with Vite, served by the API process in 1.0, installable as a PWA. It talks to the API only through the generated typed client and to run state only through SSE. It contains no business rules: validation, routing, and execution semantics live in `contracts`, `domain`, and the backend. The editor can still validate drafts locally by importing `contracts` and `domain`, since both are pure.

## Screens (Decided list, Draft details)

| Screen        | Purpose                                                                                                                                 |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Loops         | List, create, import, export, publish state, last run status                                                                            |
| Editor        | Canvas with palette, property panel, validation panel, version bar with draft and publish                                               |
| Runs          | List across loops with filters; parent and child relationships                                                                          |
| Run inspector | Timeline of events, thread view at any point, per-node diff of the patch, waiting-for-input form, cancel, pause, resume, replay-at-node |
| Settings      | Model catalog, defaults for model and effort, secrets, API keys, harness preflight status, scheduler status                             |
| Events        | Inbound events and webhook deliveries, with what they triggered                                                                         |

## Editor (Draft)

- Canvas: `@xyflow/react` with custom node components per kind, labelled output handles for decision routes and exit loop-back, and edge validation that refuses connections into triggers or out of unknown ports.
- Palette: the nine node kinds, drag to add.
- Property panel: generated from the node kind's Zod schema with react-hook-form. Templates and expressions use CodeMirror with Liquid and JSONata modes and a preview that renders against a sample thread.
- Validation panel: the same `domain` validation the backend runs, surfaced live, so publish never fails by surprise.
- Subloop picker: searches published loops and shows their trigger input schema and return shape.
- Variables: the loop's declared variables with schemas, edited in a side sheet.

## Run inspector (Draft)

- Timeline from the SSE stream with the cursor stored so reload resumes without gaps.
- Thread viewer that reconstructs the thread at any event by replaying patches client-side using `domain`.
- Node progress drawer that shows harness items as they arrive.
- Wait handling: when the run is waiting on input, a form rendered from the wait node's `inputSchema` appears inline.

## PWA behaviour (Decided)

- `vite-plugin-pwa` with Workbox, `registerType: 'prompt'`.
- Update flow: the service worker detects a new build, the app shows a toast "A new version is available" with an Update button, the user confirms, the new worker activates, and the page reloads. No automatic activation.
- Precache: the app shell only. API responses are never cached by the worker.
- Offline: the shell opens and unsaved editor drafts persist in IndexedDB. Anything needing the backend shows a clear offline state. Active queries that failed because the API could not be reached retry on the browser's `online` event, including after an offline reload, without navigating. Each fetch keeps the one-retry limit; HTTP errors keep the existing query behaviour. There is no offline execution.
- Reconnect limitation: if the `online` event arrives while a no-data fetch is still in flight, before its connectivity error is stored, recovery still depends on that fetch's remaining retry or a later refetch.
- Install: a web manifest with icons; an install hint in settings.

## State and data (Decided)

- Server state: TanStack Query over the generated client.
- Live run state: a small SSE hook that appends to a per-run event store in Zustand and exposes projections.
- Editor state: Zustand store holding the draft definition; autosave to the draft endpoint with debounce; local IndexedDB mirror for offline.

## Accessibility and UX baseline (Draft)

Keyboard navigation for palette and property panels, visible focus states, colour-blind-safe status colours, and reduced-motion support. The canvas gets keyboard shortcuts for add, delete, connect, and fit-to-view.

## Design tokens (Decided, #7)

The look comes from design tokens, implemented to the visual direction the owner approved (`docs/design/visual-direction/`, ADR-0017). Dark is the default theme and light the alternate.

- **Two tiers** in `apps/web/src/styles/tokens.css`. The primitive tier is the palette (green, brown, grey, magenta, violet, blue, orange, amber, red, teal, slate); only the semantic tier references it. The semantic tier names what a colour is for: surfaces (`--surface-app`, `-raised`, `-sunken`, `-overlay`, `-hover`, `-control`, `-field`, `-inverse`), text (`--text-default`, `-muted`, `-subtle`, `-link`, `-on-accent`, ...), borders, the accent (goblin lime, with `--accent-highlight` magenta and `--accent-glow` purple reserved for the most special moments), danger, status tones (`--status-{neutral,good,bad,warn,info}-{bg,fg,border}`: blue success, orange failure, amber waiting, violet running, always with an icon), node kinds (`--kind-<kind>` and `--kind-<kind>-subtle`), the focus ring, code, canvas, mascot, and shadows. It is declared for light on `:root, [data-theme='light']` and for dark on `[data-theme='dark']`, each with its `color-scheme`, so native controls, scrollbars, and date inputs follow the theme. Type (`--font-ui`, `--font-code`, `--font-size-*`), space, radius, and motion scales are theme independent; the motion durations drop to 0 ms under `prefers-reduced-motion`, which also stops every keyframe animation (`animation: none`, so the running and live pulses hold at full opacity) and collapses transitions to an instant change.
- **Theme.** The `data-theme` attribute on `<html>` picks the tier; it may also sit on any element, so a subtree can show the other theme. `index.html` ships `data-theme="dark"`, so anything that cannot read a choice shows the default. The theme control is described under "Theme control" below.
- **Tailwind.** `styles/theme.css` maps Tailwind's keys onto the semantic tokens with `@theme inline reference` (`bg-surface-raised`, `text-muted`, `border-default`, `ring-focus`, `bg-status-good-bg`, `font-mono`, `text-sm`, `rounded-md`, `shadow-2`, `gap-section`, `p-page`) and resets Tailwind's default scales, so palette classes such as `bg-slate-100` produce no CSS. Node-kind colours come from `KIND_INFO[kind].color`, a token name: `editor/KindChip.tsx` sets `--k` and `--k-subtle`, read by `bg-kind` and `bg-kind-subtle`. The glows and pulse of the highlight moments are utilities in `styles/utilities.css`.
- **Only `src/styles/` holds colour literals.** Components use the utilities or `var(--token)`. `theme-color` and the manifest colours are read from `tokens.css` at build time (`vite.config.ts` with `styles/palette.ts`): the dark header (`--surface-inverse`) and page (`--surface-app`).
- **Third-party widgets.** `styles/code-theme.ts` themes CodeMirror (surface, gutter, active line, selection, cursor, tooltips, the search and replace panel with its fields, buttons, and `--code-match` highlights, and syntax colours from a highlighter keyed by lezer tag names; Liquid delimiters show as operators). `styles/canvas.css` themes xyflow through its `--xy-*` variables: background dots, edges and the selected edge, handles, edge labels as pills, controls, the selection box, and a token focus ring on focused nodes. Edges use xyflow's built-in `smoothstep` path (orthogonal with rounded corners); the exit's loop-back edge keeps its animated dash in the loop colour. Routing that avoids nodes is #18.
- **Fonts.** Geist and Geist Mono (SIL OFL 1.1) are self-hosted in `apps/web/public/fonts` with `OFL.txt`, preloaded, and precached with the app shell, so the offline shell keeps them. Components never name a family; #40 switches `--font-ui`.
- **Reserved accents.** Magenta and purple appear only on the selected canvas node's ring, the heartbeat kind, the waiting-for-input dot on Runs (the navigation supports it; no data feeds it yet), notifications (the update toast), the running badge's glow, the mascot's eyes, and the header's hairline: a 2 px purple-to-magenta line along its bottom edge that fades out to the right (`--accent-hairline`, owner request after the first dark sample; in forced-colours mode it gives way to a plain bottom border). Navigation and buttons stay green and neutral; the current page has a green underline directly under its label.
- **Accessibility.** Every text and non-text token pair meets WCAG AA in both themes (the contrast table generated from `tokens.css`). The focus ring (`--focus-ring`, 2 px, offset 2 px) holds 3:1 on every surface. In forced-colours mode the selected node and the current timeline row keep outlines and badges keep a border, because box shadows are dropped.

### Theme control (Decided, #11)

- **Choice.** Settings → **Appearance** → **Theme** offers **Dark** (the default) and **Light**: two native radios in a fieldset with the legend "Theme", drawn as a segmented control. Tab reaches the chosen option, the arrow keys move the choice, and it applies at once with no reload. There is no header toggle (owner decision).
- **Storage.** `localStorage` key `graphgoblin-theme`, holding the theme's name (`dark` or `light`). Every access is guarded: an empty store, an unknown value, or storage that cannot be read (private mode, blocked site data, a throwing accessor) shows Dark, and an unknown value is left in place. `system` (follow the operating system) is reserved for the installer and reads as Dark until then. Other tabs follow a change through the `storage` event, listened to while the app is mounted (`useThemeAcrossTabs` at the root). `src/lib/theme.ts` holds the storage, `applyTheme`, `setTheme`, and the `useTheme` hook (`useSyncExternalStore` over the `data-theme` attribute, the single source of truth on the page).
- **No flash.** The build (`vite.config.ts`) adds two tags right after `<meta charset>`, ahead of the stylesheet: the `theme-color` meta tag with the dark header colour as `content` and both themes' header colours (`--surface-inverse`, read from `tokens.css`) as `data-dark` and `data-light`, then an inline classic script (`themeBootScript` in `src/lib/theme.ts`) that reads the stored theme and sets `data-theme` and the meta colour before first paint. It is inline because the API sends no Content-Security-Policy and an inline script costs no request; if a CSP is added, it moves to a precached file in `public/` loaded synchronously in `<head>`. If the script could not run, `bootstrap()` applies the stored theme when the app starts (late, but correct).
- **Regression.** `src/lib/theme.test.ts`, `src/settings/sections/AppearanceSection.test.tsx`, and `e2e/theme.spec.ts` (default Dark, Light across reloads with `data-theme` already Light when `<body>` is parsed and never changing afterwards, cleared storage, throwing storage).

### Component structure

- `components/ui/`: one primitive per file (`button`, `field` with `Input`, `Select`, `Textarea`, `Checkbox`, `Label`, `FieldGroup`, and `HelpText`, `card`, `badge`, `alert`, `table`) behind `index.ts`. Variants use `lib/variants.ts`, a typed helper over `clsx`. Long text never spills out of a primitive: a badge or button stays within its container (`max-w-full`, and it does not widen a grid column) and ends an overlong label in an ellipsis, keeping the full text as its accessible name (`ellipsis.tsx`), and an alert breaks a word too long for its line.
- `components/icons/`: the SVG stroke glyphs (`Icon`), `KindIcon`, `StatusIcon`, and the goblin `Logo` (mark and wordmark, or the wordmark alone). Icons are decorative; the text or label beside them carries the name.
- `components/layout/`: `AppShell` (header, offline banner), `MainNav` (green underline, optional attention dot, a Menu button below 640 px), `Page`, and `PageHeader`.
- `components/status.tsx` (`RunStatusBadge`, `QueryState`) and `components/ErrorBoundary.tsx`.
- Feature folders assemble primitives and keep their public exports: `editor/` (`EditorPage` with `EditorToolbar`, `EditorSidePanel`, `useLoadEditor`, `useResolveConflict`; `KindChip`), `runs/` (`RunInspectorPage` with `runs/inspector/`: `RunControls`, `WaitPanel`, `Timeline`, `ThreadViewer`, `ProgressDrawer`), `settings/` (`SettingsPage` with `settings/sections/`), and `forms/` (`fields.tsx` re-exporting `forms/fields/`: `shared`, `text`, `choice`, `json`, and `structure`, which holds the dispatcher with the object, array, record, and union fields so the recursion has no import cycle).

### List actions and destructive confirmations (#6, #12)

Loops groups **Edit**, **Export**, and **Delete** as bordered 32 px buttons with decorative icons. Edit remains a link using the shared `buttonStyles`. Export shows **Exporting…**, announces progress, and ignores repeated clicks until the request finishes. Its `aria-disabled` state retains keyboard focus while displaying the disabled style. Row Delete and Settings Delete/Revoke use `destructive-soft`; confirmation uses solid `destructive`, with a trash icon for Delete and a ban icon for Revoke. All variants inherit the shared pointer, hover, active, focus-visible, and disabled states in both themes.

`components/ui/confirm-action.tsx` supplies a native modal `<dialog role="alertdialog">` for deleting loops, models, and secrets and revoking API keys; triggers announce `aria-haspopup="dialog"`. Its heading names the item, its description explains the consequences and that the action cannot be undone, and initial focus goes to **Keep**. The native modal blocks background interaction; the component's Tab handler cycles between Keep and Confirm. Keep or Escape cancels while idle. During the request both buttons are disabled, Escape cannot dismiss, and a status announces progress. The keydown handler prevents busy Escape's default action before the browser can close the dialog or return focus to the background. The close handler remains a backstop for other native closes while busy, consumes queued programmatic close events, and ignores stale close events when the dialog is already open again. Pending content prevents text selection from repeated clicks.

Focus returns to the opener after cancellation, or to `returnFocusTo` (an element id) when its row disappears. The default fallback is the owning section's `aria-labelledby` heading; a heading without `tabindex` receives `-1` only while focused and removes it on blur (immediate removal would blur it in Chromium). Existing focus attributes are preserved. A newly focused API key input takes precedence over restoration. Errors remain announced inside the dialog until Keep/Escape dismisses it or **Confirm delete/revoke** retries; a loop's 409 `LOOP_IN_USE` retains the API's reason. Settings refreshes the affected list after dismissing a 404 so the vanished row disappears while the error stays readable until dismissal. Focus restoration also runs after that refresh settles, preserving a deliberate focus change and covering delayed row removal. API-key revocation closes when DELETE succeeds; its optional `onConfirmed` list refresh runs separately, with focus restored after it settles. A 401 refetch or its retry cannot extend the confirmation's pending state or delay focus into the API-key panel.

Consequences include removal of a loop's versions and triggers and unavailable subloop starts; a seeded model returning at the next server start; missing secrets causing webhook 503 `HOOK_NOT_READY`, unsigned return deliveries, script `SECRET_MISSING`, and (for `jev-api-key`) unavailable Jev decisions; and API clients receiving 401 immediately after revocation. If `GG_JEV_API_KEY` is set at startup, the deleted `jev-api-key` secret is re-seeded at the next server start. When this browser stores a key, every revocation warns that revoking its key loses access and shows the API key panel. A rejected key focuses that panel's input once the modal closes. The API does not reveal the current key's identity, so this warning is conditional rather than identifying a particular row. Regression coverage is in `LoopsPage.test.tsx`, `SettingsPage.test.tsx`, `confirm-action.test.tsx`, `api-key.test.tsx`, and Edge `e2e/actions.spec.ts`; visual evidence lives in `docs/qa/2026-10-04-loops-and-settings-actions/`.

## What shipped in M5, first pass (Draft)

`apps/web` (`@graphgoblin/web`) implements every screen above except replay-at-node (M8) and a list of webhook endpoints on the Events screen (see "After the WP-D2 QA pass").

- **Serving.** The API serves the production build when `GG_WEB_DIST` points at `apps/web/dist` (`apps/api/src/plugins/static.ts`). The app lives under `/app/`, so its routes (`/app/loops`, `/app/runs/:id`, ...) never collide with API paths such as `/loops`; `/` and `/app` redirect to `/app/`, extension-less `/app/*` paths fall back to `index.html`, a missing asset is a 404, fingerprinted assets are immutable, and `index.html`, `sw.js`, and the manifest are `no-cache`. In development, `vite` serves `/app/` and proxies the API (`GG_API_URL`, default `http://127.0.0.1:4747`).
- **Client.** One `@graphgoblin/api-client` instance created with `client: 'ui'`, so runs started here are `manual.ui`. TanStack Query holds server state; Zustand holds the editor draft (`src/editor/store.ts`), per-run event logs (`src/runs/event-store.ts`), and the PWA update state. Browser code imports only `contracts`, `domain`, and `api-client`; lint (`no-restricted-imports`) and dependency-cruiser (`web-is-browser-only`) refuse `engine` and `infrastructure`.
- **Editor.** Palette of the nine kinds (drag onto the canvas, or press a palette button to add below the graph). Custom node cards with an input handle (none on triggers) and one labelled output handle per port: decision routes, script exit-code routes, and the optional exit `loopBack`, which is always drawn; connecting it sets `config.loopBack.targetNodeId`, removing the edge clears it. Connections into triggers, from unknown ports, or from an already connected port are refused. Validation runs `LoopDefinitionSchema` then `validateLoop` from `domain` on every change; schema issues are listed first with their node and path, and clicking an issue selects its node. Autosave is debounced (600 ms): every edit is mirrored to IndexedDB first, then a schema-valid draft goes to `PUT /loops/{id}/draft`; a schema-invalid draft stays on the device with a notice, an offline save retries on the `online` event, and an unsynced local draft wins over the server copy on reload. Publish saves first, then shows the 422 issue list if the server refuses. A Run tab starts the published version from any manual trigger, with an input form generated from the trigger's `inputSchema`. A subloop picker lists published loops and shows their trigger input schemas and return mappings.
- **Schema-driven forms** (`src/forms`). `SchemaForm` takes a node kind's config schema from `contracts` and renders it with react-hook-form and the Zod resolver; the same component renders loop settings and declared variables. Introspection reads Zod 4's `_zod.def`: strings (plain, `TemplateSchema` as a Liquid CodeMirror editor, `ExpressionSchema` as a JSONata editor, both with a live preview against `sampleThread()`), numbers (integer, bounds), booleans (checkbox, or a tri-state select when optional without default), enums and multi-value literals (select; arrays of enums become checkbox groups), single literals (read-only), objects (optional ones get Add and Remove), arrays (add and remove items, respecting min and max), records (stacked key and full-width value rows that remain usable in narrow panels; string values as inputs, anything else as JSON), discriminated and plain unions (a variant picker that seeds the chosen variant), defaults and prefaults (shown as placeholders or initial selections), and `unknown`, `z.json()`, and `JsonSchemaSchema` as JSON editors. Array Add and Remove actions use the latest child edits, so the displayed values and autosaved draft agree. Parsed JSON editors follow changes to their row values after removal. Unparsed JSON text is kept per row until fixed or discarded, and may sit on a different row after a removal; this known limitation is tracked separately. Exactly empty optional Liquid and JSONata fields are absent and omit the preview; required empty expressions and malformed supplied expressions still show errors. Optional JSON fields clear without a parse error and have no expression preview. Refinements are not introspected; their messages appear in the form's issue summary. Clearing a field stores an internal "unset" marker that is stripped before validation, because react-hook-form otherwise restores a field's initial value when it becomes `undefined`.
- **Run inspector.** The timeline comes from `subscribeRunEvents`; events are kept per run in session storage, so a reload resumes after the stored cursor and a finished run does not reopen the stream. Selecting an event reconstructs the thread at that point with `replayThread` from `domain` (starting from the initial thread recorded on `run.queued`, and counting `node.started` for node visits, which the engine keeps outside patches); a `node.finished` event also shows its patch with the value before and after each path. A progress drawer groups `node.progress`, harness session, usage, decision, and heartbeat events per node. Waiting runs show an input form generated from the wait node's `inputSchema` (or a signal form); cancel, pause, and resume are buttons.
- **Settings.** Model catalog (add, edit, enable, delete), default model and effort (stored as the owner settings `defaultModel` and `defaultEffort`, which the engine reads at run start ahead of `GG_DEFAULT_MODEL` and `GG_DEFAULT_EFFORT`), write-only secrets, API keys (the token is shown once), harness preflight, and an install hint.
- **PWA.** `vite-plugin-pwa` generates the worker (`registerType: 'prompt'`, `injectRegister: false`, scope `/app/`); the app registers it with `workbox-window`. A waiting worker raises the "A new version is available" toast; only Update sends `SKIP_WAITING`, and the page reloads when the new worker takes control. Only the app shell is precached, there is no runtime caching, and navigation fallback is limited to `/app/`. `window.graphgoblinPwa.simulateUpdate()` drives the same toast for tests. The manifest has 192 and 512 px icons (generated by `scripts/generate-icons.mjs`). Screens that need the API show an explicit offline notice, and a banner appears while the browser is offline.

Deviations: the canvas has no custom keyboard shortcuts beyond Delete or Backspace (which remove the selected edge or node only while focus is on the canvas) and xyflow's controls for fit-to-view; palette buttons add nodes from the keyboard and the property panel's Connect form draws edges. Templates use CodeMirror's Jinja2 stream mode for Liquid and its JavaScript mode for JSONata (stand-ins: no Liquid- or JSONata-aware highlighting or completion). There is no undo.

## After the WP-D2 QA pass (Draft, 2026-10-03)

The adversarial QA report is `docs/qa/2026-10-03-wp-d2.md`. Behaviour that changed:

- **API key entry.** With `GG_REQUIRE_API_KEY=true` the shell under `/app/` is public; the first 401 shows an "API key required" panel, the key is kept in `localStorage` and sent on every request and event stream, a refused key asks again, and Settings has "Forget key". Entering a key refetches every screen and restarts event streams, so a deep link opened before the key goes live without a reload; forgetting the key (in any tab, followed through the `storage` event) drops loaded data and restarts streams without it.
- **Validation agrees with the API.** The panel lists the local `domain` issues (now including Liquid and JSONata syntax), the issues only the API can find (cron syntax, subloop references) from `POST /loops/{id}/validate` after each save, and `FIELD_UNPARSED` for JSON editors holding text that does not parse. Publish refuses while any field does not parse. The unparsed text and its issue stay in the editor state when the field is left (coming back shows the text again) until the text parses or the user discards it, in the field or from the panel. Publishing an unchanged loop says there is nothing to publish; the outcome message clears on the next edit.
- **Drafts.** Every edit is mirrored to IndexedDB at once and flushed to the server when the editor unmounts, so leaving inside the debounce window loses nothing. An unsynced local draft older than the server's last save is set aside, under its own IndexedDB key that later edits do not touch, and offered (use or discard) on every load until the user chooses. Draft saves for a loop are serialized, including the one sent when leaving the editor, and a save updates the editor only while the same loop and editor generation are loaded, so an older save never lands after a newer one. Two tabs no longer overwrite each other: see "Draft conflicts" below.
- **Editor.** Palette additions pan into view. List fields with a default show the default and a Customize button instead of item fields bound to nothing. Settings' "(server default)" deletes the setting.
- **Run inspector.** Replay starts from `run.queued`'s `initialThread`, so subloop child runs reconstruct correctly; a log that does not replay shows an explanation; an error boundary per screen keeps the shell alive. Events are appended, rendered, and reported in 100 ms batches and session storage never throws on quota: a 1,211-event run opens in about 0.5 s with a handful of run fetches (it took 7 s and one fetch per event before).
- **Events screen** shows each event's source (API, webhook delivery, or the run whose exit emitted it) and links to the runs it started. Webhook endpoint configuration stays on the API (`GET /loops/{id}/triggers`); the screen does not list endpoints yet.
- **Settings** check the secret name rule before sending, and validation messages name the first failing field.

## Draft conflicts (Decided, WP-F2)

- The editor keeps the server `draftToken` its copy is based on (from `GET /loops/{id}` at load, then from each save's response) and sends it as `If-Match` on every draft save, including the save sent when leaving the editor. The IndexedDB mirror stores it with the device copy (`baseToken`), so a copy restored after a reload is saved against the token it was based on; copies written before tokens existed use the server's current token.
- Every accepted save advances the loop's token, even when the editor that sent it has closed, so the save sent on leaving the editor (queued behind it) is based on it. The device copy is updated in one IndexedDB transaction: a copy of exactly the saved definition becomes synced, and a newer unsynced copy keeps its definition but takes the new token as its base.
- Reload and overwrite act only on the editor that asked: each step after an await re-checks the loop id and editor generation, so a slow answer never lands in another loop's editor.
- A 409 `DRAFT_CONFLICT` stops autosave and shows "The draft changed on the server" with two buttons: **Reload server draft** (load the server draft and mark it synced on the device, dropping this editor's unsaved changes) and **Overwrite with this copy** (save again with the server's token from the conflict). Nothing is overwritten without one of these clicks. Edits made meanwhile stay on the device, the save state reads "Draft changed elsewhere", leaving the editor sends nothing, and Publish refuses until the conflict is resolved.
- Choosing "Use this device's copy instead" for a set-aside copy is an explicit overwrite of the server draft shown.
- Regression: `src/editor/EditorPage.conflict.test.tsx` and the two-tab E2E `e2e/drafts.spec.ts`.
