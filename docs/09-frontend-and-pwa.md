# 09 - Frontend and PWA

## Shape (Decided)

A React single-page application built with Vite, served by the API process in 1.0, installable as a PWA. It talks to the API only through the generated typed client and to run state only through SSE. It contains no business rules: validation, routing, and execution semantics live in `contracts`, `domain`, and the backend. The editor can still validate drafts locally by importing `contracts` and `domain`, since both are pure.

## Screens (Decided list, Draft details)

| Screen        | Purpose                                                                                                                                        |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Loops         | List, create, import, export, publish state, last run status                                                                                   |
| Editor        | Canvas with a collapsible palette and loop panel, issue badges on nodes, node editor dialog, version bar with draft, issue counts, and publish |
| Runs          | List across loops with filters; parent and child relationships; New run, the only place runs start                                             |

## Editor (Draft)

- Canvas: `@xyflow/react` with custom node components per kind, labelled output handles for decision routes and exit loop-back, and edge validation that refuses connections into triggers or out of unknown ports.
- Palette: the nine node kinds, drag to add.
- Node editor: a modal dialog opened from the canvas, generated from the node kind's Zod schema with react-hook-form (see "Node editor, loop panel, and New run" below). Templates and expressions use CodeMirror with Liquid and JSONata modes and a preview that renders against a sample thread.
- Validation: the same `domain` validation the backend runs, surfaced live as an issue badge on each node and the counts beside Publish (see "Validation badges" below), so publish never fails by surprise.
- Subloop picker: searches published loops and shows their trigger input schema and return shape.
- Variables: the loop's declared variables with schemas, edited in the loop panel.
- Undo and redo: every change of the draft, from the toolbar or with Ctrl+Z and Ctrl+Shift+Z (see "Undo and redo" below).

## Run inspector (Draft)

- Timeline from the SSE stream with the cursor stored so reload resumes without gaps.
- Thread viewer that reconstructs the thread at any event by replaying patches client-side using `domain`.
- Node progress drawer that shows harness items as they arrive.
- Wait handling: when the run is waiting on input, a form rendered from the wait node's `inputSchema` appears inline.

## PWA behaviour (Decided)

- `vite-plugin-pwa` with Workbox, `registerType: 'prompt'`.
- Update flow: the app asks the service-worker registration to check for a new build at registration, on window focus (at most once per 60 seconds, with a throttled focus deferred until that boundary) or becoming visible, hourly while visible, on browser reconnect, and when API reachability returns after an outage. Checks run only while visible, browser-online, and without a known API outage, with at most one check in flight. Scheduled checks and listeners are removed on unmount or page unload; a rejected check warns once per failure streak. A worker already waiting at registration shows the toast on first render. Each trigger also checks for a waiting worker, and the app owns a registration `updatefound`/worker `statechange` listener so later builds still prompt after Later even when Workbox detaches its listener. Each updated worker prompts once; the initial installation does not prompt. The app shows "A new version is available" with Update and Later; Later dismisses the prompt for that worker, Update activates it and reloads when it takes control. No automatic activation.
- Precache: the app shell only. API responses are never cached by the worker.
- Offline: the shell opens and unsaved editor drafts persist in IndexedDB. Anything needing the backend shows a clear offline state. Active queries that failed because the API could not be reached retry on the browser's `online` event, including after an offline reload, without navigating. While an active query holds a connectivity error, a public `GET /healthz` probe through the API client's base URL retries after 2 seconds, doubling to a 30-second cap. A successful health response refetches only active connectivity-failed queries without cancelling their in-flight fetches. Recovery is confirmed once per outage only after those reads cease holding connectivity errors; a healthy `/healthz` with a stuck route keeps backing off and leaves the banner stable. There is at most one probe in flight, with a 5-second timeout; probes stop when no query needs recovery, the tab is hidden, or the browser is offline, and resume when visible and online. HTTP 4xx/5xx query errors never start probing. Each fetch keeps the one-retry limit; HTTP errors keep the existing query behaviour. The banner says "You are offline" for browser connectivity and "Cannot reach the GraphGoblin API" for an API outage while the browser is online; confirmed recovery clears API unreachability. Signal sources are active query transport failures, draft-save transport failures, and run-stream transport failures; accepted streams report reachability through the same transition functions. A failed draft save refreshes its active loop read once per revision, and a dropped run stream refreshes its active run read once per outage, so loaded screens also create probe demand. A stream whose last failure was a transport failure restarts at its committed cursor on recovery. Stream outages are reported once until an event advances the cursor or an accepted stream stays open for at least one 15-second heartbeat interval; acceptance alone and repeated short connections do not re-arm them. HTTP refusals, invalid stream frames, and a clean end-of-stream do not create connectivity failures; their retries keep the existing SSE backoff. When no active query needs recovery, the unreachable claim clears after one tick and a fresh check for active failures or reads, without a recovery notification; cached errors are remembered across inactivity and do not reopen an outage until a fresh failure arrives. There is no offline execution.
- Reconnect: a connectivity error that lands after the browser's `online` event still starts probing, so a no-data fetch also recovers without focus or navigation. The API-unreachable banner is suppressed until the browser reconnect refetch cycle settles or five seconds elapse, whichever comes first. Unrelated active reads do not extend this grace.
- Install: a web manifest with icons; an install hint in settings.

## State and data (Decided)

- Server state: TanStack Query over the generated client.
- Live run state: a small SSE hook that appends to a per-run event store in Zustand and exposes projections.
- Editor state: Zustand store holding the draft definition and its in-memory undo history; autosave to the draft endpoint with debounce; local IndexedDB mirror for offline.

## Accessibility and UX baseline (Draft)

Keyboard navigation for the palette, the node editor dialog, and both side panels, visible focus states, colour-blind-safe status colours, and reduced-motion support. The canvas gets keyboard shortcuts for add, delete, connect, and fit-to-view. The editor's undo and redo have the platform's shortcuts and named toolbar buttons (#17).

## Design tokens (Decided, #7)

The look comes from design tokens, implemented to the visual direction the owner approved (`docs/design/visual-direction/`, ADR-0017). Dark is the default theme and light the alternate.

- **Two tiers** in `apps/web/src/styles/tokens.css`. The primitive tier is the palette (green, brown, grey, magenta, violet, blue, orange, amber, red, teal, slate); only the semantic tier references it. The semantic tier names what a colour is for: surfaces (`--surface-app`, `-raised`, `-sunken`, `-overlay`, `-hover`, `-control`, `-field`, `-inverse`) and the `--scrim` behind a modal dialog, text (`--text-default`, `-muted`, `-subtle`, `-link`, `-on-accent`, ...), borders, the accent (goblin lime, with `--accent-highlight` magenta and `--accent-glow` purple reserved for the most special moments), danger, status tones (`--status-{neutral,good,bad,warn,info}-{bg,fg,border}`: blue success, orange failure, amber waiting, violet running, always with an icon), node kinds (`--kind-<kind>` and `--kind-<kind>-subtle`), the focus ring, code, canvas, mascot, and shadows. It is declared for light on `:root, [data-theme='light']` and for dark on `[data-theme='dark']`, each with its `color-scheme`, so native controls, scrollbars, and date inputs follow the theme. Type (`--font-ui`, `--font-code`, `--font-size-*`), space, radius, and motion scales are theme independent; the motion durations drop to 0 ms under `prefers-reduced-motion`, which also stops every keyframe animation (`animation: none`, so the running and live pulses hold at full opacity) and collapses transitions to an instant change.
- **Theme.** The `data-theme` attribute on `<html>` picks the tier; it may also sit on any element, so a subtree can show the other theme. `index.html` ships `data-theme="dark"`, so anything that cannot read a choice shows the default. The theme control is described under "Theme control" below.
- **Tailwind.** `styles/theme.css` maps Tailwind's keys onto the semantic tokens with `@theme inline reference` (`bg-surface-raised`, `text-muted`, `border-default`, `ring-focus`, `bg-status-good-bg`, `font-mono`, `text-sm`, `rounded-md`, `shadow-2`, `gap-section`, `p-page`) and resets Tailwind's default scales, so palette classes such as `bg-slate-100` produce no CSS. Node-kind colours come from `KIND_INFO[kind].color`, a token name: `editor/KindChip.tsx` sets `--k` and `--k-subtle`, read by `bg-kind` and `bg-kind-subtle`. The glows and pulse of the highlight moments are utilities in `styles/utilities.css`.
- **Only `src/styles/` holds colour literals.** Components use the utilities or `var(--token)`. `theme-color` and the manifest colours are read from `tokens.css` at build time (`vite.config.ts` with `styles/palette.ts`): the dark header (`--surface-inverse`) and page (`--surface-app`).
- **Third-party widgets.** `styles/code-theme.ts` themes CodeMirror (surface, gutter, active line, selection, cursor, tooltips, the search and replace panel with its fields, buttons, and `--code-match` highlights, and syntax colours from a highlighter keyed by lezer tag names; Liquid delimiters show as operators). `styles/canvas.css` themes xyflow through its `--xy-*` variables: background dots, edges and the selected edge, handles, edge labels as pills, controls, the selection box, and a token focus ring on focused nodes. Edges use xyflow's built-in `smoothstep` path (orthogonal with rounded corners); the exit's loop-back edge keeps its animated dash in the loop colour. Routing that avoids nodes is #18.
- **Fonts.** Geist and Geist Mono (SIL OFL 1.1) are self-hosted in `apps/web/public/fonts` with `OFL.txt`, preloaded, and precached with the app shell, so the offline shell keeps them. Components never name a family; #40 switches `--font-ui`.
- **Reserved accents.** Magenta and purple appear only on the selected canvas node's ring, the heartbeat kind, the waiting-for-input dot on Runs (the navigation supports it; no data feeds it yet), notifications (the update toast), the running badge's glow, the mascot's eyes, and the header's hairline: a 2 px purple-to-magenta line along its bottom edge that fades out to the right (`--accent-hairline`, owner request after the first dark sample; in forced-colours mode it gives way to a plain bottom border). Navigation and buttons stay green and neutral; the current page has a green underline directly under its label.
- **Accessibility.** Every text and non-text token pair meets WCAG AA in both themes (the contrast table generated from `tokens.css`). The focus ring (`--focus-ring`, 2 px, offset 2 px) holds 3:1 on every surface. In forced-colours mode the selected node and the current timeline row keep outlines and badges keep a border, because box shadows are dropped.

### Theme control (Decided, #11)

- **Choice.** Settings → **Appearance** → **Theme** offers **Dark** (the default) and **Light**: the shared segmented control (see "Form controls" below), two native radios in a fieldset with the legend "Theme". Tab reaches the chosen option, the arrow keys move the choice, and it applies at once with no reload. There is no header toggle (owner decision).
- **Storage.** `localStorage` key `graphgoblin-theme`, holding the theme's name (`dark` or `light`). Every access is guarded: an empty store, an unknown value, or storage that cannot be read (private mode, blocked site data, a throwing accessor) shows Dark, and an unknown value is left in place. `system` (follow the operating system) is reserved for the installer and reads as Dark until then. Other tabs follow a change through the `storage` event, listened to while the app is mounted (`useThemeAcrossTabs` at the root). `src/lib/theme.ts` holds the storage, `applyTheme`, `setTheme`, and the `useTheme` hook (`useSyncExternalStore` over the `data-theme` attribute, the single source of truth on the page).
- **No flash.** The build (`vite.config.ts`) adds two tags right after `<meta charset>`, ahead of the stylesheet: the `theme-color` meta tag with the dark header colour as `content` and both themes' header colours (`--surface-inverse`, read from `tokens.css`) as `data-dark` and `data-light`, then an inline classic script (`themeBootScript` in `src/lib/theme.ts`) that reads the stored theme and sets `data-theme` and the meta colour before first paint. It is inline because the API sends no Content-Security-Policy and an inline script costs no request; if a CSP is added, it moves to a precached file in `public/` loaded synchronously in `<head>`. If the script could not run, `bootstrap()` applies the stored theme when the app starts (late, but correct).
- **Regression.** `src/lib/theme.test.ts`, `src/settings/sections/AppearanceSection.test.tsx`, and `e2e/theme.spec.ts` (default Dark, Light across reloads with `data-theme` already Light when `<body>` is parsed and never changing afterwards, cleared storage, throwing storage).

### Form controls (Decided, #8)

Every form control comes from `components/ui/` and takes its look from the tokens, so the forms read as one system in both themes. The density is unchanged: 36 px controls and a 6 px gap between a label and its control. Screenshots before and after: `docs/qa/2026-10-04-issue-8-forms/`.

- **Text entry.** `Input`, `Textarea`, and `Select` (native, with a drawn chevron) share `FIELD_FRAME`: a 3:1 `--border-strong` edge with 8 px corners on the field surface, a lighter edge on hover, a green edge with the 2 px focus ring outside it, and the bad-tone edge when `aria-invalid`. Number inputs drop the browser's spin buttons (the arrow keys still step). The CodeMirror fields (`forms/CodeEditor.tsx`) wear the same frame, with the ring while focus is inside; one line is as tall as an input (`codeLinesHeight` in `styles/code-theme.ts`), a tag beside the label names the language (Liquid, JSONata, JSON; `LanguageTag` in `forms/CodeField.tsx`), and Tab is not captured, so Tab and Shift+Tab leave a code field.
- **Checkbox.** A native checkbox drawn as an 18 px box: the 3:1 edge, and when checked the accent fill with an ink tick (forced colours show the system checkbox). Used for the members of an array of enums and the model form's allowed efforts.
- **Switch** (`switch.tsx`). A `button role="switch"` with `aria-checked`, 44 by 24 px, whose thumb slides right and turns the track green when on; a click, Space, or Enter toggles it, and a `<label htmlFor>` naming it toggles it too. Props: `checked`, `onCheckedChange`, `disabled`, `aria-label` or `aria-labelledby`, `id`. For a boolean that always has a value (a default, or required) and for the model catalog's Enabled column. In forced colours the thumb keeps a solid edge, so its side shows the state.
- **Segmented control** (`segmented-control.tsx`). For a choice of two to four options: a fieldset (`role="radiogroup"`, named by its legend) of native radios drawn as connected segments on a sunken track, the chosen one in the accent's subtle fill with a 3:1 inset edge. Tab reaches the chosen segment (the first when none is chosen) and the arrow keys move the choice. `notSet` adds a first segment that leaves the value unset (typed: `onChange` then also receives `undefined`); without it a required choice starts with nothing chosen. A segment never grows wider than its field: a long label ends in an ellipsis (the shared `ellipsize`), keeping the whole text as the radio's name and as the segment's tooltip. The Appearance theme control uses it.
- **File picker** (`file-picker.tsx`). The native `input type="file"` lies transparent over an outline button ("Choose file" with an upload icon), so a click, Tab, Space, and Enter stay native and a `<Label htmlFor>` names it; the focus ring is drawn on the button, and the last chosen file's name sits beside it and describes the input. The Loops import uses it. No drop zone.
- **Fieldset and Legend** (`fieldset.tsx`). `Fieldset` is the quiet bordered group with a semibold `Legend` (a nested object, array, record, or union); `Legend variant="label"` names a borderless group of choices and looks like a field label; `Fieldset variant="section"` with `Legend variant="section"` is a borderless, ruled-off section with a quiet uppercase heading (a group under a form's Advanced options, #14).
- **Disclosure** (`disclosure.tsx`, #14). A button with `aria-expanded` and `aria-controls` that shows and hides a panel kept mounted while hidden: `variant="box"` is a bordered section whose full-width header is the toggle (a form's Advanced options), `variant="row"` a compact list item header with `actions` beside it. `summary` adds to the toggle's text, `defaultOpen` sets the first state, and `revealDisclosures(element)` opens every collapsed one around an element at once.
- **Labels, help, required.** `Label required` puts the `RequiredMarker` (an asterisk in the bad tone, `aria-hidden`) after the label, outside the `<label>`, so the accessible name stays the field's name; a control carries `aria-required`. A group (an array, a record, a set of checkboxes) shows the marker after its legend instead, since a group takes no `aria-required`, and states its minimum as text that describes it ("Choose at least 1.", "At least 2 items."); its checkboxes are not each marked. A form with required fields starts with `RequiredNote` ("Required fields are marked \*", hidden from assistive technology, which hears "required" on each control instead). Help text (`HelpText`) is linked to its control with `aria-describedby`.
- **Errors.** Where a field shows its own error, the message sits under it, describes the control (`aria-describedby`, after any help), sets `aria-invalid`, and is announced (`role="alert"`; a JSON parse error, which changes as you type, is a polite live region instead). That covers every field of the schema-driven forms, including record values (which react-hook-form does not track: their messages come from SchemaForm's check of the whole value, by exact path) and collections (the group's error describes the fieldset, which takes no `aria-invalid`); each `JsonSchemaForm` property and its raw JSON editor; the node dialog's id (its own check) and label (the loop's validation), the loop panel's name (the contract's check), Loops create (the API's refusal), the import picker (the refusal describes it and marks it invalid until the next file), the secret name rule (it turns into an alert while the name breaks it), and the Connect form's refusal (it describes the To select). Not linked to a field: a nested object's own error (shown in its fieldset, announced), `JsonSchemaForm` problems with the value as a whole (a summary under the form, announced), the schema-driven forms' Config issues summary, and the API's refusals in Settings (model form, secrets, API keys, defaults), shown under their form without an announcement.
- **Where.** The schema-driven forms (below), `JsonSchemaForm` (New run and the waiting-for-input form), the node dialog's id and label and its Connect form, the loop panel, Loops create and import, Settings (model form and Enabled switch, defaults, secrets, API keys), and the API key panel. `JsonSchemaForm` marks the properties in the JSON Schema's `required` list and uses the same controls, with one difference: it starts empty and sends only what it shows, so a boolean is never a switch (always on or off) but **Yes** / **No** segments, after **Not set** unless required (a required one starts with neither chosen). An enum of two to four members is a segmented control (a required one starts with nothing chosen), and a longer one a select ("(choose)" when required, **Not set** otherwise); a default shows as a placeholder (strings, numbers) or as help ("Default: true"). Its ids are generated per field, so a property may have any name. Each problem shows beside its property under the property's title ("Approval is required", "Reason must NOT have fewer than 3 characters", "Labels: invalid JSON (…)"), located through `validateJson`'s `issues` in `domain` (path segments, a missing property at itself); editing a field clears its problems. What it sends is unchanged: a field left unset sends nothing.
- **Contrast.** The controls use token pairs already in the contrast table (field and track edges, the selected segment, the switch thumb on and off, the checkbox tick, the focus ring on every surface); #8 added the error text and marker, and the invalid edge, on the sunken surface (the model form).

### List actions and destructive confirmations (#6, #12)

Loops groups **Edit**, **Export**, and **Delete** as bordered 32 px buttons with decorative icons. Edit remains a link using the shared `buttonStyles`. Export shows **Exporting…**, announces progress, and ignores repeated clicks until the request finishes. Its `aria-disabled` state retains keyboard focus while displaying the disabled style. Row Delete and Settings Delete/Revoke use `destructive-soft`; confirmation uses solid `destructive`, with a trash icon for Delete and a ban icon for Revoke. All variants inherit the shared pointer, hover, active, focus-visible, and disabled states in both themes.

`components/ui/confirm-action.tsx` supplies a native modal `<dialog role="alertdialog">` for deleting loops, models, and secrets and revoking API keys; triggers announce `aria-haspopup="dialog"`. Its heading names the item, its description explains the consequences and that the action cannot be undone, and initial focus goes to **Keep**. The native modal blocks background interaction; the component's Tab handler cycles between Keep and Confirm. Keep or Escape cancels while idle. During the request both buttons are disabled, Escape cannot dismiss, and a status announces progress. The keydown handler prevents busy Escape's default action before the browser can close the dialog or return focus to the background. The close handler remains a backstop for other native closes while busy, consumes queued programmatic close events, and ignores stale close events when the dialog is already open again. Pending content prevents text selection from repeated clicks.

Focus returns to the opener after cancellation, or to `returnFocusTo` (an element id) when its row disappears. The default fallback is the owning section's `aria-labelledby` heading; a heading without `tabindex` receives `-1` only while focused and removes it on blur (immediate removal would blur it in Chromium). Existing focus attributes are preserved. A newly focused API key input takes precedence over restoration. Errors remain announced inside the dialog until Keep/Escape dismisses it or **Confirm delete/revoke** retries; a loop's 409 `LOOP_IN_USE` retains the API's reason. Settings refreshes the affected list after dismissing a 404 so the vanished row disappears while the error stays readable until dismissal. Focus restoration also runs after that refresh settles, preserving a deliberate focus change and covering delayed row removal. API-key revocation closes when DELETE succeeds; its optional `onConfirmed` list refresh runs separately, with focus restored after it settles. A 401 refetch or its retry cannot extend the confirmation's pending state or delay focus into the API-key panel.

Consequences include removal of a loop's versions and triggers and unavailable subloop starts; a seeded model returning at the next server start; missing secrets causing webhook 503 `HOOK_NOT_READY`, unsigned return deliveries, script `SECRET_MISSING`, and (for `jev-api-key`) unavailable Jev decisions; and API clients receiving 401 immediately after revocation. If `GG_JEV_API_KEY` is set at startup, the deleted `jev-api-key` secret is re-seeded at the next server start. Settings marks the row whose list-response `current` is true with the existing **This browser** badge, linked to its Revoke button through `aria-describedby`. Only that row's confirmation adds: "Revoking this key will sign this browser out and show the API key panel. Enter another valid key to continue." Every active key keeps the general 401 consequence. When a key is stored and no row is marked (including trusted mode), every active row instead adds: "This browser still sends a stored API key. If this is that key, revoking it signs this browser out and shows the API key panel; Forget key in Settings also clears it." A rejected key focuses the API key panel's input once the modal closes. Regression coverage is in `LoopsPage.test.tsx`, `SettingsPage.test.tsx`, `confirm-action.test.tsx`, `api-key.test.tsx`, `api-key-fetch.test.ts`, `ApiKeysSection.test.tsx`, `apps/api/src/api-key-current.test.ts`, and Edge `e2e/actions.spec.ts` and `e2e/api-key-current.spec.ts`; visual evidence lives in `docs/qa/2026-10-04-loops-and-settings-actions/`.

## What shipped in M5, first pass (Draft)

`apps/web` (`@graphgoblin/web`) implements every screen above except replay-at-node (M8) and a list of webhook endpoints on the Events screen (see "After the WP-D2 QA pass").

- **Serving.** The API serves the production build when `GG_WEB_DIST` points at `apps/web/dist` (`apps/api/src/plugins/static.ts`). The app lives under `/app/`, so its routes (`/app/loops`, `/app/runs/:id`, ...) never collide with API paths such as `/loops`; `/` and `/app` redirect to `/app/`, extension-less `/app/*` paths fall back to `index.html`, a missing asset is a 404, fingerprinted assets are immutable, and `index.html`, `sw.js`, and the manifest are `no-cache`. In development, `vite` serves `/app/` and proxies the API (`GG_API_URL`, default `http://127.0.0.1:4747`).
- **Client.** One `@graphgoblin/api-client` instance created with `client: 'ui'`, so runs started here are `manual.ui`. TanStack Query holds server state; Zustand holds the editor draft (`src/editor/store.ts`), per-run event logs (`src/runs/event-store.ts`), and the PWA update state. Browser code imports only `contracts`, `domain`, and `api-client`; lint (`no-restricted-imports`) and dependency-cruiser (`web-is-browser-only`) refuse `engine` and `infrastructure`.
- **Editor.** Palette of the nine kinds (drag onto the canvas, or press a palette button to add below the graph). Custom node cards with an input handle (none on triggers) and one labelled output handle per port: decision routes, script exit-code routes, and the optional exit `loopBack`, which is always drawn; connecting it sets `config.loopBack.targetNodeId`, removing the edge clears it. Connections into triggers, from unknown ports, or from an already connected port are refused. Validation runs `LoopDefinitionSchema` then `validateLoop` from `domain` on every change; schema issues are listed first with their node and path, and clicking an issue selects its node (since #13 it opens the node's editor; since #15 the issues are listed in each node's badge and beside Publish, and choosing one opens the node's editor at the issue's field). Autosave is debounced (600 ms): every edit is mirrored to IndexedDB first, then a schema-valid draft goes to `PUT /loops/{id}/draft`; a schema-invalid draft stays on the device with a notice, an offline save retries on the browser's `online` event or confirmed API reachability recovery, and an unsynced local draft wins over the server copy on reload. Publish saves first, then shows the 422 issue list if the server refuses. A Run tab started the published version from any manual trigger, with an input form generated from the trigger's `inputSchema` (since #46 runs start from Runs → New run). A subloop picker lists published loops and shows their trigger input schemas and return mappings.
- **Schema-driven forms** (`src/forms`). `SchemaForm` takes a node kind's config schema from `contracts` and renders it with react-hook-form and the Zod resolver; the same component renders loop settings and declared variables. ## Draft conflicts (Decided, WP-F2)

- The editor keeps the server `draftToken` its copy is based on (from `GET /loops/{id}` at load, then from each save's response) and sends it as `If-Match` on every draft save, including the save sent when leaving the editor. The IndexedDB mirror stores it with the device copy (`baseToken`), so a copy restored after a reload is saved against the token it was based on; copies written before tokens existed use the server's current token.
- Every accepted save advances the loop's token, even when the editor that sent it has closed, so the save sent on leaving the editor (queued behind it) is based on it. The device copy is updated in one IndexedDB transaction: a copy of exactly the saved definition becomes synced, and a newer unsynced copy keeps its definition but takes the new token as its base.
- Reload and overwrite act only on the editor that asked: each step after an await re-checks the loop id and editor generation, so a slow answer never lands in another loop's editor.
- A 409 `DRAFT_CONFLICT` stops autosave and shows "The draft changed on the server" with two buttons: **Reload server draft** (load the server draft and mark it synced on the device, dropping this editor's unsaved changes) and **Overwrite with this copy** (save again with the server's token from the conflict). Nothing is overwritten without one of these clicks. Edits made meanwhile stay on the device, the save state reads "Draft changed elsewhere", leaving the editor sends nothing, and Publish refuses until the conflict is resolved.
- Choosing "Use this device's copy instead" for a set-aside copy is an explicit overwrite of the server draft shown.
- Regression: `src/editor/EditorPage.conflict.test.tsx` and the two-tab E2E `e2e/drafts.spec.ts`.

A browser without the popover API gets a fixed-position element portalled to `document.body` while open, out of the canvas's transformed nodes, with the keyboard order kept by hand (Tab from the badge to the first row, Shift+Tab from the first row back to the badge, Tab past the last row on to what follows the badge, where the usual rules decide whether it stays, and Shift+Tab from there back to the last row); inside the node editor, a modal dialog that makes the rest of the page inert, it stays in place.
- **Rows.** Each issue shows its severity as an icon and a word (Error or Warning), its code, its message, and its field path in `<code>`. Choosing one opens the node's editor with the control at that path focused: `openNode(id, { field })` leaves a pending target in the store that the dialog uses once, and `editor/focus-field.ts` finds the first control inside the element whose `data-field` equals the path (config paths in the config form, `id` and `label` among the node's own fields), trying the parent paths, else the dialog's heading. Paths come from user data (a record key may hold a quote, a backslash, or a newline), so the values are compared as strings, never built into a selector. An issue without a path opens the node with focus on the heading. A `FIELD_UNPARSED` row keeps **Discard text**; when that removes the last issue, and with it the badge, focus goes to the node card (or the dialog's heading) rather than the page. Since #14, `focusField` first opens any collapsed Advanced group or list item that holds the field.
- **In the node editor.** The same badge sits beside the dialog's title (the `Dialog` primitive's `actions` slot), so the issues are at hand while editing; choosing one focuses its field in place. The form's own Config issues summary is unchanged.
- **Beside Publish.** `editor/ValidationIndicator.tsx`, left of Publish, is a status, not a button, when there is nothing to list: "Ready to publish" once the API's checks of the saved draft (`POST /loops/{id}/validate`: cron syntax, subloop references) have answered with nothing to fix, "Checking…" while they are under way, and "Validation unavailable" (muted, with a tooltip: nothing is known to be wrong, and Publish runs the checks again) when they could not run, offline say. ## Undo and redo (Decided, #17)

The owner's request of 2026-10-04: undo and redo for the editor, with Ctrl+Z and Ctrl+Shift+Z.

- **Steps.** Every change of the draft goes through the store's `edit` with a step: a label for the buttons and an optional merge key (`editor/history.ts`). The steps are adding, moving, connecting, renaming, and deleting nodes, removing edges, a node's label and config, the loop's name and description, its settings, and its variables. A change that leaves the definition as it was is not an edit: no revision, no save, no step. Changes with the same key less than a second apart (`COALESCE_MS`, counted from the step's latest change) are one step: typing in one field (a node's label; a node's config form, per node, since the form reports the whole config; the loop's name; its description; settings; variables), a drag (it ends in one move, since xyflow's second report of the same position changes nothing, and its start closes the step before it, so two quick drags are two steps), and a run of arrow-key nudges of one node. A merged step that ends where it started (typed, then deleted) is dropped. An undo or redo closes the open step, so the next change starts a new one, and a new step clears redo.
- **Unparsed text.** A step holds `fieldErrors` with the definition, and a form's report of unparsed text is a change like any other, merged into the step of that form's edits. Undo therefore takes back text that does not parse together with the typing that produced it, and redo brings it back with its blocking issue. **Discard text**, in the field or in an issue's row, is a step of its own that never merges, however soon it follows the typing (the form reports it as a discard, `reason` `'discard'`, not as text that started to parse), so undo always brings the discarded text back; undoing a node's deletion or rename brings back its unparsed text under its id. This keeps the stored text consistent with the definition it was typed against: no undo leaves text behind for a node or path that the restored draft does not have.
- **Not steps.** Selection, the open node editor, the loop panel's state, and save state. The history holds at most 100 steps (`HISTORY_LIMIT`, the oldest forgotten first), lives in memory only, and starts afresh on every load: opening the editor, **Reload server draft**, and restoring a set-aside device copy.
- **Undo and redo are edits.** They bump the revision (unless only unparsed text changed) and set the save state to pending, so autosave, the IndexedDB mirror, `If-Match`, and the conflict stop apply as to any edit; `useAutosave.ts` is unchanged. Undoing a rename keeps the node selected and its editor open, now on the old id. A node that an undo removes is deselected and its editor closes (focus returns to the canvas); redo brings the node back without reopening its editor.
- **Forms.** `historyEpoch`, bumped by every undo and redo, is part of the keys of the node editor's config form and of the loop panel's forms, so they remount with the restored values; the node editor's id draft resets with it. A node's label and the loop's name and description are controlled inputs and follow at once.
- **Shortcuts.** `editor/useUndoShortcuts.ts`, one `keydown` listener on `document` while the editor is mounted: Ctrl+Z undoes; Ctrl+Shift+Z and Ctrl+Y redo; on macOS and iOS (`navigator.userAgentData.platform`, else `navigator.platform`) Cmd+Z undoes and Cmd+Shift+Z redoes. The letter comes from the key's character, or from its place (`code`) on a non-Latin layout; presses with Alt (so AltGr), during composition, or already handled (`defaultPrevented`) are left alone. With focus in a text editor (an input of a text-entry type: text, search, url, email, password, number, tel, or a date or time type; a textarea; a content-editable element; or CodeMirror, including anything inside one, such as the checkboxes of CodeMirror's search panel), the keys belong to that control and its own text undo applies. Everywhere else they undo and redo the editor: the canvas, the toolbar, the page, and controls without text to undo, such as checkboxes, radios, switches, selects, and buttons, in the node editor or the loop panel. When a remount replaced the focused control, focus moves to the same control in the same field of the new form (the same element, type, role, and name, counted among its namesakes), else to whatever stands in its place there, else to the field's first control; outside any field, to the same control in the part of the page that stayed; failing those, to the heading of the dialog or panel it was in, else to the canvas. A radio stands for its group's checked radio, so after an undo that changed the choice the newly checked radio has focus (`groupFocus` in `editor/focus-field.ts`, which `focusField` uses too).
- **Toolbar.** Undo and Redo icon buttons open the toolbar's action group (`editor/UndoRedo.tsx`). Each is named by the step it will change ("Undo move start", "Redo edit label of start"; plain "Undo" or "Redo" with nothing to do), with the same text as its tooltip, and `aria-keyshortcuts` (`Control+Z`; `Control+Shift+Z Control+Y`; `Meta` on Apple platforms). With nothing to do a button is `aria-disabled`, not `disabled`, so it keeps its place in the Tab order. The names are visually hidden text rather than `aria-label`, so a lookup of a field by its label ("Description") never finds "Undo edit loop description". The buttons are 32 px for a mouse and 44 px where the primary pointer is coarse (`pointer-coarse:size-11`). While the node editor is open the page behind it is inert, so there the keys are the way to undo.
- **Regression.** `editor/history.test.ts`, `editor/store.test.ts` (every change undone and redone exactly, merging, deletion and rename, the 100-step cap), `editor/useUndoShortcuts.test.tsx`, `editor/UndoRedo.test.tsx`, `editor/EditorPage.undo.test.tsx`, `editor/EditorPage.conflict.test.tsx` (an undo saved with `If-Match` and mirrored to the device, a conflict on undo, and a reload clearing the history), and `e2e/undo.spec.ts`.
