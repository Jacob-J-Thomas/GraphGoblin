# 09 - Frontend and PWA

The public webhook response is fixed `202 {accepted:true}`. Events reads private delivery state,
retry metadata, safe pinned configuration and run links; acknowledgement does not imply run
creation or deduplication of unkeyed repeats. Its per-delivery **Webhook configuration** disclosure
shows authentication recipe, secret names, body/extraction/key settings or unavailable history.

## Shape (Decided)

A React single-page application built with Vite, served by the API process in 1.0, installable as a PWA. It talks to the API only through the generated typed client and to run state only through SSE. It contains no business rules: validation, routing, and execution semantics live in `contracts`, `domain`, and the backend. The editor can still validate drafts locally by importing `contracts` and `domain`, since both are pure.

## Editor (Draft)

- Canvas: `@xyflow/react` with custom node components per kind, labelled output handles for decision routes and exit loop-back, and edge validation that refuses connections into triggers or out of unknown ports.
- Palette: the nine node kinds, drag to add.
- Node editor: a modal dialog opened from the canvas, generated from the node kind's Zod schema with react-hook-form (see "Node editor, loop panel, and New run" below). Templates and expressions use CodeMirror with Liquid and JSONata modes and a preview that renders against a sample thread.
- Run-thread template and expression fields have a collapsed **Earlier node outputs (N)** list with syntax-specific copyable references and output notes. It follows draft paths, nearest first, includes a cyclic node's previous visit, and omits nodes without automatic outputs. Empty lists and fields with other evaluation roots show nothing. This is interim help, not validation; it does not populate the sample preview or repair renamed references. (#341)
- Webhook receiver: webhook trigger dialogs show a **Receiver** section with the published, enabled endpoint URL from `GET /loops/{id}/triggers`, resolved against the API base URL. The secret token is absent from the DOM while masked; Reveal/Hide and Copy receiver URL control access to the address, with polite copy feedback and Retry after a failed load. Publish again to apply draft changes. The section provides the address only; signing instructions stay in the [trigger guide](guide/04-triggers.md).
- Validation: the same `domain` validation the backend runs, surfaced live as an issue badge on each node and the counts beside Publish (see "Validation badges" below), so publish never fails by surprise.
- Subloop picker: searches published loops and shows their trigger input schema and return shape.
- Variables: the loop's declared variables with schemas, edited in the loop panel.
- Undo and redo: every change of the draft, from the toolbar or with Ctrl+Z and Ctrl+Shift+Z (see "Undo and redo" below).
- Edge routes: a selected connection's segments can be dragged or nudged out of the way, and the route is saved with the edge (see "Manual edge routes" below).

**Fit View** fits the whole graph into the canvas between the open panels, with room for the zoom controls. The canvas zooms from 0.1 to 2, so a long graph fits even with both panels open. Opening the editor fits the graph too, but never below 50%, so cards stay readable; a larger graph may then extend past the canvas until Fit View is used.

### Editing decision routes

Adding, renaming, reordering, or removing a decision route refreshes the canvas's measured output handles after the new rows render, including changes that leave the card the same height. New and renamed outputs can be connected immediately by dragging or through the node dialog's Connections form, without reloading. A connected route's rename keeps its edge id, target, and manual layout while changing its source port; removing a route removes its outgoing edge, even while its label is temporarily invalid. The config and edge change are one undo step, and redo restores both. Reordering routes keeps connections with their labels. Blank, duplicate, and otherwise invalid labels still block publishing; temporarily invalid input stays visible in the draft without rewiring a connection to an invalid port. Each row owns its connections while being edited, so completing multiple incomplete rows in any order keeps each connection with its own row, including when another row remains blank.

Options have persisted stable IDs independent of their display labels. Edges use those IDs, so label edits and reordering preserve connections and manual edge geometry. Invalid or incomplete IDs do not transfer an edge to another row; removal and undo/redo keep option ownership consistent. Numeric display labels are permitted and never become object/array indexes in route ownership.

### Backward-edge routing (#18)

Exit `loopBack` connections and self-loops always use the routed `orthogonal` edge type (named `backward` before #44, which draws forward edges with it too). Other connections compare the **measured output tip's x** with the **input tip's x**: an output at or to the right of the input routes backward. Once classified, an 8 px hysteresis band keeps small moves from switching the shape (a backward connection becomes forward below -8 px; a forward one becomes backward above +8 px). This includes stacked cards without a one-pixel card-position boundary. The band is not persisted: a drag that ends inside it can show the other shape after a reload, which classifies afresh. Forward edges retain xyflow's existing `smoothstep` paths (the orthogonal edge draws the same path while one is selected) and remain outside #18's obstacle-avoidance scope; an author can reroute one by hand (#44).

Straight return lanes run **at least 32 px from cards**: the requested 24 px clearance plus an 8 px allowance for rounded corners. Horizontal endpoint stubs enter their own card's padding. Tight gaps reduce padding only on the escape and entry approaches, down to 0 px; the central lane and its label retain the full 32 px stand-off. An obstructed endpoint can need several approach bends before reaching that lane. The path never enters another card. There is **no 64 px minimum gap**: leave **at least 8 px between facing card bodies** for the measured protruding handles. The 12 px port handles that protrude 6 px from a card's sides count as part of that card for clearance: a route keeps up to 12 px (never more than its own padding) from another card's handles, so an entry column no longer passes a few pixels from a neighbour's `out` handle and reads as joined to it, while its own cards' handles, where its ports sit, are exempt. Only when no route fits that way does a last attempt ignore handles (never card bodies), using the same full, half, and zero endpoint-padding ladder, so a connection squeezed along touching cards is still drawn. Every corner takes the full 8 px radius unless its curve would enter a card or handle; only such corners shrink, down to square, so a tight escape no longer squares the corners of the whole route. Only a port inside another real card is marked blocked, with **Port covered by a card; move the card**. A completely enclosed endpoint, or an exhausted bounded search, uses **No clear route; move a card**. Both warnings keep their pill: the router reserves the whole text (the edge never shortens a warning) and searches upward from above the port until the pill clears every card, handle and earlier label, so no card paints over the explanation.

Shorter horizontal spans receive lanes first, with edge id only breaking ties. **Every free 24 px lane candidate outranks compressed or shared candidates**, regardless of travel distance. Only when none fits does the router try 12 px separation, then sharing. Labels reserve a 22 px high envelope, including pill padding and stroke; neighbouring pills move along their straight lanes into disjoint intervals. Text shortens only as needed, retaining the full title and accessible name. Candidate collection examines all obstacle and reserved-lane boundaries within 192 px of the endpoint span before compressing; there is no 32-candidate cutoff. Cached vertical clear intervals, shared horizontal collision checks and travel-cost bounds keep that wider search local. Separate escape/entry columns use 12 px steps, including a column for each port/incoming-edge rank; the 80-return regression requires at least 40 routes with no shared vertical trunks or overlapping labels. Obstructed escapes use a direction-aware A* search with a bend cost, a maximum 64-by-64 coordinate grid and 2,048 expansions per attempt. Scratch buffers are reused. A valid detour is always retained, including a forward-pointing loop-back whose Z path has no middle horizontal segment. A short lane can use another horizontal segment for its label, or a clear fallback position above the path; label placement never makes a valid connection disappear. These finite bounds do not guarantee discovery of every possible route. Cards are never repositioned.

`editor/routing.ts` remains independent of the store and DOM. Geometry snapshots retain unchanged measured nodes and skip only cards awaiting measurement. Incremental planning replays the same span/id order as a fresh plan. It records the individual obstacle and reservation regions consulted, including rejected alternatives, and invalidates dependencies on changed boxes, earlier lanes/labels and port/incoming ranks. Long returns retain separate trunk strips and candidate intervals that can beat the current cost, rather than treating empty space between trunks as an obstacle dependency. Vertical travel is constant between endpoint heights, including at fractional drag coordinates. Tests compare incremental and fresh results at intermediate drag steps as well as after returning, for the same direction classification; the explicit hysteresis still applies. Adding/removing an edge invalidates its dependants instead of resetting all routes. An indexed box lookup limits collision checks to nearby cards. Unchanged routes, nodes, edges and handlers keep their identity. Per-edge view subscriptions publish path changes without rebuilding xyflow's connection index or rendering the full canvas. The `gg:backward-routing` Performance API measure sums geometry preparation and the entire cache miss: comparisons, invalidation, routing and identity reuse. It excludes React's scheduling delay between those phases, keeps only the latest timeline entry, and exposes every measurement to observers. It never writes to history: `onNodeDragStart` closes the previous step and a released drag records one move. The router returns ordered points, approach padding, lane padding, per-corner radii and a label position/envelope. Manual routes (#44, below) enter the same plan as fixed input.

The animated loop-back dash, label pills, click/keyboard selection and Delete/Backspace/Undo behavior stay. Long labels retain their full SVG title and accessible name. Colours match the drawn surfaces: `--canvas-edge`, `--canvas-edge-loop`, `--canvas-edge-selected` and `--focus-ring` strokes on `--canvas-bg` (3:1); `--text-muted` and `--text-default` labels on their `--surface-raised` pill (4.5:1). Existing registered pairs cover these combinations in `tooling/scripts/design-contrast.pairs.json` and `docs/qa/design-contrast.md`. Forced colours use system `Canvas`, `CanvasText` and `Highlight`; reduced motion stops the dash.

### Manual edge routes (Decided, #44)

The owner's request: move the horizontal and vertical break points of a line to get it out of the way, especially for the loop-back. Automatic routes stay the default; a manual route overrides the automatic one for its edge.

- **Contract.** A manual route is stored on the edge it draws, as `edge.ui.route` (`EdgeRouteSchema` in `contracts/src/loop.ts`), mirroring a node's `ui`. Edges are stored with stable ids, so the route needs no separate layout block keyed by source, port, and target: deleting the edge deletes its route, a rename (which rewrites the edge's ends) keeps it, and nothing can be left orphaned. The value is the positions of the route's inner segments in canvas coordinates, alternating the x of a vertical segment and the y of a horizontal one (`x, y, ..., x`: an odd count from 1 to 63, finite numbers). The first and last segments are horizontal and are not stored: they run from the ports' own heights to the first and last stored x, so they are recomputed from the current port tips whenever a card moves. This keeps the route when one end moves (the inner segments stay put and the stubs stretch), which is how cards move here (one at a time); relative offsets would only win when both ends moved together. Loops without the field route automatically. The route field introduced no format bump; the later format-2 cutover preserves it unchanged. The engine ignores the field (`engine/src/edge-routes.test.ts` runs a routed loop and its unrouted twin to identical events); published versions pin it with the rest of the definition; export and import carry it unchanged.
- **Router.** `RoutingEdge.route` is fixed input to `createRoutingPlan`. Fixed routes are planned first, in id order: drawn exactly as given (`manual-route.ts` turns the stored form into points between the current port tips), described as the router describes its own routes (the live plan exposes the longest inner horizontal as the lane, a label placed clear of cards and earlier labels on another horizontal or above the path, per-corner radii that keep curves out of cards, reservation bounds), and reserved before every automatic route, every horizontal (including the endpoint stubs from the current port tips) as a lane and every vertical as a trunk, so the automatic routes keep their spacing from them. They join the incremental planner's dependency graph like any route, and when a route changes in place the planner now invalidates later routes by the exact reserved elements that changed (trunks, lanes, labels) rather than the route's whole envelope (a route that appears or disappears still counts with its envelope): dragging a manual lane or stretching an endpoint stub replans only the routes whose candidate lanes it touched (13 to 26 of 600 per step in the 300-card fixture, bounded at 32 in `routing-manual.test.ts`; a 60 x 48 px card drag may replan 38 there). The direction hysteresis compares connections, not routes. The routing cache's key includes the routes.
- **Edge type.** The edge type is `orthogonal` (`editor/OrthogonalEdge.tsx`, formerly `BackwardEdge`): it draws a backward route, a manual route, or, for a forward edge without one, xyflow's own smoothstep path (computed with `getSmoothStepPath`, so selecting a forward edge changes nothing on screen). Unselected forward edges without a manual route keep xyflow's `smoothstep` type.
- **Selecting and dragging.** A selected edge draws above the cards and shows a handle on each segment of non-zero length: the port stubs, every vertical and horizontal segment, and the loop-back's return lane. A lane handle moves aside from the label pill when the lane has room. Dragging a handle moves its segment along its own axis; the route stays orthogonal because the neighbouring segments stretch. Dragging the first or last segment off its port's height keeps a stub of at most 24 px on the port and moves the rest; a straight line keeps a stub at both ends. The canvas does not snap (nodes do not either), so a drag lands on whole pixels where it is released. While the pointer is down the route is a preview routed through the plan (the automatic routes make way live); releasing it stores the route in one undo step, closing the open step both before the drag and on release, so a following keyboard nudge starts another step. Escape or a cancelled pointer drops the preview; a press without a move stores nothing. After an edit the stored route is normalised: segments that collapsed onto their neighbours are removed, and a route that became a plain straight line is removed (the automatic path is the same line). The normalised candidate must fit the contract's 63-coordinate limit before it is stored: a split or nudge that would exceed it keeps the valid route and politely announces "This route has as many segments as a route can hold". An edit that collapses redundant segments and still fits is accepted, even at the limit.
- **Keyboard.** With an edge selected, Tab moves from the edge into its handles in segment order and on to **Reset route** (Shift+Tab goes back). The arrow keys along a handle's axis (Left and Right for a vertical segment, Up and Down for a horizontal one) move the segment to the next grid line (22 px, the background's dot spacing), Shift+arrow five lines; a run of nudges of one edge is one undo step, and focus stays on the moved segment even when moving a port stub split it. The other arrows, Enter, Space, Delete, and Backspace do nothing on a handle (it is `nokey`, so the canvas's Delete never removes the edge from there). Escape returns focus to the edge, which stays selected. Each handle is a `role="button"` named "Route segment 2 of 5, vertical" with a description of its keys and `aria-keyshortcuts`; a polite live region announces each change ("Segment at y 264.", "Route changed.", "Route reset: the connection routes automatically."). The edge's accessible name ends in "manual route" while it has one.
- **Crossing cards.** Where the author puts a segment is kept, even across a card: rerouting can take several moves whose in-between states still cross one. The route is dotted, its toolbar says **Crosses a card**, and its accessible name and announcement say so. At node-drag start, each manual route pins the specific cards it already crossed. In `createRoutingPlan`, a new intersection outside that set computes the automatic fallback first (including forward smoothstep geometry). The route is set aside **only if the fallback crosses no card**; otherwise the preview stays manual, dotted and flagged as crossing. At the drop position, the canvas removes only routes in that same plan's suspended set, in the move's undo step. Preview and release therefore agree. A final position change and arrow-key move also wait for the plan at the new position. One live announcement combines the counts of reset routes and routes kept because their replacements are obstructed. Undo restores the position and routes together. Existing intersections do not exempt a route from a newly crossed card; a move with no new intersection keeps the route and its stubs follow the ports. Adding or growing a card can also leave a dotted crossing until the author edits or resets the route.

- **Reset route.** A selected edge with a manual route shows a **Reset route** button (the outline button style, 32 px, 44 px for a coarse pointer) above its label, reachable with Tab after the handles. It removes the manual route in an undo step of its own and returns focus to the edge.
- **Look.** Handles are 12 px dots in the selected-edge stroke (`--canvas-edge-selected`, 3:1 on `--canvas-bg`, an existing registered pair) on the raised surface, filled on hover, with a 24 px target (44 px under a coarse pointer); keyboard focus draws the `--focus-ring` ring (3:1 on the canvas). They are scaled against the zoom, so they keep their screen size. Forced colours use `Canvas`, `CanvasText`, and `Highlight`; the toolbar takes system colours. Styles live in `styles/canvas-routes.css`.
- **Tests.** `editor/manual-route.test.ts` (the stored form, segments, moves and splits, normalisation, nudges, smoothstep equivalence), `editor/routing-manual.test.ts` (fixed routes in the plan, node moves, crossing and fallback, reservations, incremental equality and the replanning bound), `editor/OrthogonalEdge.test.tsx`, `editor/Canvas.test.tsx` (drag, nudge, reset, crossing, node moves, undo), `editor/store.test.ts`, `editor/useRouting.test.ts`, contracts and domain round-trips, the engine test above, and Edge E2E in `e2e/edge-routes.spec.ts`. The QA hand-off with screenshots is [docs/qa/2026-10-05-issue-44-waypoints](qa/2026-10-05-issue-44-waypoints/README.md).

## Run inspector (Draft)

- Exact execution evidence (#255): selecting any timeline event offers **Exact recorded event**, with bounded JSON, Show all and an exact JSON download. "Exact" means every value as GraphGoblin recorded it: numbers are recorded from JavaScript values, so each stored number token round-trips unchanged; a store edited by hand outside GraphGoblin with an integer beyond JavaScript precision (above 2^53) is read, shown and downloaded rounded, as every other reader of that store already does. **Execution context** identifies the pinned definition and offers the exact run record and definition JSON. Missing definitions, labels and cancellation actors are identified explicitly; historical threads come from the run's stored initial thread on the server (#186 round 2), so no client-side seed fallback exists.
- Patch diffs show each `add` operation's recorded inserted value, including `null`, nested arrays and multiple `/-` appends in one patch. **Added value** describes the operation's value rather than the final array or an absent value at the append pointer. Other operations retain the completed patch's before/after path view; the exact operations remain in the selected event.
- Timeline, node progress, wait, patch and evaluation labels use only the immutable version named by the run's `versionId`. Labels appear beside stable IDs. Run-list names use `run.pinned.name`, so later loop renames do not relabel history. Unavailable pinned definitions never fall back to the current draft or published version.
- Probabilities and confidence use percentages with at most two decimal places. Nonzero values below 0.01% show **<0.01%**; values above 99.99% below one show **>99.99%**, preserving the distinction from zero and one. Exact recorded numbers remain in event JSON. Choice alternatives show their pinned route labels beside IDs; Score probability keys remain rubric indices. Both probability lists sit under a visible heading (**Alternative probabilities** or **Rubric index probabilities**) that also names the list for assistive technology.
- A cancelled run identifies its recorded cancellation-request actor and event numbers, or says the actor was not recorded. An incomplete event prefix is distinguished from unrecorded facts; a missing terminal cancellation event is named without denying a request that was recorded. The recorded node position is labelled separately. Cancellation never displays a stale failure alert. Provider failures retain the recorded diagnostic and raw failure evidence; the list shows its recorded code and message. An elapsed run deadline remains the distinct engine failure `RUN_DEADLINE_EXCEEDED`, as recorded, rather than a provider error or an invented cancellation actor.

- Timeline from the SSE stream with the cursor stored so reload resumes without gaps.
- Cached terminal events do not prove the stream is complete: the hook subscribes from its stored cursor and waits for the helper's authoritative `stream.complete`. This includes historical failures followed by resume and delivery audits after the final outcome. Unconfirmed EOF retains reconnect/backoff; a typed fatal history error becomes the hook's error state.
- Thread values come from server read models (#186 round 2). The live view uses #116's current-thread read, labelled **Current thread**. Selecting a sequence uses `GET /runs/{id}/thread?at=N`; a selected completion also reads `at=N-1` for its patch diff. A default selection on a completion uses those exact reads too. Historical reads carry domain replay state across 128-event pages on the server, using a verified checkpoint only when it precedes the boundary. The browser never reconstructs variables, messages, gates, visits, usage counters or iteration from a truncated window. A pending read leaves the preceding thread mounted with its own label and an explicit reading note; read failures are visible. Selected snapshot queries have zero inactive retention, rather than accumulating a cache per sequence.
- Large values remain bounded through `BoundedValue` (#259): 4,096-character previews (1,024 in patch/progress cells), full text and exact JSON downloads on request. Fifty recent messages render initially, with Show all and download controls. Expansions reset when the resolved value changes and keyboard hand-offs remain in the viewer. The engine's context and stored history are unchanged. The old browser replay/cache and large-history reconstruction threshold are retired.
- Node progress explicitly covers the **retained history window**. Earlier activity is available through Timeline browsing. Oversized markers load exact payloads in the Timeline selection panel rather than expanding node progress groups.
- Wait handling: when the run is waiting on input, a form rendered from the wait node's `inputSchema` appears inline.
- Completion evidence: **Exit evaluation** shows the exit outcome, the last gate decision, and why a run whose exit returns None has no result (see "Gate and terminal exit authoring" below).

The timeline lists selectable `harness.turn` and `harness.submission` rows with the node ID.
Selection reads the exact thread at that event from the server. The authored prompt, visit ID, turn ID,
acceptance marker and submission classification are available through REST; the inspector
does not display them as event details today.
The provenance detail view is coordinated with #379.

The inspector displays finalization separately from execution (#185, ADR-0057).
A terminal run without finalizedAt says "Execution ended; finalization pending."
Its timeline remains live until authoritative stream.complete. Once the marker is
present and no webhook is pending it says "Fully finalized."; failed webhook delivery remains visibly failed
beside the unchanged execution outcome. Terminal snapshots poll once per second
while the marker is absent, and stream completion refreshes the snapshot. EOF never
marks the timeline complete. After completion, any new history discovered by the
remote-resume watcher opens a fresh SSE subscription, even if that attempt has already
ended, so pending delivery cannot be finalized by JSON polling alone.

## PWA behaviour (Decided)

- `vite-plugin-pwa` with Workbox, `registerType: 'prompt'`.
- Update flow: the app asks the service-worker registration to check for a new build at registration, on window focus (at most once per 60 seconds, with a throttled focus deferred until that boundary) or becoming visible, hourly while visible, on browser reconnect, and when API reachability returns after an outage. Checks run only while visible, browser-online, and without a known API outage, with at most one check in flight. Scheduled checks and listeners are removed on unmount or page unload; a rejected check warns once per failure streak. A worker already waiting at registration shows the toast on first render. Each trigger also checks for a waiting worker, and the app owns a registration `updatefound`/worker `statechange` listener so later builds still prompt after Later even when Workbox detaches its listener. Each updated worker prompts once; the initial installation does not prompt. The app shows "A new version is available" with Update and Later; Later dismisses the prompt for that worker, Update activates it and reloads when it takes control. No automatic activation.
- Precache: the app shell only. API responses are never cached by the worker.
- Offline: the shell opens and unsaved editor drafts persist in IndexedDB. Anything needing the backend shows a clear offline state. Active queries that failed because the API could not be reached retry on the browser's `online` event, including after an offline reload, without navigating. While an active query holds a connectivity error, a public `GET /healthz` probe through the API client's base URL retries after 2 seconds, doubling to a 30-second cap. A successful health response refetches only active connectivity-failed queries without cancelling their in-flight fetches. Recovery is confirmed once per outage only after those reads cease holding connectivity errors; a healthy `/healthz` with a stuck route keeps backing off and leaves the banner stable. There is at most one probe in flight, with a 5-second timeout; probes stop when no query needs recovery, the tab is hidden, or the browser is offline, and resume when visible and online. HTTP 4xx/5xx query errors never start probing. Each fetch keeps the one-retry limit; HTTP errors keep the existing query behaviour. The banner says "You are offline" for browser connectivity and "Cannot reach the GraphGoblin API" for an API outage while the browser is online; confirmed recovery clears API unreachability. Signal sources are active query transport failures, draft-save transport failures, and run-stream transport failures; accepted streams report reachability through the same transition functions. A failed draft save refreshes its active loop read once per revision, and a dropped run stream refreshes its active run read once per outage, so loaded screens also create probe demand. A stream whose last failure was a transport failure restarts at its committed cursor on recovery. Stream outages are reported once until an event advances the cursor or an accepted stream stays open for at least one 15-second heartbeat interval; acceptance alone and repeated short connections do not re-arm them. HTTP refusals, invalid stream frames, and a clean end-of-stream do not create connectivity failures; their retries keep the existing SSE backoff. When no active query needs recovery, the unreachable claim clears after one tick and a fresh check for active failures or reads, without a recovery notification; cached errors are remembered across inactivity and do not reopen an outage until a fresh failure arrives. There is no offline execution.
- Reconnect: a connectivity error that lands after the browser's `online` event still starts probing, so a no-data fetch also recovers without focus or navigation. The API-unreachable banner is suppressed until the browser reconnect refetch cycle settles or five seconds elapse, whichever comes first. Unrelated active reads do not extend this grace.
- Install: a web manifest with icons; an install hint in settings.

## Design tokens (Decided, #7)

The look comes from design tokens, implemented to the visual direction the owner approved (`docs/design/visual-direction/`, ADR-0017). Dark is the default theme and light the alternate.

- **Two tiers** in `apps/web/src/styles/tokens.css`. The primitive tier is the palette (green, brown, grey, magenta, violet, blue, orange, amber, red, teal, slate); only the semantic tier references it. The semantic tier names what a colour is for: surfaces (`--surface-app`, `-raised`, `-sunken`, `-head`, `-overlay`, `-hover`, `-control`, `-field`, `-inverse`) and the `--scrim` behind a modal dialog, text (`--text-default`, `-heading`, `-table-head`, `-muted`, `-subtle`, `-link`, `-on-accent`, ...), borders, the accent (goblin lime, with `--accent-highlight` magenta and `--accent-glow` purple reserved for the most special moments), danger, status tones (`--status-{neutral,good,bad,warn,info}-{bg,fg,border}`: blue success, orange failure, amber waiting, violet running, always with an icon), node kinds (`--kind-<kind>` and `--kind-<kind>-subtle`), the focus ring, code, canvas, mascot, and shadows. It is declared for light on `:root, [data-theme='light']` and for dark on `[data-theme='dark']`, each with its `color-scheme`, so native controls, scrollbars, and date inputs follow the theme. Type (`--font-ui`, `--font-code`, `--font-size-*`), space, radius, and motion scales are theme independent; the motion durations drop to 0 ms under `prefers-reduced-motion`, which also stops every keyframe animation (`animation: none`, so the running and live pulses hold at full opacity) and collapses transitions to an instant change.
- **Theme.** The `data-theme` attribute on `<html>` picks the tier; it may also sit on any element, so a subtree can show the other theme. `index.html` ships `data-theme="dark"`, so anything that cannot read a choice shows the default. The theme control is described under "Theme control" below.
- **Tailwind.** `styles/theme.css` maps Tailwind's keys onto the semantic tokens with `@theme inline reference` (`bg-surface-raised`, `text-muted`, `border-default`, `ring-focus`, `bg-status-good-bg`, `font-mono`, `text-sm`, `rounded-md`, `shadow-2`, `gap-section`, `p-page`) and resets Tailwind's default scales, so palette classes such as `bg-slate-100` produce no CSS. Node-kind colours come from `KIND_INFO[kind].color`, a token name: `editor/KindChip.tsx` sets `--k` and `--k-subtle`, read by `bg-kind` and `bg-kind-subtle`. The glows and pulse of the highlight moments are utilities in `styles/utilities.css`.
- **Only `src/styles/` holds colour literals.** Components use the utilities or `var(--token)`. `theme-color` and the manifest colours are read from `tokens.css` at build time (`vite.config.ts` with `styles/palette.ts`): the dark header (`--surface-inverse`) and page (`--surface-app`).
- **Third-party widgets.** `styles/code-theme.ts` themes CodeMirror (surface, gutter, active line, selection, cursor, tooltips, the search and replace panel with its fields, buttons, and `--code-match` highlights, and syntax colours from a highlighter keyed by lezer tag names; Liquid delimiters show as operators). `styles/canvas.css` themes xyflow through its `--xy-*` variables: background dots, edges and the selected edge, handles, edge labels as pills, controls, the selection box, and a token focus ring on focused nodes and edges. Forward edges use xyflow's built-in `smoothstep` path; backward edges use the padded obstacle-avoiding router above (#18); an edge with a manual route draws it (#44). The explicitly marked repeat edge keeps its animated dash in the loop colour.
- **Fonts.** Every face is self-hosted in `apps/web/public/fonts` with its licence text, declared in `styles/fonts.css` with `font-display: swap`, and precached with the app shell, so the offline shell keeps it. Geist and Geist Mono (SIL OFL 1.1) are the defaults. Components never name a family: text uses `--font-ui`, headings (`h1` to `h6`, a base rule in `fonts.css`) and the header wordmark (the `font-display` utility) use `--font-display`, and code uses `--font-code` (Geist Mono, never switched). Both switchable tokens fall back to `--font-fallback` (the system UI stack). The Font control below switches them; the boot script preloads the chosen face's files.
- **Reserved accents.** Magenta and purple appear only on the selected canvas node's ring, the heartbeat kind, the waiting-for-input dot on Runs (the navigation supports it; no data feeds it yet), notifications (the update toast), the running badge's glow, the mascot's eyes, and the header's hairline: a 2 px purple-to-magenta line along its bottom edge that fades out to the right (`--accent-hairline`, owner request after the first dark sample; in forced-colours mode it gives way to a plain bottom border). Navigation and buttons stay green and neutral; the current page has a green underline directly under its label.
- **Accessibility.** Every text and non-text token pair meets WCAG AA in both themes (the contrast table generated from `tokens.css`). The focus ring (`--focus-ring`, 2 px, offset 2 px) holds 3:1 on every surface. In forced-colours mode the selected node and the current timeline row keep outlines and badges keep a border, because box shadows are dropped.

A `button role="switch"` with `aria-checked`, 44 by 24 px, whose thumb slides right and turns the track green when on; a click, Space, or Enter toggles it, and a `<label htmlFor>` naming it toggles it too. Props: `checked`, `onCheckedChange`, `disabled`, `aria-label` or `aria-labelledby`, `id`. For a boolean that always has a value (a default, or required) and for the model catalog's Enabled column. In forced colours the thumb keeps a solid edge, so its side shows the state.

For a choice of two to four options: a fieldset (`role="radiogroup"`, named by its legend) of native radios drawn as connected segments on a sunken track, the chosen one in the accent's subtle fill with a 3:1 inset edge. Tab reaches the chosen segment (the first when none is chosen) and the arrow keys move the choice. `notSet` adds a first segment that leaves the value unset (typed: `onChange` then also receives `undefined`); without it a required choice starts with nothing chosen. A segment never grows wider than its field: a long label ends in an ellipsis (the shared `ellipsize`), keeping the whole text as the radio's name and as the segment's tooltip. The Appearance theme control uses it. Help buttons open the same non-modal popover on hover or tap and use `tabIndex={-1}`, preserving one Tab stop per group. Each radio retains its accessible description while help is closed.

The native `input type="file"` lies transparent over an outline button ("Choose file" with an upload icon), so a click, Tab, Space, and Enter stay native and a `<Label htmlFor>` names it; the focus ring is drawn on the button, and the last chosen file's name sits beside it and describes the input. - **Disclosure** (`disclosure.tsx`, #14). A button with `aria-expanded` and `aria-controls` that shows and hides a panel kept mounted while hidden: `variant="box"` is a bordered section whose full-width header is the toggle (a form's Advanced options), `variant="row"` a compact list item header with `actions` beside it. `summary` adds to the toggle's text, `defaultOpen` sets the first state, `open` with `onOpenChange` lets the caller keep the state instead (so it outlives a remount), and `revealDisclosures(element)` opens every collapsed one around an element at once (through `onOpenChange` when the caller keeps it).

Its ids are generated per field, so a property may have any name. Each problem shows beside its property under the property's title ("Approval is required", "Reason must NOT have fewer than 3 characters", "Labels: invalid JSON (…)"), located through `validateJson`'s `issues` in `domain` (path segments, a missing property at itself); editing a field clears its problems. What it sends is unchanged: a field left unset sends nothing.
- **Contrast.** The controls use token pairs already in the contrast table (field and track edges, the selected segment, the switch thumb on and off, the checkbox tick, the focus ring on every surface); #8 added the error text and marker, and the invalid edge, on the sunken surface (the model form).

### Bounded stream batches (#186 round 1)

`useRunEvents` retains the 100 ms batching window but flushes early at 256 events or
1 MiB of estimated UTF-16 JSON storage, including during throttled browser timers.
The client supplies the received JSON text's size as `onEvent`'s second argument,
so the hook does not serialize events again merely to measure them.
A single larger event flushes immediately; no server payload is truncated. Browser
retention and exact payload loading are described below. A typed `SSE_SLOW_CONSUMER` or `SSE_REPLAY_FAILED` error flushes the old batch and shows
the server's one-sentence reason as the stream error while the client retries from
its last delivered event. A successful open clears that error. Slow-consumer errors
do not report the API as unreachable. Fatal stream controls use the ordinary error
state. The existing session-storage/quota behavior is unchanged.

### Retained history and Timeline browsing (#186 round 2)

Each run retains at most **512 rows and 1,048,576 estimated UTF-16 row-JSON bytes** in memory and in its session cache; at most 20 runs remain cached. These are engineering parameters, not owner-approved limits. The ordinary window spans about 40 passes of the measured cyclic workload; bytes independently bound payload-heavy windows. Eviction changes only a browser copy. The full SQLite event log and execution context remain complete.

An event larger than the byte budget is represented by a small selectable sequence/type marker that keeps its ordinary row description and accessible name. The marker keeps the description as its parts: recorded text, cut to the existing 4,096-character preview budget, and the IDs of the nodes and decision routes it names, which the row names with the pinned version's labels like any other. The parts carry no other value of the event, so a payload of many small values, many patch operations or a wide schema leaves the marker as small as any other. Clicking it fetches the exact event and shows a bounded Event payload preview with full text and JSON download; one explicitly requested intrinsic payload can exceed the history budget, is never persisted, and is released on another selection. This distinguishes a value the reader requests from incidental history retention. No payload is truncated or silently skipped.

`lastSeq` acknowledges live delivery independently of the visible window. The heading reports that live sequence position; mounted and retained rows are counted separately. Live mode slides the window forward. Interacting with rows, scrolling away through a wheel, touch or scrollbar gesture, or loading history pauses that window while the live stream keeps advancing its acknowledgement. **Load older** prepends a 128-event page, deduplicates by sequence, sorts in server sequence order, and evicts from the newer end; **Load newer** reverses that process. Server-issued opaque cursors are stored and passed back unchanged. Initial seeks (including a newly evicted live boundary) use numeric `around`/`after` positions to obtain a fresh boundary. A trimmed page cursor is invalidated so it cannot skip the retained boundary. Identical timestamps do not affect membership.

**Event sequence / Go to event** loads a sequence outside the window, then its exact historical thread. **Follow live** reads the latest window and catches any concurrently acknowledged suffix before enabling live retention, with at most eight 128-event catch-up reads per action; if a reader cannot catch up within that bound it receives an explicit retry message and stays in history mode. Layout/font changes and programmatic scrolling never pause follow. Reload restores the window, browsing mode, opaque boundaries and independent live acknowledgement. Pending reads are cancelled on a run/client change; their busy/error state cannot carry into another inspector or revive when returning to an aborted read. Quota/storage-denial failures remain nonfatal; a missing cache replays from the server. Device cache version 2 discards the old unbounded cache shape once; no server migration is involved.

The Timeline mounts at most **80 event rows**. Previous/Next rows move the rendered window without assuming a fixed height for wrapped descriptions. Arrow, Home/End, Page Up/Down and Tab at row-window boundaries move focus without losing the selected sequence; ordinary buttons retain their event names and Enter/Space selection. Row focus pauses live retention so arrivals cannot unmount the focused row. Follow live restores the tail and keeps its scroll at the live end. Paging controls remain mounted when disabled.

## Draft conflicts (Decided, WP-F2)

- The editor keeps the server `draftToken` its copy is based on (from `GET /loops/{id}` at load, then from each save's response) and sends it as `If-Match` on every draft save, including the save sent when leaving the editor. The IndexedDB mirror stores it with the device copy (`baseToken`), so a copy restored after a reload is saved against the token it was based on; a missing token means the base is unknown, so loading still compares server and device timestamps.
- Every accepted save advances the loop's token, even when the editor that sent it has closed, so the save sent on leaving the editor (queued behind it) is based on it. The device copy is updated in one IndexedDB transaction: a copy of exactly the saved definition becomes synced. A differing unsynced copy takes the new token only when its defined base matches the request's `If-Match` token **and** its definition and decision routes match this editor's latest in-memory mirror inside that transaction. Unread copies retain their original base even when it matches the request token. This is deliberately conservative: if one of this editor's own earlier mirror writes failed, its older device copy also keeps its base, so reopening asks for an explicit choice rather than guessing; no work is lost. Unknown bases and the mandatory conversion token also remain unchanged for explicit reconciliation; a retained copy is not marked durable for this save. Device mirrors and server-save records share a per-loop write queue; a mirror queued after the server save carries the new token already and needs no rebase.
- Reload and overwrite act only on the editor that asked: each step after an await re-checks the loop id, editor generation and revision, so a slow answer never lands in another loop's editor.
- A 409 `DRAFT_CONFLICT` stops autosave and shows "The draft changed on the server" with two buttons: **Reload server draft** (load the server draft and mark it synced on the device, dropping this editor's unsaved changes) and **Overwrite with this copy** (save again with the server's token from the conflict). Nothing is overwritten without one of these clicks. Edits made meanwhile stay on the device, the save state reads "Draft changed elsewhere", leaving the editor sends nothing, and Publish refuses until the conflict is resolved.
- Choosing "Use this device's copy instead" for a set-aside copy is an explicit overwrite of the server draft shown.
- The conflict notice says where the unsaved changes are, as the device copy stands: "kept on this device", "kept in this window only" while device storage refuses them, or "kept in this editor" while the device write runs. Reload works while device storage is unavailable: the server holds the draft, and a copy left unsynced on the device is based on an older token, so its next save asks again.
- Regression: `src/editor/EditorPage.conflict.test.tsx` and the two-tab E2E `e2e/drafts.spec.ts`.

## Device storage and the save states (Decided, phase review F2)

### Device-first editor loading (#171)

The loop request and the active, set-aside and archive IndexedDB reads start together.
Eligible current-format device work renders before a slow server answers. Warm navigation
uses the latest per-loop in-memory copy, including edits whose durable write is still pending
or failed; it never borrows another loop's copy. Memory presence and successful durable
persistence are separate facts. Active writes are ordered per loop; an older completion
cannot mark a newer copy durable. Copies in another format are listed as unsupported and
never loaded (below); archives are never activated.

Loading has two independent milestones: **editor available** means a device or server
copy can be edited; **server reconciled** means this opening's fresh server request and
device reads have settled safely. A cached query alone cannot authorize saves. While
checking, edits enter the per-loop memory copy immediately; durable mirrors wait for a
successful device inspection, and all server saves (debounce, flush, leaving, reconnect and
recovery) wait for reconciliation. Offline work remains editable and reconciles when the
server returns. A failed storage read reports the storage problem and permits a usable
server editor. Inspection is complete even on failure, so server reconciliation and saves
continue normally. Device mirrors stay memory-only until storage is successfully inspected;
a server save may still attempt its safe read-modify-write, which preserves unrelated device work and its original base token
and reports durability only for the exact copy stored. Rebasing a differing copy requires a defined, matching request base
and matching this editor's latest definition and decision routes at transaction time; a conversion
token never authorizes it. After a failed read, the differing unread copy keeps its base and reaches
the conflict or set-aside path on reopening.
**Retry device read** inspects and preserves unread work before durable mirrors resume;
retrying preserves edits, held input and the current editor generation. Successful
independent storage operations do not clear this unresolved read notice.
Preservation or conversion failures keep their stronger pause.

A late response may replace only an untouched displayed copy. Edits, held field input,
undo/redo or opening a node dialog prevent replacement. If the server is newer, the original
unsynced copy is retained separately; any earlier set-aside copy is archived and verified
before that slot is reused. An untouched editor then shows the server with **Use this
device's copy instead**. An editor changed during loading keeps its work and, when its base
is stale, asks **Reload server draft** or **Overwrite with this copy**. Old base tokens
remain old until explicit resolution or an accepted save from that same base advances this editor's matching mirror.
Two absent tokens do not prove a shared base; the server's `updatedAt` comparison still applies. A different durable copy found behind a warm cache is retained with **Another device copy is available**, without replacing the editor. A failed restore
or discard retains the backup and reports a retryable notice.

The timed regression in `editor/useLoadEditor.test.tsx` distinguishes this set-aside
notice from a save's 409: the original reproduction had server response at 199 ms,
query cache at 205 ms, device read at 212?214 ms and first render at 219 ms, with no PUT
or 409. After the change, a cold copy rendered at 40 ms before the server answered at 254 ms; a warm copy rendered at 3 ms before its server answered at 168 ms. These are controlled test timings, not a production latency guarantee. The test requires device rendering and the device read to precede the held
server response. It also exercises cold and warm openings. Browser regressions in
`e2e/device-first.spec.ts` cover a slow server, two-loop warm navigation, edits before a
late response, offline reload/recovery and explicit conflict overwrite; two-tab 409 cases
remain in `e2e/drafts.spec.ts`.

A completed save from a previous editor advances the cached base token before
reconciliation chooses a device copy. A matching server token prevents that accepted
save from producing a newer-server prompt, including when newer edits remain in memory.
Server-save recording marks only the definition actually stored as durable; a different
memory-only definition stays memory-only. Current-format recovery copies retained in
the archive are labelled **Saved device backup**, separately from unsupported older copies.
A successful server read with no draft or published definition finishes checking: device
work remains available, or the editor explains that no definition is available.

### Device drafts in another format

A device copy written by an older build (its definition's `schemaVersion` is not the
current format, or it has no definition) is never converted, loaded into the editor or
overwritten ([ADR-0042](decisions/ADR-0042-explicit-resets-replace-conversion.md)).
`useLoadEditor` lists it as **Unsupported device draft (format N)**, naming the loop,
which copy it is (an unsaved draft, a set-aside draft or an archived copy) and when it
was saved. While such a copy sits under the active or set-aside key, the editor shows only
these notices: editing, autosave and device writes pause, and a write that would replace
it is refused inside its IndexedDB transaction (`UnsupportedDeviceDraftError`), so even
another window cannot overwrite it silently. **Export this device draft** downloads the
stored record unchanged. **Discard this device draft** (its description says that only
this browser's copy is removed) deletes exactly that record; when the last copy that paused
editing is gone, the editor reads device storage and reconciles with the server again, as
on opening. An old archived copy is listed the same way without pausing editing.

Current-format copies archived before a newer set-aside replaced them are labelled
**Saved device backup**. When such an archive write or its read-back fails, editing pauses
on **Device copy preservation failed** until the blocked copy is exported or discarded.
Regression: `editor/EditorPage.restore.test.tsx`, `editor/useLoadEditor.test.tsx`,
`drafts/local-drafts.test.ts` and Edge `e2e/device-draft-format.spec.ts`.

Run events and their SSE resume cursors are the only persisted run data, in
`sessionStorage`. Their key is `graphgoblin-run-events-v4`; earlier keys are removed
once at module initialisation before hydration. Repeated reads do not repeat cleanup. No old-event reader exists. React Query data is memory-only and
the service worker caches the app shell, never API responses.

The IndexedDB mirror can be refused: an older GraphGoblin tab or PWA window that keeps its version 1 connection open blocks the version 2 store upgrade, and storage can fail for other reasons (quota, private modes). The editor reports where the edits are only after the write that keeps them has answered.

- **Explicit storage state.** `drafts/local-drafts.ts` keeps the device storage's state (`deviceStorageProblem`: undefined while it works, `blocked`, or `failed` with the reason) and tells subscribers when it changes (`subscribeDeviceStorage`). Every operation updates it: a success clears it, a failure sets it. An upgrade still blocked after a three-second grace counts as blocked; from then on operations fail at once instead of waiting again, loads read as no device copy (the editor opens on the server's), and the pending upgrade is kept: when the other windows let go it completes, the store becomes available, and subscribers hear so without waiting for the next write. A `failed` state clears when an operation succeeds again (the next edit's write re-checks).
- **The device copy of the current revision.** The editor mirrors each edit and records the revision once the write succeeds (`deviceRevision` in the store). The current revision is then `device` (written), `writing` (under way), or `memory` (refused, so it lives in this window only; `editor/save-status.ts`). When storage becomes available again, unsaved edits that are only in memory are written to the device at once.
- **Three states in the indicator and its messages.** In memory only: "Kept in this window only" (or "Offline: kept in this window only"), and the save notice says "Changes are kept in this window only." Saved on this device only: "Saved on this device only" (or "Offline: saved on this device"), with "Changes are kept on this device." Saved to the server: "All changes saved". While the device write runs, a schema-invalid draft reads "Unsaved changes" and its notice claims no device copy yet. A successful server save shows as saved to the server even while device storage refuses its record of the save (`recordServerSave`): that refusal never holds the save pending.
- **The device notice.** While device storage is blocked or failing, a notice of its own ("Changes are not kept on this device") says why, that changes the server has not saved are kept in this window only and closing it loses them, and to close other GraphGoblin tabs and windows (the CHANGELOG's upgrade instruction; a failure also names its reason and suggests a reload if it persists). It is dismissible for the editor load and returns when its text changes or the editor loads again; it disappears when storage works again.
- **Regression.** `drafts/local-drafts.test.ts` (fake-indexeddb with a version 1 connection that does not close on `versionchange`: loads skipped, saves and records refused at once after the grace, the state and its notifications, recovery when the old connection closes; other failures and their recovery), `editor/save-status.test.ts`, and `editor/EditorPage.device.test.tsx` (a schema-invalid edit kept in this window only with no stored draft and no server write, then written to the device and labelled so when the old connection closes; a valid edit saved to the server with the device notice apart, and the notice gone on recovery), and Edge `e2e/drafts.spec.ts` (an older version's connection held in a second page).

## Editor notices (Decided, #45)

The informational notice that a device draft was restored, save notices for schema-invalid, offline, or failed saves, and the device storage notice (see "Device storage and the save states") can be dismissed. A restored notice stays dismissed for that editor load; a later load that restores a device draft shows it again. A save notice stays dismissed through edits that end in the same state; it returns after a successful save, a different save problem or message, or a new load. The toolbar keeps the local-only or failed-save status visible with a warning icon after the notice closes. Dismissal is announced politely, and focus moves to the next dismiss control or the toolbar save status. Alerts with a required action, including set-aside drafts and draft conflicts, remain until answered.

### Typed inputs and section JSON (Decided, #170 part B)

A vanished ID removes its connections even if a new ID takes its place at the same route count; JSON never retargets a connection to another ID. Before Apply changes anything, the JSON editor lists every connection to be removed by route ID and target node, requiring a separate **Confirm Apply JSON** action. **Keep editing JSON** cancels that review; text changes reset it, and confirmation rechecks the current connections. With no removals, Apply applies at once. To rename a route while keeping its connections, edit its ID in the structured editor. The replacement and any edge removals form one undoable edit scoped to that decision.

Stable form bindings avoid rendering unrelated fields on autosave echoes. Render-count tests measure zero unrelated-field renders for two inference prompt or decision question edits.

Tab reaches Confirm Apply JSON and then Keep editing JSON; cancelling returns focus to Apply, or to the JSON editor if Apply is disabled. Held candidate validation is cached by its text and semantic whole-config replacement, so unchanged snapshots and sibling held-input keystrokes reuse the result; meaningful config changes and Apply still validate the parent rules.

### Validation badges (Decided, #15)

The owner's decision of 2026-10-04: a node's problems show on the node, as a warning icon whose tooltip-style popup explains them, instead of a list at the bottom of the panel. Loop-level and edge issues move beside Publish.

- **Node badge.** A node with issues shows a button in its header band (`editor/IssueBadge.tsx`) named "N issues on <id>" ("1 issue on ..."). It shows the worst severity: a cross on the bad tone for any error, a warning triangle on the warn tone for warnings only, so the two differ by shape as well as colour; from two issues on it shows the count too. It is at least 24 px, its edge holds 3:1 on every node band, and it carries xyflow's `nodrag`, `nopan`, `nowheel`, and `nokey`, so pressing it never drags the node and its keys never select, move, open, or delete the node (the canvas's own key handler ignores `nokey` too). A click on it opens only its popover, never the node's editor.
- **Popover.** `components/ui/popover.tsx` meets WCAG 1.4.13. It opens on pointer hover after 150 ms, on keyboard focus of the badge, and on click or tap (touch has no hover); the focus a pointer press brings opens nothing by itself (the click decides), and a press that ends without a click, such as a touch that turned into a scroll, leaves keyboard focus working. Hover (the pointer over the badge or the popover, so the pointer can move into it) and focus (keyboard focus on the badge, or focus inside the popover; the focus a click leaves on the badge does not count) are tracked separately, and an open popover stays while either holds: it closes 200 ms after the pointer has left both while focus is elsewhere, or when focus leaves both while the pointer is elsewhere. A click pins it: a pinned popover ignores hover and closes when focus moves on to another control, and a second click closes it. It also closes on Esc (focus returns to the badge when it was inside; a dialog around it stays open), on a press outside, and when its badge has left the viewport (the window shrank, say). It is a non-modal `role="dialog"` named "Issues on <id>", rendered in the top layer with the native `popover` attribute (`showPopover()`), so no node, panel, or dialog covers it and the canvas zoom does not scale it. ## Undo and redo (Decided, #17)

The owner's request of 2026-10-04: undo and redo for the editor, with Ctrl+Z and Ctrl+Shift+Z.

- **Steps.** Every change of the draft goes through the store's `edit` with a step: a label for the buttons and an optional merge key (`editor/history.ts`). The steps are adding, moving, connecting, renaming, and deleting nodes, removing edges, rerouting an edge and resetting its route (#44), a node's label and config, the loop's name and description, its settings, and its variables. A change that leaves the definition as it was is not an edit: no revision, no save, no step. Changes with the same key less than a second apart (`COALESCE_MS`, counted from the step's latest change) are one step: typing in one field (a node's label; the loop's name; its description; one field of a schema-driven form), a drag (it ends in one move, since xyflow's second report of the same position changes nothing, and its start closes the step before it, so two quick drags are two steps), a run of arrow-key nudges of one node, and a run of arrow-key nudges of one edge's segments. A segment drag is one step like a node drag; **Reset route** is a step of its own; a node move that takes a manual route back to automatic does so inside the move's step. A merged step that ends where it started (typed, then deleted) is dropped. An undo or redo closes the open step, so the next change starts a new one, and a new step clears redo.
- **Form changes.** The schema-driven forms (a node's config, the loop's settings, its variables) report each change with the field's path and its kind (`FormChange`, `forms/changes.ts`), decided in the shared form layer: every field binds with `useField(name, kind)`, and an action that makes several writes wraps them in one change (`useFormChange`, the outermost description wins). A **commit** is a discrete choice: a select or picker (model, effort, classifier, a union's variant, the cron preset), a switch, a segmented control, a checkbox, a button that sets a value (Use my time zone, Add or Remove of an optional object, Customize), and adding or removing a collection's rows. Each commit is a step of its own, however soon it follows the last change, and the writes one commit makes (its value and the unparsed text it moves or drops) are that one step. **Typing** (text, number, code, JSON, the cron builder's step and time inputs, a record's key or value) merges per field path: three keystrokes in one field are one step, typing in another field starts another, and typing after a commit starts a new one. So changing Model and then Effort within a second is two steps, and toggling a switch twice is two. A record key's rename merges by its row, since the key itself changes; a record value's typing by the value's path. A change no field describes is a step of its own. The store (`updateNode`, `updateSettings`, `updateVariables`, `setFieldError`) turns a change into the step's merge key: the form and the field's path for typing, the form and the commit's id for a commit.
- **Held input.** A step holds `fieldErrors` with the definition, and a form's report of held input (unparsed text, an incomplete schedule or unapplied section JSON) is a change like any other: typed text merges into the step of the typing in that field, and text a commit moves or drops (a row's removal) is part of that commit's step. Refreshing the message or pending/invalid classification of unchanged held text after parent validation adds no history step and preserves redo. Undo therefore takes back text that does not parse together with the typing that produced it, and redo brings it back with its blocking issue. **Discard the unparsed text**, in the field or in an issue's row, is a step of its own that never merges, however soon it follows the typing (the form reports it as a discard, `reason` `'discard'`, not as text that started to parse), so undo always brings the discarded text back; undoing a node's deletion or rename brings back its unparsed text under its id. This keeps the stored text consistent with the definition it was typed against: no undo leaves text behind for a node or path that the restored draft does not have.
- **Not steps.** Selection, the open node editor, the loop panel's state, and save state. The history holds at most 100 steps (`HISTORY_LIMIT`, the oldest forgotten first), lives in memory only, and starts afresh on every load: opening the editor, **Reload server draft**, and restoring a set-aside device copy.
- **Undo and redo are edits.** They bump the revision (unless only unparsed text changed) and set the save state to pending, so autosave, the IndexedDB mirror, `If-Match`, and the conflict stop apply as to any edit; `useAutosave.ts` is unchanged. Undoing a rename keeps the node selected and its editor open, now on the old id. A node that an undo removes is deselected and its editor closes (focus returns to the canvas); redo brings the node back without reopening its editor.
- **Forms.** `historyEpoch`, bumped by every undo and redo, is part of the keys of the node editor's config form and of the loop panel's forms, so they remount with the restored values; the node editor's id draft resets with it. The node editor keeps its config form's disclosures (Advanced, collapsible list items) open or collapsed across the remount (see "Basic and advanced fields"). A node's label and the loop's name and description are controlled inputs and follow at once.
- **Shortcuts.** `editor/useUndoShortcuts.ts`, one `keydown` listener on `document` while the editor is mounted: Ctrl+Z undoes; Ctrl+Shift+Z and Ctrl+Y redo; on macOS and iOS (`navigator.userAgentData.platform`, else `navigator.platform`) Cmd+Z undoes and Cmd+Shift+Z redoes. The letter comes from the key's character, or from its place (`code`) on a non-Latin layout; presses with Alt (so AltGr), during composition, or already handled (`defaultPrevented`) are left alone. With focus in a text editor (an input of a text-entry type: text, search, url, email, password, number, tel, or a date or time type; a textarea; a content-editable element; or CodeMirror, including anything inside one, such as the checkboxes of CodeMirror's search panel), the keys belong to that control and its own text undo applies. Everywhere else they undo and redo the editor: the canvas, the toolbar, the page, and controls without text to undo, such as checkboxes, radios, switches, selects, and buttons, in the node editor or the loop panel. When a remount replaced the focused control, focus moves to the same control in the same field of the new form (the same element, type, role, and name, counted among its namesakes), else to whatever stands in its place there, else to the field's first control. A row's header toggle and Remove button follow that row when its index changes. When the focused row is gone, focus moves to the nearest surviving row's shown header, else the collection's Add button, else its fieldset, and never opens a row. Nested rows use their nearest surviving ancestor to remap the collection path; when the ancestor is gone too, its containing collection supplies the fallback. Outside any field, focus moves to the same control in the part of the page that stayed; failing those targets, to the heading of the dialog or panel it was in, else to the canvas. A radio stands for its group's checked radio, so after an undo that changed the choice the newly checked radio has focus (`groupFocus` in `editor/focus-field.ts`, which `focusField` uses too).
- **Toolbar.** Undo and Redo icon buttons open the toolbar's action group (`editor/UndoRedo.tsx`). Each is named by the step it will change ("Undo move start", "Redo edit label of start"; plain "Undo" or "Redo" with nothing to do), with the same text as its tooltip, and `aria-keyshortcuts` (`Control+Z`; `Control+Shift+Z Control+Y`; `Meta` on Apple platforms). With nothing to do a button is `aria-disabled`, not `disabled`, so it keeps its place in the Tab order. The names are visually hidden text rather than `aria-label`, so a lookup of a field by its label ("Description") never finds "Undo edit loop description". The buttons are 32 px for a mouse and 44 px where the primary pointer is coarse (`pointer-coarse:size-11`). While the node editor is open the page behind it is inert, so there the keys are the way to undo.
- **Regression.** `editor/history.test.ts`, `editor/store.test.ts` (every change undone and redone exactly, edge routes included, merging, commits and typing per field, a commit's writes as one step, deletion and rename, the 100-step cap), `forms/SchemaForm.test.tsx` (wired to the store: model then effort two steps, three keystrokes one, a toggle a step each, a row removal with the text it moves one step, and the paths reported), `editor/NodeEditorDialog.test.tsx` (Advanced and list items kept open through undo and redo, with focus restored), `editor/useUndoShortcuts.test.tsx`, `editor/UndoRedo.test.tsx`, `editor/EditorPage.undo.test.tsx`, `editor/EditorPage.conflict.test.tsx` (an undo saved with `If-Match` and mirrored to the device, a conflict on undo, and a reload clearing the history), and `e2e/undo.spec.ts`.

Decision details add the chosen route's authored **Label** and, for a classifier Choice option or Noul side, its **Criterion**, from the immutable run version. Terminal exit details show outcome; Result shows the returned value, including `null`. **Exit evaluation** at the top keeps the last gate decision (route, pass, stopping limit) beside the exit outcome. When Returns was None it states that nothing was returned by configuration, naming the exit and start-request destinations that received nothing, or identifies a quiet exit. It derives this from the run's version and the absent result, not from delivery events, and only a pinned exit whose Returns is None supports the statement: when the pinned exit's Returns is an expression, or the pinned definition is unavailable, the inspector says that the history alone cannot show whether nothing or an unrecorded null was returned (a format-4 run recorded by an older build omitted a null result). Exhausted is available in run filters and badges and stops SSE/MCP waiting.

Historical threads are resolved on the server from the run's stored initial thread (#186 round 2), which every run records at admission, including replay-fork seeds; the inspector neither seeds gates nor reconstructs a thread from the browser's event window.

## Template gallery (#28, #160)

The Loops page's **New from template** action opens the installed catalog. Each card shows its description, tags and one green **Use &lt;template name&gt;** button. Using it immediately creates an ordinary independent draft and opens the editor. The gallery has no settings form, repository or GitHub URL field, prerequisite report, readiness presentation or configured-automation action. It does not fetch model choices or harness preflight for setup. Prompts consume the run's input and existing context; instructions, variables, model choices, limits and working directory can be configured in the copied loop. Cards share intrinsic grid rows so descriptions, tags and primary actions stay aligned across siblings and wrap at narrow widths.

A synchronous in-flight guard prevents repeated draft creation across cards while creation or editor handoff is pending. Pending controls stay focusable with `aria-disabled` and `aria-busy`, and a polite status announces progress. A failed creation shows an alert and refreshes the loop list without automatically retrying a request that might already have committed. A navigation failure after successful creation retains the loop ID: the same **Use** button retries opening that draft, and the alert offers an editor link. The loop opens with normal undo, autosave, validation and publication behavior. Default canvas spacing and layout persistence follow their separate backlog issues #124/#125.

Every use creates an owner-scoped ordinary loop with an independent definition. The catalogue exposes only a manifest (`id`, asset `version`, `title`, `description`, `tags`, `draftFile`); templates themselves are never runnable. Loop detail carries no template origin, and the editor performs no instance lookup or binding-based warning. Publish and run use ordinary graph validation and model admission. The shipped graphs have manual triggers and caller-only returns, with prompts and schemas embedded in their draft exports. Their assessments grant no GitHub authority or evidence isolation. [ADR-0030](decisions/ADR-0030-templates-are-starting-points.md) records the one-action gallery and retirement decision.

### Claude readiness and saved selections

Settings separates owner catalog enablement from prerequisite health. The seven server states are
`unknown`, `ready`, `cli-missing`, `cli-incompatible`, `auth`, `quota` and `transport`; `checking`
is client-only while no result exists yet.

On first load, readiness is `checking` until a result arrives; the Settings preflight card shows
"Loading preflight…". A background recheck (window focus or Retry preflight) keeps the last result
on screen. The card announces "Rechecking…" in a muted live region; when its request is paused
offline, it keeps the last result and announces "Offline; showing the last check." A completed
lookup failure or timeout replaces the card's badge list with "Could not load preflight", with no
state badge; the model picker and policy field show `unknown` instead of cached success.

After a successful lookup, **Harness preflight** shows one badge per harness with a label, never
the enum, which stays in `data-state`: Ready, Unknown, CLI not found, CLI update needed, Sign-in needed, Usage
limit, Connection failed. Missing, outdated and signed-out CLIs use the failure tone; unknown,
usage limit and connection failures the warning tone. Under it are the server's problems, each one
detail sentence and one action (for example "Claude is not signed in. Run claude auth login, then
retry preflight."). Claude rows add the adapter's model listing ("listed by adapter", neutral tone)
and state that listings do not confirm account access. **Retry preflight** in the card head
refetches and is disabled while a check runs.

**Defaults** gives each harness, Codex and Claude alike, at most one short line under its fields:
"Checking…" while the catalog first loads, the saved model's catalog problem (not in the catalog,
disabled), or "<Harness> readiness: <label>. See Harness preflight below." for a harness that is
not ready. A saved model the list does not offer stays selected as "<name> (saved)", "(disabled)"
or "(not in catalog)"; the full problem stays in Harness preflight. Catalog rows of a harness that
is not ready say "Enabled in catalog. <Harness> readiness: <label>." for Claude and Codex rows
alike; nothing is shown during the first check.

The **model picker** keeps a ready Claude field editable, with its label, through a background
recheck. While Claude is not ready its choices are read-only; the note is the server's first
problem followed by "Model choices are read-only until Claude is ready.", a saved model reads
"<id> (saved)", and **Retry Claude preflight** refetches. A known Codex failure adds the server's
problem as a warning and **Retry Codex preflight**; Codex choices stay editable, and neither the
first check nor a previously ready recheck adds a new failure note; an existing Codex failure
note stays visible while Retry rechecks it. The Claude policy field uses the same "Claude readiness:
<label>." line. Adapter model listings do not establish account access, and failed catalog fetches
do not prove removal. `MODEL_DISABLED` and `MODEL_NOT_IN_CATALOG` are catalog facts independent of
auth, quota or transport failures. Omitted `authenticated` means login could not be established.

Transport detail says "Claude reported a connection or provider service error." (or Codex),
followed by "Check the network connection and the provider's service status, then retry preflight."
It covers provider HTTP 500 responses as well as connection failures; it does not establish a
connectivity diagnosis.

Draft create, import, template draft and save (including 600 ms idle autosaves) never probe
readiness (D-017). The editor fetches readiness independently from `/harness/preflight`. Validate,
publish, preflight and run start probe once per referenced harness at request admission, sharing
the result within that operation and probing distinct harnesses concurrently. Each new operation
probes afresh; a later Claude turn-launch inspection is a separate check. These failures preserve
authored model/effort values.
Switching an inference node to Claude resets its policy to `read-only`/`never`; full access remains
explicit. Other authored harness options remain, with unsupported settings reported for correction.
Models retain exact identity and effort checks (ADR-0029).

### Loop history summaries

The Loops page reads each loop's `latestRun` and exact `runCount` from `GET /loops`,
refreshed every five seconds. Last run links to the latest run by creation time, breaking
ties by descending run ID, which follows creation order within one process. A zero
count and null summary says "never run"; a positive count and null summary says
"latest run unavailable" with "Check run history diagnostics." when the selected
latest run's record (including its pin), initial thread or present cached thread
snapshot, or an event in its history fails strict decoding. Event checks are cached
by run identity and event count; manual database repairs require an API restart.
An absent cached snapshot remains valid. It shows
neither a partial status badge nor an older run in its place. `GET /runs/diagnostics`
identifies the damaged row, including after restart when its stored status is valid
but stale. Unrelated loops
filling a global history page cannot hide older history. Deletion confirmation shows the exact
server count, including above 500 runs. A failed listing shows its error.

## Explicit node harness changes (#204)

Changing an inference node's Harness is one undoable authoring action. An unset model stays unset
(**(loop default)**); an unset effort also stays unset. Inheritance remains within the selected
harness, so a fully inheriting node switches without a catalog, Settings or readiness lookup.
For an explicit model, choose the first enabled compatible destination model from the **loop
default, Settings default, then ecosystem default** (D-023), matching runtime default precedence.
The catalog response identifies ecosystem defaults from the adapters' own constants (currently
Codex `gpt-6-luna`, Claude `claude-opus-5-5`); the web does not repeat those identities. Disabled,
missing or adapter-incompatible configured models are skipped. No arbitrary catalog entry is
chosen and no disabled entry is enabled. Claude compatibility includes its preflight capabilities.

A supported explicit effort stays. An unsupported one uses the first compatible loop effort,
Settings effort, then the selected entry's suggested effort. An effort-only node keeps model
inheritance and checks its authored effort against the destination's effective model. A known
unsupported effort can be replaced or cleared to inherit; failed checks keep the authored effort.
The action starts no new lookup and shares the editor's already running first checks.

The editor starts Settings and no-turn readiness checks when it mounts, alongside the catalog.
A switch with an authored model or effort waits for first-time lookups already in flight, showing a loading notice
under Harness; it applies the harness and dependent fields together when those checks finish.
Failed lookups are reported immediately rather than retried by the action. A known failure is not
queued behind another loading check, and a retry after failure does not count as the first load. The field reads shared
query state at action time and does not remount the form or refetch after a switch. Opening a
trigger or exit dialog adds no harness lookups. Undo/Redo clears the switch notice; a pending
switch is cancelled by dismissal, history changes or a concurrent field edit. When a concurrent
edit cancels the current attempt, its waiting notice clears as the checks finish; an older attempt
does not clear a newer attempt's notice.

A failed/paused catalog or Settings lookup, unready/unknown harness, or unavailable compatible
default retains explicit authored values and shows a warning under Harness, with an alert icon.
Use **Retry model catalog** or **Retry Claude preflight** / **Retry Codex preflight** on the
corresponding field. Recovery alone never authors a replacement: choose a model or switch again.
During a catalog failure the editor shows **Validation unavailable** and disables **Publish**, even
when a failed background refresh leaves cached choices available in the picker. Recovery restores
validation for the saved draft without changing authored values or clearing the switch warning. A blocked switch leaves an
incompatible draft that cannot be saved: resolve the lookup, then choose compatible values before
saving or publishing. Loaded incompatible values without a
switch remain visible and labelled incompatible, and ordinary validation reports their problems
when the catalog is available.

Successful changes save and reopen identically, and the adapter request uses those saved values.
Switching to Claude also starts its supported `read-only`/`never` policy; other authored harness
options remain for correction when unsupported. Runs never substitute models. Runtime resolution
still uses node, loop, owner and process defaults; this action adds no runtime fallback or stored
value migration. Model and effort sit on the node's Settings, outside Advanced (#205).

### Missing-session recovery control (#265)

The inspector names a missing provider handle and its origin in the failure alert. While such a failure awaits the explicit fresh-session choice, the inspector keeps checking the run every two seconds, so a choice made here, in another tab or through the API is followed to its next outcome without a reload. Long node IDs wrap in the recovery controls.
For an eligible inference failure it offers **Start fresh session for <node>**.
The explanation states that prior provider conversation is not carried over, earlier
provider actions are not undone, and configured context mode, selected loop inputs,
model and effort remain the same. Leaving the choice untouched keeps the run failed.
The control waits for the observed failed event and disables during submission;
API refusals remain visible. Plain Resume is never a fresh-session fallback.

A durable recovery note shows who chose, when, which node, and the lost prior
handle/origin after reload or completion. Inspector edits are confined to failure
and recovery controls; evidence projections and the event-stream hook are unchanged.

## Gateway shutdown notice (#319)

Every page observes `GET /system/shutdown`. While draining, a notice explains that
independent starts are refused, active work may finish, and durable waits/pauses and
queued independent work survive restart (D-038). Active run IDs link to inspectors;
existing run reads supply the immutable pinned loop name, with IDs retained if those
reads are unavailable or lack permission. Earlier unconfirmed terminations are listed
separately from active force targets.

At gateway grace expiry the notice explains the choice. **Keep waiting** acknowledges
waiting with no browser countdown or automatic force. Both choices follow the gateway's
advertised availability, including force before expiry. **Force stop** first opens a
confirmation naming active runs, required child work, uncertain external effects, and
non-automatic recovery. **Force exit** after `force-failed` separately confirms leaving
the lock for next-start reclamation without confirmed process cleanup. `drain-failed`
offers inspection, not an incompatible force transition. No browser control starts drain.

Observation polls every ten seconds while the gateway is running and every two seconds
once a shutdown phase is observed, with no automatic retry on failure, focus or
reconnect. The stopped phase and observation errors stop this polling; ready/exiting
continue to observe HTTP closure. An explicit **Check gateway state** performs a read, and
the app's reachability probe refetches it after a transport failure once the API answers.
A key without `system:read` (401/403) shows no notice while the gateway runs.
A lost connection after any healthy snapshot, including a quick drain between polls, says
**Gateway stopped or disconnected**, preserving the distinction between an observed
phase and a lost connection. Existing application connectivity recovery retains its
bounded backoff. Actions are never automatically retried; a lost action response
reports an unknown outcome. A 409 replaces the displayed snapshot with the returned
current state, including when another tab acted first. Each tab observes the gateway;
navigation, reload and tab closure send no shutdown action. Each response includes an opaque `controlToken`. Choices send it as
`x-graphgoblin-shutdown-token`; the gateway compares it synchronously before dispatch.
A phase change, another control's accepted choice or another gateway incarnation makes a
stale choice return 409 instead of turning it into a different force operation; a phase
that recurs gets a new token, so a confirmation opened before it stays stale. Changing the token unmounts any open
confirmation, requiring a fresh deliberate choice; keyboard focus then moves to the notice heading, as it does after a sent choice, and to the page heading when the notice leaves because the gateway is running again while it held focus (focus elsewhere is left alone). A missing token is an invalid
snapshot and never permits an unguarded browser choice. These choices preserve engine
drain, seal, force and recovery semantics (ADR-0049).

## History selection and confirmation

Runs offers a checkbox for each visible record, a selection count, **Review delete-ready history**, and **Withdraw delete-ready mark**. The inspector offers the same actions for its one run. Review freezes the explicit IDs and displays protection reasons; active, paused, unfinished or required retained history cannot be silently skipped from a bulk selection. Confirmation marks only the reviewed selection. Cancelling, Escape or closing leaves history unchanged; polling and later history never join that selection. Filter controls clear selection. A stale confirmation requires a new review. Retention labels and the inspector show the persisted approval and confirming actor/time. Withdrawal also retains the related dependency component. Confirmation itself deletes nothing; automatic deletion is limited to the measured-pressure policy below.

## Storage pressure notice

A subtle nonmodal notice below gateway status uses a polite live status and a link to Runs. It explains measured pressure with cleanup restricted to explicitly approved history, pressure with no eligible history that could be cleaned, or unavailable measurement/cleanup. Shared, linked and unproven resources remain kept. Adequate storage shows no notice. The browser polls the cached system observation every 15 seconds; it does not measure capacity, run cleanup or grant consent. Keys without `system:read` cannot observe the notice. The confirmation dialog clearly says that pressure cleanup can permanently remove selected history and its owned, unshared workspaces/artifacts; later history stays retained.

The no-eligible notice requires a concluding server observation with no approved candidates; a bounded batch or an older run approved since the preceding pass does not justify that notice. Workspace sharing includes configured junction/symlink/short-name aliases and aliases above missing child directories; uncertain resolution keeps the workspace. Artifact downloads use the exact canonical reference produced by publication; differently spelled references are missing rather than an alternate way to reach retained bytes.
