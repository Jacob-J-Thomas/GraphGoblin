## Summary

The browser notice, the keep-waiting and force choices, the stale-token guard, tab lifecycle, managed force, failed-cleanup handling and restart records all behaved as specified on every path driven through the API or the browser. 151 of 159 scenario checks passed. Two defects sit in the shutdown model the choice depends on:

- **D-1 (High): on Windows, the documented terminal Ctrl+C kills every in-flight Codex turn immediately.** A Ctrl+C only asks for a normal drain, but no explicit force is involved and the turn still dies. The run fails as `HARNESS_DELIVERY_UNCERTAIN` (resumable), not as an interruption. That work never gets the grace period, the explanation or the keep-waiting choice. With no other work active, the gateway exits within half a second. Cause: the Codex CLI is attached to the gateway's console.
- **D-2 (Medium; needs a live check for real-CLI relevance): explicit force can wait forever in `forcing`.** This happens when the provider CLI's child process keeps the CLI's output pipe open. No `force-failed` is reported and no further action is offered. It was reproduced with a controlled fake CLI. The real Codex CLI may contain its commands in a job object, so the live check below decides whether real use can hit it.

One human QA item remains (notice content and wording). There are three live provider checks for the orchestrator.

## Defects

### D-1 (High): Windows terminal Ctrl+C kills in-flight Codex turns during a normal drain

**Steps.** These run on built `main` on Windows.

1. In a terminal window, set `GG_DATA_DIR` to an empty directory, `GG_PORT=6463`, `GG_REQUIRE_API_KEY=false` and `GG_SHUTDOWN_GRACE_MS=300000`. Set `GG_CODEX_BINARY` to the repository's fake Codex CLI (`apps/web/e2e/shutdown-fake-codex.ps1`, compiled) and `SHUTDOWN_FAKE_PID=<dir>\harness.pid`. Then run `node apps/api/dist/main.js` in that window.
2. Create and publish trigger → inference (`harness: codex`) → exit, and start a run. Wait for `harness.pid`: the turn is now in flight.
3. Press Ctrl+C once in the terminal window.

**Expected.** A normal drain starts and the turn keeps running. After the grace, the notice lists it and offers Keep waiting or Force stop. Only an explicit force interrupts it, recorded as `RUN_INTERRUPTED_BY_STOP` (#319 owner feedback; ADR-0049; guide 07 "Gateway is draining"; guide 01 "Press Ctrl+C in the API terminal").

**Actual.** Observed twice (D1, J):

- 19 ms after `shutting down {action: drain}`, the log shows `codex turn failed: Codex Exec exited with code 3221225786`. That code is `0xC000013A`, `STATUS_CONTROL_C_EXIT`.
- The run fails as `HARNESS_DELIVERY_UNCERTAIN` (`resumable: true`, `submission: delivery-uncertain`) and drops out of `activeRunIds`.
- In J (only that turn active), the drain finds nothing to wait for and the gateway exits 0 within 0.5 s, with no grace, no notice and no choice (`s-j-gateway-j1.log.txt`).
- In D1 the expiry notice listed only the script run, and after restart the harness run still showed the provider failure, not an interruption.

**Mechanism.** `GetConsoleProcessList` on the gateway's console lists `shutdown-codex`, `node` (the gateway) and the launcher. The script process has its own console (F1). `@openai/codex-sdk` 0.160.0 spawns the CLI without `windowsHide` (`node_modules/@openai/codex-sdk/dist/index.js:263`), so libuv does not give it a separate hidden console. The CLI therefore receives the terminal's Ctrl+C directly. By contrast, `ProcessScripts` and the Claude CLI runner spawn with `windowsHide: true` and all stdio piped, which gives the child its own hidden console.

A plain probe reproduces the difference outside GraphGoblin (`probe-console-ctrlc.log.txt`): a piped child without `windowsHide` exits with `3221225786` on one Ctrl+C, and a hidden child survives. An API drain does not kill the turn (F2), so the defect is specific to the documented terminal-signal path.

**Scope note.** The #319 browser code is not at fault. The defect is in the drain path the choice relies on (#224 normal drain and `packages/adapter-codex`). Whether the real `codex.exe` also exits on Ctrl+C is live check LP-1. The console delivery itself is operating-system behaviour and does not depend on the CLI.

### D-2 (Medium): explicit force waits indefinitely when the provider CLI's child keeps its output open

**Steps.**

1. Use the same setup as D-1, but run the API normally and set `GG_CODEX_BINARY` to `scripts/tree-codex.cs.txt` compiled with `csc`. This is a fake CLI that starts one "tool" child process before blocking. The child inherits the CLI's inheritable handles, including its stdout pipe.
2. Start an inference run. Drain with `POST /system/shutdown {"action":"drain"}`.
3. In Edge, click **Force stop**, then **Confirm force stop**.

**Expected.** Force ends the provider work and verifies release within the documented five-second acknowledgement. Otherwise it reports `force-failed` with `HARNESS_TERMINATION_UNCONFIRMED` and offers **Force exit** (ADR-0049; docs/05 "Deliberate shutdown").

**Actual** (H; first seen in `attempts/s-g-attempt1-tool-child-hang.log.txt`):

- The CLI is killed at once, but its child keeps running.
- The gateway stays in `forcing` with `choices: []` and the run still listed as active for 84 s, until the child was killed by hand with `taskkill`.
- The notice says "Interrupting active work and checking cleanup…" and offers no action (`s-h-force-pending-notice.png`).
- A further force returns 202 and changes nothing.
- 0.2 s after the child was killed, the force completed (exit 0) and the run recorded `RUN_INTERRUPTED_BY_STOP`.
- Had the operator killed the gateway instead, no interruption would have been recorded.

**Likely cause.** `CodexHarness.run` waits for the SDK event stream to end. The SDK reads the CLI's stdout until EOF, and the surviving child holds that pipe. The force path has no bounded acknowledgement for Codex turns: `cancel()` races 5 s, but the executor still awaits the result. The adapter's comment says the real CLI 0.160.0 runs commands in its own job object, so aborting ends them (verified 2026-10-02). The real CLI may therefore never trigger this, and LP-2 decides that. ADR-0049 lists Codex descendant cleanup as residual risk N10. What N10 does not cover is that force then never concludes and never reports failure.

## Human QA items

**HQ-1: Is the notice's explanation of active work, and its wording around the choice, what the owner wants?** The behaviour is verified. The open question is product judgement on content and wording. #319 requires owner product acceptance, and "explain active work" has no objective threshold.

1. On a build of `main`, start the API on a spare port with a disposable `GG_DATA_DIR`, `GG_REQUIRE_API_KEY=false` and `GG_SHUTDOWN_GRACE_MS=60000`.
2. Create two loops:
   - one with a script node that waits for a file (for example `node -e "setInterval(()=>{if(require('fs').existsSync('C:/temp/release'))process.exit(0)},200)"`);
   - one parent with a subloop pointing at it.
3. Start one run of each. Open `/app/loops` and the parent's inspector in two tabs.
4. Run `Invoke-RestMethod -Method Post -Uri http://127.0.0.1:<port>/system/shutdown -ContentType application/json -Body '{"action":"drain"}'`.
5. Read the draining notice. Within 10 s it should say starts are refused, active work is finishing, and waits and paused runs and queued work stay recoverable. It should list each active run as "<loop name> — <run id>" and already offer **Keep waiting** and **Force stop**.
6. Wait 60 s. The notice should add "The gateway grace period elapsed. Keep waiting without a hidden kill timer, or deliberately interrupt the active work."
7. Click **Force stop** and read the confirmation: run links, required children, uncertain external effects, no automatic resume. Click **Go back**.
8. Click **Keep waiting**. The notice should return to draining with no countdown.
9. Click **Force stop**, then **Confirm force stop**. The notice should show "Gateway is force stopping", then "Gateway stopped or disconnected".
10. Restart the API on the same store and open an interrupted run. The inspector should show "Failed: RUN_INTERRUPTED_BY_STOP — Explicit force-stop interrupted this run; external effects may have happened", with no Resume or Replay control.

Decide:

- (a) whether loop name, run ID and link are enough to "explain active work", or whether the current node or elapsed time should be shown;
- (b) whether offering Keep waiting before the grace (which suppresses the later prompt) is intended (O-3);
- (c) whether the forcing text (O-2) and the "changed in another tab or control" message after a grace expiry (O-1) are acceptable;
- (d) whether interrupted runs should offer a browser Replay instead of the API or MCP route (O-4).
