  489  Before calling the process runner the script handler appends `script.dispatched { nodeId, visitId, dispatchId }` durably. `visitId` is `<runId>:<first node.started sequence since that node last finished>`; retries retain the visit and allocate a new dispatch ID. The runner distinguishes `definitely-not-started` (synchronous refusal, missing command or an already-aborted request), `outcome-uncertain` (a dispatched process whose disposition is unknown), and `completed` (observed process termination). A proven refusal fails with resumable `SCRIPT_START_FAILED`; ordinary explicit Resume tries it again. A completed nonzero exit retains `SCRIPT_EXIT_CODE`; timeouts retain `SCRIPT_TIMEOUT`.
  490  
  491  Script failures after dispatch carry `failure.script = { visitId, dispatchId, state, exitCode? }`; the dispatch ID is absent when no durable dispatch identity exists, including an interrupted pre-change visit. A `run.failed` disposes a pending dispatch only if its script provenance matches the node, visit and dispatch. If progress or completion persistence fails after dispatch, the failure recorder preserves `SCRIPT_OUTCOME_UNCERTAIN` and that provenance instead of replacing it with a generic bookkeeping error. A known typed completed/start-failed disposition retains its class. A parent subloop failure preserves its child's typed script provenance and identifies the child run, so nested recovery exposes the same dispatch evidence. Forced stop, run deadline and unconfirmed process termination retain their non-resumable failure causes alongside the uncertain script provenance. Only explicit script-consent recovery leaves an uncertain failed run; its observed Resume knowingly retries the same visit with a new dispatch. Plain Resume refuses with `SCRIPT_CONSENT_REQUIRED`. A crash during that new dispatch is uncertain again. A crash after process exit but before recording a disposition is also uncertain. The inspector explains that the previous attempt may already have produced its effect: **Recover script** offers **Resume**, **Replay** from the failed node, and **Cancel** (leave the run failed without running anything). API and MCP return the same failure and provenance; MCP must obtain the user's explicit retry choice. No exactly-once external-effect guarantee is made; Resume or Replay may repeat an effect.
