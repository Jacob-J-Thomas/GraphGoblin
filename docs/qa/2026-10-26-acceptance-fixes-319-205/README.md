## Task 1: #319 D-1, terminal Ctrl+C on Windows

**Cause.** `@openai/codex-sdk` 0.160.0 starts the Codex CLI with `spawn(path, args, { env, signal })` and no `windowsHide`. libuv then lets the child inherit the gateway's console, so a Ctrl+C typed in the gateway's terminal is delivered to the CLI as well, and it exits with `STATUS_CONTROL_C_EXIT` (`0xC000013A`). The script runner, the Claude runner and Codex preflight already spawn with `windowsHide: true` and piped stdio, which makes libuv start them with `CREATE_NO_WINDOW`: each gets its own hidden console.

**Mechanism probe** ([console-probe.log.txt](console-probe.log.txt), [scripts/console-probe.mjs](scripts/console-probe.mjs)): a Node process attached to a console starts one hidden piped child and one piped child without `windowsHide`; one real `CTRL_C_EVENT` to that console. The parent handles SIGINT, the plain child exits `3221225786`, the hidden child keeps running.

**SDK finding: patch, not upgrade** ([sdk-releases.log.txt](sdk-releases.log.txt)). Every stable release after the pin (0.160.1, 0.161.0, 0.162.0, 0.162.1, 0.163.0, 0.164.0, the current `latest`) spawns the CLI exactly as 0.160.0 does, with no `windowsHide`. The fix is therefore a pnpm patch: `pnpm patch @openai/codex-sdk@0.160.0`, one added line `windowsHide: true` in `dist/index.js`, `pnpm patch-commit`. pnpm recorded it as `patchedDependencies` in `pnpm-workspace.yaml` and `patches/@openai__codex-sdk@0.160.0.patch`; the lockfile carries the patch hash. Nothing else in the SDK changes. The pinned CLI (0.160.0) is unchanged.

**Native reproduction of acceptance scenario J** ([scripts/j-ctrlc-codex-turn.mjs](scripts/j-ctrlc-codex-turn.mjs); helpers [scripts/console-tool.cs.txt](scripts/console-tool.cs.txt) and [scripts/fake-codex.cs.txt](scripts/fake-codex.cs.txt), compiled with Windows PowerShell's `Add-Type`). The built gateway runs attached to a console of its own, as in a terminal window, with one controlled fake Codex turn in flight; one real Ctrl+C is delivered to that console.

- Before ([j-before.log.txt](j-before.log.txt)): 0.5 s after the Ctrl+C the gateway had already exited 0 and the CLI was gone. The log shows `codex turn failed: Codex Exec exited with code 3221225786`, and after restart the run is `failed` / `HARNESS_DELIVERY_UNCERTAIN` (resumable). This matches acceptance J.
- After ([j-after.log.txt](j-after.log.txt)): for 3 s after the Ctrl+C the phase is `draining`, the run is `running` and listed in `activeRunIds`, and the CLI is alive. Releasing the fake turn lets it finish; the gateway exits 0 and the run is `succeeded` after restart.

**Regression test** (`apps/api/src/shutdown-console.test.ts`, Windows only). It compiles the same two helpers, starts the built gateway attached to its own console through `createApiProcessFixture`'s environment and ports, and delivers a real `CTRL_C_EVENT`:

- `one terminal Ctrl+C drains while a running Codex turn keeps running, then completes when it finishes`
- `a later terminal Ctrl+C explicitly forces the running Codex turn` (exit 0, CLI gone, `RUN_INTERRUPTED_BY_STOP` after restart)

Both fail with the unpatched SDK, `Error: The gateway exited with code 0 after one Ctrl+C instead of draining` ([tests-console-ctrlc-before.log.txt](tests-console-ctrlc-before.log.txt), produced by restoring the unpatched `dist/index.js` in `node_modules` for the run), and pass with it ([tests-console-after.log.txt](tests-console-after.log.txt)).

## Task 2: #319 D-2, force waiting in `forcing`

**Cause.** `CodexHarness.run` iterated the SDK's event stream until it ended. The SDK reads the CLI's stdout until EOF, so a process the CLI started that inherited the pipe keeps the stream open after the abort kills the CLI. The executor awaited the turn, and force never reached `force-failed`.

**Fix** (`packages/adapter-codex/src/harness.ts`). An abort arms the acknowledgement bound `cancelGraceMs` (five seconds, the harness bound ADR-0049 already names). Both the SDK call and every stream step race that bound; if it expires, the turn fails `HARNESS_TERMINATION_UNCONFIRMED` (non-retriable, submission `delivery-uncertain`) and the stream is closed without being awaited. `cancel()` now waits for the result and rethrows only unconfirmed termination, as the Claude harness does. The engine already treats that code as a cleanup failure: with `interruptedByStop: true` it holds force in `force-failed` with the run in `unconfirmedRunIds` and offers Force exit.

**Descendants.** The SDK keeps the CLI's process private and the patch may only add `windowsHide`, so GraphGoblin cannot end a process the CLI started without reaching into the SDK. ADR-0049 N10 now says exactly that, including that such a process survives Force exit (it is outside Node's kill-on-close job). Live check LP-2 decides whether the real CLI can leave one.

**Regression tests**, all failing before the fix:

- `packages/adapter-codex/src/termination.test.ts`: `reports unconfirmed termination within the acknowledgement when a CLI descendant keeps its output open after abort`. A real fake CLI ([`fixtures/tree-cli.mjs`](../../../packages/adapter-codex/src/fixtures/tree-cli.mjs)) starts a detached tool process that inherits its stdout (the shape of acceptance `tree-codex.cs.txt`); the client follows the SDK's `CodexExec.run` contract over the real process. Before: `expected 'still waiting for the CLI output' to match object` after 10 s. After: unconfirmed termination in about 0.5 s, the CLI killed and the tool still alive. A companion case confirms that cancellation still succeeds when only the CLI held the output.
- `packages/adapter-codex/src/harness.test.ts` (cancellation): `cancel() reports unconfirmed termination when the turn does not end within the grace period` replaces the test that encoded the old silent give-up (before: `promise resolved "undefined" instead of rejecting`); `stops waiting for an event stream that outlives an abort, even one it cannot close` (before: timed out); `cancel() after a completed turn has nothing to stop`. Output: [tests-d2-adapter-before.log.txt](tests-d2-adapter-before.log.txt).
- `apps/api/src/shutdown-controller.test.ts`: `force over a Codex turn whose CLI output outlives the kill fails cleanup instead of waiting in forcing`, through `ShutdownController`, `RunManager` and a real `CodexHarness`. Before: `expected 'forcing' to be 'force-failed'` ([tests-d2-api-controller-before.log.txt](tests-d2-api-controller-before.log.txt)).
- `apps/api/src/shutdown-console.test.ts`: `force over a Codex CLI whose tool process keeps its output open fails cleanup and offers Force exit`, the native acceptance scenario H with the real SDK, the built gateway and a compiled fake CLI that starts a tool child (`SHUTDOWN_FAKE_TOOL_CHILD=1`). After the fix: `force-failed`, `unconfirmedRunIds: [run]`, `HARNESS_TERMINATION_UNCONFIRMED` with `interruptedByStop: true`, the CLI gone and the tool alive, Force exit with code 1 and the lock kept, the failure preserved after restart. Before (adapter dist rebuilt from the original harness): force did not conclude within 30 s ([tests-console-force-before.log.txt](tests-console-force-before.log.txt); this run predates the test's clearer timeout message).

## Task 3: #319, a process that already exited

**Reproduction first** ([scripts/exited-root-kill.mjs](scripts/exited-root-kill.mjs), helper [scripts/hold-process.cs.txt](scripts/hold-process.cs.txt)). A child exits on its own and Node observes the exit; then the built `killTree` runs on it. A helper holds an open handle to the exited process for the whole check, so Windows cannot reuse its PID and the taskkill can only find it gone. Before ([o1-before.log.txt](o1-before.log.txt)): `taskkill /T /F` on that PID exits 128 ("The process ... not found") and `killTree` resolves `false`, which the script and Claude runners report as unconfirmed termination. Group A's O1 holds. After ([o1-after.log.txt](o1-after.log.txt)): `killTree` resolves `true` without running taskkill.

**Fix** (`packages/infrastructure/src/process/scripts.ts`, used by the Claude runner too). On Windows a root whose exit Node has already seen is not signalled at all: Node has closed its handle, so its PID may already belong to another process. For a taskkill exit of 128 the root is no longer running; it counts as released once Node reports its exit. Any other taskkill failure, a launch failure, or a missing exit stays unconfirmed. The callers are unchanged: they still require the root's output to close within five seconds, so a descendant that inherited it still yields unconfirmed termination.

**Regression tests.** `packages/infrastructure/src/process/scripts.test.ts`: `does not signal the PID of a Windows root whose exit was already observed` and `counts taskkill not finding the root as released once the root is seen to have exited` fail before (timeout, `expected false to be true`; [tests-o1-killtree-before.log.txt](tests-o1-killtree-before.log.txt)); `reports any other taskkill failure as unconfirmed` passes before and after. Native Windows cases through the public runners: `releases a cancelled script whose root already exited once the last holder of its output closes` (`ProcessScripts`) and `counts a turn process that exited before its cancellation as stopped once its output closes` (`runClaudeProcess`), plus `reports a real Windows root that exited before the kill as released`. The native cases were run only after the fix: before it they would have run `taskkill /T /F` on a PID Windows may already have reused, which could end an unrelated process tree. The held-handle reproduction above is the safe before evidence for that path.

## Task 4: #205 D1, Codex max

**Question.** Does the Codex CLI the product runs (0.160.0, pinned by the SDK) accept `model_reasoning_effort="max"`?

**Evidence, no provider call:**

- Configuration parsing does not decide it. `codex exec` with the SDK's arguments and an isolated, empty `CODEX_HOME`, no API key and every proxy pointed at the closed local port 9 gets past configuration and starts the turn for `max` and for an invalid value alike; the CLI does not validate the effort.
- What the CLI sends ([codex-effort-probe.log.txt](codex-effort-probe.log.txt), [scripts/codex-effort-probe.mjs](scripts/codex-effort-probe.mjs)). The same run with `openai_base_url` pointed at a local capture server on 127.0.0.1:6501, which records each request and answers 400. For `gpt-6-luna` the request carries `"reasoning":{"effort":"max"}` for `max`, `"xhigh"` for `xhigh`, `"minimal"` for `minimal` and even `"bogus"` for `bogus`; `gpt-6.1-sol` and `gpt-5.5` with `max` carry `max`. The CLI passes the value through unchanged.
- Which models the CLI itself supports ([codex-model-catalog.log.txt](codex-model-catalog.log.txt), [scripts/codex-model-catalog.mjs](scripts/codex-model-catalog.mjs), read from the binary without running it). The model catalog compiled into CLI 0.160.0 lists `low`, `medium`, `high`, `xhigh`, `max` for every GPT-6 and GPT-5.6 model GraphGoblin seeds (and `ultra` for most), but only `low` to `xhigh` for `gpt-5.5`.

**Branch taken: send `max` unchanged.** `mapEffort` is removed (and its export with it) and the thread option carries the requested effort, so the session row, the run record and the CLI argument agree. Because the CLI's catalog does not list `max` for GPT-5.5, the seeded GPT-5.5 entry now offers `minimal` to `xhigh`: the editor no longer offers `max` there, and a saved GPT-5.5 `max` (node, LLM decision, Settings default) is refused with `EFFORT_UNSUPPORTED` before any request, as Claude refuses `minimal`. The upgrade note in the CHANGELOG covers stored GPT-5.5 `max` values.

**Regression tests**, all failing before the fix:

- Adapter, the argv the fake CLI receives: `packages/adapter-codex/src/effort.test.ts` runs the real SDK with `codexBinary` set to Node and the fake CLI [`fixtures/argv-cli.mjs`](../../../packages/adapter-codex/src/fixtures/argv-cli.mjs) preloaded (`NODE_OPTIONS=--import`), once per canonical effort. Before: `expected [ 'model_reasoning_effort="xhigh"' ] to deeply equal [ 'model_reasoning_effort="max"' ]` ([tests-d1-adapter-argv-before.log.txt](tests-d1-adapter-argv-before.log.txt)). The `harness.test.ts` case that encoded the mapping now expects `max`.
- API: `apps/api/src/catalog.test.ts`, `Codex efforts are sent unchanged and offered per model (#205)`: GPT-5.5 lists no `max`; an inference node and an LLM decision with GPT-5.5 `max` are refused 400 `EFFORT_UNSUPPORTED`, as is the Settings default; GPT-6 Luna `max` reaches the harness and the decider as `max`. Before: three failures ([tests-d1-api-catalog-before.log.txt](tests-d1-api-catalog-before.log.txt)). `packages/infrastructure/src/sqlite/storage.test.ts` now expects the GPT-5.5 seed without `max`.
- Editor: `apps/web/e2e/model-effort.spec.ts`, `Codex effort choices follow the model: max is offered and requested unchanged, but not for GPT-5.5`: GPT-6 Luna offers `max`; switching to GPT-5.5 shows the kept `max` as `max (not supported by this model)` and offers `minimal` to `xhigh`; back on Luna, `max` survives publish and reload and the harness request carries `max`. Before: `Expected: "max (not supported by this model)" Received: "max"` ([tests-d1-editor-before.log.txt](tests-d1-editor-before.log.txt)).

**Observation for a product decision (not changed).** GraphGoblin's Codex catalog offers `minimal` for every Codex model, but the CLI's catalog lists `low` as the lowest level for all of them. The CLI sends `minimal` unchanged, so the record stays truthful; whether the provider accepts it is a live question (LP-5).
