## Readback and cleanup

An attempt retains request bodies and raw REST response text, the raw MCP stdio transcript and structured output, published IDs, durable SQLite rows and events, exact patches, private gateway logs, browser network and DOM evidence, screenshots, and the first failure with case and stage. The binding captures the served file identities separately from browser observations. Baseline records can contain the observed installation path and stack. Treat that raw baseline packet as external QA evidence.

The browser closes through its owned context and checks the exact disposable profile and previously observed process identities. The MCP process exits on stdio EOF. Each gateway drains through its own verified PID and instance with no active runs, then the driver checks its port is closed. Cleanup may forcibly stop only a directly owned gateway or MCP child if managed stop fails and records that as incomplete. A process or listener cleanup error leaves the disposable resources identified for follow-up.

After clean shutdown, the supervisor verifies every parent read-only SQLite client closed, yields between two explicit GC passes, and checks exclusive read handles for each present DB, WAL and SHM in both disposable gateway stores. A single Windows helper holds all of those handles at once and reports their identities and any sharing error. Missing sidecars are recorded. This follows the [#361 exclusive-handle continuation](../runtime-361-native/cleanup-continuation.ps1) and the repository's docs/research/sqlite-libsql.md. A failed confirmation retains the directory. Verified cleanup then checks the resolved owned directory, removes it once, verifies absence, and rereads the build/source binding. Retain the first numbered attempt before any explicitly admitted follow-up.
