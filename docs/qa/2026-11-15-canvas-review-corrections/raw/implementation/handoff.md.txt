## Production changes and rationale

### F1: the shared removal boundary needs exactly one holder

- **`model.ts`:** new pure `onlyEdge(definition, id)`, moved from `stranded-edges.ts`, which now imports it. Stranded recovery behaves as before.
- **`store.ts`:** new exported `edgeRemovalRefusal(definition, system, edgeId)`.
  - It checks for more than one holder **first** and returns `More than one connection uses the ID "<id>"; this action cannot choose just one.`
  - Only then does it check the single holder for voice protection (`VOICE_STEP_MESSAGE`).
  - Otherwise it returns `undefined`. An absent ID is also `undefined`.
- **`removeEdge`:**
  - On a refusal it sets only `connectionError`. Definition, decisionRoutes, past/future, revision, saveState and token stay identical.
  - Otherwise it removes exactly the `onlyEdge` record (`e !== edge`), with the same label and one step.
  - An absent ID is silent.
- **`OrthogonalEdge.tsx`:** the selector returns the same refusal string. The button uses `disabled={!!refusal}` and `title={refusal}`, and `removeSettling = refusal ? undefined : settling`, so the stronger reason beats the gesture state.

### F2: the selection belongs to its draft and drawn connection (`Canvas.tsx`)

- **What a selection holds:** `EdgeSelection = { generation, id, ends }`. `ends` is a JSON tuple list, `[from.node, from.port, to.node, to.port ?? 'in']`, over every holder in stored order. It is Canvas-local and does not rely on renderer object identity.
- **Two separate checks:**
  - *Stored identity:* same generation and same `ends`.
  - *Drawability:* `drawsAll`, which is `canvasDrawsEdge` for every holder. That matches xyflow's EdgeWrapper (both nodes and both handles).
- **Capture:** `onEdgesChange` reads `useEditorStore.getState()` before any `remove` change in the batch. An ID with no stored holder selects nothing. A repeated `select` of the same ID with an equal generation and ends keeps the same selection object; xyflow re-emits `select` under its multi-selection key.
- **Render cleanup:** `selectedEdge` is memoised on `[selection, definition, generation]`, so the port parse is skipped on drag frames. A selection that is not live is cleared during render. Undo cannot bring it back.
- **Action-time guard:** `mayAct(current, expected, edgeId)` reads `selectionRef`, which is synced in a layout effect like `planRef`, and the store's current draft. It is used by:
  - `remove` and `reset`;
  - the shared `store()` path behind nudge and the drag commit;
  - the keyboard.
- **Route drags:** `begin` binds `selectionRef.current`. A pointer move after the binding stops being current ends the drag without a write. The commit requires the bound object, not just an equal ID, so a same-ID reselect before release cannot write.
- **Stale path (`refuseStale`):** no edit, the selection is cleared, the polite live region says "That connection changed since it was selected; nothing changed.", and focus moves to Undo via `removalFocusTarget()`. Undo is `aria-disabled`, never `disabled`, so it stays focusable with an empty history.
- **Refusals keep the selection:** a refused live removal (duplicate or voice) keeps it, on the toolbar and on the keyboard. This is root-accepted choice (b).
- **Interface:** the `RouteEditing` interface and context value are unchanged. `editing` is not recreated when the selection changes.
- **Bug found by T8 and fixed:** the Reset route `onClick` used to call `editing.reset()` and *then* focus the edge. On the stale path that moved focus back into the canvas, so Delete could reach the selected node. It now focuses the edge first and then resets. On the live path the outcome is identical: the store write renders after the handler.

### F3: a card drag arms the gate (`Canvas.tsx`, typed `OnNodeDrag<FlowNode>`)

- `onNodeDragStart` calls `gesture.move(event)` before its existing `closeCanvasPopovers()`, `closeStep()` and `setNodeDrag(...)`. Those three are unchanged.
- Installed XYDrag starts a drag on the `mousemove` whose distance from the press, in client px, exceeds `nodeDragThreshold`. Canvas sets that to `CLICK_DISTANCE` (3), the same value it passes as d3-drag's `clickDistance`. d3-drag sets `mousemoving` on `dx²+dy² > 9` on that same event, so the gate is armed exactly for drags whose release adds `click.drag`.
- Touch, keyboard and `{}` events are ignored by the existing type check.
- **Unchanged:** the one mount-time listener, the two-task barrier and the `ViewportGestureGate` interface (kept for the later Space cards). There is no replay, patch, pointerdown replacement, delay or new framework.
- **"Rendered state and action-time guard":** the button's `aria-disabled`/`data-gesture` and the handlers' refusal both read the same rendered gate snapshot, so they agree for card drags exactly as for pans.
- I deliberately did not add a hidden *live* gate check inside `editing.remove`. A click that reaches React was not cancelled by d3, and a silent live refusal would recreate the "looks available but does nothing" defect.

## Source limitations and unresolved items

1. **`decisionRouteEdges` is keyed by edge ID (pre-existing; not changed).** With a Decision-owned duplicate ID, any successful edit that goes through `edit()` re-ports the *other* holder to the row's port. Observed: removing the unrelated `c1` turned `start→via e1` into port `yes`. The refusal itself is exact, and T1 asserts identical decisionRoutes. Fixing this would broaden store routing semantics and is out of scope.
2. **Ambiguous route editing is unchanged.** `setEdgeRoute` writes every holder of a duplicate ID. A live duplicate selection can still Reset, nudge or drag a route, and that affects both holders (geometry only, undoable). The new guard checks only selection identity and liveness.
3. **Duplicate IDs in xyflow and the harness.** xyflow keys wrappers by ID and resolves them to the last holder (stacked toolbars, per scan-1). The stand-in edge layer, keyed the same way, kept a stale toolbar after reselection, so tests use `getAllByRole` and scope queries. Routing `routes` is a `Map` by ID.
4. **Public Chat admission.** The protected-holder order tests are local store and toolbar guard tests. Public Chat admission of duplicate IDs is not established here.
5. **Unchanged edge priority.** A live, drawable selected edge still takes Delete before a node opened from Loop issues. No new rule was added.
6. **Focus fallback.** Without an Undo control (a bare canvas), the stale path focuses the canvas root, which is the existing `removalFocusTarget` fallback. EditorPage always renders an `aria-disabled` Undo.
7. **Stale clearing is literal.** In the "same ID reselected before release" case the deliberate second selection is also cleared, as the brief says.
8. **F3 threshold equivalence.** It relies on `CLICK_DISTANCE` being used for both `nodeClickDistance` and `nodeDragThreshold`, and on both libraries measuring client px from the press. It is pinned at the integer boundary only; fractional-pixel rounding at exactly 3 px is untested. Any mouse drag start arms the gate, including non-Control drags, where the toolbar is gone anyway.
9. **Existing tests not modified, but now weaker or trivial.**
   - "deletes the selection with Delete or Backspace…": its edge step was already trivial at HEAD, because `e1` is removed along with `prep`.
   - "keeps the replacement edge selected…": it uses `e11`, which `kitchenSinkLoop` does not hold, so its first `select` now captures no selection. It still passes.
10. **Not done here:** jsdom evidence is not native. Corrected-head native QA (F1/F2/F3), CI, coverage gates, the build, the independent correction review and root freeze/integration are all still open. With duplicate IDs there is still no single-edge removal in the UI; the message says the action cannot choose one.
