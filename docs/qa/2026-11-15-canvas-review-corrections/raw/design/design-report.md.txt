## F1: one shared removal guard

**The store refuses unless exactly one stored edge holds the ID** (`store.ts`):
- Export `edgeRemovalRefusal(definition, system, edgeId): string | undefined`.
  - It checks for duplicates first: if more than one record holds the ID, it returns the duplicate-ID message.
  - Only then does it check voice protection, on the one record.
  - Checking duplicates first means a protected holder is refused the same way whichever order the two records are in.
- `removeEdge`:
  - On a refusal, set `connectionError` and return.
  - Otherwise find the one record with `onlyEdge` and remove that exact record (`d.edges.filter((e) => e !== edge)`).
  - Keep the label `remove edge …`, one step and the `void` signature. Absent IDs still return silently, as now.
- Move `onlyEdge` from `stranded-edges.ts` into `model.ts` next to `canvasDrawsEdge`. `stranded-edges.ts` imports it and behaves as before.
- No schema, draft-admission, migration or compatibility change.

**The toolbar shows the same refusal** (`OrthogonalEdge.tsx`):
- `removalBlocked` becomes a selector that returns `edgeRemovalRefusal(...)` as a string.
- The button uses `disabled={!!refusal}` and `title={refusal}`, with `removeSettling = refusal ? undefined : settling`. A duplicate ID therefore beats the pan gate, as the voice reason already does.
- Reset route is unchanged.

**Message** (one shared string; final wording is copy): `More than one connection uses the id "e1"; removing it here would remove them all.` It mirrors the existing node-rename refusal. The keyboard path shows it as "Connection refused: …".

**What the user sees:**
- A duplicate ID can still be selected. Installed xyflow puts every holder's ID in `edgeIds`, and each wrapper resolves to the last holder, so there may be stacked toolbars.
- Every Remove is disabled with the reason.
- Delete or Backspace refuses with the page notice. It does not fall through to a selected node, and the selection stays.

## F2: selection tied to the loaded draft and to a drawable connection

**Model** (Canvas-local, no general selection framework):
- `type EdgeSelection = { generation; id; holders }`, where `holders` is a key built from the stored ends of every record holding the ID, in stored order: `[from.node, from.port, to.node, to.port ?? 'in']`.
- It is captured in `onEdgesChange` from `useEditorStore.getState()` before any remove in that batch is applied.
- **Stored identity** is the generation plus the ID plus the ends. **Renderability** is a separate check: `canvasDrawsEdge` holds for every holder, the same test the stranded-edge list uses.
- It never depends on xyflow edge objects or stored-record object identity.

**Cleanup at render:**
- Canvas reads `generation` from the store.
- `liveSelectedId` is memoised on `[selection, generation, definition]`. That keeps the Zod port parse out of drag frames.
- If a selection is held but is not live, it is cleared during render, using the pattern at lines 481–482.
- `buildEdges` receives `liveSelectedId`.
- This clears the selection on:
  - any load: Reload server draft, device restore, server reconcile, set-aside restore;
  - an ID whose ends change: a preset reusing a freed ID via `nextEdgeId`, rewired successors, a whole-draft voice or audio replacement;
  - a port that disappears: a Script label removed, a Decision route ID left blank.
- It keeps the selection through moves, route edits, label and config edits that keep the ports, issue refreshes, and Undo/Redo of those.
- Undo does not bring a cleared selection back.

**Refusal at the moment of action** covers render lag and act-batched updates:
- One check, `liveSelected(edgeId?)`, reads `selectionRef` (synced in a layout effect, like `planRef`) and `useEditorStore.getState()`.
- It is used by `editing.remove`, by `editing.reset`, and by the shared `store()` path behind drag commit and nudge, so a load in the middle of a drag cannot write a route.
- A stale toolbar or route action: no change, selection cleared, a polite announcement ("That connection changed since it was selected; nothing changed."), focus to `removalFocusTarget()`. That target is Undo, outside the canvas, so a repeated Delete cannot hit a selected node.
- **Keyboard**, when an edge selection exists:
  - Call `preventDefault`.
  - If the selection is stale, clear it, announce, and stop. It does not fall through to the node in the same key press.
  - If live, call `removeEdge`. Clear the selection only if the definition actually changed; a store refusal keeps it, matching the toolbar.
- Node removal and Enter on a node are unchanged.
- The `RouteEditing` interface is unchanged, so the context value is not recreated when the selection changes.

**Two behaviour choices for GPT to accept or reject:**
- **(a) A node rename or Decision route-ID rename clears the edge selection, because the ends changed.** Keying on ends is what catches the same-step ID reuse by presets. Following renames would need history plumbing. The cost is benign: these edits happen in the dialog and nothing is deleted.
- **(b) A refused keyboard removal now keeps the selection.** Today it is cleared, so a second Delete removes a selected node.

**Pan gate and later #208:** `viewport-gesture.ts`, its attach and move calls, `editing.viewport`, the gate's first-input timing and `inert` are all untouched. #208's Space cards need no gate change. Expect rebase conflicts in these Canvas.tsx regions: `onEdgesChange`, `editing`, `onKeyDown`, and `onNodeDragStart` if the change below lands.

## Node-drag overlap: only if the probe shows a blocked click

The overlap is still unproven. Make this change only if the CDP probe sees a separate trusted click on an enabled Remove cancelled by the active `click.drag` capture listener.

- **Change:** in `Canvas.onNodeDragStart`, add `gesture.move(event)`.
  - With `nodeDragThreshold = 3`, XYDrag's `startDrag` passes the drag's native `mousemove` (system 2265/2308).
  - That matches d3-drag's `clickDistance(3)`, which arms `yesdrag`.
  - Touch is ignored by the existing type check.
- The gate's mount-time release listener comes before d3-drag's per-press `mouseup.drag`, so the same two-task barrier applies. No new prop, listener patch, replay or timer.
- **Docs:** docs/09's sentence "after a node drag … not gated", ADR-0076 "a mouse pan's first move", guide 02 line 129.
- If the probe passes or is inconclusive: no change, and the existing docs/09 disclosure stands.

## Risks

- **Ambiguous route edits:** `setEdgeRoute` still writes every holder of an ambiguous ID. That predates this PR, is geometry only and is undoable. I left it out of F1. If wanted: add a uniqueness guard and announce only when something changed.
- **Duplicate React keys:** these come from xyflow (console noise and stacked toolbars); tests must use `getAllByRole`.
- **Static test harnesses:** `renderCanvas` passes a fixed definition while the store moves on. The selection is captured from the store but rendered from the prop; the existing kitchen-sink tests should still pass, but check them.
- **Disabled button with a title:** keyboard and screen-reader users cannot reach the reason on the button. That matches the existing voice-step pattern; the keyboard path shows the reason in the page notice.
- **Pre-existing, out of scope:** `decisionRouteEdges` removes edges by ID for every holder.
