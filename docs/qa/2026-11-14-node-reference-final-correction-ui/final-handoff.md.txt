## 2. Diagnosis of the two batch-1 failures (`ui-273-final-correction/logs/08-batch1-second-run.log`)

1. **Source typing put `/x` before the last character** (`/counters/nodeVisits/draf/xt`). This is a test artifact; the production code is not wrong.
   - user-event's `mousedown` sets the caret (`startSelecting`, at the end of the *old* 25-character value) *before* it moves focus (`focusElement`).
   - The focus move blurs Node id, which renames and repairs the value in place to 26 characters. user-event's tracked caret stays at 25.
   - A browser instead moves focus first and then places the caret at the pointer.
   - The batch-0 test only saw an end-of-input caret because the remount created a new input.
   - Correction (test only): `await user.keyboard('{End}/x')`, with a comment. The repaired-source and no-stale-overwrite assertion is kept exactly (`source: '/counters/nodeVisits/draft/x'`). Production does not move the caret.
2. **The pointer-press release loop.** I isolated each ending event with a temporary diagnostic, which is preserved and then deleted (`logs/02-…`, `logs/03-…attempt2.log`, `03-….test.tsx.txt`). Observed results:
   - `pointercancel` `true->false`, `mouseup` `true->false`, `dragend` `true->false`, `window blur` **`true->true`**.
   - Cause (inferred): `onWindowBlur` compared `event.target === window`. In vitest-jsdom the global `window` is not the jsdom window object that becomes `event.target`.
   - Fix: `event.target === event.currentTarget`. This is correct in both environments, because the listener is non-capture and `blur` does not bubble.
   - Separately, per the root note, batch 1 released the hold at `pointerup` capture, *before* `mouseup`/`click`. That gesture boundary was corrected (section 3).

## 3. Correction batch 2: the gesture boundary (`apps/web/src/editor/pointer-press.ts`)

The canonical rename and repair stay synchronous and atomic: one store write and one undo step. They are applied in place by `SchemaFormHandle.applyRepair` before anything renders. That batch-1 mechanism is unchanged; `SchemaForm.tsx`, `NodeEditorDialog.tsx` and `store.ts` are byte-identical to the checkpoint. Only the cosmetic notice hold changed.

- **Press starts:** primary `pointerdown` or `mousedown`, seen by a window capture listener. Touch's compatibility `mousedown` also counts.
- **Release:** primary `pointerup` or `mouseup` (capture) does **not** end the press. It records that a release happened and arms a fallback for the next task (`setTimeout(…, 0)`).
- **Click after a release:** heard by a window **bubble** listener, so after every handler of that click, including React's root handler. The click ends the press and clears the fallback.
  - This covers a release on the button and a release elsewhere, where the click goes to the common ancestor.
  - A click without a prior release (a keyboard click) neither holds nor ends a press.
- **No click follows, or the click is stopped before the window:** the press ends at the fallback task. This is the "may settle after native click dispatch" allowance, and only the notice's display waits. No click is synthesized, replayed, delayed, prevented or intercepted. Listeners only observe, never `preventDefault`/`stopPropagation`.
- **Ends at once:** `pointercancel`, `dragend`, and the window's own `blur`, since no click follows them.
- **Scope:** the only consumer is `RenameNotice` (`useHeldDuringPress`). There is no generic pointer framework. Listeners exist only while a subscriber exists; the last unsubscribe also clears the fallback and the state.
- **Design assumption, not proven here:** the engine dispatches the click in the same task as its `mouseup`. For a touch tap, the compatibility `mousedown`/`mouseup`/`click` come together in a later task and re-arm the press. jsdom cannot prove geometry, hit-testing or engine task ordering, so this needs native verification.

## 7. Known boundaries (reported, not widened)

- **Remount fallback loses the click.** In-place repair applies only when the open form shows exactly the stored config (ignoring cleared-field markers) and the repair changed nothing but strings, in the variant shown. Otherwise the form remounts as before (`formEpoch` key), and a press on a control of that form loses its click. This is documented in docs/09, and the existing test covers the remount.
- **Page-level notice mounts at once.** `EditorPage` mounts its page-level `RenameNotice` conditionally (`hasRenameNotice(renameReport)`), so a rename during a press mounts it immediately with the new report. It sits on the page, which is inert behind the node dialog. The node dialog is a native `showModal()` top-layer dialog, so it cannot move dialog content. Not changed.
- **Stale e2e wording.** The promoted e2e case `apps/web/e2e/rename-references.spec.ts` still says "remounted form" in its title and comments (lines 6, 597, 680). Its assertions are focus- and value-based and should hold on the in-place path. I did not rename the promoted case, because its name is referenced by retained evidence. It was not run (browser runs are not authorized).
- **Caret is the browser's.** After an in-place repair of the focused field, production code does not position the caret.
