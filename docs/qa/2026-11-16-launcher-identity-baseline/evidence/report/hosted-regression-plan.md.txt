# #435 hosted Windows regression design

The existing Windows CI job builds the checked-out source and runs `tooling/scripts/windows-launcher.acceptance.mjs`. Extend that suite with two independent Windows subtests, one for a junction and one for a true directory symlink. The current native compile, execution, listener, health and file APIs cover most of the test. Captured CI stdout is the evidence to retain.

1. Allocate an alias root in a disposable Windows temporary directory outside the physical checkout. Creating a reparse point inside the checkout and pointing it back at the checkout can create an archive traversal cycle. Create the exact alias with `fs.symlink(target, alias, 'junction')` or `'dir'`, use a bounded native PowerShell provider query to read `LinkType` plus Directory and ReparsePoint attributes, and compare real paths of the target and compiled helper. Use a progress-silent query while retaining raw failures. A Windows capability refusal records the actual code, syscall, alias absence and stage in the CI log and fails that subtest. Give the other alias subtest its own opportunity to execute.
2. Read the built identity helper through the canonical and actual aliased argv with equivalent settings and store. Capture both alias helper calls and the real aliased cold launcher outcome before enforcing success. This establishes whether old source exited silently and refused the actual cold attempt. Preserve the aliased argv/config path, exit and stream lengths/content for these small controlled outputs. Validate exact one-digest and `--store-state` records when execution reaches product-ready results. Reuse a single port per cold scenario for equivalent config and warm/negative controls.
3. On the fixed source, cold-start each spelling against its own isolated store. The other spelling must reuse that exact gateway on the same port and store, as must same-spelling warm. Capture actual gateway PID, Windows creation identity, expected serving fingerprint, and stable byte digests of both leases. For each cold gateway apply wrong-store and changed `GG_REQUIRE_API_KEY` configurations, assert the refusal and verify process/fingerprint/lease preservation and empty alternate store. Keep separate config directories where absence of the product’s adjacent `gateway.log` is the no-start evidence. Use the existing gateway shutdown API with the original verified identity and empty active-run snapshot, keep its credential in memory, and confirm listener/leases release. Unlink only the proven owned alias entry. Preserve unrelated launcher tests.
4. Emit a small sanitized JSON diagnostic for each alias from its `finally`, including the stage, native type or exact creation error, CLI/launcher statuses, observed identity and cleanup evidence. Use executable/process details and digests as appropriate. Exclude shutdown credentials and raw lock tokens. Emit before failure can conceal old behavior. Avoid changes to the artifact uploader unless the ordinary Windows job logs fail to retain this evidence.

## Hosted old-source evidence

Use a test-only draft head against the live post-#419 target and retain the exact native test file digest plus unmodified product input digest. The Windows job builds the old source from its actual checkout. Record the GitHub run/attempt, native job, checked-out SHA, regression file digest, Win32 build/test disposition, and both structured alias records. A meaningful old-source result reaches real alias creation and native refusal. Host inability to create a symlink leaves that old-source observation unavailable.

After the old-source Windows outcome is recorded, publish the product fix separately on the same PR with the identical test bytes. A passing current-head Windows job must exercise both physical aliases including real directory symlink metadata and the native success, reuse, refusal and cleanup assertions. A missing or skipped native symlink leaves the owner-required verification open. A portable alias helper test can corroborate the CLI behavior.
