## Defects

### D4-343-03 — major: accepted embedded-NUL request key permanently fails admission

Reproduction: run [nul-reproduction.mjs.txt](nul-reproduction.mjs.txt) against the retained QA server after publishing a simple owned Event loop. POST `{loopId,type:"nul-repro",dedupeKey:"before\u0000after",payload:{original:true}}`; allow dispatch to settle; retry the identical key with changed payload. No injected storage fault applies to this loop. A plain nonempty-key control uses the same loop and succeeds.

Expected: well-formed Unicode key reuses one delivery and admits exactly one run; the complete key survives in the run envelope. Actual: first response is 202/pending, delivery `01M5PSF7XK5CWPJR774ENCKSE0`, admission `01M5PSF7XK5CWPJR774ENCKSE1`. After one attempt it is failed with `EVENT_INTENT_CONFLICT`; retry reuses that failed delivery, exposes `dedupeKey:"before"`, and `runIds:[]`. Both inbound/receipt text columns have the full bytes `6265666F7265006166746572`; the frozen intent retains the complete key. There are **zero runs** for this Event. The plain control admits one run. This also reproduces with `left\u0000right` in the first pass.

Evidence: [nul-reproduction.json](nul-reproduction.json), [nul-reproduction.log.txt](nul-reproduction.log.txt), initial API/diagnostic records. Relevant implementation: `packages/infrastructure/src/sqlite/admission.ts:159` compares a returned text key to the intact JSON intent key. Text decoding truncation is observed; the full lower-level cause is not asserted as a separate native-library finding. The request is schema-valid, so terminal admission failure violates the specified boundary and accepted-delivery contract.

### D4-343-04 — major: receipt-specific retry-metadata failure starves later due Events

Reproduction: [sweep-isolated.mjs.txt](sweep-isolated.mjs.txt) on a fresh store containing exactly two Event receipts; [sweep-reproduction.mjs.txt](sweep-reproduction.mjs.txt) independently reproduces it on the shared QA fixture. Publish two loops. Block their first run inserts using one SQLite trigger; accept one keyed Event for each and settle (both pending, attempts=1). Remove that trigger. Add a run-insert failure for **only the first loop** and an Event-receipt UPDATE failure for **only its inbound ID**. Advance the clock and invoke three separate public recovery sweeps. Then remove only the receipt UPDATE fault and sweep again, leaving the first loop's run-insert failure active.

Expected: each sweep continues past the failing receipt and admits the healthy second recipient. Actual: both receipts remain pending with attempts=1 across all **three** sweeps; the healthy receipt `01M5PSXK43QQ7HF9WJPMX7HWTR` is not attempted. Once only the metadata fault is removed, it becomes admitted, attempts=1; the first receipt remains pending, attempts=2. Its failure therefore suppresses unrelated accepted work for as long as that metadata write keeps failing. Ordinary admission failures alone are isolated correctly, and the separate webhook sweep still works.

Evidence: [sweep-isolated-results.json](sweep-isolated-results.json), [sweep-isolated.log.txt](sweep-isolated.log.txt), [sweep-reproduction.json](sweep-reproduction.json), [sweep-reproduction.log.txt](sweep-reproduction.log.txt); independently observed in [diagnostics-summary.json](diagnostics-summary.json) and the initial API run. Relevant implementation: `packages/engine/src/run-manager.ts:738`, where one catch surrounds the Event loop instead of each dispatch. This finding is bounded to per-receipt metadata-write failure; it does not claim that all normal failed admissions block recovery.
