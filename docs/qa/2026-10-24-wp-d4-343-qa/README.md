## Defects

### D4-343-01 — major: an accepted empty request key silently becomes unkeyed

Steps: publish an owned Event loop with one matching entry and no authored node key. POST `{loopId,type:"ready",dedupeKey:"",payload:{keyCase:"",i:0}}`; repeat with the same request key and `i:1`. Both requests return 202 and `duplicate:false`. The accepted delivery IDs are `01M5PDJZM3EXN190YZ1P6D8CFD` and `01M5PDJZM3EXN190YZ1P6D8CFH`. Both response bodies omit the supplied key; SQLite contains 2 distinct runs, `01M5PDJZM3EXN190YZ1P6D8CFF`, `01M5PDJZM3EXN190YZ1P6D8CFK`.

Expected: an explicit accepted request key reuses its original delivery and payload, or the API clearly refuses an empty key before storing anything. Actual: the schema accepts the string but truthiness checks drop it; a sender can retry the accepted key and admit another run. Space and embedded-NUL keys both reused their original delivery in the same probe. This violates #343 keyed retry and declared dedupe behavior at a schema-accepted boundary. Relevant source: `apps/api/src/routes/triggers.ts:194` and `:212`; `apps/api/src/triggers/trigger-service.ts:561`, `:631`. No fix made.

Evidence: [empty-key-reproduction.json](empty-key-reproduction.json), [empty-key.log.txt](empty-key.log.txt), [key-boundaries.json](key-boundaries.json), [empty-key.mjs.txt](empty-key.mjs.txt); initial request source is [initial-browser.mjs.txt](initial-browser.mjs.txt).
