## Defects

### D3 (Low, predates this change): a failed store read under the lock lets a confirmed reset remove the database while keeping the run workspaces it can no longer identify

**Reproduction** (`r2-d2-copies.mjs`, scenario D3):

1. Seed a format-3 store with run `01JQAB3INTRUNAAAAAAAAAAAAA`, its workspace and artifacts.
2. Run `node apps/api/dist/main.js --reset --yes --data-dir <data>`.
3. When the second private copy appears (the plan under the lock) and its marker records the worker, kill the copy owner with `taskkill /F /PID <owner pid>`.

**Expected:** ADR-0042 removes workspaces and artifacts first "so that a reset that stops part of the way still has the run IDs it needs when it is run again". The read-only preview in the same invocation had read the store, so a confirmed reset whose own read then fails should stop rather than remove the database.

**Actual:** The confirmed reset printed `Database: …\graphgoblin.db (unreadable: store reader exited with 1)` and `Keeps: workspaces/01JQAB3INTRUNAAAAAAAAAAAAA  the store could not be read to match run IDs`. It then removed `artifacts`, `graphgoblin.db`, `-wal` and `-shm` and ended `Reset complete.` with exit 0. The run workspace remains, and with the database gone no later reset can identify it; the operator must find and delete it by hand.

By code reading, the same path existed at `603cbaa6`: any reader failure, including the 120 s reader timeout on a large store, returned `readable: false`, and the confirmed reset proceeded. The new copy owner adds one more way to trigger it.

**Severity:** Low. It needs the reader to die or time out during the locked plan. Nothing outside the manifest is removed, and the manifest shows the degraded plan before removing.

## Observations

- **O1:** Killing only the copy owner during a dry run makes that dry run report the store as `unreadable: store reader exited with 1` and keep every run workspace, with exit 0. The next dry run reads it normally.
- **O2:** While a dead marked copy cannot be cleaned (E2: a file in it held open by another process), every reset, for any data directory, refuses with the raw `reset refused: EBUSY: resource busy or locked, unlink '%TEMP%\gg-reset-store-QAhld1\store.db-wal'` and `Nothing was changed.` ADR-0042 documents the refusal, and the data directory was indeed unchanged. The reaper had already removed `store.db` from that stale copy, though, and kept `owner.json` as designed. So "Nothing was changed" holds for the data directory, not for the temp directory. The message names the file but gives no guidance.
- **O3:** Stale-copy cleanup runs at the start of every reset, including dry runs, refused resets and resets for other data directories (D2 scenario). This is as documented.
