## Findings

### F1 · P1 · FIX-IN-PR · publish-retry/divergent-readback-dispatches

`apps/web/src/editor/usePublish.ts:142–175, 203–215`. A retry GET that succeeds settles the unresolved guard and compares only `current.definition` before permitting a new POST. The available `draftToken` is checked for divergence only after that POST, through the returned version or subsequent readback. The gateway's detail token describes the actual draft if present (otherwise the published version), and the unconditioned POST validates then freezes the admitted draft and arms its triggers (`apps/api/src/routes/loops.ts:238–252, 375–393`).

1. The editor has acknowledged A1. The publish transport fails with no usable answer, along with its initial readback. Start with current v1 containing older content and have the first POST fail before admission.
2. Another writer saves B into the draft. Leave the original editor's A1 unchanged. Retry's flush is clean and does no PUT (`useAutosave.ts:181–191`). The retry GET returns older current v1 and B's divergent token.
3. The current comparison fails, the local guards pass, and the editor POST publishes B. Only afterward does the result report mismatch and put A1 behind the conflict choice.

The server already showed a conflict before dispatch. The accepted design requires divergent readback to preserve the local copy and use explicit conflict/reconciliation without resubmitting. An ordinary first POST can still publish a competing write that arrives after dispatch, as documented. The retry path can prevent the write above without a new API contract. Apply divergent readback evidence before a retry can dispatch, including when held input appears during the GET. A successful GET must not both clear the guard and discard conflict evidence through a local refusal. If the initial post-failure readback already proves divergence, its notice should point to the actual recovery controls. Cover v1, B's unchanged draft identity/content, A1's local/device copy, and zero additional publish POSTs. Preserve the positive control with an unchanged acknowledged draft.

### F2 · P2 · FIX-IN-PR · publish-retry/unknown-notice-rebinds-draft

`apps/web/src/editor/usePublish.ts:142–147, 160–165, 242–251, 318–325`. The hook retains unresolved loop and generation only. A failed check on a later click creates the outcome using that click's new acknowledged snapshot, then says the earlier request may have published “the draft saved for this publish.” For example, A1's POST is unknown, A3 is saved later in the same mounted load, and A3's first precheck fails. A3's click has sent no publish request. The wording mixes that click's saved draft with the earlier request whose outcome remains uncertain. The controlled A3 case already reaches this sequence, but verifies only the leading failed-check text (`EditorPage.publish.test.tsx:723–759`).

Keep the failed retry's message about the previous request and its earlier snapshot. Wording that states the earlier request's outcome is still unknown without naming a snapshot is sufficient if it clearly states that the current click sent no publish request. Assert the complete distinction in the existing A1/A3 scenario.

### F3 · P2 · FIX-IN-PR · publish-notice/older-release-implies-current-draft-unpublished

`apps/web/src/editor/usePublish.ts:296–317, 334–340, 350–380` and `EditorPage.tsx:402–409`. The notice receives the latest detail but uses only its version number. It compares the editor against the attempt's older release to say “changes made after that are not published” or “This editor’s draft is not published.” That comparison establishes what is in the older release.

A native schedule can hold the v1(A1) response after commit. While it waits, update the local editor to A2 and independently save and publish exactly A2 as v2. Then release v1. The older result is accurately attributed to v1, but the settled notice also says the later changes are unpublished and that version 2 has since been published, even though refreshed detail shows that version 2 contains exact A2. For a mismatch, a returned v1 containing a different draft can precede a v2 matching the editor, and the broad claim fails in the same way. Existing controlled tests separately exercise later local editing and later external publication, leaving their combination untested (`EditorPage.publish.test.tsx:55–87, 384–405`).

Keep the comparison scoped to the identified immutable release, or make any claim about the current published version from that version's exact content. Preserve the separate warning when the editor holds input that never became a draft. Exercise the combined held-reply order and assert v1 and v2 immutable contents and the final visible notice.

### F4 · P2 · FIX-IN-PR · publish-refresh/dependent-validation-late-result-clears-staleness

`apps/web/src/api/queries.ts:287–310` invalidates other loops' validation keys without cancelling in-flight reads. Once catalogs resolve, these results have `staleTime: Infinity`, and the validation query does not consume an AbortSignal (`EditorPage.tsx:210–236`). TanStack Query 5.104.0 clears `isInvalidated` on success and therefore regards an old answer that lands after invalidation as fresh. The gateway checks the published existence of a target referenced by a subloop (`apps/api/src/loop-issues.ts:25–58`).

Warm loop B's validation cache while its subloop target A is still draft-only. An unrelated publication can mark B's old key stale. Start Publish A, hold the request before admission, and return to B. Hold the answer to B's new validation after it reads A as unpublished. Admit A and allow A's publication refresh to mark B stale, then release B's prepublication results. B continues to show `SUBLOOP_NOT_PUBLISHED`, even on a subsequent editor mount with the same key. In the immediate base, the broad publish invalidation refetched active warm B, cancelling its in-flight refetch. A test currently checks only a seeded inactive validation cache immediately after invalidation, with no late response (`EditorPage.reconcile.test.tsx:224–244`).

Discard in-flight validation results whose dependencies could have changed with publication. Ensure an affected active editor can recover and that an inactive key remains stale for its next use. Keep this exact enough to avoid rechecking the publishing editor's own unchanged draft. The source already uses cancel-then-invalidate for other cache state changes. A held validation across A's publication can assert B's stale answer cannot become fresh.
