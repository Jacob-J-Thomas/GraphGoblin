## First failures on the unchanged source

The final regression tests were run against unchanged HEAD source (`logs/first-failures-final.log`). Of 52 tests in 3 files, **20 failed and 32 passed**. The baseline before any edit was 41/41 in the same 3 files.

### F1 (P1): a retry check that reads a divergent draft token still sent a POST

- *sends nothing when the check before a retry finds another draft, and keeps both copies*: the expected notice was missing. A temporary diagnostic, removed before the fix (`logs/first-failures-f1-diag.log`), showed what the old code did. It sent a **second POST** (2 in total), the server's current version became **version 2 holding B**, and the notice read "A different draft was published".
- *keeps that evidence when held input arrives during the check*: the old code showed only the held-input refusal (1 POST, no conflict), so the check's evidence was lost. After the text was discarded, the next Publish **sent a POST and published B as version 2** (same diagnostic log).
- *points to the conflict choice when the check after a lost request finds another draft*: in the first post-failure readback, the old notice ended "Publish again to retry." although the editor was in the draft conflict and Publish would refuse.
- Control, passing on both old and new code: *applies that evidence to no newer load of the editor, even on the same token*. During the check, a newer load of the same loop opens on the same token. Release produces no conflict, no notice, the token unchanged and no POST.

### F2 (P2): failed-check wording named this click's snapshot

Four EditorPage tests and one unit test fail on the full-text assertion, which replaced the earlier prefix regex. The old text ended "…Nothing was sent, and it is still not known whether the earlier request published the draft saved for this publish."

In the A1/A3 scenario (*stays unresolved through a Publish whose save failed, then sends once after a check*), the test now also asserts three things:
- The notice does not contain "the draft saved for this publish".
- The server still has current version 1 = A1 and draft A3.
- Afterwards, one GET-then-POST publishes A3 as version 2.

### F3 (P2): the notice made claims beyond the named release

- *describes a delayed reply by its own version when a later version holds the newer work*: the v1 (A1) reply is held, the editor moves to A2, and exactly A2 is saved and published elsewhere as v2. The old notice said "…; changes made after that are not published. Version 2 has been published since." Immutable v2 holds exactly A2.
- *describes a returned different draft by its own version when a later version holds the editor’s work*: returned v1 holds B, and v2 holds the editor's exact A2. The old notice said "This editor’s draft is not published."
- Both tests assert the immutable v1 and v2 contents by version ID, the current detail (v2 = A2) and the toolbar's "published v2".

### F4 (P2): a late validation answer from before the publication made the key fresh

- *Warm, active*: B's warm check is marked stale by an unrelated publication. A's Publish is held before admission while the user returns to B. B's check reads A as unpublished and is held. A is then admitted and B released. Old code: `isInvalidated: false` with the `SUBLOOP_NOT_PUBLISHED` data, so reopening B would not check again (`logs/first-failures-f4-warm.log`).
- *Nothing cached (cold control)*: the old code stored `[SUBLOOP_NOT_PUBLISHED]` as fresh. The test expected no data and `isInvalidated: true`.
- *Installed query library control* (TanStack Query 5.104.0, real `QueryClient`): first it confirms the library's own behaviour, where a fetch answer landing after `invalidateQueries({ refetchType: 'none' })` clears `isInvalidated`. Then, with old code, `refreshLoopAfterWrite(A, { published: true })` let B's late answer replace the earlier data as fresh.
- Test-fixture correction (not a product finding): the warm test's first draft failed at the unrelated loop's notice because an unedited draft-only fake loop publishes as "version 2". I changed that assertion to `/^Published version \d+\.$/`, matching the existing test, before recording the failures above.

## Changes (batch 1)

- **`usePublish.ts` (F1)**: new outcome kind `changed`. When the check before a retry answers, the current version does not hold the attempt's acknowledged copy and `draftToken !== acknowledged.token`, nothing is sent. This outcome is decided before the `sendable()` recheck, so held input or a refusal that appears during the GET cannot discard it. It goes through the existing mismatch path, which enters the conflict only when the same loop **and** generation is still loaded, still on the acknowledged token and not already in conflict. Device copy and server B are both kept.
  - An unchanged acknowledged draft still gets exactly one POST after an answering check.
  - A first POST is unchanged; its race after dispatch still relies on the existing immutable-mismatch recovery.
  - No API, token or conditional contract was added.
- **`usePublish.ts` notices**:
  - **F1, `changed`**: "Nothing was published / This Publish sent no request: a check found that the server holds a different draft from the draft saved for this publish. Its current version, version N, does not hold … either." It names the recovery choices while the editor is in conflict.
  - **F1, initial readback with a different draft token**: no "Publish again to retry"; it names **Reload server draft** / **Overwrite with this copy** while the editor shows the conflict.
  - **F2**: "This Publish sent no request, and the outcome of the earlier Publish request is still not known. Publish again checks the server first." No snapshot state was added.
  - **F3**: content comparisons are scoped to the named release ("…, without the changes made after that."; "It does not hold the editor’s current draft."). Held input gets its own warning: "Some fields still hold input that is not saved or published."
- **`EditorPage.tsx`**: passes the live `conflict` into `publishNotice`.
- **`queries.ts` (F4)**: on a publish, `refreshLoopAfterWrite` now cancels other loops' validation queries first (default `revert`), then marks them stale with `refetchType: 'none'` as before. The publishing loop's own checks stay excluded, running or not. There is no forced refetch, dependency graph or new cache layer.
- **Docs**: the #237 section of `docs/09-frontend-and-pwa.md` and the #237 CHANGELOG entries. `docs/guide` has no notice wording, so it is unchanged. No API, contracts, schema, runtime evaluator or parent #273 file was touched.

## F4 bounded-policy consequence (not broadened)

Under the root's policy, another loop's editor that is open while a publication lands does not check again immediately. If its check was running, that check is cancelled.
- With an earlier answer, the editor keeps it, marked stale.
- With no answer yet, it shows **Checking…**. That does not block Publish.

It checks again on next use: reopening, refocus (the app's `QueryClient` sets `refetchOnWindowFocus: true`) or a new draft key. This is the same state a completed, non-running check already had under the existing policy, and it makes no false fresh claim. A targeted refetch of cancelled active checks would be the broadening option. I did not take it, because correctness does not require it.

## Effective controls (green on the final source)

- **Positive same-draft retry**: *sends one request after the check when nothing changed meanwhile*; the A1→A3 GET-then-single-POST case.
- **Loop and generation ownership**: the new same-token newer-load control; *sends nothing, and shows nothing, once another editor opened during the check*.
- **U2 (unknown survives a local refusal)**: *reads the server first after a held-input refusal*; *stays unresolved through refusals and a failed check*; *stays unresolved through a refusal met where the request would be sent*.
- **Ready-to-send check after the await**: *refuses held input that arrived during the check, and sends nothing*, where the draft is unchanged.
- **Same-loop token ancestry**: both *the save sent on leaving* tests.
- **Explicit conflict recovery**: *does not carry an unresolved request into a newer load (control)* and the existing conflict/readiness tests.
- **Exact refresh**: the *Loops list after a save* convergence tests.
- **F4 extended test**: after a publish, A's own key is the same key with the same data, `isInvalidated: false`, and no new validate call. Another loop's detail key and the model catalog are not invalidated. Another loop's seeded check keeps its data, marked stale. A's own check runs no more times when the target is published.
