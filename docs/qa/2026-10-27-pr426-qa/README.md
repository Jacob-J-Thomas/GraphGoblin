## Method

- **The built product.** Each scenario starts `node apps/api/dist/main.js` as a hidden child process on a fresh disposable store, and stops it with `POST /system/shutdown {action: drain}`; every gateway exited 0. The drivers and helpers are in [scripts/](scripts/). [lib.mjs](scripts/lib.mjs) is patterned on the F2 record's helpers.
- **Controlled fake CLI for the provider-free checks.** [fake-cli.cs.txt](scripts/fake-cli.cs.txt) is compiled twice by [prepare.ps1](scripts/prepare.ps1), once as `codex.exe` and once as `claude.exe`, and set as `GG_CODEX_BINARY`/`GG_CLAUDE_BINARY`.
  - It answers the readiness probes like the real CLIs (`--version`, `--help`, `login status`).
  - It appends every turn it receives to `requests.jsonl`. "No provider request" in check 1 therefore means "no turn reached any CLI", which is a stronger statement.
  - Its failure modes stream the failure the way Codex CLI 0.160.0 does: `thread.started` and `turn.started`, then `error` and `turn.failed` with the provider's JSON body, then exit 1 with only the `Reading prompt from stdin...` banner on stderr. The Claude modes stream an `assistant` record with `error`, then exit 1 with a stderr banner.
- **Live provider (checks 2 and 3).** [c23-live.mjs](scripts/c23-live.mjs) runs the product's own default Codex CLI. Before any real turn it was dry-run twice against the fake CLI ([dryrun/](dryrun/)); the dry runs only debugged the driver and are not evidence. The SQL edit of `model_catalog` was made with `@libsql/client`, the product's own SQLite driver, because no `sqlite3` shell is installed on this machine. It was the same `UPDATE` the brief describes.
- **Process evidence.** A long-lived PowerShell polls `Win32_Process` for `codex.exe` every 100 ms. It keeps only the `--model`, `model_reasoning_effort`, `resume` and `--output-schema` tokens of processes whose parent is the gateway.
- **Provider-side history.** I read only the Codex session-history files of the two threads this QA created, found by thread ID. I recorded only entry kinds, the `turn_context` model and effort, and error messages. No prompts, replies, instructions or account fields were recorded.
- **Turn accounting.** Real turns are counted from the runs' durable `harness.turn` events, cross-checked against the `codex.exe exec` processes seen. Refused resumes would count, but the refused resume here (409) started no process and recorded no turn.
- **Redaction.** Profile paths in every spelling (including JSON-escaped), the machine name, SIDs and the user name are replaced, and anything shaped like a token, key, email or account ID would be replaced too. Every text file is UTF-8 without a byte-order mark, and every file is under 1,000,000 bytes, so there is no `NOT-KEPT.md`.

## Defects

### D-1 (Low, #205 residual of D1): Settings still offers Codex `minimal` when the Codex Default model is "(server default)"

- **Reproduce.**
  1. Build and start the PR head on a fresh store (`pnpm build`, then `node apps/api/dist/main.js` with a new `GG_DATA_DIR`).
  2. Open `/app/settings`. Under Defaults, Codex, leave Default model at "(server default)", the fresh state, and open Default effort.
  3. The list is `(server default)`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`.
  4. Choose `minimal`.
- **Expected.** The CHANGELOG says "Codex no longer offers effort `minimal`", and U16 says "visible selections accurately describe what can execute". Codex Default effort should offer only efforts the effective Codex model accepts. The server default model is `gpt-6-luna`, which accepts `low` to `max`. Failing that, a refusal should say which value is not supported and why.
- **Actual.**
  - `PUT /settings` answers 400 `EVALUATION_INVALID_CONFIGURATION` with `errors[0].resolution.code: EFFORT_UNSUPPORTED`. Nothing is saved, and the select returns to "(server default)".
  - The only message is "invalid harness defaults (EVALUATION_INVALID_CONFIGURATION)", shown at the bottom of the Defaults card under the Claude section. It names neither the field, the effort nor the model ([c1-settings-minimal-offered-before.png](c1-settings-minimal-offered-before.png), [c1-settings-minimal-offered-after.png](c1-settings-minimal-offered-after.png), [c1-catalog.log.txt](c1-catalog.log.txt) 1b-4 and 1b-5).
  - With Default model set to GPT-6 Luna, the list is correct: `low` to `max` (1b-6).
- **Likely cause** (read from source, not traced). In `apps/web/src/settings/sections/DefaultsSection.tsx`, the Codex effort options are `selectedEntry?.efforts ?? EffortSchema.options`. With no model selected, the full canonical scale is offered, and since this PR that scale contains a value that no Codex model accepts. The node editor does not have this problem, because it resolves the inherited model through `GET /system/model-defaults`. By the same code path, `max` would be offered and refused if the process default model were GPT-5.5; I did not exercise this.
- **Severity.** Low. The refusal happens before any request, no run can fail at the provider, and the server-side fix of D1 holds on every path I tried. It is a visible selection that can never be saved, with an unhelpful message, and the CHANGELOG claim is inaccurate for this list.
