## What the candidate does (root's accepted direction, unchanged)

A pointer click (`detail >= 1`) that the existing viewport gate admits measures the offer section before
acting and passes `{width, height}` to the canvas. The canvas then renders `SpaceCardsResult` in the same
wrapper, same classes (background, border, shadow) and same box in the commit that removes the offer:
**Spaced _n_ cards.**, the stale-draft refusal line, or **Suggestion dismissed.** The result has no control,
`tabindex`, handler, live region, timer or hidden shield, and `select-none` text. Nothing is prevented,
stopped, delayed or replayed. It ends at the next `pointerdown` outside it (document capture, passive,
event untouched), when the live offer returns, on any load (generation change), and on unmount.
`detail 0` (keyboard, scripted) leaves no result and retires the offer at once. The gate, store, layout
helper, history, save and fit are unchanged (one step, one fit, one save). The announcement and the focus on
the canvas root are unchanged.

## Changes in this resume

1. **Gate test: the old-production control now fails for the right reason.** The checkpoint's run test waited
   for the result element, so at old production it merely timed out. A `landing(covered)` helper now states
   the premise jsdom cannot test: the next press lands on the result while one exists, else on what the offer
   covered (Zoom Out at 512 px, as the native failure showed). The installed xyflow/d3 then do whatever they
   really do. Assertions were reordered so the viewport comparison comes first.
2. **New gate cases:** a press dragged on the result (Shift off and on): no pan, no selection box, no d3
   window listener, no `data-gesture`, selections kept, view still the one fit.
3. **Gate test isolation:** `afterEach` now releases any in-flight mouse gesture and lets d3's click-blocker
   task run (see first failure 3 below). Without it a failing test left d3 mid-gesture and swallowed the
   next test's click.
4. **Outside-pan assertion reconciled** (the checkpoint's first gate failure). The intended behavior is "the
   result ends at that pointerdown and the press continues untouched". With a native `dispatchEvent`, the
   document listener only schedules the end; React commits it in the microtask after the listeners return,
   which is before the press's own `mousedown`. The test therefore awaits microtasks after the
   `pointerdown`, then asserts the result is gone before the pan continues, and says so in a comment. The
   production code was correct; the test's immediate assertion was wrong. (`fireEvent.pointerDown` in the unit
   file wraps in `act` and is synchronous, so that file was unaffected.)
5. **Unit test lint fix:** `act(() => vi.advanceTimersByTime(...))` resolved to the Promise overload; it now
   uses a block body.
6. **Docs:** `docs/09` regression bullet now describes the dragged-press cases, the stated hit premise and that
   without the result the same presses zoom out twice or pan. `CHANGELOG.md` now says the double hit was
   "found at 512 px, where it covers **Zoom Out**" instead of "at narrow widths" (that is the only evidence).

## Remaining limitations (also in docs/09 and the CHANGELOG)

- jsdom has no hit-testing, layout, browser click counting or touch. The gate tests state where each press
  lands; native QA must prove which element a real press hits, including at 512 px (93,290), touch and pen taps,
  Shift runs, route-handle/node/connection drags after the result ends, geometry at the documented viewports and
  text sizes, and that the result box equals the offer box. I did not emulate touch in jsdom (jsdom has no `Touch`
  constructor), so "touch-emulated" presses remain a native check.
- Not run, per instruction: the corrected seven-group native plan, builds, coverage, browser, provider,
  owner store. The Space global fixture budget (1/2) was not touched; this was unit work only.
- The cost is as root accepted: the covered area (up to 392 × 129.5 px at 512 px, which includes Zoom Out) and
  any card the fit places there stay covered until a press elsewhere. Resize, panel toggle, text-size change or a
  press elsewhere are lifecycle boundaries, not geometric protection.
- `docs/guide/02-build-a-loop.md` (line 12) describes the panel and was not in the brief's doc list, so I left it.
  It is still accurate, but a user-facing sentence about the result staying until the next press would be
  consistent. Your call.
- Canvas is the older #207 version, as briefed; the new Space block touches only the import (line 77), lines 934–949,
  968–988 and the render at ~1067, away from #207's regions, for the later integration.
