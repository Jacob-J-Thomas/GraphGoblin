# Independent behaviour QA: PR #412, deletion eligibility (#187) and pressure cleanup (#322)

Head `a5d90fe584b0cb3b9f35cca868edea5b053b5547` (PR #412 integrated with `main`), worktree `qa-e3-412`. Independent QA by Claude Opus 5.5. No product code or tests were changed.

Consent (#187) behaves as specified. Loop deletion is unchanged. Nothing is deleted while storage is adequate. Under simulated pressure only approved, eligible history and resources it provably owns were removed, and interrupted cleanup recovered consistently. The verdict is **FAIL** for three reasons:

- **D1:** the status and notice can say that no approved eligible history could be cleaned while approved, eligible history is still waiting.
- **D2:** a startup cleanup pass delays the API from listening.
- **D3:** a running cleanup pass stalls every database-backed request and active runs for seconds.

D4 is a low-severity selection defect in the Runs page.

## Defects

### D1: the status and notice say "no approved eligible history" while approved, eligible history remains (Medium)

The cleanup cursors are per-process. A pass reads approved roots only above the previous pass's last root ID, and reads resource jobs only after the previous pass's last 32-job window. A pass that finds nothing above its cursor reports `no-eligible`, and only then resets the cursor.

Reproduction (`d1-repro.mjs`, `13-d1-repro.log.txt`):

1. Create two runs, `older` and then `newer`, and let both finish and finalize.
2. Confirm `newer` delete-ready (preview, then confirm, 200).
3. Set storage pressure (0.5 GiB free of 100 GiB). Wait for a pass. `newer` is deleted and the state is `pressure`.
4. Confirm `older` delete-ready (200, `deletionApproval` recorded).
5. Wait for the next pass.

- **Expected:** `older` is deleted, or at least the status does not claim that nothing eligible exists.
- **Actual:** `GET /system/storage` returns `state: "no-eligible"` and `deletedRuns: 0`, and `GET /runs/<older>` returns 200 with its approval. Edge shows "Storage is low. No approved eligible history could be cleaned. Review history you can remove or free disk space." The following pass deletes `older`.

The same mechanism shows up in two other places:

- **Resource window.** Store A had 61 artifact jobs held back by the proof budget, and they sorted before 61 workspace jobs. The startup pass reported `no-eligible` with nothing removed, then three later passes removed 12 MB of owned workspaces (`05-interrupt.log.txt`, line 35 onward).
- **Alternating count.** `preservedResources` alternates between 3, 0 and 3 across passes, so "Shared, linked or unproven resources are kept." appears on one pass and disappears on the next (`04-integrated.log.txt`, passes 1-4).

This violates #322's requirement that the warning truthfully explain pressure or a lack of eligible history. It also delays cleanup by at least one pass. There is no data risk.

### D2: under pressure, the API does not listen until the startup cleanup pass finishes (Medium)

`container.start()` awaits the first storage pass, including filesystem reclamation, before `buildApp` and `listen`.

Reproduction (`startup-latency.mjs`, `08-startup-latency.log.txt`):

1. Approve 20 runs with 1,900-file workspaces.
2. Stop the API.
3. Set pressure.
4. Start the API.

- **Expected:** the API listens within its normal startup time, and cleanup proceeds in the background.
- **Actual:** the API took 76.9 s to listen; the pass ran from 3.5 s to 76.9 s after spawn. The same store started in 3.6-4.4 s with adequate storage, and in 7.3 s under pressure once nothing was left to reclaim. The web app and API are unreachable for that whole time on every restart that happens under pressure. Some of the I/O was contended: another QA run was active.

ADR-0060 disclaims a latency guarantee for SQL batches, but it does not say that startup waits for the pass.

### D3: a cleanup pass stalls every database-backed request and active run (Medium)

Each resource's reference check and filesystem removal run inside one SQLite write transaction. The client serialises every statement through a single process mutex, so all other database work waits while files are unlinked.

Reproduction (`latency.mjs`, `12-latency.log.txt`, run alone):

1. Approve 16 runs with 1,900-file workspaces.
2. Measure `GET /runs?limit=1` and a run that appends 400 events.
3. Set pressure and repeat the measurement during the next timer pass.

- **Expected:** reads and run progress remain responsive during cleanup.
- **Actual:**

  | Measurement                   | Baseline | During the pass                    |
  | ----------------------------- | -------- | ---------------------------------- |
  | `GET /runs?limit=1`, p50      | 3.5 ms   | 5,620 ms                           |
  | `GET /runs?limit=1`, max      | 26.7 ms  | 6,807 ms (only 4 requests in 20 s) |
  | 400-event run to finalization | 1.8 s    | 44.3 s                             |

  A busier run in `03-api-extra.log.txt` showed a maximum of 6,638 ms, with 7 requests over 1 s.

With up to 32 workspaces of 2,000 entries per pass every 60 s, sustained loops degrade for as long as approved large workspaces remain. This works against I05's "keep sustained loops responsive".

### D4: the Runs selection keeps IDs that cleanup removed, and they cannot be unchecked (Low)

Reproduction (`ui-edge-2.mjs`, `02-ui-edge-followup.log.txt`, `ui-ghost-selection.png`):

1. In Runs, select two runs and confirm them delete-ready. The selection stays: "2 selected".
2. Let a pressure pass delete them while the page stays open.
3. After the list refreshes, select one visible run and choose **Review delete-ready history**.

- **Expected:** the selection holds only existing, visible runs, or removed IDs can be cleared.
- **Actual:** the count reads "3 selected", but only one row is checked. The dialog lists the two deleted IDs with "Run not found." and disables Confirm ("No history will be marked…"). The deleted rows no longer exist, so they cannot be unchecked; only a filter change or a reload clears them.

The failure is safe: no consent is broadened. Loop deletion while the page is open would presumably have the same effect, but that was not tested.

## Observations (not counted as defects)

- **O1. Artifact reclamation rarely happens.** The proof budget (ADR-0060: 2,000 retained JSON documents or 2 MiB in total) is exceeded by small stores. With 14 retained runs and 2,660 events, none of 61 unshared artifacts belonging to deleted approved runs (1.9 MB) was removed. They stay pending and are examined again on every pass. This is documented and conservative, but in practice only workspaces are reclaimed (`05-interrupt.log.txt`, `03-api-extra.log.txt`).
- **O2. Loop deletion frees no files.** Explicit loop deletion leaves the deleted runs' workspaces and artifacts on disk permanently, and they never become eligible for pressure cleanup (`03-api-extra.log.txt`: "deleted loop run workspace still on disk true"). This matches ADR-0033 and ADR-0060, but the dialog's "including run history and artifact references" does not tell someone deleting loops to free space that no files are freed.
- **O3. Dialog and inspector copy.** The dialog lists bare ULIDs, with no loop name, status or time. The inspector shows "Delete-ready: confirmed by local at 2026-10-26T07:15:09.424Z.": a raw UTC ISO time and the owner ID, whereas other dates in the UI are localized. The withdraw dialog repeats the protection paragraph, which is less relevant there.
- **O4. Minor accessibility.**
  - The "N selected" count is not a live region.
  - The review buttons sit above the table: 15 Shift+Tab presses from a row checkbox in a 7-run list.
  - The disabled Confirm button looks only slightly dimmed.
  - After confirming, the selection stays checked.
- **O5. Unavailable readings keep old data.** An unavailable reading keeps the previous observation's `checkedAt` and `volumes` (`04-integrated.log.txt`, line 118).
- **O6. Interim replay refusals during a race.** During a race, replays briefly got 409 `INVALID_STATE` or 409 `REPLAY_NODE_NOT_REACHED` while their source was being removed, before 404. No fork was created.
- **O7. Outside scope.** Cancelling forks with running scripts logged `SCRIPT_TERMINATION_UNCONFIRMED` once (`race-replay-detail.mjs` teardown). This is a Windows process-tree behaviour that predates this PR.

## Human QA items for the owner

1. **Notice.** Decide on its placement and look (global under the navigation, as observed above, or Runs only) and on its three texts.
2. **Confirmation dialog content.** Run IDs alone, or add loop name, status and time; and the inspector's "confirmed by local at <ISO>" line.
3. **D2 and D3.** Decide whether startup unavailability and request stalls during cleanup are acceptable under low storage, or whether reclamation must move out of the startup path and the database transaction.
4. **O1.** Decide whether artifact reclamation being effectively limited to workspaces is acceptable.
5. **O2.** Decide whether the loop deletion copy should say that files stay on disk.

## Method and test seams

- **Composition (`qa-server.mjs`).** It composes the **built** API exactly as `apps/api/src/main.ts` does (`createContainer` plus `buildApp`), with a file-backed SQLite store in a disposable data directory, the real clock and 60-second timer, real ids, real process scripts, the real filesystem, HTTP and the web build. It differs only in two public `ContainerOverrides`:
  - **`storageCapacity`**: the public `StorageCapacityPort` from ADR-0060. It reads a JSON control file on every call: a fixed reading, the production `FsStorageCapacity`, or a throw. No product code was changed, and this is the documented public dependency rather than a test-only override.
  - **`harnesses`**: `FakeHarness` from `@graphgoblin/engine/testing`, scripted by prompt directives, so that inference nodes complete without live provider turns. No live-provider behaviour is claimed.
- **Pass marker.** The QA port prints `QA_CAPACITY_READ` when a pass reads capacity. This is the only instrumentation, and it lives in QA code.
- **Unmodified entry point.** Check 3 was repeated on `apps/api/dist/main.js` with real `fs.statfs`.
- **Browser.** Edge 156.0.4314.42 through Playwright 1.63.0 (`channel: msedge`, headless).
- **MCP.** The built `apps/mcp/dist/main.js` in HTTP mode against the QA API.
- **Kills.** `child.kill('SIGKILL')`, which is TerminateProcess on Windows.
- **Store inspection.** `inspect-db.py`, run with `python -I` on a **copy** of the stopped store, read-only.
- **Scripts.** `smoke.mjs`, `ui-edge.mjs`, `ui-edge-2.mjs`, `ui-edge-3.mjs`, `integrated.mjs`, `api-extra.mjs`, `api-keys.mjs`, `interrupt.mjs`, `interrupt-reap.mjs`, `race.mjs`, `race-replay-detail.mjs`, `startup-latency.mjs`, `latency.mjs`, `main-adequate.mjs` and `d1-repro.mjs`, with shared helpers in `qa-lib.mjs`.

**Superseded runs, kept for honesty.** None of these failures is a product defect:

- `01-ui-edge.log.txt` ends with an error at the loop-deletion step. My selector `/Delete/` did not match "Confirm delete". Check 2 was redone in `02-ui-edge-followup.log.txt` and `07-ui-loop-deletion-child.log.txt`.
- `03-api-extra.log.txt` has 4 API-key FAIL lines. I sent `name` instead of `label`, so no key was created and every call got 401. This was redone in `11-api-keys.log.txt`, where all checks pass.
- `04-integrated-run1.log.txt` has 4 FAIL lines that cascade from a mistake of mine. My first "unfinalized" run used a start-time `return` channel without an exit `returns` mapping, so it delivered nothing and finalized at once. Its last step also waited for a new `checkedAt` that an unavailable reading never sets (O5). The rerun `04-integrated.log.txt` fixes both; its only FAIL is D1, which the first run also showed.
- `10-race-run1.log.txt`: my classifier counted "409, then removed by cleanup" as inconsistent. The rerun `10-race.log.txt` records the refusal details, and all runs are consistent.
- The FAIL lines in `02-ui-edge-followup.log.txt` and `13-d1-repro.log.txt` are D4 and D1.
