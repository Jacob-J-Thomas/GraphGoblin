## 2. Per bolt

**Confirmed and fixed: #246's post-integration terminal-return gap.** The original fixture
was created through the actual archived API, not by editing its run rows. A child waits for
input, then returns `old-child-result` to a webhook, Event, caller and log, in that order.
Its parent is parked on its child. The controlled receiver holds the webhook without
acknowledging it; after that request arrives, the old API process is killed with `SIGKILL`.
SQL inspection verifies one durable `run.finished`, child status `succeeded`, a null
`finalized_at`, a waiting parent and no return receipts. The Event sink has not been reached.
Two copies of this same old store supply the before/after runs.

The measured before log is `finalize failed` with error:
`Generated run event could not be recorded: channel.kind: Invalid discriminator value. Expected 'caller' | 'file' | 'log'`.

| Check                       | Before: integrated `670527cf`                                                | After: this patch                                                            |
| --------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Child execution             | `succeeded`, result `old-child-result`                                       | Same outcome and result                                                      |
| Child finalization          | `finalized_at` stays null; `finalize failed` logs receipt validation failure | `finalized_at` becomes `2026-10-21T22:33:17.679Z`; no `finalize failed`      |
| Retired destination         | Cannot append either current receipt shape                                   | Skipped; warning code `LOOP_UPGRADE_REQUIRED` names run, loop and version    |
| Parent                      | Already continues once through WP-C6's independent startup reconciliation    | Continues once with the child's succeeded outcome and result                 |
| Old history and definitions | Original raw event rows and stored definition strings unchanged              | Original raw event rows and stored definition strings unchanged              |
| Second startup              | Not claimed in the negative control                                          | Runs, events and definitions identical; zero new requests or diagnostic logs |

The reproduction confirms the stuck finalization. It does **not** reproduce a stranded parent
on this integrated branch: its independent reconciliation already wakes the parent. The fix
also restores the child's normal notification/finalization path rather than relying on that
fallback. Parent continuation is asserted exactly once in both controls.

The diagnostic occurs twice during the after run: once while its durable webhook is pending
and again when that webhook completes. It is per finalization attempt, not a fabricated
delivery receipt. After the finalization marker is durable, the next startup emits none.

Evidence is retained in [before.json](2026-10-21-wp-d2-report/before.json),

## 7. Decisions and parameters

Implementation decision for review: when terminal bookkeeping encounters an exit Event
destination saved before its retirement, skip that effect and log a warning containing
`code: LOOP_UPGRADE_REQUIRED`, `runId`, `loopId`, `versionId` and `channelKind: event`.
Do not publish the Event, fabricate a receipt, change the execution outcome or rewrite the
definition/history. Complete the supported returns, notify the parent with the recorded
execution outcome and mark finalization when the remaining delivery work finishes.

This is consistent with D-020's explicit operator repair and WP-C6's refusal before execution.
It does not assert whether any effect happened before the upgrade; historical Event receipts
or invalid return defaults that make history unreadable still require the documented operator
repair/deletion. No compatibility channel, legacy publication port or migration is introduced.

No webhook policy parameters changed. Manual regression listeners use available ports in
5800-5809; every old/new server has its own `GG_DATA_DIR` under the bounded fixture root.
Existing gate fixtures retain their repository-defined automatic test ports and prefixes.
