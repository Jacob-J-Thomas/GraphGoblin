### Product change, in substance

`GET /runs/:id/thread`:
- With `at === undefined` (current thread), the code is unchanged: `ownedRun` then `manager.getThread`.
- With `at` set, the handler registers `reply.raw.once('close')` and defines the monotonic `isDisconnected = () => closed || response.destroyed`. It checks before `ownedRun`, passes the predicate into `historicalThread`, and checks again afterwards. On disconnect, both the success path and the `catch` path `return reply.hijack()`. A connected error is rethrown unchanged. A `finally` always removes the listener.

`historicalThread(container, runId, at, isDisconnected)` checks the predicate:
- on entry;
- after `getInitialThread` (merged with `!thread`);
- after `getThreadCheckpoint`;
- after the boundary `events.read`;
- after each page `events.read`, before `replayThread`;
- after the existing `setImmediate` inter-page yield.

On disconnect it returns `undefined`.

## Correctness and lifecycle analysis

1. **Every asynchronous boundary is guarded, with no window before the next call.** Each predicate check is followed synchronously by the next repository call: no `await` and no macrotask between them. A close event is delivered by I/O, so no new ownership, initial-thread, checkpoint, boundary or page read can start after Node has emitted response `close`. At most the operation already pending settles. This matches the issue's expectation that abandoned reads cost at most one page.
2. **Response already closed before handler entry.** The listener is added after the fact, but `response.destroyed` is already true. In Node 22.23.4, `emitCloseNT` sets `destroyed = true` and then emits `close`, which I read offline from the runtime's own `_http_server` source. The handler therefore hijacks before `ownedRun`. The unit 'before handler' case and native `closed-before-handler` confirm this with 0 operations.
3. **Outgoing close versus a completed incoming GET.** The implementation listens only on the outgoing `ServerResponse`, never on `request.raw` `close`/`end`. In Node 22, a response gets `close` only from its socket closing (`onServerResponseClose`), from `destroy()`, or after `finish`. So a fully received bodyless GET with a live response is not treated as abandoned. The focused keep-alive test checks `inputEnded === true`, a 200 with exact bytes, `writableFinished === true` at close, and reuse of the same socket. Native `historical-completed-input` checks the drained-input wire bytes against baseline.
4. **Fastify 5.12.5 hijack semantics (installed source read).**
   - `Reply.prototype.hijack` sets `kReplyHijacked`. `wrapThenable` returns before `reply.send`, and the rejection path is never entered because the catch converts a disconnected error into a resolved hijack.
   - The async handler returns the `reply` thenable. `Reply.prototype.then` calls `fulfilled()` immediately because `sent` (hijacked) is true, so nothing hangs.
   - `onResponse` hooks run only on response `finish`/`error`, which a client-closed response never emits. Skipping them via hijack therefore matches baseline disconnect behaviour.
   - The only app-level `onResponse` hook, in `chat.ts` on the root instance, releases WeakMap audio reservations that exist only for `POST /chat/audio`.
   - No `handlerTimeout`, `onTimeout` or diagnostics-channel subscriber is configured.
   - SSE already uses `reply.hijack()` the same way after its own close checks.
5. **Listener cleanup.** `once` plus `off(onClose)` works with the `once` wrapper, and `finally` covers success, connected error, disconnected error and early-hijack paths. The listener is per-`ServerResponse`, so it never accumulates on a keep-alive socket. Native snapshots show `added: 0` at handler settlement in all 24 entered cases and +1 only while held.
6. **Error behaviour.** A disconnected rejection is silent, with no `onError`, error handler, send or write. A connected rejection is rethrown into the unchanged error handler: `INTERNAL_ERROR` 500, `STORED_EVENT_INVALID` 500, `STORED_RUN_INVALID` 500, `RUN_NOT_FOUND` 404 and `THREAD_NOT_FOUND` 404 are all preserved, per the unit tests and the native negatives.
7. **Auth isolation.** Auth, scope and validation still run in hooks or schema before the handler, and these failures never reach the product handler: 401, 403 and 400 show no operations and no listener snapshot in the native data. Ownership is still checked before any history read. The disconnected path writes nothing, so no ownership information can leak.
8. **Preserved semantics.** Sequence bounds, checkpoint selection and boundary verification, replay state carried across pages, the 128-row page size, isolation of damaged later records, and the current-thread path are textually unchanged apart from the guards. Nothing adds truncation, retries, persistence or time limits, and no pending promise is force-interrupted.
9. **`setImmediate` seam.** The candidate keeps `await new Promise<void>((resolve) => setImmediate(resolve))` byte-for-byte as a context line. The native harness intercepts global `setImmediate` only when it is scheduled from compiled `historicalThread` in `run-history.js`. The candidate trace records `replay-yield-scheduled` from `dist/run-history.js:63:15`, then `replay-yield-callback` and the `yield-1` barrier. **There is no seam mismatch.**
10. **Design boundary.** The HTTP lifetime stays in the route, and `run-history.ts` receives only a transport-agnostic predicate. This is the smallest local connection, with no new framework, package or subsystem. `historicalThread` is called only from this route; the signature change is type-enforced and CI typecheck passed.

## Observations and proposed dispositions (none blocking)

- **O1 — Focused tests do not pin the inter-page-yield check individually (test adequacy, low).**
  - *Reachability:* only a future regression that deletes or breaks the post-yield check (line 67), or the post-read check (line 60), alone would pass CI.
  - *Impact:* no current defect. Behaviour at the yield is established on the compiled candidate by native `closed-at-yield` (5 → 0 pages). docs/15 allows native-process evidence where a criterion needs it.
  - *Proposed disposition:* root's choice. Either ACCEPT with the native evidence as the yield criterion's proof, or add one focused case in a later hardening change. That case would hold the first `setImmediate` scheduled from `historicalThread` during an observed request, close the client, release, and expect exactly one page. I do not recommend reopening this PR solely for O1.
- **O2 — HTTP/1.1 pipelined requests (residual, informational).**
  - *Behaviour:* a historical request pipelined behind another response on the same socket sits in Node's `state.outgoing` queue without a socket. If the connection dies, Node 22.23.4's `abortIncoming` destroys only the incoming request (its own source comment: "Abort socket._httpMessage ?"). The queued response never gets `close` or `destroyed`, so that request still replays fully, as on baseline.
  - *Reachability:* browsers, undici's default and curl do not pipeline. The issue contract is scoped to an observed response close.
  - *Proposed disposition:* no action; note as a limitation if desired.
- **O3 — Disconnected rejections leave no server-side diagnostic (informational).**
  - *Behaviour:* a genuine infrastructure fault on an abandoned read is silently dropped, not logged.
  - *Basis:* this follows the brief's explicit "silent" contract. Persistent corruption resurfaces with the existing logging on the next connected read.
  - *Proposed disposition:* no action in #419. A future debug-level log is optional.
- **O4 — `undefined` means two things (informational design).**
  - *Behaviour:* `historicalThread` returns `undefined` both for a missing initial thread and for a disconnect. The single caller disambiguates safely with the monotonic predicate, but a future caller must do the same.
  - *Proposed disposition:* no action.
