## 1 · Cause and correction

**Cause, confirmed in source and natively.** 9e44 derived `checkFirst` only from the latest mutation result: `outcome?.kind === 'unknown' && !outcome.readback.ok`. A refusal thrown by `publishAttempt` replaces `mutation.data`, so the next Publish lost the check. That covers three refusals:

- held input before the flush
- a failed flush
- a refusal met when the queue reaches the attempt

**Correction.** `usePublish` keeps one explicit piece of load-scoped state: `unresolved`, a `useRef<{ loopId, generation } | undefined>`. It is independent of the latest result and error. `start` sets `checkFirst` only when it equals the current loop and generation.

`publishAttempt` gets a callback that records the outcome only where a read or an answer happens:

| Event inside the attempt | Effect on `unresolved` for this load |
| --- | --- |
| Refusal before the flush, failed flush, refusal at the queue, load replaced | none (nothing read, nothing answered) |
| Check-first read **failed** | stays set (`unresolved(true)`) |
| Check-first read **answered** | cleared, even if a refusal then stops the POST |
| POST answered (published, `NO_DRAFT`) | cleared |
| POST unanswered/5xx, read back OK | cleared |
| POST unanswered/5xx, read back failed | set |
| Definite 4xx refusal (e.g. `LOOP_INVALID`) | none; a POST is only sent once the flag is clear for this load |

Unchanged:

- latest-attempt reporting and the `ours` filter (a refusal still shows as **Publish failed**)
- `running` / `pending` (the unconfirmed pending-state hypothesis was not touched)
- the `sendable()` checks at the queue turn and immediately before the POST after an awaited read
- acknowledged-snapshot capture, divergence → conflict, refresh, notice wording, `useAutosave` and name-retry ownership

Background reads (`refreshLoopAfterWrite`, query retries, the discard-time detail read) are deliberately **not** used to settle the flag. They are not compared with the attempt's acknowledged draft.

Docs: the docs/09 **Publish not confirmed** bullet and Regression note, and the CHANGELOG #237 sentence, now say:

- the outcome stays unknown in that editor load until a read answers
- refusals and failed checks in between leave it unknown
- a newer load starts without it

## 5 · Observations and limits (for root and reviewers)

1. **What the user sees after a refusal.** After a refusal, the visible notice is only **Publish failed**. The earlier "Publish not confirmed… checks the server first" notice is replaced, as the latest-attempt rule requires. Behavior still reads first, but the screen no longer says the outcome is unknown. I did not change error UI, per the brief.
2. **Load scope.** A newer editor load starts without the flag (test 7, same as 9e44). This covers reload, restore, any remount from navigating away, and switching loops. The next Publish there may send a POST that answers `409 NO_DRAFT`, then reads back. That is the original's harmless path, with no duplicate version in the fixtures. This follows "keep loop/generation isolation"; root may decide whether a load should inherit it.
3. **A successful check settles the flag before a refusal stops the POST.** The next Publish then sends without another read. This matches the previous handoff's reasoning and the existing "check OK → Publish again" path; the existing held-input-during-check test and native control cover it.
4. **Comment wording nit.** The `publishAttempt` comment says "A refusal, sending nothing, changes nothing", but a failed-save refusal did send its PUT (never a publish request). Fixing the wording changes the bound source and needs a rebuild and native rebind, so I left it.
5. **Tiers.** The flushed and queued refusals are proven at the component tier (fake API) only. Native covered the early held-input refusal (the confirmed defect) and the three readback controls.
6. **Parent integration.** `origin/main` is now `a817e5cc` (#470 merged). This candidate has not been integrated, tested or built against it.
