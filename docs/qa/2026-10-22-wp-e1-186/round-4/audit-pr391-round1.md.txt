1. **P1 — Replay reports completion at an obsolete terminal event and omits durable suffixes.** `apps/api/src/sse.ts:155` calls `end()` on every terminal event; `packages/api-client/src/sse.ts:257` independently returns success on the same event. The new lifecycle-tail check at `apps/api/src/sse.ts:245` is never reached when replay hits that earlier marker. Through the real manager and REST API with a fake harness, a run failed at seq 12, resumed at 13, and succeeded at 24. Both raw SSE and the typed client delivered only 1–12, closed successfully, and reported no error. A separate page-boundary fixture had failed/resumed/finished/audit rows at 128/129/131/132: opening at 126 stopped at 128; opening after 128 stopped at 131 and omitted the already-durable `return.delivered` row 132. This violates the requested complete, ordered replay and truthful completion for resumed runs. The unconditional-stop rule predates this PR but is retained in its rewritten replay path and is explicitly inside the audit brief's lifecycle cases.

   Smallest fix: make completion depend on the current lifecycle outcome after catching up through the currently durable suffix. Continue past superseded terminal markers; make the client follow the server's authoritative completion rather than stopping on any historical terminal event. Preserve bounded reads and update the contradictory terminal-close sentence in docs/07. Add regressions for a real failed/resumed/succeeded run and for a terminal marker followed by durable delivery audits.

   Reproduction: after `pnpm.cmd build`, run `node --experimental-import-meta-resolve <auditRoot>/transport-probe.mjs <auditRoot>` from this worktree. Cases: `real manager failure then resume through REST`, `failed then resumed then finished with audit`, and `cursor after former failure`. Inspect `transport-results.json`.

2. **P2 — A successful terminal-cursor response becomes an endless retry or a false client failure.** `packages/api-client/src/sse.ts:214` returns false on every clean EOF; the retry loop consequently labels a correctly completed empty response as “the event stream closed before the run finished.” At a cancelled run's final seq 387 and at 487, raw SSE returned HTTP 200 with only `: connected`, while the typed client reopened twice and rejected `done` after `maxAttempts: 2`. Its default has no attempt ceiling, so it keeps reconnecting. After the terminal seq 131 followed by audit seq 132, the client delivered 132, then exhibited the same failure. No network or store fault was involved.

   Smallest fix: provide an unambiguous completion signal for a consumed terminal cursor and have the helper resolve on that signal. Do not equate arbitrary EOF with success, since the same EOF can represent a disconnected active run. Test the helper against the real route at, past, and after a terminal marker with trailing rows.

   Reproduction: the same script, cases `terminal cursor 387`, `terminal cursor 487`, and `cursor after current terminal with trailing audits`. Raw replies and helper errors are retained together.

3. **P2 — Corruption is retried when it is detected before streaming starts.** `packages/api-client/src/sse.ts:196` classifies HTTP failures by status alone, whereas line 237 treats an in-stream `STORED_EVENT_INVALID` control as fatal. A corrupt row on the first page, or a corrupt terminal marker found by the new consumed-cursor lookup, returns HTTP 500 `STORED_EVENT_INVALID` from the real route. The helper requested it twice and rejected with a generic “gave up” error when limited to two attempts; its default retries indefinitely. No event was delivered and the cursor stayed unchanged (0 and 8 respectively), but the promised fatal handling depends incorrectly on whether headers have already been sent.

   Smallest fix: apply the same fatal stored-event error classification to initial HTTP Problem Details and in-stream controls, preserving the typed error and the cursor. Add route/client regressions for first-page corruption and a corrupt lifecycle marker at a consumed cursor.

   Reproduction: `node --experimental-import-meta-resolve <auditRoot>/initial-corruption-probe.mjs <auditRoot>`. This uses built exports, a disposable real SQLite store, the public route via Fastify HTTP injection, and the client's supported fetch adapter; no network listener is involved. `initial-corruption-results.json` records both HTTP 500 responses per case, the code, unchanged cursor, and generic rejection.
