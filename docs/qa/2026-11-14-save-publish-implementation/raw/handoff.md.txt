## Implementation (apps/web, docs, CHANGELOG)

`git diff --stat HEAD` covers 12 tracked files (+227/−118), plus 4 new files. The exact candidate source is in `evidence/candidate/source-manifest-1.txt` (per-file SHA-256 and the tracked diff hash `0927a70f…`).

- **`src/editor/usePublish.ts` (new).** `usePublish` (hook), `publishAttempt` (one attempt), and the pure `sameDefinition`, `editorHolds`, `acknowledgedDraft` and `publishNotice`.
  - **Attempt identity.** `{loopId, generation, checkFirst}` is captured at the click. A same-task double click is ignored through a ref, cleared on settle.
  - **Before saving.** Held input refuses. Then `flush()` runs. If the load changed meanwhile, nothing is sent and nothing is shown. Otherwise the existing barriers are rechecked: held input, conflict, name refusal, unsaved.
  - **Acknowledged copy.** It is captured once here. It is the PUT answer (`draft.definition`, `draftToken`) for `savedRevision`. When this load made no save, it is the loaded copy parsed with `LoopDefinitionSchema` plus `baseToken`, because the server stores exactly that parse (`packages/infrastructure/src/sqlite/loops.ts` saveDraft stores the route's parsed body unchanged). A later revision is never relabelled as this attempt's copy.
  - **The request.** The POST is sent from `serializeSave(loopId, …)`. Inside that queued callback, immediately before the POST, it rechecks the same load and the held-input, conflict and name barriers. There is no recursive flush.
  - **Outcomes.** `published`: the returned immutable version. `not-published`: `NO_DRAFT` plus a readback. `unknown`: network or 5xx, plus a readback. A definite 4xx such as `LOOP_INVALID` rethrows as "Publish failed".
  - **Check before resending.** `checkFirst` is set when the previous outcome in this load was unknown and its check failed. The next attempt reads the server before sending. If the check fails again, nothing is sent. If the current version already holds the copy, nothing is sent and the notice names that version.
  - **Comparison.** Full canonical content via `stableStringify`: absent defaults and key order are ignored. A row ID, version number, revision or hash alone is never evidence.
  - **Mismatch recovery.** This happens when the server's next-save base no longer descends from the acknowledged copy: a different returned version, or a readback `draftToken` that differs. The editor then enters the **existing** conflict state, exactly as `useLoadEditor` does: revision bump when saved, `setConflict({serverToken: undefined})`, `setSaveState('conflict')`. It does so only for the same load, with `baseToken === acknowledged.token`, and not already in conflict. The publish answer is never used as a base.
  - **Copy.** Neutral: "Version N holds a different stored draft from the draft saved for this publish." No writer is named. "Changes made after that are not published" is computed live from content and held input. "Version M has been published since" is added from a fresh detail read. The notice has no link.
- **`src/api/queries.ts`.** `keys.triggers` and `refreshLoopAfterWrite(queryClient, loopId, {published})`.
  - Exact list and detail keys, plus versions and triggers after a publish. It does a silent no-revert cancel, then invalidates, so a cancelled first load is replaced, not joined (TanStack 5.104 `query.ts:594-608`, `retryer.ts:116`).
  - Other loops' validation is marked stale with `refetchType: 'none'`. Nothing is patched from write answers. Errors stay in query state; `refetchQueries` does not reject.
- **`src/editor/useAutosave.ts`.**
  - The global `latestTokens` map is replaced by a per-hook `chain` ref `{generation, token}`. It follows the store's `baseToken` for the load and is advanced only by that load's accepted saves, including after unmount.
  - The leaving save is skipped when `chain.generation !== snapshot.generation`; otherwise it uses `chain.token`.
  - `recordSaved` records the device copy first (its in-memory part is synchronous), then calls `refreshLoopAfterWrite`, for active and leaving saves. Successful saves pass the server answer as `acknowledged`.
- **`src/editor/store.ts`.** An `acknowledged` field (`AcknowledgedSave`), set only together with `savedRevision`, and cleared by `load`/`reset` through `INITIAL`.
- **`src/editor/EditorPage.tsx`.**
  - The old mutation, `publishedRevision` and the prefix invalidation are replaced by `usePublish`.
  - One notice slot, with dismissal (`announceDismissalAndRestoreFocus`).
  - "Publish failed" is shown only to the attempt's own load.
- **`ConflictNotice.tsx` / `CONFLICT_MESSAGE`.** The body and tooltip are now neutral: "The server now holds a different draft from the one this editor's changes are based on." The title "The draft changed on the server" is unchanged.
- **`WebhookReceiver.tsx`.** Uses `keys.triggers`, with the same key value.
- **Docs.** `docs/09-frontend-and-pwa.md`: new section "Publishing and the Loops list (#237)"; the Draft conflicts token rule; the outcome line; the Runs-link sentence. `docs/guide/03-run-and-observe.md`: the Runs link. `CHANGELOG.md`: Unreleased entries, with no upgrade note (no API, schema, stored-format or device-format change). No ADR: no decision changed.

### Decisions a reviewer should check

1. **The POST runs in the window's per-loop save queue.** An autosave typed while a publish request is slow now waits behind it; the device mirror is still immediate. Natively, A2's and E's PUTs were sent 32 ms and 21 ms after the held reply was released (`evidence/candidate/attempt1/scenarios/publish-held-response-*.json`). This is what prevents this editor's own later save from being stored before admission.
2. **Conflict entry on a confirmed mismatch.** It reuses existing semantics. The candidate's reload after a mismatch keeps A1 as an unsynced device copy behind Reload/Overwrite. The baseline silently dropped A1.
3. **The notice's Open in Runs link is removed** (root refinement 3). `EditorPage.test.tsx` "publishes, surfaces 422 issues…" now asserts exactly one toolbar link and follows it. All repository e2e specs use `.first()` or have a single link.
4. **Neutral conflict copy** (refinement 2). The title is unchanged, so existing tests and e2e that match the title still pass.
5. **Test fixtures.**
   - `fake-api.ts`: PUT and `saveDraftElsewhere` now set or remove the summary `description` as the repository does; `publishElsewhere` was added.
   - `useAutosave.test.tsx`: two held PUT answers changed from non-contract `{draftToken, issues}` bodies to the fake API's own held answer. The assertions are unchanged.
   - The D6 component test overrides the detail's `updatedAt` as the real API stamps it. Without that, jsdom took the conflict path, and the test passed on the baseline (retained in `logs/15`).
6. **Not changed (optional).** For an unknown outcome whose check finds the draft current, the title is "Publish not confirmed" and the body says the version holds the draft. A reviewer might prefer the title "No answer from the server". This is a copy preference, not an observed defect.
7. **Not changed (transient only).** The chain effect pairs the rendered `baseToken` with `getState().generation`. A mismatch is transient and cannot be observed: React flushes the pending effect synchronously before the next render, so no save or unmount can interleave. Using the rendered `loadGeneration` would be equivalent and cleaner.
