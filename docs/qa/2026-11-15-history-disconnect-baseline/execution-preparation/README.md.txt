## Read process, harness and fixture evidence

- `launch-attempt.json` precedes spawn, and `launch.json` binds the direct child PID, process creation timestamp or its readback error, exact executable and argv. `child-exit.json` records the true OS exit before derived readback. `child-close.json` records successful raw stdout/stderr stream closure separately. A preflight or reporting failure has its own receipt once the external receipt directory has been created. Existing outputs are never overwritten.
- The frozen watchdog is 115 seconds. The supervisor records a 135-second missed deadline. With the example’s `stopExactSupervisorOnDeadline: false`, it stays attached and leaves disposition to root. With explicit true admission and a known matching birth timestamp, it can stop only its original direct process handle, without tree termination. The deadline always makes the attempt incomplete. No automatic build or fixture retry is added.
- A completed supervisor disposition confirms the harness’s 8 disconnect, 11 connected positive and 10 negative cases, with the correct baseline or candidate interpretation. The baseline harness expects replay past the observed response close for the non-rejection cases. The candidate requires no further read or write after observed close, and checks connected bytes against the same frozen harness’s accepted baseline. This is instrumented compiled Fastify over actual TCP and file SQLite with synthetic history. Independent QA still reads the exact per-case traces and first failure.
- The supervisor checks the harness’s exact Node PID and all 11 loaded binding entries, closed Fastify/container, zero reported sockets, null remaining listener, closed SQLite exclusivity probe and an actually empty owned store. It deletes no process or file during cleanup. Root can separately verify the recorded process/listener disposition. Keep unresolved owned evidence and report the actual child exit independently of any closing readback failure.
