## The product change (`JsonSchemaForm.tsx`)

1. `clearNumberInput(control)` is new. It sets `control.value = ''` on an `HTMLInputElement`.
2. `OmitButton` takes an optional `reset?: ((control: HTMLElement) => void) | undefined`. Its click handler now looks up the control once by the existing `controlId`, and if found it runs `reset?.(control)`, then `control.focus()`. It then runs `onOmit()`, which deletes the map entry. Before, the handler did `getElementById(controlId)?.focus()` then `onOmit()`, so the only change in order is that the reset comes first.
3. `PropertyField` passes `reset={type === 'number' ? clearNumberInput : undefined}`. Text and JSON fields and the raw JSON editor's Omit pass nothing, so they behave exactly as before.

### Why this, and the lifecycle

- **Cause (matches the review).** An incomplete native number reads `value === ''` with `validity.badInput`. The form holds `''` before and after Omit, because `onInput` records `''` as an edited blank and Omit then deletes the entry, which renders as `''`. React's `updateInput` for `type="number"` assigns `node.value` only when `node.value != value` (with a numeric-zero special case), so it assigns nothing and the browser's buffer survives. This is the installed `react-dom@19.3.0` code (`react-dom-client.development.js`, `updateInput` around L1851).
- **Why an explicit assignment is safe for React.** `trackValueOnNode` (L1738) installs an own `value` accessor on the node whose setter updates the tracker's `currentValue` before calling the native setter. Our `control.value = ''` therefore keeps the tracker at `''`. It fires no `input`, `change` or `blur` event. The next real edit still produces a change event, and a repeated `-` still reaches `onInput` and the `badInput` check.
- **Order: reset, then focus, then forget.** The reset happens before `focus()` (as asked) and before `onChange(undefined)` removes the map entry and Omit button. React batches state updates in the click handler, so nothing re-renders between the three steps, and the render after them sees `''` against an already-empty node and skips its own write. No ref plumbing, no remount, and no change to `Input`, `LabelLine` or any class string. It uses the same `getElementById` lookup the focus step already used, so the element cleared is the element focused.
- **Scope.** Number fields only. A nullable number (`type: ['integer','null']`) goes through the same `propertyType === 'number'` branch. Required numbers still have no Omit and keep their text and refusal, which is correct because the form refuses them.
- **Distinctions kept.** Only the Omit action changed. Absence versus `''`, `null`, `0` and `false` is untouched, and all existing tests asserting it still pass (first and later tests in the same file).
- **Alternatives rejected.** A `key` remount of the number input would lose focus and need re-focusing after commit. A ref or layout effect keyed on `value === undefined` would add a post-render DOM write and a new `Input` ref type. Changing the `onInput` model so `-` is not recorded would drop the "edited blank is refused" behaviour the review accepted.

### Geometry and appearance

No class string, `OMIT_BUTTON`, `OMIT_ROW`, `LabelLine`, placeholder stand-in or layout code was edited, and the coarse 44 × 44 / 12 px gap / 16 px clearance test is byte-identical. This is visible in `patches/product-JsonSchemaForm.patch`. I did not re-measure geometry (that needs a browser).

## Tests

### Native browser regression (written, NOT RUN): `apps/web/e2e/form-controls.spec.ts`

New test: `Omit takes a number the browser holds as incomplete away with its field, on New run and Wait (#235)`, placed after the existing #235 test and before the coarse describe. `playwright test --list` (no browser launched, `logs/08-playwright-list-only.log`) discovers it; the file lists 9 tests (8 existing, unchanged, plus this one).

Schema: optional `note` (text), optional `size` (number), optional `count` (integer), and **required** `limit` (integer). The same schema is used for New run's trigger and Wait's `inputSchema` (the shared component).
Per form (New run: first omit by keyboard then by click; Wait: click then keyboard):

1. `note.fill('keep me')` and `size.fill('0')` (neighbour text and a valid numeric zero).
2. Real key presses: `count.press('-')` and `limit.press('-')`. It asserts through `el.evaluate` that each has `{ value: '', badInput: true, valid: false }`. `value` alone would read `''` throughout.
3. Only `count` shows Omit; `limit` (required) has none. Submit sends no POST and shows `count: enter a number` and `limit: enter a number`.
4. Omit `count`. It asserts Omit is gone, `count` is focused, and the browser's own state is `{ value: '', badInput: false, valid: true }`, with no `aria-invalid` and no error text.
5. Neighbours preserved: `note` still `keep me`, `size` still `0`, and the required `limit` still `badInput: true` with its refusal.
6. Re-edit cycle: press `-` again, `badInput` true and Omit reappears, then omit by the other route and assert the same cleared state.
7. Submit again: still no POST (required `limit` refused). `limit.fill('0')`, then `form.checkValidity() === true` (no control holds text the request would leave out).
8. Start/answer: POST bodies `.input` equal `{ note: 'keep me', size: 0, limit: 0 }` with no `count` property (checked with `not.toHaveProperty`); the Wait body is `{ waitId, input }`; run result is `{ started: input, answered: input }`.

### Unit regression (RUN, passes): `JsonSchemaForm.test.tsx`

`empties the number input itself on Omit, before focus, so incomplete native text goes with the field`. It overlays a stand-in for the editing buffer (an own `value` accessor on the element wrapping React's tracker accessor, plus a `validity.badInput` getter reading the buffer). It asserts that Omit assigns `""` to a node React already holds as `""`, before focus: the recorded events are exactly `['assign ""', 'focus, buffer ""']`. It also checks `badInput` false afterwards, focus on count, no `aria-invalid`, Omit gone, `note` and a valid `size` zero preserved, and the submitted value `{ size: 0, note: 'keep' }` with no `count` property. It ends with Omit of the complete number and of the text field.
It establishes the new ordering logic (React does not assign by itself). It does **not** prove that Chromium clears `badInput`; its comment says so and points to the Edge test.

## Genuine uncertainty

1. **Native clearing is the premise, and I have not observed it.** The fix assumes assigning `''` to a number input that already reports `value === ''` clears its editing buffer in Chromium/Edge. My basis is Chromium's `TextFieldInputType::SetValue` (an editor update when a `kDispatchNoEvent` assignment differs from the inner editor text) and the usual advice to clear a stuck number input with `input.value = ''`; I did not verify this against the installed Edge. The reviewer's reproduction confirms only the failing state. If Edge keeps the text, the fallback to evaluate is toggling `type` (`text` then `number`) or remounting just that input, both heavier; I did not build them.
2. **The e2e test was never executed**, so locator, timing or assertion errors in it are possible (e.g. `fill('0')` onto a field holding `-`; the existing test does the same with `fill('1')`). The typecheck and `--list` only show it compiles and registers.
