## R1-575-1 · P1 · FIX-IN-PR

The short-lived reopened stream in `apps/web/src/runs/useRunEvents.ts` has two different ways of ending. A transport error directly from the open response triggers the new receipt at line 187. A graceful shutdown first yields ordinary EOF. Lines 173–181 clear `openedAt` on that EOF and return. When the next connection is refused, line 187 sees `opened` as false and line 188 returns before recording the loss. The first outage's direct-refetch budget is still spent, even though the stream reopened and a qualified run read recovered the inspector in between.

This ordering occurs in the production protocol. Gateway shutdown ends the HTTP response without a completion frame at `apps/api/src/sse.ts` lines 26, 118 and 126. The client converts EOF into an ordinary stream error, waits, and attempts another connection at `packages/api-client/src/sse.ts` lines 291–306. The ordinary EOF alone should keep its existing behavior. Once the reconnect is refused, the confirmed reopen between outages distinguishes this refusal from retries during a continuous gap.

Submit input stayed enabled. Delivering the held response left it enabled. Implicit form submission then reached the fake API once. The fixture allowed writes to be counted and refused fresh run GETs during the second outage. The result establishes client dispatch.
