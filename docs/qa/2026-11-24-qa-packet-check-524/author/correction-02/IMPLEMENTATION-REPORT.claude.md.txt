**What changed in the checker** (`tooling/scripts/check-qa-packet.mjs`)
- **Selection:** the `git ls-files --modified` step is gone. An unstaged `M` path that is not also staged or committed is now kept only if `git diff --patch --no-ext-diff --no-textconv --no-color -- <path>` produces output. To build that patch, Git hashes the work-tree file the way it would store it, applying attributes, line-ending normalization and the loaded index, then compares contents. A path whose stored content would not change gives an empty patch and is dropped.
- **Read-only:** index refresh stays off (`--no-optional-locks` and `-c diff.autoRefreshIndex=false`), and no Git config is changed. I added `--literal-pathspecs`, because the per-path call passes a file path as a pathspec. Without it, a name like `notes [v2].md` also matches `notes 2.md`.
- **Comments:** the header and function comments now describe this mechanism.

**Remaining limits and gaps**
- **Cost:** the checker now starts one Git process per unstaged-only modified path. A mass line-ending rewrite across many files would start many processes.
- **Large patches:** a real change's patch is held in memory, capped at 256 MiB. A larger patch would stop the check with exit 2 rather than report it.
- **Line-ending format verdict (unchanged design):** formatting is still judged on the work-tree bytes. A real edit saved with CRLF under `eol=lf` is reported UNFORMATTED. That is a false failure, never a false pass, and I left it alone as out of scope.
- **Reasoned but not tested:** three cases rest on my reading of Git's source rather than a test.
  - Mode-only changes are still selected; this host has `core.filemode=false`.
  - Files whose indexed blob already has CRLF are not normalized, because `git diff` uses the loaded index.
  - Binary and very large files are compared by content or hash.
- **Version tie:** the fixture controls depend on Git's current stat and size behavior. I couldn't run `git --version`; the Git 2.49.0.windows.1 figure comes from your brief.
