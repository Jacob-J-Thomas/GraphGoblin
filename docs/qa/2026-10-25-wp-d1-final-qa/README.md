## Defects

### D1: the user guide contradicts the integrated inspector behaviour (severity low, documentation)

- **Reproduction.** Open `docs/guide/03-run-and-observe.md` at the head below and read lines 141, 164 and 192. Then run `node --expose-gc check5-inspector.mjs`, or follow these steps:
  1. Build and start the API with `GG_WEB_DIST` pointing at `apps/web/dist`.
  2. Run a loop whose script you hard-kill mid-dispatch, then restart the API.
  3. Open `/app/runs/<id>`, choose **Recover script**, then **Resume**.
- **Expected** (ADR-0059 and `docs/05-execution-engine.md` line 463): the guide says the inspector offers **Recover script** on such a failed run, with Resume, Replay and Cancel, and follows the resumed attempt live.
- **Actual.** The guide still says:
  - line 141: "The current UI hides controls on terminal runs."
  - line 164: "the current inspector retains its original terminal event and does not restart its live subscription."
  - line 192: "After 1.0: A replay button in the run inspector. Use the API or MCP until then."

  The inspector shows **Recover script** on the failed run. Replay is offered in that dialog. The resumed attempt was followed to `#659` without a reload.

- **Severity.** Low. Product behaviour is correct, and `docs/05` and ADR-0059 already describe it. The guide sentences predate this PR (blame 2026-10-03) but now conflict with the merged behaviour; AGENTS.md requires numbered docs and the guide to stay in sync.

## Observed outside scope (not defects of #320/#321)

1. **Failed parent records keep `waiting`.** A parent that fails at its subloop node keeps `waiting` (`kind:'child'`, `childRunId`, `waitId`) on its run record. This shows in `GET /runs/:id` and in the MCP `list_runs` summary next to `status:'failed'` (`probe-stale-waiting.{mjs,json,log.txt}`, also seen in check 2D). The cause is that `RunManager.failRun` (`packages/engine/src/run-manager.ts` around line 2673) and the `run.failed` branch of `completeFromLog` (around line 2457) do not clear `waiting`. The code is identical on `main` (`fc3e6cee`). The web inspector gates `WaitPanel` on `status === 'waiting'`, so only API and MCP consumers see it. Low severity.
2. **`shutdown-process.test.ts` uses a fixed port range.** `boot()` at `apps/api/src/shutdown-process.test.ts:15` hard-codes 5760–5769 and ignores `GG_TEST_PORT_START` and `GG_TEST_PORT_COUNT`. That is how the first run collided (`EADDRINUSE`) on this shared machine. Its two D-015 Windows cases also skip themselves wherever `taskkill` works.
3. **A parent does not wait for its child's webhook delivery (check 4C).** The parent continued, finished and delivered its own webhook while its child's webhook was still in retry backoff. The child finalized only after the restart. This matches the documented independence of delivery from execution. It is recorded so nobody expects a parent to wait for child delivery.
4. **The Timeline heading can briefly say "live" on a failed run.** In one of the two inspector runs, the first read straight after page load said "Timeline (512 events, live)". The other run said "(649 events, complete)". This is a transient state before `stream.complete` arrives.

Two finishes, failed then succeeded, are correct there. The product data in that run already showed `failed+succeeded` with one child. After the fix (and adding per-trial landing deltas), the whole check was rerun and passed.
- **Check 5, first run** (`check5-inspector-run1-harness-expectation.log.txt`). The script counted a same-document URL change as a reload: the document marker was kept and there was 1 load event. It also compared the Timeline against a `lastEventSeq` (658) read before the finalizer appended `#659 return.delivered`. Reload detection now uses a document marker plus load events, and the check waits for `finalizedAt`. The rerun passed.

The first attempt of check 1 also stopped before doing anything, because the script published before starting the API. That run left no data.
