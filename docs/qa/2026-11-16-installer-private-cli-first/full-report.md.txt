## 2. Introduced candidate finding

### F1 (low): private CLI accepts drive-relative paths as "rooted"

**Reproduction (observed):** the child working directory was `<RUN>\fx\child-cwd` on drive C:, and it contained `rel-config\GraphGoblin.exe.json`, a byte copy of the valid staged config with SHA-256 `70d189b6…`. The command was:

```
<RUN>\fx\stage-exe\GraphGoblin.exe --validate-install --config C:rel-config\GraphGoblin.exe.json
```

| | Expected (strict private shape) | Observed |
| --- | --- | --- |
| Exit | 1 | **0** |
| stderr | `Invalid staged launcher configuration path.` + CRLF | **0 bytes** |
| stdout | 0 bytes | 0 bytes |
| Side effects | none | none (tree unchanged, no canary record) |

The child was PID 15948, born 2026-11-16T05:59:37.3524591Z. It exited at 05:59:37.4251598Z after 72 ms, and its streams closed within 0 ms. Evidence: `work/run-01/receipts/25-C11a.receipt.json`, `.stdout.bin`, `.stderr.bin` and `matrix-outcome.json` → `firstFailure`.

**Cause (source reading, consistent with the observation):** `PrepareInstallation` guards the staged config with `Path.IsPathRooted(args[2])` at `Launcher.cs:147`. It guards the staged link and final EXE the same way at `Launcher.cs:152`. On .NET Framework, `IsPathRooted` is also true for drive-relative paths (`C:x`) and root-relative paths (`\x`), which are not fully qualified. The config was therefore read relative to the process's current directory and validated.

**Reach and impact:** low, and not reachable through the candidate installer (source reading). The installer builds `$stagedConfig`, the staged link path and `$exe` from `Get-InstallerPath` / `GetFinalPathNameByHandle` results (installer lines 247–255, 336, 343–344, 396–398). Those are always fully qualified. The weakness is that the boundary is looser than its "strict argument shapes" contract and its own refusal text claim.

**Not executed:** C11b, the same probe for a drive-relative `finalEXE` under `--stage-shortcut`, was not run because of the stop rule. A **source-only inference, not observed:** `Path.GetFullPath(args[3])` would canonicalise such a path against the current directory and embed it as the link target, config argument and working directory. A drive- or root-relative `stagedLNK` would be passed unnormalised to `IPersistFile.Save`.

**Suggested remediation (design critique):** require fully qualified paths for all three path arguments. Accept only drive-absolute `X:\…` or UNC `\\server\share\…`. .NET Framework 4.x has no `Path.IsPathFullyQualified`, so this needs an explicit predicate. Keep the existing `GetFullPath` canonicalisation of `finalEXE`, which C08 showed works for `sub\..\`. If the owner wants the boundary pinned, a C11a/C11b-style negative case could be added to the permanent Windows PowerShell 5.1 group.

No other candidate defect was observed in scope.

## 11. Design critique (source reading; not observed unless stated)

- **D1. Non-atomic staged write on failure.** `CreateShortcut` saves the `.lnk` and only then stamps the AUMID (`Launcher.cs:466–468`). If the stamp fails, a link without AUMID remains at the staging path, and the process exits 1 with the generic fallback. The installer treats a non-zero exit as a refusal and deletes its owned stage folders, so no defective link would be published. As a component contract, though, "writes the requested staging path" is not all-or-nothing. Not exercised: there is no safe in-scope fault injection.
- **D2. Token-membership dispatch.** `args.Contains("--validate-install") || args.Contains("--stage-shortcut")` routes before the strict positional parse. Observed (C06c/d/e/h): every argv containing an exact token was captured and refused, with no fall-through. Case variants such as `--Validate-Install` are not private tokens and reach the pre-existing normal launcher path, which writes `launcher.log` and shows a MessageBox for unknown arguments. That is pre-existing behaviour, not introduced, and was deliberately not exercised because it raises a modal dialog.
- **D3. Single fallback text.** Malformed JSON, a type mismatch, a missing config and a shell-link write failure all share one fallback message (C02a/b, C05, C10). This is safe and echo-free, but it is undifferentiated. The installer replaces it with its own fixed refusal anyway, so the only cost is diagnosability.
- **D4. Config argument derived from the final EXE.** The staged link's config argument comes from `finalEXE + ".json"`, not from `stagedJSON` (observed in C07/C08). Correctness therefore depends on the installer publishing the staged JSON to exactly `<finalEXE>.json`. The installer enforces adjacency (`$destinations[1].Path -ine "$exe.json"`, line 338).
- **D5. Same validation for both policies.** `--validate-install` uses `Validate(false)`, so `-NoShortcuts` installs still require the Chrome/PWA fields. This matches the implementation note.

## 12. Limits

- **Host:** a single local host (Windows 11 Pro 10.0.26300, PowerShell 5.1.26100.9818, `csc` 14.8.10001.0). This is not the hosted image or the public installer, and not the 32-case matrix or rollback.
- **Process creation:** no ETW or other process-creation trace. Accidental launch detection relies on canary records at the configured Node, ChromeProxy and final-EXE paths, plus direct-child receipts. A start of some other binary, for example a shell default-browser launch, would not be detected.
- **Named mutexes:** the launch and port mutexes cannot be observed after process exit, and their absence was **not observed**. Observed instead: no store directory, no logs, no canary invocation, and prompt exit (≤152 ms). Source shows that private dispatch returns before the mutex code.
- **Dialogs:** no UI automation was used. Every child exited within 190 ms with redirected streams, which is inconsistent with a blocking modal dialog but is not a direct UI observation.
- **Outside the fixture:** side effects outside `fx` were not observed (registry, shell caches, Jump Lists, CLR usage logs under `%LOCALAPPDATA%`). Owner profile, desktop, Start menu and store were intentionally not inspected.
- **Icons:** icon files were nonexistent placeholders, and icon rendering was not tested.
- **Not executed:** C11b, under the stop rule.
- **Concurrent checkout activity** by another actor occurred outside the manifest, as reported in §3.
