## Findings requiring correction

### R2-1. An agreeing cached row hides a newly witnessed terminal event

**P2 · FIX-IN-PR · header-status/uncertified-agreement-suppresses-current-terminal.** On a cold provider with a populated QueryClient, the cache held a successful row at #3. This run had no retained event cursor. The current connection actually delivered `run.finished #3`. The Timeline showed that event, the event store advanced to 3 and the current observation independently returned the same success. While the current run GET was held, the header showed **Updating status…** with no status badge. Once the GET returned the same status and sequence, it showed **succeeded**. This contradicts the original #386 condition precisely where an independently witnessed event must carry the header through a delayed read. A cached-only row with a different, lower progress value already allows the event badge.

The new selector returns a record for an agreeing label before considering whether the row has a current receipt. Lacking that receipt, the wrapper replaces the entire result with updating. The current terminal marker is still available. The supporting selector test at line 90 explicitly expects this loss for equal-sequence agreement. See `apps/web/src/runs/run-header-status.ts:165–175,183–188`, `apps/web/src/runs/run-header-status.test.ts:87–96`, `apps/web/src/runs/RunInspectorPage.tsx:233–242` and the original brief at `../i5-386-root-inputs-01/BRIEF.md:15`. Reproduction and direct cache, Timeline and header assertions are in `terminal-witness.test.tsx:13–42` and `witness-run-02.log`.

**Repair contract.** When a same-run, current-scope terminal event establishes the status at the known tail, render the event label and its sequence while the row lacks a receipt, including when the cached label agrees. Continue to suppress the cached position. Keep the existing cold cursor protection against a genuinely unseen suffix and the uncertainty owed to a later resume. An agreeing authorized read can then switch the position to its qualified record attribution. Add the desired rendered outcome with the GET held.

### R2-2. A foreign returned row borrows a valid earlier receipt

**P2 · FIX-IN-PR · header-row/foreign-id-borrows-same-position.** A genuine response for A established **waiting #3 at real-wait**. A later HTTP 200 on A's GET returned B's ID with the same status and sequence, but a different node. React Query installed this response under A's key. On the unchanged URL for A the inspector displayed B's heading, the **waiting** badge and **at foreign-position**. The tested input is a controlled wrong-ID response. No claim is made that GraphGoblin's normal API generates one. Correct handling of such a successful response is an explicit boundary of this repair.

The query correctly declines to add a receipt for B but still returns the row to React Query. The candidate's new verification compares only status and sequence against receipts already in A's slot. Consequently A's prior receipt certifies B's position. The underlying query's willingness to return a wrong-ID body predates the candidate. The new receipt-based certification and its failure on a warm slot belong to this correction. The existing negative test starts from an empty slot with a different status and sequence. See `apps/web/src/api/queries.ts:139–155`, `apps/web/src/runs/useRunHeaderStatus.ts:29–37`, `apps/web/src/runs/run-header-status.ts:138–141`, `apps/web/src/runs/RunInspectorPage.tsx:225–242`, `apps/web/src/api/queries.reconnect.test.tsx:347–358`. The rendered route, cache key, foreign heading, badge and node were checked in `boundary-witness.test.tsx:25–42` and `witness-run-01.log`.

**Repair contract.** Enforce the requested run identity at the GET-to-cache boundary so a wrong-ID body cannot serve as A's successful row. The existing error presentation can represent a malformed response without clearing A's evidence as definitively deleted. If performing this validation at the presentation boundary, require matching row identity before either badge or position consumes a receipt and ensure the wrong run cannot stand in for the requested run. Exercise the second response after a real receipt with identical status/sequence and a distinct node. Keep successful same-ID responses, cancellation and definitive 404 handling intact.

### R2-3. Same-key recovery can strand an idle waiting run on Updating status

**P2 · FIX-IN-PR · header-auth/same-key-recovery-misses-quiet-run-read.** An already parked run had a confirmed **waiting** badge, node and retained cursor 3. One real in-process HTTP 401 rejected the synthetic key. Entering the same key through the visible API key panel recovered the credential state and opened a second SSE at cursor 3. The server accepted it and had no newer frame. During the following 2.2 seconds the inspector made zero new run GETs and showed **Updating status…**. One explicit test-side invalidation then obtained the available row and restored **waiting at real-wait**. The observed interval is bounded. Source tracing shows the idle stream has no autonomous trigger to resolve the badge until another event, focus, refresh, or other external invalidation occurs.

Credential recovery correctly retires prior evidence. However, the API key panel invalidates active queries on a changed key string only. A successful SSE open sets transport state. A run GET is invalidated on stream completion, unavailability or a delivered batch, and an idle parked run meets neither condition of the run-query timer. The independently passing same-key fixture triggers an extra invalidation itself and supplies a resume event. See `apps/web/src/api/api-key.ts:30–35,54–55`, `apps/web/src/api/ApiKeyPanel.tsx:53–70`, `apps/web/src/runs/useRunEvents.ts:69–76,143–154,188–213`, `apps/web/src/api/queries.ts:159–165`, `apps/web/src/runs/RunInspectorPage.corrective.test.tsx:279–287` and the independent boundaries suite at lines 289–304. The real form submission, resumed stream, request count and recovery control are in `boundary-witness.test.tsx:45–75` and `witness-run-01.log`.

**Repair contract.** On accepted recovery with the same key, arrange one fresh read for the active inspector when it needs a current receipt. Reuse the existing run query and coalescing behavior. Its request must start under the recovered generation even if a previous-generation request is still pending. Keep the existing handling of replacement and forgotten keys, suppress work while rejected, and leave ordinary active-stream polling and reconnect budgets intact. Cover a stable parked run with no new events, no test-driven refresh and a successful current response. Also cover the old-request-overlap variant.
