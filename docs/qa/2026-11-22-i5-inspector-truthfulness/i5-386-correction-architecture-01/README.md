# #386 corrective architecture advice

**Recommendation.** Preserve the newest lifecycle marker, a separate preceding-terminal sequence, and contiguous stream coverage in a bounded, in-memory registry owned by the mounted app providers. Deliver accepted batches and successful observation reads directly to that registry with their source identity. Render one header presentation from its current evidence and the server row. This repairs R1–R3 without changing an API contract, the persisted event window, the run snapshot, or any action authority.

## Decide what the row can support

1. **R1.** In `run-header-status.ts`, fold the maximum valid terminal sequence independently of latest-marker selection and contiguous coverage. Apply this to both accepted stream batches and successful lifecycle observations for the same run and generation. A late failure #3 after resume #4 can improve the predecessor watermark, but cannot replace #4, change coverage backwards, or reinstate failure. An exact duplicate changes nothing. Preserve distinct start/resume semantics where needed: a resume supplies no active phase, and the ordinary initial start retains the existing row fallback. When a prior outcome and its supersession are known, an active row captured before the superseding marker cannot establish the new attempt's phase, including a row whose tail passed the old outcome via delivery bookkeeping. Display neutral **Updating status…** and hide its position until evidence supports a current phase. A subsequent compatible row saying waiting must be accepted on a parked resume. Sequence comparisons, never receipt timestamps, order execution events.
2. **R2.** Evaluate the row's relation to the marker **before** testing status equality. If the row predates the terminal marker, render the marker's actual outcome and its existing event provenance even when both labels read failed. For a same-status terminal row at or beyond the marker, the agreement supports the displayed terminal label subject to the existing unseen-tail rules. It does not certify the node as the current execution position: event append can advance `lastEventSeq` before status or position projection. Preserve the node information as **Last node in run record: X** if the header uses that terminal row. This wording truthfully identifies its source even at an equal sequence. Keep the existing short event qualification in place of a node on event-derived outcomes and omit the node on an unresolved header. Record-backed active positions keep their existing treatment when the row is supported. This avoids manufacturing attempt identifiers or storing full failure/result/position payloads.
3. **R3.** Mount the registry above the pathname-keyed `ErrorBoundary` (`app/App.tsx:49`) using the existing `Providers` lifetime (`app/bootstrap.tsx:24–51`). A bounded map keyed by run ID belongs to that provider's current API client, QueryClient and authentication generation. Prefer the same **20-run limit** as `event-store.ts:119`. Keep only small lifecycle/coverage flags and scalars per run. Evict an old entry on capacity. Expose a stable snapshot and a subscription for the displayed run using the existing React/Zustand primitives. Update it at actual receipt boundaries, outside render. A route switch detaches A's subscriber and attaches B's. Returning to A reads A's retained resume, so an older observation cannot relaunch a terminal badge. No mutable module-wide map keyed only by run ID, new storage, per-run timers, or application data in a query key is needed.

## Receipt boundaries, resets and the cold path

- **Stream.** At `useRunEvents.ts:59–69`, fold the raw accepted batch before payload trimming using the captured run ID and current scope. The normal refresh callback still runs only for an active view. During cleanup `active` becomes false before the last buffered batch is appended. Account for this final already-accepted batch in the old run's still-valid registry entry whenever its cursor is advanced. Otherwise a buffered resume can disappear on navigation and the next subscription starts after it. A connection or generation that was already invalid when a new frame arrived has no write authority. A stream's retained token, current entry identity and event.runId must match. A late callback must never recreate an evicted entry, repopulate a retired scope, or write B from A.
- **Observation.** At `RunInspectorPage.tsx:122–129`, wrap the existing observation query function. At request start capture the current run entry and generation. On a successful response, accept only its validated, same-run lifecycle if the signal and lease are still live; return the original observation response to React Query. Ordinary rendering of `observation.data` continues to serve the existing panels. Merely seeing a cached query value on render never creates new header evidence. Do not use query freshness timestamps, payload object identity or React Query structural sharing as a lifecycle clock. The existing attempt follower also reads the actual whole-run observation; when cold stabilization needs that result, forward it through the **same** collector at the existing successful read, with its abort/generation checks. This reuses network work.
- **Authentication and source identity.** The app client wraps fetch with the current key, so its object alone cannot scope evidence. Use an **opaque, non-secret in-memory auth generation** that changes synchronously on key replacement/forget, first rejection and recovery from rejection, including cross-tab transitions. A small field on the existing auth store, updated at the four state writes in `api/api-key.ts:34,38,40,51`, gives subscriptions and late callbacks the same comparison token. Repeated identical accepted state or repeated 401 while already rejected needs no new token. Explicit forget/reset can retire an already-empty scope. Never put the bearer value, its digest or its storage key in the registry. Replace the provider registry on API client, QueryClient or generation replacement. On rejection, immediately withhold header-derived data, discard the old scope, and keep the existing key/error UI and server controls. Every writing callback checks the captured generation against the live store as well as its entry; this closes the interval before React rerenders. Preserve the existing check on delayed 401s for a previously sent key. The stream already restarts on real key change; bind its lease to the generation so reaccepting the same key cannot keep callbacks tied to a rejected generation. A rejected generation must not open a new stream solely to refresh the header.
- **Run rows and authentication.** The run query remains the source for record-backed status and all server-authorized fields. At a scope change with a still-populated QueryClient, its cached row/observation can be from the retired authorization or client. Suppress a source-derived header claim until the current scope has an actual authorized read or accepted evidence. Where the existing run GET supplies that proof, capture its successful run ID, status and sequence through the existing query function (`api/queries.ts:137`) or the already-running attempt follower; keep this as a small current-scope receipt and require agreement with the row used by the header. The receipt carries no raw row, failure, result or node details. Compare the request's captured generation, even when the library deduplicates or structurally shares a result. In a replacement scope where only the former row is available, retain neutral presentation until current-scope evidence supports the label; showing an event label must not authorize the former row's position. Clear the affected entry on a definitive current-scope missing run. The existing app-wide query reset on forgetting a key is covered by the generation switch. A fresh provider/client after reload or explicit teardown starts empty. A late lower-sequence read is not a reset signal.
- **Cold reload and bounded eviction.** A persisted cursor is evidence that a stream may skip history; it can *prevent* an unsupported promotion. It neither proves a terminal marker is current nor proves every intervening sequence belongs to the current source. On a cold/evicted entry, do not reconstruct current status from cached payloads, selected rows, stale observations, or EOF. If the cached-only row or marker predates an acknowledged tail, use neutral synchronization until an existing same-scope request or stream receipt reconciles it. For the ordinary initial load, a current-scope run read with no contradicting marker or unresolved tail is displayed as before. A fresh terminal row and fresh compatible lifecycle observation settle a stable finished run even when later delivery audits left the cursor past the terminal event. A current stable terminal record that covers the acknowledged tail and agrees with the lifecycle does **not** require replaying every old audit, a new SSE event, or `finalizedAt` before displaying its recorded status. Where a cold persisted cursor belongs to another generation, it cannot permanently overrule congruent current-scope server reads. On normal terminal reconnect the server completes even empty replay at or past its terminal cursor; that already triggers real run/observation reads. Only those reads, or a matching accepted lifecycle event, supply the outcome. Preserve failure/refusal through existing QueryState. No new polling loop, unconditional mount refetch, retry, backend field or rate increase.
- **Recovery and controls.** Compute a single `HeaderStatus` for both badge and position in `RunInspectorPage.tsx`. Pass the unmodified server row to failure/result/recovery/action consumers. Preserve the existing reader's history/cursor and storage version 2. Existing app code covers the pertinent reset and provider boundaries. A hypothetical server reset reusing an immutable run ID without a new client or signal cannot be identified from a lower sequence alone.

## Why this lifetime

A route-local map/ref is destroyed by the keyed error boundary and cannot recover the resume from a stream subscribed after it. Ignoring stale query reads on mount addresses one symptom but discards an actual accepted same-run resume; a cache hit inside the two-second stale time may make no follow-up observation immediately. Using retained Timeline entries fails for history mode, count eviction and oversized payloads. Adding fields to the persisted Zustand store would serialize them under its existing middleware. A WeakMap keyed only by the stable app client survives key rejection/rotation on that same client. The provider-owned bounded registry gives the needed lifetime and a place to retire the whole namespace on a source change. A generic polling or cache migration solution would widen the fix unnecessarily.
