**Verdict: PASS** for PR #418 at `5684e2d5d7eab48b05e6b12327ba1e21d925db0e`, with one minor defect (Q1) that the PR introduces and five pre-existing findings outside its scope (O1 to O5).

# Independent behaviour QA: PR #418, bounded live following (#186 acceptance fix)

On 2026-10-26 I tested the built product of PR #418 through its public interfaces only: the API process (`node apps/api/dist/main.js`), its HTTP and SSE surface, and the built web app in Microsoft Edge driven by Playwright. Each probe used a disposable store under the system temp directory (prefix `gg-qa-418-`) and ports 6560 to 6569. No provider was called: the loops contain no inference node, and both harness binaries point at files that do not exist. I did not change product code or tests. I read the implementer's record [`../2026-10-26-acceptance-fix-186/README.md`](../2026-10-26-acceptance-fix-186/README.md) for orientation only. Every result below comes from my own probes.

D1 from acceptance group B is fixed. Following a long cyclic run live no longer slows the gateway: the followed run and its neighbour kept 90 to 93 events/s against 91 to 97 events/s with no inspector, at about 5,000, 10,000 and 20,000 events. The inspector made no `thread?at` read. Its per-refresh reads kept the same latency and body size at every history length. The run record, the observation panels and the current thread ended equal to the API in every ending and control scenario, none stayed stale after the last event, and the round-2 bounds still hold.

## Defects

### Q1 (Minor): a pending selection read shows an older selection's thread, not the thread on screen before it

This PR introduces the defect. Before it, the selected-thread query also resolved the latest completion while following, so its placeholder was at most one batch old. Now the query runs only for explicit selections, so its retained placeholder is the last explicit selection, however old (`RunInspectorPage.tsx`, `selectedThread` with `placeholderData: (previous) => previous` and `enabled: selectedSeq !== undefined`). I established the before-and-after difference by reading the code; I did not run the base build.

**Reproduction** ([pending-read.mjs](pending-read.mjs), section 2):

1. Start an endless cyclic run and open `/app/runs/{id}` in Edge. Wait for "Current thread".
2. Click a `node.finished Grow` row, for example #2626, and wait for "Thread at event 2626" (`n = 525`).
3. Click **Follow live**. Let the run advance for about 8 s. The panel says "Current thread" with `n = 727`.
4. Click a newer completion, for example #3641. On a long history the read takes up to about 1 s; the probe delayed `thread?at` responses by 2 s in the browser to make the state observable.

**Expected** (docs/09: "A pending read leaves the preceding thread mounted with its own label and an explicit reading note"): while #3641 is read, the panel keeps the current thread (`n = 727`, "Current thread") with "Reading the thread at event 3641…".

**Actual:** for the whole read, the panel shows "Thread at event 2626" with `n = 525`, the selection the reader left. The reading note says "Reading the thread at event 3641…" and the Timeline marks #3641 as current ([pending-read-during.png](pending-read-during.png), [pending-read.json](pending-read.json) `pending.samples`). After the read, the panel is correct: "Thread at event 3641", `n = 728`, with the patch diff.

**Impact:** transient and labelled with its own event number, so it does not misstate which event's values are shown. It does contradict docs/09 and confuses a reader who has just left that selection. A screen-reader user reading the panel meets the old heading. No data is wrong after the read.

## Observed outside scope (pre-existing; not changed by this PR)

- **O1 (Low): opening the inspector replays the whole history over SSE.** A fresh tab subscribes with `GET /runs/{id}/events?after=0` ([bounds.json](bounds.json) `memory.sseRequestsAtOpen`) and receives every event to fill its bounded window. Catch-up took 2.7 s at 5,081 events, 2.2 s at 9,641 and 3.8 s at 20,146, and both runs ran at 60 to 76 events/s meanwhile instead of about 95. It is a one-time, paged cost per open and does not recur while following. It grows with history, though; starting a new tab near the tail (`around=lastSeq`) would bound it. `useRunEvents.ts` is changed by this PR only in its callback signature.
- **O2 (Medium, accessibility): the Timeline's polite live region announces on every stream batch while following.** "Showing events X–Y of the retained window." changed 82 to 86 times in 10 s, about every 120 ms ([a11y.json](a11y.json) `liveRegionsWhileFollowing`). A screen reader would be flooded while following live. The source is `Timeline.tsx`, `<span aria-live="polite">`, which this PR does not touch.
- **O3 (Low, keyboard): Shift+Tab does not leave the Timeline list.** At the window's top row, Shift+Tab moves the window back one row (`Timeline.tsx` `onKeyDown`), so 200 Shift+Tab presses from a row never reached Follow live. Home (the first retained row) followed by 3 Shift+Tab does ([a11y.json](a11y.json) `keyboardBackToFollowLive`).
- **O4 (Low, keyboard and screen reader): Follow live drops focus, and following state is not announced.** Activating Follow live from the keyboard leaves focus on `<body>`, because the button disables itself. When a selection or row focus pauses following, nothing is announced: the Timeline heading keeps saying "live", which is the stream state ([pending-read-during.png](pending-read-during.png)), and only the Follow live button becoming enabled shows the pause.
- **O5 (Info): abandoned historical reads keep running on the server.** Six rapid selections issued 12 `thread?at` reads, and Edge aborted 10 of them ([history.json](history.json)). The implementer already filed this as a follow-up: the server finishes such reads after the client goes away.

## Human QA item

- **The live view no longer shows the latest completion's patch diff.** While following, the panel always shows "Current thread". The reader selects a completion to see its patch, which pauses following. The page gives no hint of this. ADR-0050 records it as the intended trade-off for D1. Whether the live view should say how to see a patch is a product wording choice for the owner, not a defect.

## Probe corrections (for transparency)

- `live-state.mjs` scenario 4, `history.mjs` section D and `bounds.mjs` sections B and C failed on probe errors: a wrong event field; the heading read before the new selection's read finished; a `last` count taken before finalization appended its audit event (608 against the actual 609); and a 7 s stall that ended exactly at the 5 s drain plus 2 s close window. `gate-recheck.mjs`, `pending-read.mjs` section 1 and `bounds-recheck.mjs` repeat each with the corrected assertion, and all pass. The original outputs are kept unchanged.
- `a11y.mjs` was run three times. The first two runs stopped at the Shift+Tab loop, which led to O3. Only the third run's output is kept.
- The first two `pending-read.mjs` attempts used port 6566. Node's fetch and browsers refuse that port (a WHATWG "bad port"), so the API never looked healthy. The first attempt left its disposable store behind, which I removed. The probe now uses 6567.
- `lib.mjs` `startApi` gained a cleanup on startup timeout after the throughput, live-state, history, nav and gate-recheck runs. It does not change a successful run.
