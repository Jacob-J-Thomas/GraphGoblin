**One deliberate difference from the accepted design text.** The design says the claim hook runs in `EditorPage` before its early returns, keyed to "loaded and not staging". I put the claim in a small component that the loaded, non-staging frame renders. The effect is the same set of states, but ownership is exactly "that component is mounted", so it cannot drift from the early-return conditions, `EditorPage` gains no hook, and `EditorPage` does not re-render on connection changes. Say so in review if the literal hook placement is wanted.

Behaviour of the claim: loading, error, `unsupportedBlocked`, `preservationBlocked`, no-definition and voice-staging (the frame is `inert`) states mount no claimant, so the shell banner stays. Release happens on unmount, navigation, an error-boundary replacement and strict-mode effect replay (tested). The layout effect makes the claim before paint so the shell and editor banners are not both painted; jsdom cannot show paint, so that is a native check.

## 5. Not proved: left to independent native QA and later gates

jsdom has no layout, hit testing, paint or screen-reader output. Nothing below was measured:
- **Geometry.** That Undo and Redo keep the same viewport box through content-width changes, wrapping (long name at the boundary, 512×384 at 200% reflow, 768 and 1440 wide), the load-time "Checking…" to "Ready to publish" change, publishing, and connection changes. Design estimates, not evidence, for the first boxes: fine pointer Undo (16, 68, 32×32), Redo (56, 68); coarse Undo (16, 66, 44×44), Redo (68, 66). Header single-row height should be unchanged.
- **Hit testing and the lost click.** The baseline's top-pixel-row press held 250 ms must now deliver the click and change history once; rest-position hit grids; near-edge points; touch taps; the unresolved touch-hold case remains unresolved. The `!important` `translate: none` was verified only against Tailwind's generated stylesheet, not computed style in a browser: check `getComputedStyle(...).translate` while pressed.
- **Banner.** One status only, never two painted, under the editor's toolbar in `offline`, failed-transport and PUT-only-failure cases and recovery; the editor banner does not shift the toolbar; the canvas gives up its height. A possible usability cost to look at: at 512×384 (frame 328 px) a 150–194 px toolbar plus an 80 px banner leaves roughly 54–98 px for the canvas, where before the document grew instead. The banner is a flex child with no `shrink-0`; it relies on `min-height:auto`. Announcement delivery (a `role="status"` inserted into the editor instead of the shell, and the one transfer on entering/leaving a loaded editor and around voice staging) needs a screen reader or accessibility-tree check.
- **Visual alignment.** The slot is 36 px tall and centred on the first row only when that row is 36 px. In a state where Publish and the Runs link wrap to a second row, the first row (breadcrumb, name, badges, save status) is shorter, so its text centres a few px above the history buttons. Undo and Redo themselves do not move; this is a polish question for native or design review, not changed here.
- **Keyboard.** Undo and Redo are now the first Tab stops of the toolbar, before the Loops link (intended by the design, a behaviour change). Check Tab/Shift+Tab, Space/Enter, repeated keys and that `removalFocusTarget` still lands on Undo.
- **Narrow layout.** The slot costs 84 px (108 px coarse) of the bar's width: check 320–360 px, no horizontal overflow, name truncation, and that every control still wraps rather than clips (`e2e/responsive.spec.ts` asserts all four toolbar actions are on screen; `e2e/palette.spec.ts` expects Publish to be the last toolbar stop; `e2e/undo.spec.ts` checks 32/44 px; none was run).
- **Not exercised in the baseline either:** other shell notices (auth, storage, shutdown) moving the editor, offline in a valid-graph state, real text-size enlargement, other engines.
