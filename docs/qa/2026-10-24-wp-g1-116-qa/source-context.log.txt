  /** Read-only thread through the durable event tail; snapshots are verified caches. */
  async getThread(runId: string): Promise<ContextThread | undefined> {
    const checkpoint = await this.ports.runs.getThreadCheckpoint(runId);
    if (checkpoint) {
      const tail = await this.ports.events.read(runId, checkpoint.seq - 1);
      const boundary = tail[0];
      if (boundary?.seq === checkpoint.seq) {
        // One execution token: started/waiting names its open visit. The engine writes a
        // matching node.finished before checkpointing a completion or appending run.finished,
        // so those boundaries have strict replay with no open visit. Recovery can checkpoint
        // other terminal/progress events; their state is ambiguous and needs the full prefix.
        if (boundary.type === 'node.started' || boundary.type === 'run.waiting')
          return reconcileThread(checkpoint.thread, tail, {
            ...checkpoint,
            replayState: { strict: true, openNodeId: boundary.nodeId },
          });
        if (boundary.type === 'node.finished' || boundary.type === 'run.finished')
          return reconcileThread(checkpoint.thread, tail, {
            ...checkpoint,
            replayState: { strict: true },
          });
      }
    }
    const initial = await this.ports.runs.getInitialThread(runId);
    if (!initial) return undefined;
    return reconcileThread(initial, await this.ports.events.read(runId), checkpoint);
  }

## Current thread and resumed history (#116)

`GET /runs/{id}/thread` and MCP `get_run_thread` reconstruct the current thread through
the observed durable event tail, using verified snapshots only as a cache. A delayed snapshot
cannot hide completed patches or an unfinished node's visit count. These reads do not write
snapshots or execution state. `GET /runs/{id}` and MCP `get_run` retain the run-record
projection (status, position, result and failure); the record contains no context-thread
snapshot. Separate reads can observe different event prefixes while execution advances.

A terminal SSE event closes that subscription, not the lifetime of a resumable failed run.
Observers following all attempts first catch up with JSON event pages after their stored
cursor through an observed `lastEventSeq`, then open a new SSE tail if execution is active.
Historical terminal events in JSON pages do not end this catch-up. Lifecycle events determine
whether to follow a live tail when a page overtakes the captured run record. Terminal observation
checks a lagging run record until its status agrees and refreshes metadata without needing another
event. A resumable failure continues checks because another client may resume it; other terminal
outcomes stop once the run record agrees. This leaves return-delivery finalization separate.

### Bounded current-thread reads (#116)

Current-thread reads first request only the checkpoint boundary and its tail using
`events.read(runId, checkpoint.seq - 1)` and verify that the first returned sequence is the
checkpoint's. Bounded replay state follows from the engine's single execution token and write
order: a `node.started` or `run.waiting` names the open visit; a matching `node.finished` closes
it, and an exit's `run.finished` follows that completion in the same append. These boundaries
therefore prove strict replay state without their prefix. Other boundary kinds, a missing
boundary, or an unsequenced snapshot fall back to the full admitted seed/history. This fallback
covers recovery snapshots at failed/cancelled or later progress/delivery events whose open visit
is not established by that event alone. Execution's `loadThread` keeps its existing full history.
The proven state is an in-memory reconciliation input, not a new stored field or migration.

## Inspector contract
- **Run inspector.** The timeline comes from `subscribeRunEvents`; events are kept per run in session storage, so a reload resumes after the stored cursor. A cached terminal event triggers JSON history reconciliation rather than permanently suppressing the stream. After a terminal subscription, finite JSON pages catch up through an observed run cursor; active execution opens a new SSE tail, while resumable failures are checked every two seconds for a resume from another client. Durable lifecycle events choose the tail state if a page overtakes the captured run record; two-second checks then refresh metadata until the record agrees. Success, cancellation and non-resumable failures stop polling once that status agrees. Unmounting cancels observation and discards late responses. Selecting an event reconstructs the thread at that point with `reconcileThread` from `domain` (starting from the initial thread recorded on `run.queued`, and counting `node.started` for node visits, which the engine keeps outside patches); a `node.finished` event also shows its patch with the value before and after each path; reconstruction results are cached per sequence while the log grows (`createThreadCache`, #259), and every shown value is bounded on screen with the whole text and an exact download on request (`BoundedValue`). A progress drawer groups `node.progress`, harness session, usage, decision, and heartbeat events per node. Waiting runs show an input form generated from the wait node's `inputSchema` (or a signal form); cancel, pause, and resume are buttons.
