## 2. Defects

### D1 — Major: isolated event/checkpoint damage still yields a normal run snapshot

This fails the dispatched requirement that `GET /runs/<damaged>` return typed `STORED_RUN_INVALID` or `STORED_EVENT_INVALID`. It is a concrete acceptance mismatch: the reviewed implementation deliberately reads run metadata without checking the full history, so it should be adjudicated explicitly, rather than described as an accidental response-serialization failure.

Steps:

1. Create/publish a manual → input-wait → exit loop; start it and wait for `waiting`.
2. Stop the built API. In the disposable SQLite store, set the first event's `payload` to `'{broken'`.
3. Start a new API process. Diagnostics identifies the run as `HISTORY_UNREADABLE`, and recovery logs the damaged run.
4. Read `GET /runs/<id>` and `GET /runs/<id>/events`.

Expected: the damaged run snapshot returns the typed error required by the QA brief.

Actual: the snapshot returns **200**, status `waiting`, without a damage indication; the event page returns **500 `STORED_EVENT_INVALID`**, with a readable run/sequence/type reason. A separate `thread_snapshot='{broken'` fixture similarly returns a **200** snapshot; `/thread` returns **500 `STORED_RUN_INVALID`**, while its otherwise valid events remain readable. The malformed `waiting` fixtures correctly return typed **500 `STORED_RUN_INVALID`** on snapshot reads.

Affected examples:

- Event: `01M59JBVPMB4RJRRJ9G57RMAGW`.
- Checkpoint: `01M59JBW11B9J7KDP4PGG5M1DP`.

### Manual disposition text and outcome

The guide's literal instructions were followed: stop, repair the named row, restart and recheck diagnostics; for another fixture, make its run terminal before deleting the containing loop. The tested input endpoint accepts `{ "input": ... }` on this head; the different wait-identity body mentioned by another wave is not this branch's contract.

The guide says:

> **Manual disposition:** Stop the API before editing SQLite. Repair the specifically named row by hand to match the current contract, then restart and check `GET /runs/diagnostics` again. Deletion of unrelated loops works while the damaged run is isolated. The damaged run's own loop is deletable once its runs are terminal or repaired. Alternatively, explicitly delete the containing loop using the existing `DELETE /loops/:id` path once all its runs are terminal. That deletion removes the loop and all its history, not just the damaged run; there is currently no individual-run deletion endpoint. If a damaged row still represents active work, manually repair it to a valid terminal run record before choosing loop deletion. Recovery never repairs, archives, reconstructs, deletes, or resets damaged data automatically.

No wrong or blocking step was found in this manual-disposition procedure. It deliberately requires the operator to supply a valid current record; QA used the known fixture's original waiting JSON. The checkpoint deletion case explicitly made the metadata terminal before deletion, and the endpoint removed that loop with 204. The procedure does not imply an individual-run delete endpoint.
