## Defect D1 — major: stale force becomes valid again after phase recurrence

1. Start held script work and request drain. In tab A, open Force stop while phase is draining; retain that confirmation/token.
2. Delay A's shutdown GET responses, allowing the real gateway to reach awaiting-choice.
3. Another control sends Keep waiting, returning the gateway to draining.
4. Release A's GET responses. Its old confirmation remains open because the current draining token equals the token before expiry.
5. Confirm in A. The stale POST returns **202 forcing**, interrupting work, instead of **409 current state** requiring a fresh choice.

This was reproduced through the real REST process and then the Edge UI. The REST proof uses an 800 ms grace; the browser proof uses 15,000 ms and delayed GETs, without changing the product or controller. This violates the requested stale-tab behavior after another choice/intervening phase. Tokens identify an incarnation and phase, but do not distinguish separate entries into the same phase. The delayed force can override a later Keep waiting decision.

Evidence: [REST phase cycle](phase-cycle-proof.json), [browser phase snapshots and confirmation persistence](d1-browser-cycle.json), [accepted browser force](d1-browser-force-response.json), [old confirmation screenshot](d1-stale-browser-confirmation.png), [browser reproduction source](supplemental.mjs.txt), and [responses from that real gateway](browser-cycle-http.json). The run ID, timestamps, identical tokens and accepted 202 are retained in these files. No fix was attempted.
