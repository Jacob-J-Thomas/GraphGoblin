## 5. Source review against the behavioral contract

### Item mode (`packages/domain/src/poll-items.ts` and `apps/api/src/triggers/poll-items.ts`)

**Check order per candidate in `preparePollItems`:**

1. `isJsonValue`, which throws `ITEM_INVALID` for the whole batch.
2. Key expression evaluation, which throws `KEY_FAILED`.
3. Type, blank and over-512-code-unit checks, which throw `KEY_INVALID` for the whole batch.
4. `isPollKeyWellFormed`. On failure the candidate becomes a rejection-only entry `{rejection: {code: 'POLL_ITEM_REJECTED', itemIndex, reason: 'MALFORMED_DEDUPE_KEY'}}` with no `dedupeKey`, and the loop continues.
5. Duplicate check against `seen`, which throws `KEY_DUPLICATE` for the whole batch.
6. Depth classification.

This matches the contract: the whole-batch guards are retained, and malformed candidates are isolated before duplicate tracking and depth classification.

- **Repeated malformed values.** These are never added to `seen`, so they cannot trigger a batch duplicate refusal and cannot starve later work. The native corrected P2 log shows rejections at indices `[0, 1, 2]` for H, H, L, followed by admission of RH and C.
- **Malformed and too deep.** Only one diagnostic is emitted, because depth classification is skipped. The domain test asserts this. On the old source this test would throw `KEY_DUPLICATE` at index 2, so it is a genuine regression test.
- **The whole set is prepared before any I/O.** `admitPollItems` awaits `preparePollItems` before `findSeen` or `start`.

**`admitPollItems`:**

- The lookup receives only well-formed keys, in index order. `findSeen` is skipped entirely when there are none (`keys.length === 0`). The empty-batch result `{runs: [], rejections: []}` is unchanged.
- The seen filter is unchanged for keyed items. Rejection-only candidates are always "unseen", so their warning is always emitted. Previously, a malformed key bound as U+FFFD could be falsely "seen" against a literal-U+FFFD run and silently dropped; see §6.
- Rejections are collected from all unseen candidates in index order, as before. The depth rule is retained: a depth-refused key that is already seen stays silent.
- The admission loop skips rejection-only candidates and depth-refused items before the cap check, so neither consumes `maxRunsPerPoll`.
- `start` returning `undefined` (an atomic reservation found) still does not count toward the cap.
- A `start` throw still returns `failedItemIndex` and leaves the tail.
- A `findSeen` throw still maps to `POLL_DEDUPE_LOOKUP_FAILED` with zero admissions.

**Typing.** `PreparedPollCandidate = PreparedPollItem | { dedupeKey?: never; rejection }`, and `item.dedupeKey === undefined` narrows correctly before `start(item)`. `preparePollItems` has exactly one caller, `admitPollItems`, and `PollItemRejection` and its `reason` union have no other consumers (repository grep).

### Single mode (`apps/api/src/triggers/poll.ts`)

- **Derivation is unchanged.** `undefined`/`null` gives no key. Otherwise the key is the string, or `JSON.stringify(value)`, then `.slice(0, 512)`.
- **The new check runs on the actual sliced key.** For a truthy key, `!isPollKeyWellFormed(dedupeKey)` logs `{loopId, nodeId, code: 'POLL_DEDUPE_KEY_INVALID', reason: 'MALFORMED_DEDUPE_KEY'}` with message `poll trigger failed` and returns `[]`. That happens before `hasDedupe` and before `startRun`, so there is no unkeyed fallback, normalization or shortening.
- **Unkeyed behavior is preserved.** An empty string `''` stays unkeyed, as before. Omitted, null and undefined results also stay unkeyed.
- **JSON-derived keys.** Since ES2019, `JSON.stringify` escapes lone surrogates as ASCII `\udxxx`, so JSON-derived keys can become malformed only when the 512-unit slice splits a valid pair. The post-slice check covers that case for both string and JSON derivations.
- **Payload strings outside the identity are untouched.** The test's `marker: 'outside-identity\uD800'` payload is admitted.

### Predicate

`isPollKeyWellFormed(key) = !/[\uD800-\uDFFF]/u.test(key)` is pure and lives in the domain layer, with no I/O. In `u` mode, a complete pair is a single code point outside the class. I verified equivalence to `String.prototype.isWellFormed()` independently; see §7.

### Warnings and security

Both warning shapes are fixed, typed and carry no payload or key text. Item mode emits at most one diagnostic per candidate, so at most 200 per poll, which matches the existing depth bound. Single mode emits one per poll. A regex over at most 512 code units has no ReDoS concern.

### Contract boundaries

- No new dependency, package, provider behavior, migration, stored-format change or compatibility path.
- `ThreadTriggerSchema.dedupeKey` (`z.string().max(512)`) is unchanged, so historical records stay readable and are not rewritten.
- The webhook and event key paths already refuse ill-formed keys. They do so through the pre-existing API helper `eventKeyIsWellFormed` and the route schemas, and this patch does not change them.

### Non-blocking observations (no action required for this PR)

- **O1 — two well-formedness predicates (maintainability; not introduced as a defect).**
  - The pre-existing `apps/api/src/triggers/trigger-service.ts` `eventKeyIsWellFormed` uses a Buffer UTF-8 round-trip.
  - The new `packages/domain/src/poll-items.ts` `isPollKeyWellFormed` uses a regex.
  - Both have the same semantics; §6.2 covers the new one, and a lone surrogate also fails a Buffer round-trip.
  - The new one is correctly placed in the pure domain layer. Consolidating on the domain helper or `String#isWellFormed` could reduce drift later. This is an optional owning-path cleanup, not a follow-up the patch needs.
- **O2 — user-guide surface (documentation; optional).**
  - `docs/guide/04-triggers.md` and the generated `items.dedupeKey` field description do not mention the per-candidate `MALFORMED_DEDUPE_KEY` refusal, or the single-result `POLL_DEDUPE_KEY_INVALID` warning that permanently refuses a poll whose 512-unit slice splits a pair.
