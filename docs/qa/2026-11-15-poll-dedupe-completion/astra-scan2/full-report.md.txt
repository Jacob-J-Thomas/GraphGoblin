**Item-mode identity validation.** The pure domain predicate uses a Unicode-aware surrogate-range regex. A valid surrogate pair is treated as its full code point, outside that range; an unpaired high or low surrogate is rejected. Existing item keys are bounded to 512 UTF-16 code units before this predicate, so this is a small linear check. It neither normalizes nor substitutes valid identities.

`preparePollItems` retains its existing whole-batch ordering for invalid JSON values, key evaluation failures, non-string keys, blank keys, and overlength keys. A malformed key then becomes a rejection-only entry, without a key or payload, before duplicate tracking and depth classification. Consequently repeated malformed keys cannot raise a whole-batch duplicate error, reach SQLite, or starve later valid candidates. A malformed deep candidate gets the malformed rejection once. A well-formed duplicate still refuses the whole batch, including when its item is too deep. All preparation completes before lookup or admission begins.

`admitPollItems` collects only actual keys for `findSeen` and skips the call when the list is empty. Seen filtering remains exact for keyed candidates, including the existing silent behavior for an already-seen depth-refused key. Rejection-only entries remain visible for diagnostics. Both malformed and depth-refused candidates are skipped before the run-cap check. Only successful admissions increment the cap; an atomic duplicate returning `undefined` does not. A lookup error prevents all starts. A start error retains already-admitted runs and stops the remaining tail. The changed union is narrowed without weakening types or adding `any`.

**Single-mode identity validation.** The new check runs on the already-derived, already-sliced 512-unit identity immediately before the existing lookup/start path. This addresses the case where truncation itself splits a valid pair. It emits the fixed typed `POLL_DEDUPE_KEY_INVALID` diagnostic and returns on malformed identity, with no fallback to unkeyed admission. Existing absent/null/undefined/empty-key behavior and intentional unkeyed starts remain intact; whitespace behavior is unchanged. A valid pair and literal U+FFFD retain their exact identities. An invalid unit outside the effective slice does not alter the existing derived identity. Unrelated payload content is not sanitized or rewritten.

**Admission and recovery boundaries.** I traced the unchanged `RunManager.startPollItem` path through `createPollItem`, the dedupe lookup, run-key scope, SQLite transaction, pending claims, and queued event creation. The patch preserves the transaction that resolves concurrent same-key admission and the scheduler's in-flight/busy behavior. It does not create an alternate reservation path or move the check after persistence. The warning fields are fixed and bounded; they contain neither the invalid key nor payload. Item batches are already bounded to 200. I found no new data disclosure, unbounded regex work, concurrency regression, or cross-package boundary violation in this change.

**Windows cleanup prerequisite #483.** Each of two test hooks adds only `globalThis.gc?.()` before its unchanged recursive temporary-directory removal. The hooks already release the container or restore mocks, and the existing test fork configuration exposes GC. The existing SQLite implementation documentation explains that closed native statements may need collection before Windows file handles disappear. This is consistent with the reproduced cleanup failure and with the corrected pair's result. Assertions, timeouts, retries, coverage thresholds, and production behavior are unchanged. This is a narrowly supported test cleanup repair; it does not establish the cause of the separate subloop timing failure or native worker crash.

The changelog, trigger documentation, and ADR-0079 describe these semantics accurately. There is no schema, stored format, dependency, provider, or compatibility change.
