## Behaviour per issue

### #560: primary startup errors survive cleanup failures

Exclusive lock record (`acquireFile`, used for both the data-directory and database locks):

- The open, stale-record handling, `EEXIST`/held refusal and public lock paths are unchanged.
- After the exclusive `wx` open, a write, attestation (`file.stat`) or close failure becomes the
  primary. The handle is closed exactly once in every case (the old code closed twice on a write
  failure and let a close failure replace the write failure).
- Proof before the sole cleanup unlink: a partial record (write failed) is matched by the
  handle's identity, read with `file.stat` before the close; a complete record (attestation or
  close-only failure) by its exact random-token bytes. Both are checked at the configured path
  with a non-following `lstat`; a non-regular entry or a different identity/record is foreign.
- Proven gone (`ENOENT`) or proven foreign: the in-process `heldPaths` reservation is dropped and
  foreign data is never touched. Identity unavailable (stat failed, inode 0), lookup failure or
  unlink failure: the file and the reservation are kept and the main path is reported as
  retained (`{ resource: 'lock-record', path }`). No destructive call is repeated.
- The guard release still follows once. If it fails, `recovery-release` is appended behind the
  record's own cleanup steps. Pre-open failures (stale refusal, open errors) keep the existing
  generic `cleanupFailure` path ("reclamation cleanup also failed"), and the post-acquisition
  rollback ("rolled back" / "ownership remains held") is unchanged.
- With nothing to report, the original primary object is thrown unchanged.

`createContainer` setup:

- The read-only client's close is in scope: a close failure no longer replaces a guard/catalog/
  store-format failure (it becomes `readonly-database-close` behind it), and a close-only failure
  is its own primary.
- Any failed SQLite close (read-only or mutable) keeps both acquired leases; no release is
  attempted, and both are reported as retained (database lease by database file path,
  data-directory lease by data directory).
- Otherwise the database lease, then the directory lease, are each released once; a failure of
  the first never suppresses the second. A failed release is reported and its lease listed as
  retained. Zero, one or two leases are handled as acquired.
- `dispose()`, `start()` failure teardown, shutdown and `serve()` stop are untouched.

Reporting (`startup-cleanup.ts`, `serve.ts`):

- `StartupCleanupError extends AggregateError`: `primary`, `errors[0]` and `cause` are the original
  failure; `cleanup` holds ordered `{ operation, code, error }` steps with closed labels and vetted
  codes; `retained` lists kept ownership; `errors` holds the original secondary objects.
  `withStartupCleanup` returns the exact primary when nothing needs reporting and flattens a
  tagged primary in causal order.
- `startupFailureCause` classifies only the tagged primary, with the existing closed table.
  Arbitrary `AggregateError` values are not interpreted.
- `shellFailureOutput` prints the primary's usual rendering (known refusals: their explanation,
  escaped where it already was; unknown primaries: `util.inspect(primary)`, the same text
  `console.error(primary)` prints) followed by one control-escaped line of labels, codes and
  retained paths. Secondary messages are never printed.

### #542: own-release successor on Windows

- Right after publication, on win32 only, the caller captures its guard identity with
  `lstat` -> sole own-marker `readdir` -> `lstat`, requiring a physical directory, inode != 0,
  a stable identity and consistency with the staging directory's identity (taken once before the
  loop). The capture never throws; any failure yields "unknown" and changes nothing else. The
  rename `try` now ends at the rename so the capture can never be mistaken for a publication
  failure (`continue` replaces the fall-through; the loop semantics are identical).
- Only when the release read its exact record, itself removed its exact marker, and has a known
  captured identity, an `EPERM` from removing the emptied guard runs #582's positive successor
  check once (`hasLiveRecoverySuccessor`) against that captured identity and own marker name.
  A verified successor completes the release: main lock kept, no extra reclamation claimed,
  `heldPaths` entry for the guard cleared as on any successful release.
- Confirmed absence keeps current success behaviour; `ENOENT`/`ENOTEMPTY`/`EEXIST` and non-Windows
  outcomes are unchanged; unchanged, changed-but-empty, invalid, unverifiable or unknown-identity
  states keep the filesystem refusal and the existing rollback/retained-main route.
- The bypass of the `heldPaths` shortcut is implicit and private: the classification reads the
  physical path; `observeRecovery`, `dataDirLockState` and ordinary acquisition admission still
  consult `heldPaths`, so failed-release reservations stay fail-closed.
- The verified acquisition successor (FUP091) still throws exactly `held(path)`: no cause, code
  or operation (pinned).

### #537: labelled residual reads and probe evidence

- A recovery-marker read that would already escape, after the existing `ENOENT` and Windows
  `EPERM`-then-absent logic, is now `observed-marker-read` (enumerated marker, acquisition and
  read-only status) or `recovery-marker-read` (own marker on release), with the marker path,
  `markerToken` from the path's own name, a vetted code or `UNKNOWN`, and the raw original cause.
  Main owner record reads still throw the raw error.
- `filesystemFailure` now vets every code (`/^[A-Z][A-Z0-9_]{0,63}$/`, else `UNKNOWN`).
- Optional failure reporting was added to `probeRecoveryDirectory` and `hasLiveRecoverySuccessor`
  without changing their decisions, order or defaults. Failed probes (`recovery-directory-lookup`,
  `successor-inspection`, `successor-liveness`, `successor-identity`) are attached to the unresolved
  `recovery-directory-remove` error as `probeFailures` with a vetted code; the raw cause is a
  non-enumerable property, so it stays inspectable but is not printed. A different creation
  identity or an unverifiable shape is a decision and adds no entry. The outer `EPERM` cause, code
  and operation are unchanged; the second disappearance probe and the initial/terminal reads stay
  where they were. No new event or envelope.

## Decisions, deviations and open points

Decisions within the contract (each is a reviewer question, not a settled product decision):

1. Detail wording is `cleanup also failed: <label> (<CODE>), ...; ownership retained: <resource>
   <path>, ...`. It started as "startup cleanup also failed" and was changed before commit because
   the lock module also serves `--reset` and `--create-api-key`, where "startup" would be wrong.
   The class keeps the contract's name `StartupCleanupError`.
2. Retained lease paths name the protected resource (data directory, database file); a retained
   lock record names the lock file itself.
3. A failed lease release is also listed as retained ownership (its real lease stays held), not
   only leases kept after an unconfirmed close.
4. A complete record whose bytes differ at cleanup time is treated as foreign: preserved, and the
   in-process reservation is dropped, matching the existing `release()` treatment of a
   non-matching record (`kept`, reservation dropped).
5. The capture and staged identity run on win32 only. A staged identity that cannot be read makes
   the captured identity unknown (fail-closed to the existing rollback), never a publication change.
6. `filesystemFailure` now vets every code, so an unusual non-string or free-text code becomes
   `UNKNOWN`; real Node codes are unchanged.
7. For an unknown primary the shell output is `util.inspect(primary)` plus the detail line, the same
   text `console.error(primary)` prints, except that a TTY would have colourised the object.
8. Operation labels were chosen here: `observed-marker-read`, `recovery-marker-read`; probe labels
   `recovery-directory-lookup`, `successor-inspection`, `successor-liveness`, `successor-identity`;
   cleanup labels `main-record-identity|close|lookup|unlink`, `recovery-release`,
   `readonly-database-close`, `database-close`, `database-lease-release`, `directory-lease-release`.
9. The rename `try` in `acquireRecovery` was narrowed to the rename itself (with `continue`), so
   nothing after publication can be caught as a publication failure. Loop semantics are unchanged.

Caveats and open points:

- No native contention, controlled filesystem-fault QA of built routes, or native multi-contender
  runs were performed, as the brief reserves them for independent QA. All new evidence is unit
  level with real disposable filesystem state and controlled faults. On Windows the win32 paths
  run natively; on Linux/macOS CI they run with `process.platform` stubbed, as #582's tests do.
- The positive own-release branch was exercised only with controlled scheduling; whether native
  Windows ever reaches it, and the historical #471 cause and frequency, remain unknown.
- `serve()`'s own startup catch still awaits `stop()` and could displace the error; `serve`-to-stop,
  `start()`-to-`dispose()` and returned-container disposal remain outside this slice (documented).
- The Mac attestation paths in `macos-local-key.test.ts` are skipped on Windows; the attested
  success/failure/release-start cases added here run on every platform, and POSIX verification
  relies on CI.
- Two Windows-venue disturbances in the full API run (a load-sensitive 20 s timeout and a libsql
  0xC0000005 worker crash) are not caused by this change as far as the evidence shows; that is an
  inference from the failing cases' content and isolated reruns, not a proven cause.
- Opposite-family (GPT) code review, independent QA, current-target CI and the fresh Astra MAX
  final remain required before merge. #533's separate QA and #582's recorded review history and
  timing exception are unchanged.
