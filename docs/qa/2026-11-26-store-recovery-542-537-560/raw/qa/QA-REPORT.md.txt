## What this QA establishes

- Through the public startup path on Windows: primary error first, cleanup steps as one escaped
  detail line with closed labels and vetted codes, no secondary message text, retained ownership
  named, and files left exactly as the contract says (proven own records removed once; unproven
  ones and their leases kept; foreign/successor entries untouched).
- No lease release after a failed read-only or mutable SQLite close; otherwise database then
  directory lease released once each, second still attempted after the first fails.
- Managed records keep the primary's closed cause (`store-refused`, `store-held`,
  `store-unavailable`) with no path or fixture text.
- The #542 own-release positive branch works natively end to end: published-guard identity
  capture, real CIM creation-time lookup of a live foreign process, main lock kept, successor
  preserved. Unchanged, mismatched and unverifiable states roll back with the original `EPERM`.
- FUP091: the verified acquisition successor still yields exactly the ordinary one-line `held(path)`.
- Ordinary contention still yields one live owner, ownership refusals for the rest and complete
  cleanup.

## Not established / limits

- How often, or whether, native Windows ever produces the own-release `EPERM` with a successor
  present; every `EPERM` here was injected (the successor and its identity were real). The
  historical #471 cause and frequency remain unknown.
- Attestation (`attestLocalArtifact`) is reachable only through the Mac launcher; it was exercised
  at module level (A9) and in unit tests, not on a Mac.
- API package coverage was not run (brief: hosted CI owns it); the author's local ≥90% gate remains
  unconfirmed.
- The D3b observation: the probe evidence on the own-release rollback is attached but not visible
  in default shell output (`[Object]`). See REVIEW R2.
- Contention used 5 contenders × 4 rounds on one machine; it does not bound rarer interleavings.
