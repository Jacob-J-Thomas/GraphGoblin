## Requirement-by-requirement assessment

### 1. Authored mutation failures map to MUTATION_ERROR (met)

- **Narrow wrapping.** `mutations.ts` wraps only the authored calls: `assertMutablePath`, `getAtPointer`, `renderTemplate`, `evaluateExpression`, `evaluatePredicate`, `compileRegex` and `validateJson` (via `authored()` or `.catch(rethrow)`), plus `applyPatch` inside `applyMutations` (`mutations.ts:161-306`, `313-336`). `makeMessage` (`ctx.newId`/`ctx.now`) and `asJson` are outside the wrappers, so ID, clock and serialization faults stay unexpected.
- **Class filter.** The mapper in `mutate.ts` maps only `ExpressionError`, `TemplateError`, `MutationError` and `PatchError`. Anything else is returned unchanged.
- **Repair path.** `runMutations` (`common.ts:266-313`) maps only `TemplateError` from the repair-prompt render (`onPromptFailure`, `common.ts:225-231`) and `PatchError` from the authored target write (`common.ts:307`). `resolveModel` and `structured.complete` errors never reach the mapper, so same-class and same-name provider or resolver exceptions stay unexpected. Tests cover `TemplateError` from both the completion and the resolver, and the functional case `a2-provider-template` covers it natively. Because `repairValue` validates before returning, `completeRepair` cannot raise a provider-result `MutationError` that would then be mapped.
- **Index and message.** `operationIndex` is the absolute loop index `i`. `startAt = pending.opIndex + 1` preserves the authored index across a repair pause; tested at index 2 and observed natively in `a2-after-repair` (`operationIndex 3`). The visible message uses `index + 1`, and the cause is bounded to 1,000 UTF-16 units.
- **Atomicity.** The handler throws before returning a patch, so the manager commits nothing for the failed node. Tests assert this, and functional cases show no partial patch and no downstream Exit.
- **Repair policies.** Unavailable (`DECIDER_UNAVAILABLE`), `OUTPUT_SCHEMA_MISMATCH`, `continue-raw` and the structured timeout are unchanged. They are observed in `a2-no-provider`, `a2-schema-mismatch`, `a2-continue-raw` and the internal late-result-after-repair-deadline case.

### 2. Final invalid ContextThread (met)

There is no per-operation restriction. `/vars` set to a scalar passes RFC 6902 and fails at `ContextThreadSchema.parse` (`run-manager.ts:2730-2747`). The result is `InternalRunFailureError("node <id> produced an invalid patch")`: nonresumable, with no details or operation attribution, and the Zod text goes only to the private log. A later operation that restores a valid thread succeeds (tested).

Shared inference transforms keep calling `runMutations` without a mapper (`inference.ts:307`, `699`), so they stay INTERNAL_ERROR.

### 3. Exit evaluation (met)

`exit.ts` catches only `ExpressionError` from `evaluateExpression(mapping, view)` and converts it to `RunFailureError('EXPRESSION_ERROR', bounded message, { nodeId, resumable: false })`. `threadView` and `toJson` stay outside the catch, and no mutation identity is attached.

The depth guard still throws `ExpressionError` (`expression.ts:167-183`). The 230-level case is tested and was observed natively (`a1-exit-depth`: `"expression exceeded max depth 200"`, no details). The wide-literal success case was observed natively (`a1-exit-width`, 211 rows).

### 4. Public failure projection and private diagnostics (met in code)

- **Single sink.** `failRun` (`run-manager.ts:3039-3075`) is the only producer of `run.failed`. `completeFromLog` only copies an existing terminal event.
- **Projection.** Script classification runs first. Then any INTERNAL_ERROR not supplied as an `InternalRunFailureError` loses `details` and gets `INTERNAL_FAILURE_MESSAGE`. The event and the row receive the same object.
- **No forgery.** `InternalRunFailureError` is not exported from `packages/engine/src/index.ts`. Adapters, ports and stored data therefore cannot forge engine-owned public copy. No plain `RunFailureError('INTERNAL_ERROR', …)` producer remains in package source.
- **Raw logging comes first.** Raw diagnostics are logged before `failRun`, and so before script evidence can replace the classification:
  - outer `tick` catch (`errorDiagnostic` with message, name and stack; `run-manager.ts:1979-2003`);
  - node catch (`2666-2677`);
  - invalid patch (`2733-2736`);
  - no-edge route (`2796-2799`);
  - inference conversion (`inference.ts:773-793`);
  - subloop mapping (`subloop.ts:312-320`).
- **Script precedence.** `classifyScriptFailure` builds the uncertainty failure fresh, so no INTERNAL details carry over. It is observed in the internal `script-dispatch-precedence` case: public `SCRIPT_OUTCOME_UNCERTAIN` without markers, raw cause in the private log.
- **Code, node and resumability preserved per producer:**
  - Outer generic: resumable true, no node (as before).
  - Decider: `InternalRunFailureError` with `{nodeId, details:{code,strategy}}`, default resumable true (as before).
  - Version/node invariants: resumable false, no node (as before).
  - Invalid patch and no-edge: node, resumable false.
  - Subloop mapping: explicit node, default resumable true. Before, the node came from the manager's `toFailure(nodeId)`.
  - Inference: `options.nodeId ?? ctx.node.id`; the existing resumability formula is unchanged.
- **Stop, deadline and cancel.** Order in the node catch is unchanged: forcing → deadline → abort → classification.
- **Production logger.** `apps/api/src/main.ts:21` uses plain `pino({level})` with no redaction. The functional gateway log shows the private message and stack (`a2-provider-error/unexpected-repair-private.json`, PID 46704, run/node correlated).

## Findings

### F1 — Documentation contradicts the new public INTERNAL_ERROR projection and omits its author-facing consequence (in-scope, required)

**Classification.** In-scope documentation blocker under AGENTS.md ("a behaviour change updates the relevant numbered doc") and the brief's criterion that numbered docs accurately distinguish new records from retained history.

**Source.**
- `docs/05-execution-engine.md:477` (Decided resiliency model, "Bug" row): "Run moves to `failed` with full diagnostics."
- `docs/05-execution-engine.md:479`: "Ordinary internal defects retain their full diagnostics." This contrasts with the decider sanitisation of stored failures, so it describes the persisted record.

Both lines predate the PR and were not updated. They now contradict the bullet this PR added at `docs/05-execution-engine.md:103-111`, and `failRun` (`run-manager.ts:3061-3067`).

There is also an omission. ADR-0080 (`:21-24`, `:39-44`), docs/04 (`:193-199`), the new docs/05 bullet and the CHANGELOG (`:7-14`) describe the new projection as applying to "unexpected faults" and "internal run failures". None of them says what happens to authored template and expression errors outside Context Mutation and Exit. Script `args` (`script.ts:40`), heartbeat probe/deadline templates and `until` (`heartbeat.ts`), subloop input mappings and custom output mapping (`subloop.ts:61`, `99`, `139`, `222`), inference prompt/context/file templates (`inference.ts:315`, `364`; `inference-context.ts:58`, `67`) and inference input/output transforms (`inference.ts:307`, `699`) still raise raw `TemplateError`/`ExpressionError`. They remain INTERNAL_ERROR, and new records now publish only "An unexpected error interrupted the run. See the server logs for this run." in place of the author's evaluator cause.

**Reachability.** Every new INTERNAL failure. For the authored-elsewhere consequence, the retained internal QA raw case shows it directly. In `docs/qa/2026-11-15-runtime-failure-candidate/internal/evidence-candidate-first/typed-subloop-mapping.json`, an authored `$error("qa-381-output-mapping")` in a subloop custom output mapping publishes the generic text. The cause `expression failed: qa-381-output-mapping` appears only in `typed-subloop-mapping.private.json`.

**Impact.** An operator or author reading the Decided resiliency model expects the inspector, REST and MCP failure to contain full diagnostics. New records do not, and the docs do not point them to the server log. Authors of non-mutation nodes lose the in-product cause they previously saw, with no documented explanation. This is not data loss or a security defect; the projection itself is the intended, safer behaviour.

**Introducedness.** Introduced by this PR's behaviour change. The text was accurate at `f91bd69b`.

**Minimum required outcome (documentation only, no product or test change):**
1. Update `docs/05-execution-engine.md:477` and `:479`. They should say that newly recorded internal failures carry the safe `INTERNAL_ERROR` message and node/resumability, with raw diagnostics in the server log correlated by run and node. Historical records keep what older builds stored. Keep the decider sentence as is.
2. State in ADR-0080 *Consequences* (or the docs/05 bullet) that authored template and expression failures outside Context Mutation and Exit stay `INTERNAL_ERROR` with their existing resumability. Their new public message is the generic safe text, and the evaluator cause is available in the server log. Name the affected paths at least by node kind: script args, heartbeat, subloop mappings, inference prompts/context/files and transforms. This is the "document affected paths" requirement in `runtime-contract.md`.
3. Optional precision, same edit: `docs/05-execution-engine.md:225` describes the parent message as `subloop child <id> failed: <child message>`. Note that for an INTERNAL child the copied message is the projected safe text. Recognised legacy name/stack and recording diagnostics are not republished.

## Durable follow-up candidates (non-blocking)

- **FU1 — Typed authored failures for other evaluation boundaries.** Script args, heartbeat templates/predicates, subloop input/output mappings and inference prompt/context/file templates and transforms could map recognised `TemplateError`/`ExpressionError` to typed `TEMPLATE_ERROR`/`EXPRESSION_ERROR` with a bounded cause. That would restore in-product author diagnostics now hidden by the safe projection. It is explicitly outside #381 ("not a new general expression overhaul"; inference transforms keep their classification), so it is a candidate issue, not a blocker.
- **FU2 — User guide failure-code table.** `docs/guide/03-run-and-observe.md:298-335` lacks a `MUTATION_ERROR` row. It also lacks 10 pre-existing codes, so the omission continues existing drift. Adding a `MUTATION_ERROR` row is cheap and could ride with F1: correct the operation named in the message and start a replay or new run, since Resume is refused. The guide is not a numbered doc.
- **FU3 — Evaluator deadline versus deterministic error (observation).** `ExpressionError("expression exceeded <n>ms")` (2 s default budget) is now nonresumable in Context Mutation and Exit, like other authored errors. Under severe host contention this could be environmental. Replay remains available, and the spec mandates nonresumable for every recognised `ExpressionError` at these boundaries, so this is recorded for owner awareness only.
