## Correctness and physical-path semantics

**Root cause confirmed.** Node expands `process.argv[1]` to an absolute path but keeps the alias spelling, while the ESM loader realpaths the main module, so `import.meta.url` carries the physical path. The old guard therefore failed through any directory link, and the helper exited 0 with no output. The launcher's `ReadHelper` regex then refused with "could not be checked".

The installer persists `Repo` via `Resolve-Path`, which does not resolve junctions, so an aliased checkout reaches the launcher configuration. This is the user path the fix addresses.

I confirmed the Node mechanism on this host with a self-contained probe (diagnostic D3, below). Through a junction, `argv[1]` was the alias spelling and `import.meta.url` the real path: the old guard was `false` and the native-realpath guard `true`. Direct absolute and relative entries were `true` for both guards.

**The fix is self-consistent.** Both sides of the comparison pass through the same `realpathSync.native` call, so:

- case and 8.3 short names are normalized identically;
- subst or mapped drives are normalized identically;
- a different existing file can never compare equal.

**Fail-closed.** Any resolution failure is treated as "not the entry", so the helper stays inert. The launcher refuses with its existing generic message and never spawns. The unchanged try/catch keeps "invalid configuration → exit 1 + fixed stderr" once the guard matches.

**Inert import is preserved.** `routes/system.ts` imports the module inside every gateway, where `argv[1]` is `main.js`, whose realpath differs. Unit, built and native controls all observe inert import (but see R2 on control strength).

**Fingerprint and identity are unchanged.** `instanceIdentity` is untouched. Every `Repo`-derived field is canonical:

- `entry` is `canonicalPath` of the loader-realpathed URL;
- `webDist`, `dataDir` and a file `dbUrl` go through `canonicalPath`;
- `goblinDist` defaults from the realpathed `import.meta.url`;
- `codexBinary` and `claudeBinary` come verbatim from the shared `Environment`, which is identical across spellings because launcher configs differ only by `Repo`.

So docs/09's "same gateway for the same configuration" holds. Hosted evidence shows identical direct and alias digests for both link types and cross-spelling warm reuse.

**No new filesystem dependency.** `canonicalPath` already calls `realpathSync.native` and rethrows non-ENOENT errors. `instanceIdentity`, which the launcher always calls first, therefore already failed on any filesystem where native realpath fails. See O6 for the cosmetic exit-code difference.

**Store ownership and no-write behavior are unchanged.** `launcherStoreState` and data-dir locking are untouched. Built and native tests assert the stores stay empty before cold launch, and the alternate wrong store stays empty.

**Races and reuse.** The helper is stateless. The launcher serializes on `Local\GraphGoblin.Launch.<hash(DataDir)>` and `Local\GraphGoblin.Port.<port>`. Neither key includes `Repo`, so concurrent alias and direct launches for the same store and port serialize, and no cross-spelling double-spawn path exists.

**Side effects.** The only change is two synchronous `realpath` syscalls at module evaluation (including in the gateway via `routes/system.ts`): no writes and no network. A hang would require `argv[1]` on an unreachable filesystem, from which Node could not have loaded the module.

### In-scope, non-blocking recommendations (P3)

**R1 — `docs/10-testing-and-quality.md` was not updated for the new native case and its host prerequisite.**

- *Root cause.* The opening paragraph enumerates what `pnpm test:windows-launcher` covers. This PR adds the junction/directory-symlink alias case without updating that list. The case also creates a new, deliberate host requirement. Without directory-symlink privilege (a non-elevated host without Developer Mode, as this batch's own local host showed with EPERM), `symlink(repo, alias, 'dir')` throws at `create-alias` and the SymbolicLink subtest fails rather than skips. That is correct per the brief (never relabel capability refusal), but it is undocumented.
- *Impact.* Developer confusion only; CI is unaffected. AGENTS.md asks to keep the relevant numbered doc in sync.
- *Disposition.* Add one or two sentences to docs/10: what the alias case covers, and that it requires symlink-creation capability and fails rather than skips without it. This is docs-only and could be folded in before the Astra final audit without touching product or test bytes. Alternatively, root may explicitly defer it.

**R2 — The inert-import controls in the built and native tests take trivially-false paths.**

- *Root cause.* The built test imports under `-e` with no script, so `argv[1]` is `undefined`. The native test passes a `file:` URL string as `argv[1]`, and `realpathSync.native` returns ENOENT. Neither exercises the realpath comparison against a different existing entry file. Probe D3 confirmed both paths.
- *Coverage that does exist.* That branch is covered by the unit test (`isLauncherIdentityEntry(fileURLToPath(import.meta.url), moduleUrl) === false`) and implicitly by every gateway start.
- *Impact.* None on the current correctness claim; the inert-import property is observed. The controls are weaker than their names suggest.
- *Disposition.* No change required. Optional strengthening: a built control that runs a real wrapper script as `argv[1]` which imports the aliased helper.

**R3 — Records: PR body, issue and in-repo packets still describe fixed-source symlink acceptance and CI as pending.**

- *Root cause.* At publication time, PR #492's body said fixed-source genuine symlink acceptance "remains a hosted Windows gate". The issue #435 checkpoint says CI "is in progress". The candidate packet and register say "not yet observed / pending". All were accurate when written. The fixed-source hosted pass now exists only in the external batch packet.
- *Requirement.* `qa:touched-systems` (docs/15) requires pass/fail results with evidence in both the PR and the issue.
- *Disposition.* Root-owned. Record the run 43790735875 / job 133048320156 result in the PR and the issue before merge. Archive the hosted candidate packet and this review in the next publication, per this batch's #419 precedent. While there, change "…formal review (0 of 3 scans used) remains pending" in the register to "remain".

### Pre-existing or out-of-scope observations (no action required for #435)

**O1 — The same entry-guard defect exists in repository gate scripts (follow-up candidate, P2/P3, unverified impact).**

- `tooling/scripts/gen-docs.mjs:110` (backing `docs:generate` and `check:docs`) and `tooling/scripts/check-migrations.mjs:104` (backing `check:migrations`) use the `resolve(argv[1])` vs `import.meta.url` pattern. `tooling/perf/summary.mjs:375` uses a close variant.
- Probe D3 confirms the Node-level mechanism on 22.23.4. Run through an aliased path, these scripts would exit 0 without doing anything, which for `check:docs` and `check:migrations` is a vacuous gate pass.
- I did not verify whether pnpm passes an aliased cwd to Node. CI uses real directories and is unaffected. `apps/api` `main.ts` and `emit-openapi.ts` use basename-regex guards; `apps/mcp` and the plugin CLIs use realpath guards. Both kinds are alias-safe.
- *Disposition.* Dedupe, then file a separate issue. Do not absorb into #435. A bounded diagnostic could be admitted: run `pnpm check:docs` from a disposable junction to a disposable clone, never this checkout.

**O2 — The Windows job's `upload-artifact` step finds no files (pre-existing; seen in the #419 and #435 runs).**

- The path is `.tmp/windows-launcher-*/`. A plausible but unverified cause is `actions/upload-artifact@v4`'s default exclusion of hidden files and directories (≥ v4.4).
- The new alias test writes its sandbox to `%TEMP%` and records evidence in the job log, so it is unaffected.
- *Disposition.* Optional CI follow-up; not #435.

**O3 — Native-suite residue.**

- The new test leaves `%TEMP%\graphgoblin-launcher-alias-*`: compiled exe, drained stores, configs, gateway logs. This is consistent with the original suite's no-delete design and avoids recursive deletion near a link to the checkout.
- When release cannot be verified, the link is deliberately kept so a possibly live gateway's cwd is never pulled out from under it.
- After a failed local run, remove any leftover link itself (not recursively through it). Informational.

**O4 — Port-window headroom.** The original suite uses 14 ports of the fixed 20-port window starting at 4830; hosted alias ports were 4844 and 4845. The new test uses 2, leaving 4 spare. `GG_TEST_PORT_START` exists for crowded hosts. Informational.

**O5 — Four near-duplicate entry guards across apps.** `isLauncherIdentityEntry` uses `realpathSync.native`, matching `canonicalPath`; the mcp and plugin CLIs use JS `realpathSync`. Both are correct for this purpose. Consolidation would cross app boundaries and is a separate refactor. Informational.

**O6 — Filesystems where `realpathSync.native` fails (some RAM-disk/virtual drives, volume-GUID-only mounts).**

- The guard now degrades to inert (exit 0, no output) instead of the old explicit exit 1 plus diagnostic.
- This is not a new failure class: the old `instanceIdentity` → `canonicalPath` → native realpath already failed there. The launcher reads the digest first and shows the same generic refusal either way.
- Explicit dispatch (the issue's alternative) would remove guard ambiguity but is a broader design change. Informational.

**O7 — Run-level CI qualifications are carried forward, not reopened.** Audit 8 low / 13 moderate (threshold passed); Browser optional strict performance off, with drag p95 33.3–33.4 ms above the optional 17 ms target; one declared live-provider skip; no native artifact. None is attributable to this diff.
