## #434 corrective report: reset output when a lock can't be taken (candidate `a8191dd9`)

The fix is done and the regression is confirmed both ways. On the held source the new tests fail and the real CLI prints the false "Nothing in the data directory was changed."; on the corrected code everything passes. Nothing is committed, HEAD is still `a8191dd9`, and no Git, owner-store, secret or other-worktree state was touched.

**The defect:** the lock module throws a plain error when taking a lock fails, and doesn't say what it left on disk. `reset.ts` decided "something changed" only from locks it was holding and stale entries that had disappeared since the preview. So when an attempt *created* a lock file and guard and then failed to clean up, the CLI said "Nothing in the data directory was changed." I reproduced this with the real built CLI at both levels: the data-directory lock and the database lock each left the lock file, the `.reclaim` guard and its marker. Store data and unrelated files were untouched.

### What changed (`apps/api/src/reset/reset.ts` only; the lock module is left to #471)
- **Typed result:** `ResetRefusedError` now carries one of three outcomes: `unchanged`, `changed` (with lines), or `uncertain` (which lock failed, with lines). Previously an empty list of strings meant both "verified unchanged" and "unknown".
- **Failed attempt to take a lock:** the reset checks that lock's file and guard just before each attempt and again after a failure. The refusal then:
  - starts `could not take the data-directory lock:` or `could not take the database lock:`, replacing the old `; stop it before resetting` suffix;
  - says `No store data was removed.` and that the attempt may have created, reclaimed or left the lock's file, guard or guard staging directory;
  - lists the file and guard as, for example, `present now, absent before the attempt`;
  - for a database-lock failure, also says what releasing the data-directory lock did.
- **What it never says:** it never claims who changed an entry, never claims a removal it didn't verify, and never tells the operator to delete a lock. If an entry can't be inspected, it shows only the raw error, not tree.ts's "move or remove that entry yourself" advice.
- **Unchanged behaviour:** read-only refusals before any lock is taken, dry runs, refusals after both locks are held, partial-removal failures and successful resets behave as before. The fault-free CLI output is byte-identical to the held build's.
- **Deliberate trade-off:** any failed attempt is now reported as uncertain, even an ordinary one that changed nothing (another process holding the lock, or a database with a hard link outside the data directory). Previously these said "Nothing changed". The reset can't tell such a refusal from a partial failure, so it lists the lock file and guard as found, e.g. `absent now and before the attempt`.
