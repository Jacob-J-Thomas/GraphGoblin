### F1 — Major: inherited labels remain stale while fresh runs use changed owner Settings

1. Open an inherited inference or Codex LLM node with process model/low and no owner override.
2. Keep the editor open and PUT owner defaults to another model/high. The first reproduction also opens Settings in another Edge tab and returns focus to the editor.
3. Start a new published run before reloading the editor.

Expected: the visible model and inherited effort follow Settings and match the new run. Actual: the editor continues to show `gpt-6-luna / Default (low)`; run `01M5PAAC2TNVN0QMHAKQ9CQK5V` requests `gpt-6.1-sol / high` and succeeds. Reload changes the label to high. The first check remained stale for 20 seconds; targeted reproductions also establish the mismatch for Codex LLM and Claude inference.

Evidence: [owner-stale.png](./owner-stale.png), [supplemental-checks.json](./supplemental-checks.json) “Changed owner default compared with fresh run”, [diagnostic-checks.json](./diagnostic-checks.json) both “Owner default stays current” records. This establishes the open-editor behavior tested; it does not assert that every possible later browser-focus event fails to refresh.

### F2 — Major: capability-only unsupported Claude effort reaches the fake adapter

1. Leave Opus catalog support for high intact; publish a Claude read-only inference with inherited high (repeat with explicit high and valid owner low).
2. Change the injected ready Claude preflight capabilities to low only.
3. Open the editor and run the published definition.

Expected: unsupported retained high is refused before an adapter request, as required by the supplied supported/unsupported cases. Actual: the dropdown correctly offers only low and marks `Default (high) (not supported by this model)`, but run `01M5PADMYREWWMY99QRJNA8QG0` succeeds and the fake receives `claude-opus-5-5 / high`. Explicit high has the same result. This is a discrepancy between the UI’s ready-capability claim and the engine-to-port request; it does **not** establish that a native Claude CLI would accept that request. Catalog-based unsupported efforts are correctly refused.

Evidence: [capability-only-true.png](./capability-only-true.png), [capability-only-false.png](./capability-only-false.png), [diagnostic-checks.json](./diagnostic-checks.json) both “Claude capability-only refusal” records and [supplemental-checks.json](./supplemental-checks.json) capability intersection record.
