## 1 · Conflict resolution: `useAutosave.ts`

The only conflict was the `save` callback. The conflicted working file is kept as [useAutosave.ts.conflicted-working](backups/useAutosave.ts.conflicted-working) (sha256 `2221a18d…`).

The resolution takes #209's structure:

- `save(retry?: NameRetry)`
- `settle()` on every early return and in `try/finally` around the queued `send()`
- a `permit` kept only for the matching loop and generation, spent by one request
- `deliberate`, and the removed generic branch that cleared another attempt's `retrying`

It re-applies #237's three in-body changes:

- the per-hook `chain` advance for the same generation
- `recordSaved(queryClient, …)` with refresh after an accepted write
- `setSaveState('saved', …, { revision, definition: saved.draft.definition, token })`, the acknowledged definition

I checked this mechanically:

- **Resolved vs theirs** differs only by #237's delta: imports, no `latestTokens`, the `recordSaved` signature and docs, `CONFLICT_MESSAGE`, `chain`, the unmount save on its own generation, and the ack payload.
- **Resolved vs ours** (`-w`) differs only by #209's delta.
- There is no global `latestTokens` and no `retrying`-as-permission. `retrying` only drives the busy display in `NameConflictNotice`.

The other `flush` callers (`usePublish`, `useResolveConflict`, the debounce timer, the recovery and online events) all call `flush()` with no permit. So a generic save cannot consume a deliberate retry.

## 2 · Confirmed defect: awaited readback could bypass the dispatch check

**Cause.** In the e12 code, the queued job checked the load and refusals once, then `await readBack(...)` when `checkFirst`, then POSTed with no second check.

**Fix.** One local `sendable()` check: same loop and generation, otherwise `undefined`; then `refusal()` (held input, draft conflict, name refusal), which throws. It runs when the queue reaches the attempt (as before) and again immediately before `loops.publish`, with no await in between.

What each path after the check does now:

- **Check failed:** unchanged. The outcome is unknown with `sent: false` and nothing is posted. The next Publish still checks first.
- **Current version holds the acknowledged draft:** unchanged. Nothing to publish, no write. With held input the notice adds "changes made after that are not published".
- **Mismatch, but the load was replaced meanwhile:** returns `undefined`. Nothing is sent and the new load shows nothing. The old attempt's outcome never reaches it, through the existing `ours` filter.
- **Mismatch, but held input, a conflict or a name refusal appeared meanwhile:** the refusal is thrown and shows as **Publish failed** with the editor's existing wording. No POST is sent and the held input stays local. A later explicit Publish proceeds as usual, because the successful check has already settled the unknown outcome, consistent with the existing "check OK → Publish again" path.
- **Healthy:** exactly one POST after the check.

Acknowledged-content capture, immutable version comparison, divergence → conflict, refresh, queue semantics and notice wording are unchanged.

## 7 · Observations not changed (for root and the reviewer)

1. **A "Publish failed" refusal stays until the next Publish attempt.** In the fresh-retry screenshot, the earlier "Publish failed — Another loop already has this name…" remains after the name was accepted. The same applies to the held-input refusal after the input is discarded. It is not a readiness claim, and I left it unchanged as outside the confirmed scope.
2. **Unconfirmed, source-level only: an earlier refusal clears check-first.** After an unknown outcome whose check failed, a Publish refused *before* its check (held input at click or at the queue turn) replaces the mutation data. The next Publish then has `checkFirst: false` and sends without reading the server first. This is pre-existing in phase1. My fix adds no new path of this kind: a refusal after the check only happens once the check succeeded, and a failed check still returns an unknown outcome with check-first preserved. It was not natively reproduced and I did not change it. Root may decide whether it warrants a separate item.
