## FIX-IN-PR · P2 · Re-observe a guard when its enumerated marker disappears during the read

At `apps/api/src/data-dir-lock.ts:245–248`, a marker read returning `absent` passes that state straight through as the enclosing guard's state. This can happen after a real `ENOENT` and after the Windows-specific independent proof that the exact UUID marker disappeared. At lines 389–402 acquisition skips the stale branch and publishes immediately. On macOS, renaming a directory over an existing empty directory succeeds. The caller can therefore remove the original guard through rename while returning `reclaimed.guard === false`. The new loop correctly re-observes when it loses a marker during unlink at line 395. Losing the same marker earlier during read needs equivalent handling. The existing marker-read test at lines 129–143 establishes acquisition and cleanup but omits the accounting assertion.

I ran the public `acquireDataDirLock` on the parent and candidate with native macOS filesystem calls and no platform, PID, WMI or errno substitution. The fixture schedules a concurrent actor's unlink just before the candidate's real read of an enumerated UUID. A native stat immediately before rename and after publication identifies the original directory by inode. Three schedules ran on each revision.

| Scheduled action | Parent reports guard reclaimed | Candidate reports guard reclaimed | Physical result |
| --- | --- | --- | --- |
| Other actor removes only the enumerated marker | true | **false** | The candidate's rename replaced the original, still-present empty guard with a different inode. The parent removed the original guard explicitly. |
| Other actor removes the marker and enclosing guard | false | false | Each revision published to an absent path. |
| Other actor leaves the stale marker in place | true | true | Each revision removed the stale guard and published its own. |

All six acquisitions and releases succeeded and each fixture finished empty. The interleaving is deliberately scheduled and uses a private fixture. The observed discrepancy is a native filesystem outcome. It does not depend on reproducing the incidental Win32 interleaving from the failing historical run.

I also ran the production `resetDataDirectory` entry point against two private, empty-store fixtures, selecting the corresponding exact-revision lock module. Both performed two read-only marker reads before the scheduled removal during acquisition. Both exited zero, removed zero store bytes and retained the unrelated fixture file byte-for-byte. The parent printed “reclaimed when the reset took the data-directory lock”. The candidate printed **“already gone when the reset took the data-directory lock”** while stat still identified the original empty guard as the rename target. The manifest consumes the returned flag at `apps/api/src/reset/reset.ts:622–635`. The post-acquisition refusal formatter also consumes it at lines 804–814. The success manifest was executed; the separate refusal formatter was inspected in source.

**Finite repair.** Distinguish an absent guard directory from an absent enumerated marker. Re-observe the guard, within the bounded acquisition loop, when its marker disappears before reading ownership. On the next observation, remove and credit an observed stale empty directory when this process actually removes it, proceed after true guard absence without credit, or preserve a successor owner. Keep public read-only ownership checks bounded. Add a public-method regression for the marker-read disappearance with the directory still present, plus a control for disappearance of both entries. Retain the normal stale, lost-unlink, live-successor, persistent-denial and private cleanup controls. High confidence. No second writer or lost user data was observed.
