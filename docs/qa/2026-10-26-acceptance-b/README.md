### D1 (High): an inspector following a long run live starves the gateway

**Summary.** While the run inspector follows a running loop live, each event batch triggers about five server reads. One or two of them are `GET /runs/{id}/thread?at=N` reads that replay the history from the run's initial thread, so each costs time proportional to the history. The single-threaded gateway saturates. The observed run, and every other run on the gateway, slows by an order of magnitude, and the slowdown grows as history grows. #186 round 2 introduced this: before round 2 the inspector read the thread once and rebuilt selections in the browser.

**Reproduction** ([p186-compare.mjs](p186-compare.mjs), [p186-rate.mjs](p186-rate.mjs), [p186-neighbour.mjs](p186-neighbour.mjs), all on the built API with a disposable store):

1. Create and publish the cyclic loop from [defs.mjs](defs.mjs): `cycle({ passes: 1_000_000 })`. A mutate node increments `vars.n`; an expression gate repeats with `maxPasses: null`; `maxNodeVisits: null`.
2. Start a run and let it pass about 4,000 to 11,000 events with no inspector open. Sample `GET /runs/{id}` `lastEventSeq` for a minute: about 120 to 160 events/s.
3. Open `/app/runs/{id}` in Edge and leave it following live. Sample again.
4. Click Load older (history mode) or close the tab, and sample again.

**Expected.** Watching a run does not materially change its execution rate, as on the pre-round-2 build `aa8b2348`: 156.4 events/s without the inspector and 158.5 events/s with it following live.

**Actual on `d42e859f`:**

| Measurement                                           | Rate                                                                                               |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| No inspector                                          | 126 to 160 events/s (one 60 s sample at the start of p186-compare read 66.5 on the shared host)    |
| Inspector following live, about 4,000 to 5,000 events | 12.1 events/s                                                                                      |
| Inspector following live, about 9,000 events          | 3.9 events/s                                                                                       |
| Inspector following live, about 11,000 events         | 4.0 events/s, and an unrelated second run on the same gateway also fell from 126.3 to 4.0 events/s |
| Inspector in history mode                             | 151.1 events/s                                                                                     |
| Inspector closed                                      | 117 to 160 events/s                                                                                |

In 90 s the inspector issued 882 `thread?at` reads and about 480 each of `/runs/{id}`, `/thread` and `/observation`. The pre-round-2 inspector issued 312 `/runs/{id}` reads and 1 `/thread` read.

**Cost per read** ([p186-cost.json](p186-cost.json)). `thread?at=tail-1` on a running loop took a median of 163 ms at about 2,000 events, 464 ms at about 6,000 and 752 ms at about 10,000. On finished runs, `at=last-1` took 1,194 ms at 10,008 events and 973 ms at 20,008, while `at=last` (served from the checkpoint) took 3.5 to 47 ms and the current-thread read took 3 to 47 ms.

**Cause, from code reading.** `historicalThread` in `apps/api/src/run-history.ts` (lines 33 to 64) uses the run's single stored checkpoint only when it precedes `N`. The executor rewrites that checkpoint after every node completion (`packages/engine/src/run-manager.ts`, lines 2395 and 2414). So the completion diff read `at=N-1`, and any `at=N` already behind the newest checkpoint, replays `N` events in 128-event pages. `docs/07` documents the read as proportional to the prefix, but the live inspector issues it on every update.

**Severity: High.** Sustained loops are central to the POC (#287: long-lived loops remain observable and responsive), and the effect reaches every run on the gateway and grows with history. No data or ordering is lost, and closing the tab or switching to history mode restores the rate.

## Observed outside scope

- **O1. Expression failures are reported as internal errors with a stack trace.** A mutate expression that fails (`$error(...)`) fails the run as `INTERNAL_ERROR`. Its `failure.details.stack` holds a full stack trace with the absolute install paths of the built packages, visible through REST and MCP. The cause is the generic mapping in `packages/engine/src/run-manager.ts`, lines 2278 to 2293. A typed expression failure code without the stack would be expected. Severity: Medium (an information leak and a misleading classification).
- **O2. Every cancellation in trusted mode is recorded as `user local`.** REST, MCP and UI cancellations all record `run.cancel_requested` with actor `{kind:"user", id:"local"}`. The contract's `mcp-client` actor kind is read in `apps/api/src/routes/runs.ts`, line 48, but no route produces it. The inspector reports what was recorded, so #255 holds; whether MCP-initiated actions should be attributed separately is a product question. Severity: Low.
- **O3. Raw Node `net` sockets read SSE slowly on this host.** A raw `net` socket reading the 23.8 MB replay on Windows loopback takes about 73 s, while fetch/undici takes about 0.5 to 1 s and curl takes 0.7 s ([p186-throughput.json](p186-throughput.json), [p186-throughput2.json](p186-throughput2.json), [p186-throughput3.json](p186-throughput3.json)). This is a client-side TCP artefact; the api-client, curl and Edge are fast. Informational.
- **O4. The run page hides its last evidence during an outage.** While the API is unreachable, the run inspector replaces the whole run page with an Offline notice, so the last-known pending delivery is not visible until the API returns. It claims nothing false. Severity: Low.
