## 4. Production correctness

**The change.** Before this change, both failure projections omitted the `waiting` member. Cancellation (`finalizeCancel`, the `run.cancelled` branch) and authored exits (`finish`, the `run.finished` branch) already passed `waiting: undefined`. Failure now matches them in both places:

- Live: `failRun` → `transition(ACTIVE_STATUSES, { status:'failed', failure, finishedAt, waiting: undefined })`. This covers every failure caller: node failures, invalid patch, missing edge, deadline (`expireRunDeadline`, in-executor), force-stop `interruptRun`, executor crash, missing version and upgrade refusal. It also covers `failRun`'s internal delegation to `completeFromLog` when a terminal event already exists.
- Event-first reconstruction: `completeFromLog` builds `{ status:'failed', failure: terminal.failure, waiting: undefined }`, then spreads it with `finishedAt`. Spreading keeps the own-but-undefined member.

These are the only two writers of failed run status in non-test engine, infrastructure, API or MCP source (`grep "status: 'failed'"`).

**SQLite NULL-clearing contract.** `SqliteRunRepository.transition` and `update` share `toColumns`, which iterates `Object.entries(changes)` and maps `undefined` → `null`. The guarded `UPDATE … RETURNING` writes SQL NULL. `run-row.ts` decodes NULL to an absent member. `storage.test.ts` pins `update({waiting: undefined})`. W1/W2 prove the native SQL NULL and the absent REST/MCP field. The in-memory fake deletes keys on `undefined`, which matches the decoded SQLite shape, so `not.toHaveProperty('waiting')` is a faithful oracle.

**Preserved:** failure code/message/node/resumability/details/script (same object in row and event, checked natively); `currentNodeId` (not touched; W2 `current_node_id: 'call'`); child linkage (`parentRunId`, `failure.details.childRunId`); pinned version/definition (W2 `version_id`/`pinned` byte-equal); finalization path; event order. Event drafts and append order are unchanged. W2 events after restart are byte-identical to the landing proof.

**Who reads a failed run's `waiting` (the regression surface).** I traced every reader:

- `notifyParent` and `wakeRun` require `status === 'waiting'`. A failed parent was never woken through its stale wait, so no wake decision changes.
- `deliverTimer`, `waitForDrain`, `reconcileChild`, `provideRunInput` and `signal` all gate on waiting/paused status. Timers are cancelled at finalization. There is no behavioral change for terminal rows.
- `reviewedChildRecovery` uses `failure.details.childRunId`, not `waiting`. Recovery-facts agreement (ADR-0061) compares lifecycle status and failure, not `waiting`.
- Web `WaitPanel` renders only for `status === 'waiting'`. MCP `describe`/`get_run`/`list_runs` include `waiting` only if present. This is the intended public change.
- **Resume (substantive check).** `completeResume` (failed→running) does not set `waiting`. `execute` passes `previousWait = run.waiting` to handlers, and only two handlers read it:
  - Subloop: `awaited = ctx.previousWait?.childRunId ?? childOfThisVisit(ctx)`. A resumed failed parent previously took the first branch through the stale wait. It now takes the event-log branch, which scans back to the visit's `child_run.started` and stops at `node.finished`. The two branches agree because child creation and `child_run.started` commit atomically (#320), and a park is only recorded after that event exists. The #251 parity suite (`child-failure-parity.test.ts`, 14 tests: same child resumed in place, exactly one `child_run.started`, child resumed by the parent actor) and the mapping-retry test (`awaited-children.test.ts:997`) now exercise this branch on the candidate and pass locally and in CI. Old failed rows that keep their stale wait still take the old branch, so they do not regress either.
  - Heartbeat: `recordedBeat = max(visit heartbeat.beat events, previousWait?.beat ?? 0)`. Every park's `beat` was first recorded as a `heartbeat.beat` in the same visit, so the log-derived maximum is identical.

**Concurrency and recovery.** The failed transition keeps its `ACTIVE_STATUSES` compare-and-set. Clearing the wait cannot let a wake through: wake CAS requires `status ∈ ['waiting']` plus a `json_extract(waiting,'$.waitId')` match. Event-first order (`run.failed` append, then status) is unchanged. Recovery still routes a non-terminal row whose log ends in a terminal event through `recovering.add` → `execute` → `completeFromLog` before any `run.started`, so nothing is appended or re-executed. W2 confirms this natively.

**Security.** There is no new input, parsing, privilege or diagnostic surface. The change only removes stale state from public projections. #381 classification/redaction is untouched: the same `boundedFailure`/`INTERNAL_FAILURE_MESSAGE` lines are in context but unmodified.

**Architecture and maintainability.** The change is the minimal symmetric correction and follows the existing cancel/exit convention. It adds no migration, compatibility converter, schema/storage format change or dependency. That is consistent with AGENTS.md "clean design" and ADR-0062, since a stale wait is not invalid stored content.

## 5. Tests

The new `it.each` regression runs the public `RunManager` over the in-memory ports. A child input wait (`timeoutSeconds: 1`, `onTimeout: 'fail-run'`) times out through `timers.fire`, and the failure propagates to the parent parked on its subloop.

- **Live:** waits for idle.
- **Recovery:** a `transition` spy hangs only the parent's `status === 'failed'` write. The test asserts that the committed `run.failed` is last, that the row is `running` with its original wait, and that `finalizedAt` is undefined. It then restores the spy and starts a fresh `RunManager` through `recover()` (start, then idle, then stop). Finally it asserts the event log is unchanged.
- **Shared assertions:** `WAIT_TIMEOUT` at `sub`, `resumable: true`, child details, `finalizedAt`, an ordered park → wake(child) → `child_run.finished`(failed) → `run.failed` history whose failure equals the row's, no `after` node start, and `not.toHaveProperty('waiting')`.

Positive controls are adequate. Existing #242/#251/#398 suites cover waiting, success, cancellation, authored exit, mid-wake recovery and resume-in-place. They all ran: focused 197/197 locally, engine 1,814/1,814 locally and in CI. CI engine coverage is 96.94% lines and 91.22% branches, the same as the implementation log.

**Old-source sensitivity.** Observation O1 explains why I re-established this. The committed test fails under an exact old-source emulation at its stale-wait assertion (line 760) with every earlier assertion passing, and the same configuration passes without the emulation.
