# Attempt notes

All outcome cases were repeated after correcting the disposable harness. No tracked product file was edited.

1. The first helper invocation omitted Windows PowerShell's directory from its process-local PATH, so it stopped before executing the installer: `The term 'powershell.exe' is not recognized as the name of a cmdlet, function, script file, or operable program.` The private PATH was corrected. This was a harness failure.
2. The first complete install/build used a synthetic CLI fixture named with a `.cjs` extension. The product accepts `.js`/`.mjs` launchers and otherwise attempts a native executable. Its final preflight reported `FAIL Harness codex Codex readiness could not be confirmed. Check that the Codex CLI starts and responds, then retry preflight.`, `1 failed, 5 warning(s): fix the failed checks before starting`, and `error: a preflight check failed; fix it (see the table above) and run this script again.` Exit was 1. The fixture was renamed `.js`, then both ready and logged-out branches were repeated. This was an invalid fixture, not a product defect.
3. Windows PowerShell transcription did not capture the native child's output in the initial run. Native output remains in the execution receipts; subsequent installer cases use captured combined stdout/stderr, published here. The cold dependency/build counts in the report are the observed initial real run; later build logs correctly show cache reuse.
4. An extra real bundled-CLI diagnostic initially used a nonexistent private CODEX_HOME. Codex reported `Error loading configuration: CODEX_HOME points to "$QA_ROOT/home/codex", but that path does not exist`, and built preflight reported unknown readiness. After creating that empty private directory, the actual CLI preflight produced the expected logged-out failure, published here. No personal credential directory was read.
5. The first independent identity calculation called loadConfig without the built web fallbacks and differed from the running identity, while listener/health/lock PIDs already agreed. Repeating with the shipped `node apps/api/dist/instance-identity.js` helper, which supplies both fallbacks, exactly matched the running identity. The earlier mismatch was retained privately and was not used to authorize shutdown.
6. Two exploratory bundled-CLI path-resolution commands used CommonJS resolution for the ESM-only SDK and failed before any CLI operation. Resolution was corrected to the product's ESM approach. All actual CLI commands were version/help/login-status only.

The source public clone completed without a retry. Slow registry-download warnings did not prevent the real frozen-lockfile installation. No product defect was inferred from these harness issues.
