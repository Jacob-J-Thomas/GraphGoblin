# #381 source admission notes

Prepared only on 2026-11-14 after reading live #381/#410 and source Git objects at main `7c6e635539e12c56b82f226f1ee734d83b985ad4`. No implementation or runtime verification grant. Refresh the final integration base after I08. #414 remains administratively consolidated into #381; its acceptance criteria are not verified by closure.

The current contract has `EXPRESSION_ERROR` but no `MUTATION_*` run code. The issue explicitly expects a mutation-specific typed deterministic failure with node, operation and useful evaluator/patch information. Adding that code must update the canonical recovery policy and generated contract/reference surfaces without compatibility aliases or historical record rewriting. `RunFailureError` defaults to resumable, so an authored deterministic failure requires an explicit false value and a public resume-refusal test.

`mutateHandler` currently delegates all work to `runMutations`. That helper alternates domain `applyMutations`, optional provider-backed `repairValue`, and domain `completeRepair`/`applyPatch`. It is shared by other node kinds. Preserve its current callers' semantics and the distinction between authored domain evaluation/patch errors and external repair failures. Do not catch arbitrary exceptions as mutation determinism, and do not infer the operation index from a formatted message. The implementation must establish an accurate operation identifier through the narrow evaluation boundary or a typed context that leaves other callers' behavior intact. This is a refinement of the accepted typed-failure contract, not permission to redesign mutation execution.

The main run-manager catch has deadline/abort/termination precedence before provider and generic-error classification. Keep those checks in the same effective order. A known domain error can carry author text, expression or patch data; choose bounded useful fields deliberately, never serialize the raw Error, stack or arbitrary `details`. An authored string that happens to resemble a path is not itself proof of an internal path leak. Use a synthetic unexpected-fault sentinel to prove internal message and details are separated from the public failure while diagnostic logging preserves them.

Sanitizing only the generic catch's `Error.stack` is insufficient to establish the full refined contract: explicit `RunFailureError('INTERNAL_ERROR', ...)` producers also exist, including inference and subloop wrappers, and the manager has several other INTERNAL_ERROR sites. Inventory the newly emitted failure paths before selecting the smallest canonical sanitization boundary. Preserve script/inference codes, resumability, progress/outcome records and existing authored diagnostics; do not broadly scrub unrelated public contracts. `failRun` classifies script failures from durable evidence and bounds the failure before appending `run.failed` and updating the projection. Any sanitation must respect that classification and preserve diagnostic evidence in the logger before irreversible public projection. Do not use general path-matching regexes as a substitute for keeping trusted diagnostic data separate.

Native verification still needs a genuine authored mutation failure, durable run/event records, REST, stdio MCP, actual inspector display and canonical resume refusal. Supported-port unexpected-fault injection with an actual file store is a separate evidence tier from a real authored expression; label it. Include provider-repair/abort/deadline and script/inference controls. Runtime #410 touches the same manager: serialize patches or explicitly combine integration, while preserving issue-specific evidence and gates. GPT implements the backend; any inspector UI change, if truly needed, goes to Claude. No UI change is assumed merely to display an already supported failure message.

## 2026-11-15 preparation clarification

Root reread the live #381 acceptance text and current `common.ts`, `mutations.ts`, `subloop.ts` and failure projection at main177f (the Space candidate has identical backend bytes). The issue covers recognized authored evaluation or patch validation failures, not only the `ExpressionError` class. A deterministic `TemplateError` from the mutation's own authored template evaluation belongs to that boundary with accurate operation context. An authored repair-prompt rendering failure is also known template evaluation at its narrow render boundary. This does not permit treating an identically named error thrown by an arbitrary provider, model resolver or other external call as deterministic. Preserve external failure semantics and do not catch the whole repair/provider path indiscriminately.

The subloop handler dynamically wraps a child's failure code, message and details. Sanitizing newly produced `INTERNAL_ERROR` failures must also prevent a newly emitted parent wrapper from republishing a historical child's internal stack/path fields. The old child's record and event history remain unchanged; preserve useful internal diagnostics in logging. Generic REST 500 responses and MCP tool-envelope errors are separate from this run-failure inventory and do not automatically enter the patch. These are source-based implementation boundaries, not runtime evidence or a release of the queued lane.
