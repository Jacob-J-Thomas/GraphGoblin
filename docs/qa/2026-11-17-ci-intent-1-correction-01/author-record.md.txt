## The three findings and their corrections

**1. Preparation failure suppressed the native command.**
- *Change.* `Prepare native evidence` now runs after `Build`. Its condition is
  `!cancelled() && steps.node.outcome == 'success'` (Node setup gets `id: node`), so it needs only
  the checkout and Node and also runs after a failed install or build.
- *What stays the same.* Install and Build keep their exact commands and GitHub's implicit
  `success()`. Native still runs on `!cancelled() && steps.build.outcome == 'success'`.
- *Gating on Prepare's outcome.* Native receives a directory only from a successful Prepare
  (`steps.evidence.outcome == 'success' && steps.evidence.outputs.dir || ''`). Finalize runs only
  when `steps.evidence.outcome == 'success'`. A failed Prepare that left outputs is ignored.
- *Outputs.* `init` now writes its step outputs last, so they exist only on success.
- *Unchanged.* No `continue-on-error`, retry or deadline change. The 20-minute job budget, the
  exact install, build and native commands, assertions, TAP and stdout lines are unchanged.

**2. The manifest's bytes were passed through after a three-field check.**
- *Change.* `parseManifest` rebuilds the manifest from its validated values: schema, state,
  UUID, timestamp and every typed binding value. It adds the static `LIMITS` and `FILES`
  declarations and the derived fields (the `unavailable` list and the checkout comparisons).
  It then compares the result with the file byte for byte.
- *What is refused.* Unknown fields at any depth, duplicate keys, a BOM, other whitespace or
  line endings, changed limits or file names, an inconsistent `unavailable` list or comparison,
  and canaries in unvalidated positions. The refusal is `manifest-invalid`, before any path is
  published. The recorder refuses such a directory too.
- *Shared composer.* `init` writes through the same composer, so genuine manifests always match.
- *Legitimately unavailable values* remain valid: null and listed. The event base is listed
  only for a pull request, and the Node version is now validated too.
- *Observations.* A file starting with a BOM is rejected as `byte-order-mark`, which claims
  nothing about disclosure.
- *Scope.* This is shape and consistency validation, not authentication. A runner that controls
  the files can still write a well-formed manifest.

**3. Contradictory bindings and repeated facts could qualify as complete.**
- *Binding.* `bindingRequirements` adds `binding-contradiction` for any false checkout comparison
  that applies to the event, and `binding-unverified` for any null one. Either keeps a passing
  native step `incomplete`, exit 1. Valid observations are still uploaded, and a failed native
  run stays `native-failed` with the entry listed.
- *Recorder.* The recorder writes its lifecycle records (`recorder-open` from the constructor,
  `overflow`, `fixture-state`, `recorder-closed`) only itself. The public `record` turns those
  types, and any repeat of a once-per-run fact, into `rejected`. Once-per-run facts are each
  test or subtest start and end, each link kind's alias outcome, each alias round
  `(kind, spelling)` and each contention trial.
- *Subtest numbering.* Subtests are numbered across their whole case, so nested subtests can
  never collide.
- *Finalizer stream rules.* The finalizer rejects a stream (reason `lifecycle`) with:
  - a second `recorder-open`;
  - a record after `recorder-closed`;
  - more than one `overflow`;
  - a closer whose `written` or `rejected` counts contradict the stream;
  - omissions without an overflow, or an overflow without omissions.

  A repeated fact is rejected as `duplicate-fact`.
- *Record consistency rules.* These hold for everything the suite writes:
  - a pass carries no failure fields;
  - an unlinked alias matched its target;
  - only a failed release names a failure;
  - contention results sum to the contenders;
  - the overflow marker follows the first omitted record.
- *Completeness.* It now needs the actual trials 1, 2 and 3 as their own single-owner records
  from the lock-contention case. It also needs both the `alias` and `direct` owner-verified,
  drained releases for each link kind from the checkout-alias case, and every started subtest
  paired with its end.
- *Thrown non-errors.* A test that throws `undefined` or `null` is still recorded as a typed
  failure.

Two contract changes need explicit reviewer and root confirmation:

- `complete` now also requires a verified binding. This is stricter than contradiction-only. An
  unobservable checkout or a malformed event head can no longer be `complete`, and local runs
  without GitHub variables report `binding-unverified`. Contradiction-only is a one-line change
  if preferred.
- `result.cases.*` gains `subtestsUnpaired`.

## Maintained regressions and mutation proof

`tooling/scripts/windows-launcher-evidence.test.mjs` has seven new tests and three extended ones
(28 tests, 21 before). The extended tests cover the observation BOM, a thrown `undefined`, and the
constructor-written header in the write-failure test.

- **Root 1.** A scheduling model reads the Windows job from `ci.yml` and evaluates its `if:` and
  `env` expressions with GitHub's status semantics. Unknown expression forms fail the test. It
  feeds the modeled outputs into the real `finalize` and recorder, covering:
  - prepare failure, even with outputs left behind;
  - setup, install, build, native and finalize failures;
  - cancellation.
- **Root 2.** Fifteen manifest tamperings are refused by `parseManifest`, `finalize` and the
  recorder, with nothing written. Legitimate unavailable values are accepted. A real CLI child
  refuses an unknown field and publishes no outputs. The observation BOM is covered.
- **Root 3.** Coverage includes:
  - binding contradictions for push and pull request (head, sha, base parent, head parent);
  - an unverified binding;
  - a failed native run with a contradiction;
  - a real CLI init and finalize on the real checkout with a wrong event head;
  - recorder refusal of repeats and of lifecycle types;
  - repeated trials and spellings;
  - case scoping;
  - nested subtest numbering and pairing;
  - eight lifecycle, three duplicate-fact and four consistency stream rejections.

`controls/regression-mutations.mjs` reverts each correction in place, one at a time. It runs the
suite once per mutation, restores the bytes and checks their SHA-256. **All 10 mutations were
killed**: 2 for root 1, 2 for root 2 and 6 for root 3. The unmutated baseline is 28/28 and both
sources were restored identically (`controls/regression-mutations/regression-mutations.json`).
