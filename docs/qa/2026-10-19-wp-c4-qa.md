## Defects

### D1 — major: an unpaced client waiter rejects during API restart

- **Steps:** Run the built authenticated API with a new disposable file store. Publish a manual-trigger → input-wait → exit loop. Start it and wait for `waiting`. Start built `waitForRun` with a 10,000 ms observation budget and 25 ms polling. After timely snapshots, hard-kill the owned API process, leave the listener down for 150 ms, and restart the built binary against the same store. Answer the recovered input wait and observe the run to completion.
- **Expected by this QA brief:** The original waiter returns the correct terminal state or a clean `{ finished: false, run? }`, once.
- **Actual:** It rejects once with `GraphGoblinApiError`, `NETWORK_ERROR: fetch failed`, `status: 0`. The run recovers in `waiting` and later succeeds. No duplicate settlement was observed.
- **Evidence:** [supplemental-runtime-results.json](2026-10-19-wp-c4-qa/supplemental-runtime-results.json), case `natural waiter over real hard restart`; [supplemental.mjs](2026-10-19-wp-c4-qa/supplemental.mjs).
- **Scope/provenance:** This is a mismatch with the requested restart outcome. The selected bolt's narrow abort/deadline criterion passed. No baseline comparison established that forwarding a transport error was introduced by WP-C4; the public client's network-error behavior already permits transport errors. The orchestrator must disposition this stricter restart expectation rather than assume a new regression.
