## What the final behavior establishes

When two rows claim the same physical connection, neither may move or delete it while that claim remains ambiguous. A later explicit edit that leaves one unique route on the connection's current port permits that route to claim it. A newly acquired connection stays on its current port during that acquiring edit. The captured saved state cannot establish which row originally drew the connection after historical ownership became ambiguous. The correction preserves the existing connections and manual geometry and follows current authored ports; it does not reconstruct missing historical identity.

The fresh browser cases cover shared and unique edge IDs, rename after a temporary row-ID collision, removal after that collision, and direct rename. The two restored-device cases start from the exact old durable definition/map, with only disposable loop identity/base bookkeeping rebound. IndexedDB restoration occurs outside a mounted editor; reopening, form edits, removal, history, offline reload, autosave and public readback use the unchanged built product. No React or product-store function replacement occurs during those browser actions.

The restored-map removal applies without a connection-removal preview and preserves both actual records. After ambiguity is resolved, the later first-row edit `yes → accepted` changes only the real `yes → done` record. The `no → other` record and manual geometry remain intact. The [device aggregate](independent/records/device-summary.json) binds the detailed phases and later-repair criteria.

There are **54 positively present, nonempty, shape-valid device-map samples**: 36 fresh and 18 restored-device samples. The first retained durable receipt contains the old contested claims. Loading sanitizes that ownership map; initial Undo restores the normalized loaded map, not the old contested durable claims. Definition history and later map round trips are compared separately. This distinction is explicit in the raw aggregate.
