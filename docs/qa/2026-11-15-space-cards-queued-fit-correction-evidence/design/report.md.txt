I've finished the design. Nothing was edited, built, run or tested, and nothing was committed. All evidence comes from reading the checkout at `daa43634`, the installed `@xyflow/react` 12.12.0 / `@xyflow/system` 0.0.83 / `d3-zoom` 3.0.0, and the four probe files.

**The fix:** stop using `fitView` for Space cards. Work out the fitted view in Canvas and apply it with `setViewport` in the same step that checks the store still holds the spaced draft. Nothing is left queued for a later graph to consume. Opening Fit and the Fit View button stay as they are.

# Space cards queued-fit correction: design

## 1. Root cause in the installed library

- **What `fitView` does** (`react/dist/esm/index.js` 1218–1226): it sets `fitViewQueued: true`, `fitViewOptions` and a resolver in xyflow's store, then pushes a no-op node update. It doesn't measure or fit anything yet.
- **When the fit actually happens:** whichever of these runs first, using the graph that is current at that moment:
  - the store's `setNodes`, once nodes are measured (3428–3455);
  - `updateNodeInternals`, on a card resize (3482–3492);
  - a deferred `requestAnimationFrame` callback (957–993). This is the callback the probe held.
- **How Undo triggers it:** when Canvas's `nodes` prop changes, xyflow calls `setNodes` from a passive effect (281–328). Undo changes that prop.
- **No way to cancel:** there is no public API to cancel a queued fit.

This matches the held-callback run exactly. The viewport went to the pile's opening fit (`translate(246px, 279.5px) scale(2)`) during Undo, before release. When the held callback finally ran, it found `fitViewQueued` already false and did nothing.

## 2. Public xyflow options considered

| Option | Verdict |
|---|---|
| `fitView(opts)` (current), or with `nodes:` / `duration` | Rejected. Still queued, and the node ids survive Undo, so it would still fit the pile. |
| `fitBounds(bounds, {padding})` | Applies immediately, but zoom can go down to the store's 0.1. docs/09 lines 264 and 277 promise "same options, never below 50%". That would be a product change. |
| `setViewport(getViewportForBounds(bounds, w, h, 0.5, 2, padding))` | **Chosen.** Same calculation as `fitView`, with nothing queued. |
| Writing `fitViewQueued` via `useStoreApi().setState` | Forbidden: it patches library state. |
| A Canvas-owned rAF plus cancel | Rejected. It reopens the window it is meant to close. |

**`setViewport` is synchronous; I checked rather than assumed.** The chain, with no duration:
- `useReactFlow().setViewport` (527–538) calls `panZoom.setViewport` before its first `await`.
- That calls `setTransform` (system 3103–3107, 3005–3012), whose Promise body runs immediately.
- `getD3Transition` (2752–2758) returns the plain selection and resolves the promise immediately.
- d3-zoom's `zoom.transform` on a plain selection (`zoom.js` 85–99, 190–216) runs start, zoom and end synchronously.
- xyflow's zoom handler (2854–2863) then calls `onTransformChange`, which writes `store.setState({transform})` (react 1315–1319). The viewport is uncontrolled, since Canvas passes no `viewport` prop.

So the transform is set before `setViewport` returns. The returned promise only reports completion.

Line 548 becomes `const { screenToFlowPosition, setViewport } = useReactFlow();` and add `const flowStore = useStoreApi<FlowNode, Edge>();`. This adds no new runtime requirement: `useReactFlow` already needs the provider.
3. **Bounds helper** (module scope, not exported). `measuredBounds(definition, measured)` returns the union of `node.ui ?? {x:0,y:0}` plus the measured size for every node in the draft. Look sizes up with `Object.hasOwn`, because node ids like `constructor` exist. It returns `undefined` if any card is unmeasured or has zero width or height, meaning "wait".
4. **Pending fit record** (lines 1099/1122). Store `{ definition, generation, revision }`, captured from `useEditorStore.getState()` right after `spaceCards()` returns `'applied'`.
5. **The effect** (replaces 1100–1110):
   ```ts
   useEffect(() => {
     const pending = spacedFitRef.current;
     if (!pending) return;
     const live = useEditorStore.getState();
     if (definition !== pending.definition || generation !== pending.generation ||
         live.definition !== pending.definition || live.generation !== pending.generation ||
   ```

### Answers to the questions in the brief

- **Where graph identity is checked.** At the top of the effect, in the same synchronous step as the viewport write, in two ways:
  - *What rendered:* the `definition` prop and `generation` match the pending record.
  - *What the store holds now:* definition, generation and revision all match. This catches rendering that lags the store, and Undo followed by Redo back to the same draft object. `revision` only increases within one load, on every edit, undo or redo that changes the draft (`store.ts` 510, 550, 870).

  Any mismatch drops the fit permanently.
- **How dimensions are captured.** Card sizes come from Canvas's `measured` state for the same render, i.e. the sizes xyflow reported through `onNodesChange`. Positions come from the spaced draft itself. Pane width and height are read from xyflow's store at the moment of fitting, which is what `fitView` reads too. The result should be identical to today's fit: the probe's pre-fix control gave `translate(72px, 303.5px) scale(1.57895)`.
- **Animation frame.** None is needed. The bounds come from Canvas's own data, so there's no need to wait for xyflow to adopt the nodes. Adding a frame would reopen the window.
- **Cleanup and repeated effects.** Nothing is scheduled, so there is nothing to clean up.
  - Repeated runs (new measurements, re-renders) find the record already cleared, or drop it on a mismatch.
  - StrictMode's double mount runs the effect with no pending fit.
  - Unmount discards the ref with the component; a remount starts with none.
  - A load drops it because the generation no longer matches.
- **Can an issued operation act later?** No. Once `setViewport` returns, all that remains is:
  - an already-settled promise, which is discarded;
  - xyflow's zero-delay `onMoveEnd`/`onViewportChangeEnd` notification, which Canvas doesn't subscribe to and which never changes the transform;
  - React re-rendering the transform that is already set.

  Nothing later reads the graph.
- **Input arriving between render and effect.** In either order this is safe. If the effect runs first, the fit lands and the later Undo doesn't refit. If the Undo lands first, the live-store check drops the fit.

Everything else on your preserve list is untouched by this change: store, history and autosave, layout, first node identity, focus and announcements, the result panel, the gesture gate (programmatic moves are ignored by `gesture.move(null)`), user Fit, opening Fit, and Undo/Redo.

## 6. Remaining risks and limits

- **Same library behavior elsewhere, out of scope.** The opening fit (`onInit`, which runs after a 1 ms timer) and the Fit View button still use the queued `fitView`. An edit landing before their frame could still be fitted. This predates #208 and wasn't introduced by it, so I left it alone as the brief asks.
- **A card that never gets a size** keeps the fit waiting. That's harmless: every later run re-checks identity and revision. xyflow's own fit would skip that card instead.
- **`setViewport` before the pane is ready** (xyflow's `panZoom` missing) silently does nothing. Space can't be pressed before the pane exists, so I don't expect this in practice.
- **Not a product change.** The zoom floor, padding, and the "fit once" timing ("after the spaced cards render") are all kept, so this stays within the accepted contract and needs no owner question.
