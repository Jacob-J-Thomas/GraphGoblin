## Defects

### Q205-1 — P2 / medium: upgrade discovery omits invalid legacy run-event efforts

Reproduction, implemented by [scripts/stored-extra.mjs](scripts/stored-extra.mjs):

1. Start the archived, built `a4fee9a9` API with fake CLIs and a fresh store; publish and run a GPT-6 Luna inference at `low`; stop the gateway normally.
2. Construct the legacy-content fixture by replacing `"effort":"low"` with `"effort":"minimal"` in that run's `harness.session` row in `run_events.payload`. The baseline already rejects `minimal` for shipped models, so this old content is explicitly planted in a real API-created row; it is not claimed to have been saved through that baseline's API.
3. Start the WP-205 build on that store. Run the exact SELECT from the top Unreleased bullet, and request `GET /runs/{runId}/events?limit=1000`.

Expected: the hand-upgrade instructions discover every legacy effort that prevents the affected records from being served, and explain its hand repair. No automatic migration is expected.

Actual: startup succeeds, `GET /runs/{id}` is 200, the published SELECT returns **zero rows**, but events return **500 `STORED_EVENT_INVALID`**, identifying run `01M60JDGMV4JD2AE3SXEPAAX9Y`, seq 7, type `harness.session`. Diagnostics are captured in the same observation. The CHANGELOG mentions this possibility as untested, but its executable discovery and repair instructions omit it. Applying only those instructions leaves this history unreadable.

Evidence: `legacy run_events minimal omitted by CHANGELOG SELECT` in [stored-extra.log.txt](stored-extra.log.txt) and [stored-extra-result.json](stored-extra-result.json). [scripts/final-checks.mjs](scripts/final-checks.mjs) then applied this **supplemental**, stopped-store repair to this disposable fixture only:

```sql
UPDATE run_events
SET payload = replace(payload, '"effort":"minimal"', '"effort":"none"')
WHERE run_id = ? AND type = 'harness.session';
```

After restart, history returned 200 with `effort:none`: `supplemental run_events hand update restores history` in [final-checks-final-result.json](final-checks-final-result.json). This proves the tested session-event case; other historical event shapes were not exhaustively inventoried. Extend the hand-upgrade discovery/repair guidance rather than adding a migration.

### Q205-2 — P3 / low: process-default rejection loses the required diagnostic code

Reproduction: start the built head on a fresh disposable store, with fake Codex/Claude executable overrides and either of these process defaults:

```json
{ "byHarness": { "codex": { "model": "gpt-5.5", "effort": "none" } } }
```

```json
{ "byHarness": { "claude": { "model": "claude-haiku-5-5", "effort": "none" } } }
```

Expected by check 3: refusal with `EFFORT_UNSUPPORTED` at `GG_DEFAULTS` startup, identifying the affected configuration.

Actual on both harnesses: exit 1 and no listener, but the only diagnostic before the stack is:

```text
Error: Invalid GG_DEFAULTS: The default reasoning effort is not supported by its model
```

It contains no `EFFORT_UNSUPPORTED`, model, harness or effort path. Startup correctly prevents execution; the defect is the required diagnostic, not acceptance of invalid configuration. No claim is made that WP-205 introduced this existing path's message.

Evidence: [process-codex-none-gateway.log.txt](process-codex-none-gateway.log.txt), [process-claude-none-gateway.log.txt](process-claude-none-gateway.log.txt), and the two `GG_DEFAULTS startup refusal .../none` checks in [complete-api-final-result.json](complete-api-final-result.json). Reproduction driver: [scripts/complete-api.mjs](scripts/complete-api.mjs).
