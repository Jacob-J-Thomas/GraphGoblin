## What changed and why

The owner decided on 2026-10-27 that `minimal` and `none` are one level for the user, shown as `none`, and that business logic swaps in the provider's name per model group. The owner also decided that nothing migrates stored data automatically before 1.0 ([ADR-0062](../../decisions/ADR-0062-stored-data-corrected-by-hand-before-1.0.md)).

- **Scale.** `EffortSchema` is `none, low, medium, high, xhigh, max` (`packages/contracts/src/common.ts`). `minimal` is gone from the contract, fakes (`packages/engine/src/testing/fakes.ts`), web fixtures, tests, the generated API client and `docs/reference/nodes.md`. A request that names `minimal` fails validation (`VALIDATION_FAILED`); no compatibility parsing exists.
- **Catalog.** Seeded GPT-6 and GPT-5.6 models offer `none` to `max`; `gpt-5.5` keeps `low` to `xhigh`; Claude models keep `low` to `max` (`packages/infrastructure/src/sqlite/settings.ts`, `packages/infrastructure/src/claude/models.ts`). The startup seed refresh applies the lists to existing stores (existing behaviour, confirmed below).
- **Provider mapping.** `packages/adapter-codex/src/effort-names.ts` holds one table from model family to the provider's name for `none`; `threadOptions` (`options.ts`) applies it where it sets `modelReasoningEffort`. Every other level passes through unchanged. The run records the canonical effort; the mapped name appears only in the CLI invocation and in one debug line, `codex: reasoning effort sent to the CLI`, with `model`, `effort` and `providerEffort`. `CodexHarnessOptions.effortFamilies` takes another table (default `CODEX_EFFORT_FAMILIES`). SDK 0.160.0 types `modelReasoningEffort` without `none`; the value is passed with one documented type assertion, and the SDK writes it into the CLI argument as is.
- **Editor and Settings.** Every effort list (inference node, LLM decision, loop defaults, Settings default effort, the LiteLLM model form) shows `none` first as **none (no reasoning)** (`effortOptionLabel` in `apps/web/src/forms/fields/model.tsx`). A kept unsupported `none` keeps the existing style: "none (not supported by this model)" and "Effort none is not supported by GPT-5.5. Choose a supported effort or Default."
- **Refusals.** `none` on GPT-5.5 and on every Claude model is refused `EFFORT_UNSUPPORTED` at draft save, validate, publish, loop defaults and Settings, and a run pinned to a stored one fails `EVALUATION_INVALID_CONFIGURATION` (`details: {code: EFFORT_UNSUPPORTED, path: effort, level?, harness?}`) before any request: the #417/#426 paths, unchanged in code, now exercised with `none`.
- **Docs.** ADR-0062; `AGENTS.md` rule; `docs/01-vision-and-scope.md` principle 8; ADR-0020 status line; `docs/06-harness-integration.md` (effort row, catalog table, the `none` paragraph and mapping table, the Claude paragraph); `docs/guide/02-build-a-loop.md`, `06-settings-and-secrets.md`, `07-troubleshooting.md`; `CHANGELOG.md` (top Unreleased bullet with the upgrade note); the design sample's effort option.
