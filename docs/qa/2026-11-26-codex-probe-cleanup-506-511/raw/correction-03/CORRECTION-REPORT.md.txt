## R1 (P2): keep the probe directory when termination is unconfirmed

`preflightCli` (`packages/adapter-codex/src/cli.ts`) used to call `rm` on its probe directory even
when a check's runner result carried `terminationUnconfirmed`. Now:

- If any check reported `terminationUnconfirmed`, preflight leaves the probe directory in place and
  makes no `rm` call. The check's typed result is kept, and only the existing fixed not-stopped
  problem is added (`Codex CLI check process did not confirm that it stopped.` plus the `unknown`
  action). The removal-failure problem is not added, because no removal ran.
- Otherwise (the checks closed, or a spawn that never started, such as a missing executable), the
  single ordinary removal runs as before, through a small `removeProbe` helper. It is not retried,
  and a failure adds the separate fixed removal-failure problem. A `ready` result still becomes
  `unknown` in that case.
- `runCli`'s first failure, timeout/abort/close logic, the single stronger signal, deadlines and
  all public contracts are unchanged. No CLI output, path or exception text reaches a result.

## R2 (P3): qualify the cancelled-listing message in docs/06

The listing runs inside `runStreamed`, which the harness wraps in its `cancelGraceMs`-bounded wait
(`harness.ts` `bounded` and the acknowledgement timer; `client.ts` `isolatedClient`). In the same
docs/06 paragraph, a cancelled turn now ends as cancelled, or with the listing's own message, only
when the listing's runner settles before that bound runs out. That holds with the default 5 s,
which is longer than the runner's two-second allowance. A custom `cancelGraceMs` shorter than the
allowance can let the bound run out first, and the turn then fails
`HARNESS_TERMINATION_UNCONFIRMED` with the harness's generic termination message. There is no
harness or deadline change. The FUP093 classification is unchanged and still documented: the
listing's error is definitely-not-submitted, the harness reports `delivery-uncertain`, and no SDK
turn starts.
