The defect's supported root cause is the absence of an outgoing-response abandonment predicate around the historical reconstruction's asynchronous boundaries. Old code continued into metadata/page reads and response/error sending after the response closed. The candidate adds a monotonic predicate based on the outgoing response's close event or destroyed state, threads that predicate into reconstruction, and hijacks the already-abandoned reply. It does not cancel an operation that has already started. The stopped-work contract is deliberately conditioned on observed outgoing-response disconnection, and begins before further repository access or page replay.

In `runs.ts:222-240`, the historical branch owns one close listener on `reply.raw`. It attaches the listener before its entry check, combines the latched event with `response.destroyed`, and checks before ownership lookup. The awaited ownership lookup remains before any history disclosure. Although there is no separate route-level check immediately after ownership resolves, `historicalThread` checks synchronously at its entry before invoking a repository, so that boundary is covered. After reconstruction, the route checks the same predicate before returning data or interpreting missing history. The catch branch suppresses a late rejection only when the response is disconnected; otherwise it rethrows the original error. The finally block removes its specific listener on every settled path, including early entry return, ownership error, missing initial thread and disconnected rejection.

In `run-history.ts:36-69`, the predicate is mandatory. There is an entry check, a check after the initial-thread await, a check after the checkpoint await, a check after the optional checkpoint-boundary event read, a check after every bounded event-page await and before either replay function, and a check immediately after the existing inter-page `setImmediate` yield. Between these checks and the next repository invocation there is no intervening await; JavaScript close callbacks do not interleave within that synchronous segment. After a close observed during an awaited operation, the continuation therefore stops before the next operation or replay of the fetched page. Replay work that is already executing synchronously is not preempted, and the accepted contract does not require that.

The checkpoint eligibility, replay-state handoff, bounded read limits, page order and output reconstruction are unchanged. Page size remains at most 128 and the last-page limit remains `Math.min(128, at - after)`. The optional checkpoint-boundary verification is still required before trusting its replay state. Storage selects eligible checkpoints before decoding, and bounded event reads exclude malformed later events. I inspected the SQLite event/run implementations, domain replay and reconciliation, current-thread manager path, existing history/paging tests and API error handling to trace these claims beyond the changed lines.

Authentication, scope checking and query validation remain in the unchanged pre-handler path. The query remains strict, with an optional nonnegative safe integer `at`. Ownership still returns RUN_NOT_FOUND for missing or other-owner runs before reading their history. Current-thread requests take the unchanged `at === undefined` branch. The helper's `undefined` represents either missing initial history or abandoned work, but its sole caller checks the monotonic disconnect predicate first; it therefore cannot convert an observed cancellation into a missing-thread error. No schema, storage format, migration, dependency, timeout, truncation policy or retry policy changes. The API document and changelog describe the implemented behavior without promising interruption of pending I/O.

This was source extraction, not a network reproduction. `emitCloseNT` sets response.destroyed before emitting close, explaining the already-closed entry guard. The active ServerResponse attaches to the socket and receives its close signal; ordinary successful response finish is a later lifecycle event, and completion of a bodyless incoming request is not this response signal.

The Opus O2 pipelining observation has a defensible static mechanism: Node queues a later ServerResponse in `state.outgoing` while an earlier response owns the socket, and socket close aborts incoming requests while `onServerResponseClose` addresses the active `socket._httpMessage`. A queued response might therefore lack the observed close/destroyed transition used by this patch. I did not reproduce that case and make no claim about ordinary browser, undici or curl defaults. The mechanism is not an introduced regression, and it does not demonstrate that reconstruction continues after the specific outgoing-response disconnection required by the admitted criterion has been observed. No new native execution was needed to decide this scoped review. A broader all-transport-loss cancellation guarantee would require a separately defined contract and evidence.
