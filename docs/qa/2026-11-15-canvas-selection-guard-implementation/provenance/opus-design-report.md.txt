I recommend one small fix: Remove connection should ignore any click that the browser counts as the second or later click of a double or triple click (`event.detail > 1`). That click should also move focus back to the connection. Clicks counted 0 (Enter, Space, `element.click()`) and 1 (the first click) still remove, as today.

The change is only in Remove's click handler in `OrthogonalEdge.tsx`. It needs no state, listener or timer, and no change to `RouteEditing`, `Canvas.tsx` or any dependency. It works alongside the accepted Reset hold. I only read files and ran nothing. I did not read the repair47b source.

## Why a click-count rule works for Remove

**Where the second press goes, in the installed xyflow 12.12.0:**
- **pointerdown** has detail 0 (as observed). Remove has no press handler. The pane's selection capture ignores it because Remove has `nokey` (react `index.js` 1488–1492), and d3-zoom's filter refuses it because Remove has `nopan` (system `index.js` 2923–2926). The only effect is that Edge focuses the button.
- **click** arrives with detail 2 (as observed). This reaches Remove's own React `onClick`, which is the only handler that deletes. The browser puts the count on the very event that does the deleting.
- **dblclick** doesn't arrive today, because Remove is already detached by then. Under the new rule Remove stays, so it will arrive, and nothing acts on it:
  - the app has no dblclick handlers (I searched);
  - the Canvas gives xyflow no `onEdgeDoubleClick` (`EdgeWrapper`, line 2993);
  - d3's `dblclick.zoom` filter refuses `.nopan` targets.
- **The first click** is unchanged. xyflow's `EdgeWrapper` selects the edge in a click handler that never checks the count (2977–2992).

**Why the same rule didn't work for Space cards:** there, the damage came from other code's press handlers, d3-zoom's `mousedown` and xyflow's pane `pointerdown` with Shift. Those run before any click, and `pointerdown` always reports 0. Guarding them would have meant stopping events that other code owns. Remove does nothing on press, and its only action is in its own click handler, which receives the browser's count.

**The repo already does this:**
- `RunControls.tsx` 46–51: Resume and Create replay run ignore clicks counted above 1, and keys report 0. The e2e test in `recovery-eligibility.spec.ts` double-clicks them and gets one accepted request.
- `dialog.tsx` 120–182: the dialog swallows the rest of the double-click that opened it.

**Why not a layout or lifetime fix:**
- **Hold, like Reset.** The Reset hold works because the Reset button can stay under the second click. Here the toolbar doesn't exist until the first click creates it, so there is nothing to hold.
- **Move the toolbar.** On an automatic forward edge the label sits at the middle of the vertical trunk. Once the ports are more than about 36 px apart vertically, a toolbar above or below the label crosses the trunk. A toolbar beside it crosses the horizontal segments, and manual or backward routes can go anywhere.
- **Avoid the clicked point.** This is the only placement that always works. It is larger, changes what users see, and gets into the parked #479 placement work.
- **Arm Remove later.** This needs a signal to end the wait. A timer is ruled out. Pointer movement fails touch and fails a deliberate click made without moving. That leaves the click count anyway.

## Contract and limits

**Contract:** Remove acts on a click counted 0 or 1. A click counted 2 or more never removes, whatever element the first click hit. The existing guards still apply independently: the disabled state for protected or duplicate connections, the pan/drag gate (`aria-disabled`), and the stale-selection check.

For a Windows mouse, Edge is expected to number clicks using the system double-click time and area (500 ms and 4 px by default). These are the same settings that make something a double-click anywhere else in Windows. That is an expectation, not a measured result. The probe's Playwright click counts only show that Edge passes a driver-supplied 2 into `click.detail`, across a change of target and through React.

**Limits:**
1. **Two separate clicks still remove.** A slow or moved double-click that Windows doesn't count as one is two single clicks, so the second click removes, as it does today. One Undo restores it.
2. **Touch and pen counts are not measured** (N7 below).
3. **Runs past three clicks** may stop at 3 or start again at 1, depending on the platform. A run of four or more clicks is outside the contract.
4. **A refused first click carries over.** If the gate refuses the first click, a quick repeat at the same spot continues the run and is refused too; the next separate click works. Reaching this needs a press during the settling window, which in practice means using two mouse buttons at once.
5. **The refusal is silent.** There's no announcement and Remove looks the same. A refused click is never the first click of a run.

## Exact change

`apps/web/src/editor/OrthogonalEdge.tsx`, in `RouteHandles`, Remove's `onClick` only (lines 370–375 at HEAD):

```tsx
onClick={(event) => {
  // The edge wrapper would select this (now removed) edge again on the same click.
  event.stopPropagation();
  // A later click of a double or triple click continues the press before it, which may have
  // selected this connection and so put this button under the pointer: it removes nothing and
  // leaves focus on the connection, as that press did. Keys and element.click() report 0.
  if (event.detail > 1) {
    edgeElement()?.focus();
    return;
  }
  if (settling) return;
  editing.remove(edgeId);
}}
```

- **`stopPropagation` stays first.** A refused click never reaches `EdgeWrapper`, so a Control/Meta second click can't deselect the connection. This matches your Reset decision.
- **Focus goes back to the connection.** Edge focuses Remove on the second mousedown. Moving focus back makes a refused double-click end exactly like a single click on the line: the connection is selected and focused, and Delete or Backspace removes it. Without this, focus stays on Remove, where Delete and Backspace do nothing.
- **Lifecycle:** none. Each click decides from its own count.
- **Unchanged:** `RouteEditing`, Canvas selection (`mayAct`, `refuseStale`, generation and drawability), the Delete/Backspace path, `toolbarKeys` and Escape, the disabled state and title, `removeSettling`, and Reset with its hold. This touches lines next to repair47b's work, so apply it on top of that.
- **Docs:**
  - one clause in the `OrthogonalEdge.tsx` doc comment (lines 71–77);
  - the Remove bullet in `docs/09-frontend-and-pwa.md` (line 273);
  - `docs/guide/02-build-a-loop.md` (around line 129): "Double-clicking a connection selects it; it never removes it.";
  - one clause in the CHANGELOG #207 entry.

## Fallback, only if N7 or N8 fails

The smallest visible change is to choose the toolbar's side from the selecting click:
- `OrthogonalEdge` records where the click that selected the edge landed, using a click handler on a `<g>` around `BaseEdge`.
- If that point falls inside the band the buttons would cover above the label, `RouteHandles` draws the toolbar below the label for that selection. It stays there until deselection, like the Reset anchor.

The costs:
- the toolbar's position depends on where the line was clicked;
- the lower position can cover the target-side segment, its handle or a card;
- it has to work with the held Reset anchor;
- it adds state, docs and native layout cases.

Keep the click-count rule as well.

## Not covered by this fix

- **After a first click on Remove, later presses land on what's underneath.** That effect was not probed and is unchanged.
- **Reset may have the same problem.** Selecting a manual route could put Reset under the second click by the same mechanism. That is a prediction only; Reset is undoable and is being changed in repair47b. If a probe shows it, the same one-line rule would apply.
- **Segment handles act on pointerdown, so no click count can guard them.** A press that doesn't move writes nothing (the release returns early without a store write). This was not observed.
- **#479 Fit placement** is not touched.

This is a read-only design. Nothing is implemented or signed off.
