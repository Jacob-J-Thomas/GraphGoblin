## Production change (`OrthogonalEdge.tsx`, Remove's `onClick` and one doc comment)

```tsx
onClick={(event) => {
  // The edge wrapper would select this (now removed) edge again on the same click.
  event.stopPropagation();
  // A later click of a double or triple click (the browser's count above one) goes on
  // from the press before it, which may have selected this connection and so drawn
  // this button under the pointer (#207). It removes nothing and leaves focus on the
  // connection, as that press did. Enter, Space and element.click() report 0, and a
  // separate click 1: both go on to remove.
  if (event.detail > 1) {
    edgeElement()?.focus();
    return;
  }
  if (settling) return;
  editing.remove(edgeId);
}}
```

The doc comment above `OrthogonalEdge` gained one clause (Remove ignores a later click of a double or triple click and keeps focus on the connection). Everything else in `RouteHandles` is unchanged: `stopPropagation` stays first, the `disabled`/`refusal` and `aria-disabled`/`data-gesture` props, `removeSettling`, the generation and drawability guards (in `Canvas.tsx`, not touched), `toolbarKeys`, and all of the Reset hold. No new state, timer, listener, event replay or toolbar placement change.

## The e2e test, and why it was not run

`edge-routes.spec.ts` has one new test: a fixture from the file's `crossingLoop()` with the six cards moved so `start-work` has ports far apart vertically and nothing else near its trunk. It selects `start-work` from the keyboard (existing `select`), measures Remove connection's box, deselects with Escape (xyflow's edge keydown unselects on Escape, read in the installed source), and samples the unselected path for a vertical-trunk point that lies inside that box and that `elementFromPoint` reports as the connection's `.react-flow__edge-interaction` line. It asserts that one ordinary click there makes the same point hit the Remove button, deselects, then calls `page.mouse.dblclick` at the point and asserts the connection stays selected, focused and available, Undo stays disabled, the viewport style is unchanged, no PUT was sent and the server draft is unchanged. A `remove.click()` then removes it once (server draft readback), and the "Undo remove edge start to work" button restores the exact draft.

It is **not executed, so these are unconfirmed**:
- The fixture geometry (card spots, other edges, Fit view zoom) was chosen by reasoning, not observed. The overlap point is computed at runtime and `expect(point).not.toBeNull()` fails with a clear message if no hit-tested trunk point lies inside the box; I could not check that it exists here. If it does not, move `work` further down (or the others further right) in the `spots` table.
- `toBeFocused()` on the connection after the double click, and the name "Undo remove edge start to work", come from reading the handler and the store label (the native probe used the same label); neither was observed.
- The PUT-count assertion holds right after the double click, and a late PUT from an accidental removal would not be caught by it; the disabled-Undo and unchanged-draft assertions catch that case.
- Click counts are the ones Playwright's mouse gives the browser (driver-supplied), the same limit as the Opus N1 to N3 rows. It does not test OS-numbered clicks, touch or pen.

## Limits and what remains for root

- Browser-counted rule only: nothing here measures how Edge numbers real mouse clicks, touch taps or a fourth click. Unit and store tests set `detail` to 0, 1, 2 and 3 explicitly (4 and above fall under the same `> 1` code, but no test asserts a four-click boundary). Opus N7 (touch, coarse context) and N8 (OS-injected mouse) remain for root's native run; per the root disposition, a same-point touch sequence that still removes the connection is a product failure for root to dispose of, not something to waive.
- Two separate clicks the browser counts as 1 each still remove (Opus limit 1), and a first click that the pan gate refused can carry a repeat into the same run (Opus limit 4). Refusal is silent: no announcement, no visual change beyond focus returning to the connection.
- The jsdom contract test dispatches events directly to the line and then the button; it does not hit-test and does not prove the browser's pointer targeting. Native N1 to N6 and N9 evidence is still needed.
- Not covered, as admitted: Reset after selecting a manual route, segment handles (press-driven), third press after Remove's own unmount, #479 and #481.
