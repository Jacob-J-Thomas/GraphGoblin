## Proposed public behavior

1. At each selected Liquid/JSONata call, catch only its own evaluator rejection and required domain type. Evaluate the view, arguments and serializations outside that catch. A shared function can accept the evaluator promise and location, or call the concrete evaluator on fully prepared arguments. A wrapper accepting an arbitrary async callback that does I/O would recreate the ambiguity. Attach the action to the actual rendering in the manager's render service (or directly use the pure renderer in the handler). Passing a safe location through a shared selector lets it attach the exact item index where the predicate runs.
2. Publish existing `TEMPLATE_ERROR` and `EXPRESSION_ERROR`; authored input/output operation errors use existing `MUTATION_ERROR`. For the new cases use `resumable:false`. The message names the field, one-based human ordinal when applicable, and safe cause. Details are small JSON such as `{boundary:"inference.output.transforms",operationIndex:1,operationKind:"set",cause:{code:"EXPRESSION_ERROR",message:"The expression raised an authored error: qa-381-output-mapping"}}`. Use zero-based integer indices, fixed field labels and finite operation kinds. Avoid arbitrary header keys, map names, paths, templates, prompt text, schema data or item values as locators. Header/map members use declaration order for that pinned object. Include effect facts only when observed, e.g. beat number, completed context-file count, or last result received. A genuine user-chosen Replay creates a new run under existing policy. A pinned run cannot adopt an edited loop. Direct authors to the field and a corrected version, with an explicit check for consumed external work where relevant.
3. The existing 1,000-UTF-16-unit `boundedAuthoredCause` is a length boundary. A genuine evaluator may echo runtime values or multiline text. Compose the *new* public cause from facts at the source, then apply that cap including the truncation marker. Use fixed descriptions for Liquid parse/render failures plus positive integer line/column when the token supplies them; JSONata compile/runtime, depth/time limit, rejected regex, assertion/explicit error plus safe numeric position or validated engine code where available; mutation target/patch/schema/regex categories use fixed action-oriented reasons. Example fallback is “The selector could not evaluate this item. Check its input type.” Keep library messages, context excerpts, evaluated values, stack, filesystem paths and `DomainError.details` out of the new projections. Distinguish an author-declared diagnostic from a value fed to `$error`. For the issue witness, when the compiled root is a direct built-in `$error` call with one static string literal, the thrown JSONata code is D3137 and the literal is a plain diagnostic label (letters/digits/spaces/underscore/hyphen), publish the bounded *literal*. All other explicit-error expressions, including nested/dynamic `$eval`, receive the fixed “expression raised an authored error” cause with location. Never parse arbitrary error prose for a secret blacklist or rerun evaluation. Supply safe evaluator facts separately from existing request-facing `details` (e.g. an optional in-memory field on domain errors). Preserve current Exit/Mutate messages and existing decision-expression contract. The diagnostic shape does not require a new public failure code, package, storage schema or conversion.
4. Raw diagnostics for unexpected external faults belong in existing private, correlated engine records. For newly projected authored failures whose raw evaluator cause is useful privately, log it once with run/node/field and turn if known, or keep a non-serialized cause on the engine error for the existing logger. Never put that cause in public options or records. Bound the public summary to the existing 10,000-character failure limit and build bounded details by construction. Avoid copying unconstrained retry prompt payloads into parent summaries.

## Inference ordering, ownership and provenance

- Read the logical visit from events. Enforce the D-022 unusable-uncertain guard before any workspace or transform side effects. For session-missing use the existing selected model and effort required by `MissingSessionSchema` and its explicit fresh-session action. Perform known missing/unsafe guards before workspace resolution, input transforms and files. Resolve the model under preparation provenance, allowing existing resolver/refusal semantics. If resolution itself fails when a prior task is known, attach its exact existing provenance and restrict recovery for unusable or missing delivery; never fabricate model/effort. Reuse durable prior missing-session facts if available. Resolver exceptions can never become template/transform errors.
- Partition preparation from invocation. Before creating a turn, keep an immutable reference to `visit.pending`. At a preparation failure, attach the known prior `provenance(pending)` when available, including the original kind, turn and visit IDs, submission and session. Preserve any unreconciled exact retry payload from the durable terminal failure; `visitTurn` currently reconstructs the task but drops its `intentUnconfirmed` flag. Preserve that evidence when rebuilding provenance in this path even across a second preparation failure/restart. On a new visit omit inference provenance. Build neither a new turn intent nor a fabricated submission, status write, acceptance marker or cleanup call during preparation failure. Preserve abort/timeout and safe external-error handling in this partition. Context-admission timeout may truthfully say “no new turn was submitted during preparation” when earlier work exists.
- Keep selected exact saved authored/repair prompts for positive non-submission, the continuation prompt only for a usable session, and the explicit fresh-session choice. The latter can lack a saved prompt (e.g. resume-own lookup failed before the first intent). In that case render from the actual transformed view. Current allowed retries reconstruct transforms and materialize files for a real attempt; keep that contract, including the transformed view used by repair, with unavailable prior-delivery guards first. These preparations can involve a structured coerce before a subsequent author error or already-written earlier files. No retries of an authored failure, compensating deletes, or second preparation inside the classifier. The guarantee here is no *additional* replay induced by this change, and zero new preparation effects on blocked old visits. This does not provide exactly-once coerce/files across process death before an intent or all pre-existing explicitly authorized recovery. Such a guarantee would need durable preparation evidence or a new checkpoint.
- In context admission separate `contextWindow` and each `window.fits` callback from the two canonical-history renders. The latter perform only pure template evaluation against a precomputed candidate view. Existing token-limit/unsupported results retain their codes. Preserve saved prompt/admitted context and avoid history trimming on pending or fresh-session retries. JSON parsing, cloning and token estimation cannot gain authored origin through this helper.
- Keep the existing record-intent → status → invocation boundary, safe transport retry, durable acceptance and cleanup evidence fold. Set a local “provider result received for this intent” fact immediately on successful consume; clear only on establishment of an actual new intent. For a repair renderer or output transform failure attribute the *last consumed* authored/repair/continuation turn, with its real ID, handle and prompt kind. No new repair turn exists until the new prompt is ready. A completed result precludes `definitely-not-submitted` even if an earlier event lacked an acceptance marker or claimed refusal. Store the conservative `delivery-uncertain` enum for incomplete graph persistence, plus safe phase copy indicating receipt of the result. Never invent a durable acceptance marker or set `accepted` merely because the result arrived. Preserve genuine missing-session and unconfirmed-termination evidence. Hold the current handle through the ordinary cleanup fold. Ordinary cleanup errors cannot make an authored failure resumable. Late interruption/timeout follows current precedence. If it wins, keep durable turn events and the appropriate existing recovery restrictions.
- Provider boundary exceptions need a negative path. The current generic fallback in `inference-failure.ts` includes raw `evidence.message`; `contextWindow/fits` also currently sends ordinary render exceptions to that fallback. Separate the source before normalizing: preserve genuine adapter refusals and evidence priority, including #427's actionable recognized model refusal. A foreign evaluator-shaped rejection (domain error, same-name Error or code-shaped object) seen at a harness callback is an unexpected port diagnostic. Privately log the raw exception, project safe internal copy and keep the actual submission/eligibility evidence. Apply at window/fits, synchronous start/resume, iterator/result and cleanup. Once start/resume is entered, a foreign throw before returning a handle is insufficient evidence of non-submission. Retain delivery-uncertain unless positive adapter evidence proves refusal; an inherited ID alone cannot authorize continuation. Before invocation (e.g. a status append) the existing uninvoked-intent proof still applies. A secondary ordinary cleanup fault only adds private diagnostics; higher safety evidence still wins. An unknown external error must never acquire authored provenance from a matching name/code. Do not change the global error-class dispatcher. Existing decision-provider, script dispatch, HTTP overflow and structured-timeout safety classifications remain in force.

## Subloops, workspace and publication

- Child identity checks and atomic child creation stay around the current input work. For an error in a terminal child's output mapping, preserve the existing `records` path so the parent's failure and observed `child_run.finished` remain one append. A mapping failure belongs to the parent subloop node. A nested execution failure belongs to the child node, and the parent records the existing child run/node link, safe message, code and eligibility. Add child-owned `details.childInference` as an optional bounded projection of real child `visitId,turnId,promptKind,submission,sessionId?`. Full retry prompt/context and missing-session recovery stay on the child. Never set parent top-level `failure.inference` from a child. Extend the precise child-wrapper recognizer in `failure-publication.ts:48–56,88–130` to validate that exact bounded optional shape, recurse through legitimate old and new wrappers, and keep recognized legacy internal and recording diagnostics private. Use the same linkage at two nesting levels. Preserve parent-owned recovery and child script consent.
- For workspace templates split evaluation from filesystem work. On a cache miss, RunManager first resolves the authored spec into a temp or fixed-path spec. A template-only render rejection or an empty trimmed result yields a typed local failure value with safe cause and no path. A successful render becomes a fixed path without extra path validation; retain trimming of templates only. `WorkspacePort.resolve(resolvedSpec,runId)` then resolves/ensures the directory. Reuse the fixed/temp union members of the authoring type, without a second public form or length-based revalidation of rendered paths. The port receives no view or template. Cache only after success. Preserve the journal's temp-only ownership claim, physical-path canonicalization and fixed/shared use records. Handler services convert the local failure value to a node error; absent explicit node ID let the executor provide the actual current node. A port rejection remains an exception outside evaluation.
- The file return caller consumes that local result itself: failed render/empty path emits one bounded `return.failed` for that destination; the run retains its terminal status. For unexpected workspace/serialization/write failures during that file channel, use fixed public delivery copy and privately log the actual exception with run/channel. Keep receipt persistence outside any provenance catch: an append error is a storage/finalization error, never a renderer result. Keep current receipt reconciliation and other channel policies. Use separate tests for return-finalization and executing nodes.
- Persistence still uses one projected failure for the new row/event. No SQL, migration, new event type, rewrites, hidden repair, or special read projection. REST and MCP full results can expose structured fields already supported by their schemas. MCP summaries and inspector alerts depend on `message`, so it must stand on its own.

## Alternatives and delivery

The existing no-change behavior leaves a demonstrated parent mapping unhelpful. A global domain-error catch would publish external exceptions. A “trusted” error accepted from arbitrary ports has the same weakness. Promoting every evaluator's raw text after truncation would expose evaluated input, absolute paths or multiline diagnostics. Changing every decision/trigger error or historical row would cross distinct public contracts. Automatic Resume after a deterministic transform can repeat a probe, structured call or provider turn. Forcing all recovery to skip preparation could change repair-template context and context-file behavior; caching full transformed threads would add sensitive durable data and a format/recovery policy. Keeping Liquid inside the filesystem adapter would leave the cause ambiguous across mkdir/journal work. These tradeoffs favor explicit source attribution, bounded field-level explanations and existing recovery ownership.
