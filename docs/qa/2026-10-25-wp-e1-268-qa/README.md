## 2. Defects

**QA-268-01 — minor: append measurement falsely fails after successful finalization recovery.** At `tooling/perf/worker.mjs:521`, the new recoverControl compares the entire RunRecord before/after clearFinalized and reopen. The finalization acknowledgement is correctly rewritten with a new finalizedAt timestamp, so raw record equality is false. Reproduce on the target with `node tooling/perf/measure.mjs append --passes=10 --items=100 --profile=inspector --port=6190 --store-prefix=gg-qa-e1-268- --out=<fresh-temp-output>`. Expected: the successful recovery control accepts the refreshed acknowledgement while checking all other durable state. Actual: exit 1, recoveryOk=false, despite identical 1,100-event hashes and two returns. Both baseline and target burst controls, and both paced controls, retain this failure. The independent public-repository diagnosis proves finalizedAt is the only changed run field; events, thread and all other metadata match. See [recovery-comparator-diagnosis.json](recovery-comparator-diagnosis.json), [recovery-diagnosis.mjs.txt](recovery-diagnosis.mjs.txt), [append-before.log.txt](append-before.log.txt), [append-after.log.txt](append-after.log.txt), and the paced evidence below. No production code was changed. A bounded follow-up should compare the expected refreshed acknowledgement explicitly instead of byte-comparing its prior timestamp.

Initial QA driver defects were corrected without changing production: an implicit harness calibration included one extra progress item; webhook journal event names were wrong; an empty mutate fixture was invalid; and the subloop assertion omitted the documented result envelope. The initial failures are retained in [independent-initial-fixture-errors.json](independent-initial-fixture-errors.json), [independent-second-fixture-errors.json](independent-second-fixture-errors.json), and [independent-initial.mjs.txt](independent-initial.mjs.txt). Final controls were rerun after changing those fixtures/assertions. The baseline loader's initial URL-object cloning error is retained in [baseline-loader-setup-error.log.txt](baseline-loader-setup-error.log.txt); using string parent URLs fixed the instrumentation. These were fixture/setup failures, not unchanged-test retries to green. [harness-corrections.log.txt](harness-corrections.log.txt) records the correction history, including the initial native REST assertion shape error.
