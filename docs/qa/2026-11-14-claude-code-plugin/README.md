# Claude Code plugin native evidence

Issue [#455](https://github.com/Jacob-J-Thomas/GraphGoblin/issues/455). Implementation verification in a fresh Windows Claude configuration with Claude Code 2.1.311 and project Node v22.23.4.

The real Claude CLI loaded the generated GraphGoblin manifest, skills, and stdio MCP process. A loopback Messages API fixture selected the tool calls and checked the returned tool results. The actual built GraphGoblin gateway persisted the draft, run, and events in a disposable SQLite store. This establishes native plugin loading and tool dispatch. The fixture controls model choices. Native macOS has yet to be exercised.

| Behavior                    | Observed result                                                                                                                                                                                                                                                                                  |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Claude validator and loader | Strict local validation passed; all three skills and one MCP server appeared. The CLI launched the default artifact and a copy using paths with spaces, Han characters, and an accented character for the plugin, Node binary, and MCP entry.                                                    |
| Design                      | Claude loaded `/graphgoblin:design-loop` and invoked `list_loops`, `create_loop_draft`, `get_loop_draft`, `validate_loop_definition`, and `save_loop_draft`. API readback found the revised draft, no published version, and no run.                                                             |
| Run                         | An explicit `/graphgoblin:run-loop` draft request used `describe_loop`, `start_run` with `allowDraft`, and `wait_for_run`. The provider-free manual → exit graph succeeded and returned `claude-native-result`. REST found exactly one run.                                                      |
| Inspect                     | `/graphgoblin:inspect-run` used `get_run` and `read_run_events`. Nine persisted events included node execution, the succeeded result, and caller delivery. Inspection worked again from the explicit skills-directory copy.                                                                      |
| Failures                    | Invalid definitions produced schema or graph issues. Missing and invalid keys returned HTTP 401, a reader could not create a draft (HTTP 403), another owner could not read the draft (HTTP 404), and stopping the disposable gateway produced `NETWORK_ERROR`.                                  |
| Copy and rebuild            | A disposable skills-directory copy loaded, was exercised, and disappeared after moving it out. Moving the MCP entry produced actionable rebuild guidance. Rebuilding into the same owned artifact updated the entry path. Generated configuration and retained evidence contained no bearer key. |

The first controlled fixture attempts reached the positive flows but assumed a freshly launched headless session would expose MCP tools on its first model request. Claude can offer `WaitForMcpServers` during initialization. The fixture now waits through that real Claude tool when advertised before requesting a GraphGoblin tool. The test preserves the failed attempts separately. The production skill workflow does not depend on fixture-only transport or settings.

The first passing full native component run used the candidate Claude and MCP builds and the production gateway build from the #344 parent checkout. The gateway source is unchanged by #455. Independent QA and a full exact-source candidate verification remain separately tracked.
