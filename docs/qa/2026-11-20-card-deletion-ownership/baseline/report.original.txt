## P1 — Deleting an edge’s target transfers the lost row claim to another connection

**Trigger.** The retained current-format device copy has Decision rows `yes/yes/maybe`. The first two rows claim the same `e1` on `yes`. The stored edges are `s1 start/out → pick [220]`, `e1 pick/yes → done [500,200,650]`, `e1 pick/no → other [670]`, and `m1 pick/maybe → done [550,440,700]`. I restored the exact captured definition and ownership table to a disposable IndexedDB record, with fresh loop and server-base bookkeeping. Readback confirmed both objects matched the retained capture. The capture’s SHA-256 is `40fd7ee7b96e0f5f78f50442ece0f1230d489c93d8be1747019c87531dd63974`. [Captured input](https://github.com/Jacob-J-Thomas/GraphGoblin/blob/afc96e2350daa6ff8d3b6d733150218e3675a2aa/docs/qa/2026-11-19-decision-row-ownership/independent/replay-inputs/prior-live-collision.json)

I used the normal editor in headless Microsoft Edge and checked the complete definitions through HTTP GET and a read-only IndexedDB transaction after each saved state.

| Browser action | Observed result |
| --- | --- |
| Reopen the captured draft and edit the second route’s ID to `affirm` | The editor first showed “Saved on this device only”. After the repair it showed “All changes saved”. The only change to the complete captured definition was the second route ID. All four ordered edges and manual geometries survived. |
| Open Done and click **Delete node** | Done and its two incident records disappeared as intended. The unrelated `e1 pick/no → other [670]` became `e1 pick/yes → other [670]`. Readback of the server and synced device matched. |

I reproduced the same result with a fresh, map-free fixture admitted through `POST /loops` (201). Its second authored route is already `affirm`, and its unclaimed `no → other` record survives import. Both failure paths differed from the requested deletion at exactly one JSON location, `/edges/1/from/port`, changing `no` to `yes`. The same browser operation preserved every surviving field when the Other edge had a unique `e2` ID. Separate store controls preserved the shared survivor when both records still had identifiable row owners, and preserved the entire edge list on an unrelated Description edit.

**Cause and scope.** The deletion removes incident records before the shared edit path reconciles ownership. Reconciliation reads the old row claim against the shortened edge list. The sole-holder shortcut then identifies the surviving `e1` as the deleted `yes` record, even though the surviving physical record was previously present on `no`. The valid Yes row writes its port onto that record. The removal preview subsequently treats the survivor as Yes-owned. The row itself was never renamed or removed in this operation. The defect is an incomplete correction of the accepted shared-identity problem. Current-format drafts deliberately retain stranded records for repair. Keep the unique-ID, independently identifiable shared-holder and restored-map repair controls. Expected post-delete edges are exactly `s1 start/out → pick [220]` and `e1 pick/no → other [670]`, in that order.
