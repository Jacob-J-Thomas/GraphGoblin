## Defect

### D1 (#205, low): Codex `max` is offered, saved and recorded as `max`, but the CLI receives `xhigh`

- **Reproduce.**
  1. Start the built API with `GG_CODEX_BINARY` set to the recording fixture (s5 setup).
  2. Create a loop with a Codex inference node. Every Codex catalog model lists `minimal`, `low`, `medium`, `high`, `xhigh` and `max`.
  3. In the editor choose Effort `max` (the option text is plain `max`), close the dialog, publish and run.
- **Expected** (#205: "saved values … match the actual provider request"): the provider receives `max`. Otherwise the editor does not offer a value the provider never receives, or it states the substitution, and the run record shows what was sent.
- **Actual.** The saved draft has `effort: "max"`. The run's session row (`/runs/{id}/sessions`) records `effort: "max"`. The Codex CLI argv carries `--config model_reasoning_effort="xhigh"`. The effort description says only `Default effort: high.`
  - s5 `205-ui-codex-max`: offered `max`, saved `max`, sent `xhigh`, session row `max`; [205-codex-max-selected.png](205-codex-max-selected.png).
  - API-only: s4 `205-codex-max-mapping`.
  - LLM decision with explicit `max`: s4b, argv `model_reasoning_effort="xhigh"`.
- **Cause.** `mapEffort` in `packages/adapter-codex/src/options.ts:25-27` (present since M4) maps `max` to `xhigh`. The seeded Codex catalog lists all six canonical efforts. This is documented in `docs/06-harness-integration.md` (Codex options table and catalog paragraph) and `docs/guide/06-settings-and-secrets.md`, but not in the editor or the run record.
- **Why earlier QA passed it.** The #205 QA rows "Every offered supported effort requests same value codex inference/llm" (`docs/qa/2026-10-23-wp-f2b-205-qa/README.md` rows 93 and 94, round-2 rows 59 and 60) observed the port-level `FakeHarness` request, which sits above this mapping.
- **Severity.** Low. The run succeeds at the nearest supported level. The impact is untruthful display and recording of one value, against the U16 outcome "visible selections … accurately describe what can execute".
- **Fix options.** Choosing between them is an orchestrator or owner decision.
  - Stop offering `max` for Codex: remove it from the Codex catalog efforts and refuse it with `EFFORT_UNSUPPORTED`, with an operator reset of stored values per ADR-0020.
  - Keep the alias but label it in the editor (for example "max (sent as xhigh)") and record the sent effort in the run.

## Human QA items

### H1 (#33): Is the three-context-mode design what you intended?

- **Uncertainty.** The owner described three context modes:
  - fresh/isolated with the authored task and selected inputs;
  - current main-loop context supplied deliberately;
  - a conversation owned by the node within the execution.

  ADR-0052 implements them without a separate context-mode field. They map onto the existing Session policy dropdown (`fresh` default or `resume-own`, raw policy values as option text) plus the existing prompt template, Context input transforms and context files. All three behaviours work as specified (above). Whether this representation is explicit enough for authors is a product judgement.

- **Steps.**
  1. On a running build with disposable data, open any loop in the editor.
  2. Add or open an inference node and stay on its Settings tab.
  3. Read Session > Policy and its help text. Choose `resume-own`, then read and set **Reset after visits**.
  4. Open the Context tab and look at the input transforms and context files.
- **Expected observations.**
  - Policy lists `fresh`, `resume-previous`, `resume-named`, `resume-own`, with `fresh` preselected.
  - The help text names deliberate main-loop context through the prompt, Context input transforms or context files, and states that resume-own keeps only this node's conversation in this run and harness.
  - Reset after visits appears only for `resume-own`, outside Advanced, blank by default, saying "Blank means no automatic reset. Main-loop context is kept."
  - Decide whether a dedicated context-mode control or friendlier option labels are wanted.

### H2 (#265): Is it acceptable that a parent run can only be resumed through the API after its child recovers?

- **Uncertainty.** When a missing session occurs inside a subloop child, the parent fails with the child's cause. The parent's message ends "Choose Start fresh session for node "worker"", but that button exists only on the child's inspector page, reached through the alert's "failed child run" link. After the child's choice the parent stays failed. The inspector shows no Resume for failed runs (`RunControls` renders Resume only for paused runs), and `docs/guide/07-troubleshooting.md` says to "use the API Resume on the containing run".
- **Steps.**
  1. Publish a child loop with an inference node using `resume-own`, a wait-for-input node and a gate that repeats the inference node.
  2. Publish a parent loop with a subloop node pointing at the child, and run the parent.
  3. After the child's first visit, make its provider conversation unavailable. This is a deliberate test action, for example a fixture or a removed session.
  4. Answer the child's wait so it fails.
  5. Open the parent run in the inspector, follow "failed child run" and choose **Start fresh session for worker**.
  6. Return to the parent run.
- **Expected observations.**
  - The parent shows `Failed: HARNESS_SESSION_MISSING` naming the child run, handle and node, a "failed child run" link, and neither a recovery nor a Resume button ([265-parent-after-child-missing.png](265-parent-after-child-missing.png)).
  - The child shows the choice ([265-child-missing.png](265-child-missing.png)).
  - After the choice the parent still has no Resume button ([265-parent-after-child-choice.png](265-parent-after-child-choice.png)), and only `POST /runs/{parent}/resume` (or MCP) completes it.
  - Decide whether this browser flow is acceptable or whether the parent needs a UI control.

## Attempts and corrections

Every check that failed on a first attempt is kept with its own log. None of the corrections was a retry of unchanged code to get a pass.

- **s3 `265-different-id-claude`.** I expected an identity error; the fixture's immediate exit raced the adapter's kill (O1). I added the `linger-ms.txt` control and re-ran the case in s3b.
