## Limits (what this QA does not establish)

- **L1.** The tests do not deterministically detect a regression of the staging itself. A plain revert passes in a single run (M11). The staging's protective effect is shown only under a modeled late finalizer (M09 against M10), not by reproducing the real GC timing that #584 observed on macOS. Ten clean runs here, plus the author's 2 full-suite and 2 focused runs, are consistent with the fix but cannot prove the race is gone. REVIEW.md R1 is the matching follow-up candidate.
- **L2.** Windows only. The original #584 failure was on macOS. The macOS hosted job is the launcher job, not the API suite.
- **L3.** API coverage was not run locally, as the brief directed. At my last readback (about 04:25Z), hosted CI run 45753245193 on `c7559bff` showed macOS launcher, Windows launcher, Template image, Repository checks (which includes typecheck, lint and format check) and Coverage as success. Browser was still in progress and Gates was queued. I did not wait for them and did not read the coverage numbers. I did not re-run typecheck or lint locally and rely on that job and the author's logs `03`/`04`/`08`/`09`.
- **L4.** The mutation harness runs the copies from `G:/ggq/tmp` through a scratch Vitest config. It resolves `@graphgoblin/*` by alias and dedupes `vitest`. The unchanged control (M00) passing 31/31 shows the harness is faithful, but it is not the repository's own config file.
- **L5.** The native checks compare DB and WAL bytes and directory listings only. `-shm` contents were not compared, which the reader exception allows. The process starts used fake or missing harnesses, so readiness against real providers is out of scope.
- **L6.** The repository QA packet `docs/qa/2026-11-24-preflight-defaults-catalog/` has not been updated for these commits. That is left to the orchestrator.
