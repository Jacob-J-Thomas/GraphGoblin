## #242 Enforce awaited parent-child execution

### Before-fix reproductions (base code, fake ports)

`packages/engine/src/awaited-children.test.ts`, run with the base `subloop.ts` and
`run-manager.ts` (the product files restored from `8589204`, the new tests kept):

| Test                                                                                             | Result on the base code                                                   |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| a stale child wake never answers a later input park of its parent                                | failed: parent `succeeded`, expected `waiting`                            |
| a stale child wake never reaches the next visit of the same subloop node                         | failed: parent `succeeded`, expected `waiting` on the second child        |
| a child that returns no output leaves the result absent in its parent                            | failed: summary carried `result: null`                                    |
| an unfinished child is never mapped: a parent woken before its child was resumed awaits it again | failed: parent mapped the running child and continued, expected `waiting` |

The constructed crossing (WP-C3 Opus review, `FOLLOWUPS.md`): the first child finishes after the
parent's park committed and before the parent's post-park check, so the child's own notification
and the check both observe the parent waiting on that child. The child's notification is held on
its single re-read of the parent inside `wake()` (one delayed read through the fake run port)
while the check wakes the parent, which runs on to its next park; then the held read returns.
Parent logs on the base code:

- Input park: `run.waiting` for `ask` at seq 13, then `run.woken {nodeId: ask, reason: child,
payload: {childRunId: <first child>}}` at seq 14; the wait node finished with
  `{wokeAt, reason: "child"}` and the parent succeeded without any input.
- Next visit: `child_run.started <second child>` at seq 16, `run.waiting` at seq 17, then
  `run.woken {reason: child, payload: {childRunId: <first child>}}` at seq 18 and
  `child_run.finished {childRunId: <second child>, status: "running"}` at seq 20; the parent
  succeeded while the second child stayed `waiting` (orphaned).

### Changes

- `RunManager.notifyParent` passes the `waitId` of the park it observed; `wake()` with reason
  `child` is accepted only by a park of kind `child` for that child run; any refusal is a no-op for
  the notifier (the paused case is reconciled on resume).
- The subloop handler takes the awaited child from its recorded park (or, before a park, from the
  visit's `child_run.started`) and never maps an unfinished child: it parks on it again.
- Absence: a child that returned no output leaves `result` out of the parent's summary and custom
  mapping bindings and removes `resultTo.var`; JSON `null` stays `null`.
- Exit-to-Event chaining retired: the exit `event` destination, `ReturnDeliveryPort.publishEvent`,
  the API's in-process event bus, the run-chain guard and `source: run:<id>` events are removed.
  External intake (`POST /events` to event triggers, inputs and signals to a run's observed wait)
  stays. Stored data is not rewritten; the CHANGELOG upgrade note has the detection queries.

### Tests

- Engine, `awaited-children.test.ts`: the four reproductions above; JSON `null` versus absence; a
  later visit without output removing an earlier result and a custom mapping seeing no `result`; a
  child exit (authored Exhausted) never finishing its parent, with the global append order child
  `run.finished` < parent `run.woken` < parent `after`; nested children; a leaf that finished while
  the process was down (finalization never ran) recovered with one continuation per ancestor; a
  parent interrupted between its durable wake and its status write recovered once, twice.
- API, `subloop-restart.test.ts` (built `dist/main.js`, disposable store, SIGKILL): eight kills at
  0 to 250 ms after a nested leaf's input (and one before the answer was confirmed), restart on the
  same store, one continuation per parent each time; the two constructed durable states above
  recovered by the built API and a second restart finding nothing to do. One run recorded where
  the kills landed: before the answer, during the leaf, during the middle run, during the top run,
  and after completion.
- API: exits with an `event` destination are refused (400); external Events still start every
  matching trigger, and finished runs record no Event.
- Domain: the format-3 converter refuses an exit with an Event channel (`V4_DEFINITION_INVALID`
  at the destination path).

## #251 Ordinary failure and recovery semantics

### Before-fix reproductions (the #242 commit, fake ports)

All 16 new or flipped tests fail with the #242 product code (`handler.ts`, `errors.ts`,
`subloop.ts`, `run-manager.ts` restored from the #242 commit, the new tests kept): the twelve
in `child-failure-parity.test.ts`, both `ADV-015` failed/cancelled cases in `adversarial.test.ts`,
and the two flipped `waiting.test.ts` cases (G12). The typical failure is
`expected 'succeeded' to be 'failed'` (or `'cancelled'`): the parent mapped
`{ status: "failed" }` into `lastOutput` and continued. G12 itself: a depth-exceeded failure two
children deep finished the top-level run `succeeded`.

### Changes

- `ChildOutcome` carries the child's runtime `failure` (absent for an authored Failure exit).
- The subloop handler records `child_run.finished` and then, for a runtime failure, fails the
  parent with the child's code and resumability (`subloop child <id> failed: <message>`,
  `details: { childRunId, childNodeId?, childDetails? }`); for a cancelled child it throws
  `ChildCancelledError`, which the executor turns into a cancel request from the child
  (`run.cancel_requested`, actor `{ kind: 'run', id: <child> }`) and `run.cancelled`.
- An explicit resume of such a parent re-executes the subloop node; when the log shows a
  `run.failed` after the node's park (or child start), the handler resumes the same child
  (`HandlerServices.resumeChild`, actor the parent) and parks on it. Crash recovery has no such
  `run.failed`, so it re-delivers the failure and never resumes the child on its own.
- The run inspector links a subloop failure to the **failed child run**.

### Parity matrix (engine, `child-failure-parity.test.ts`)

Same node inline and inside a child; parent compared with the inline run.

| Class         | Failing node                        | Inline failure (code, resumable)               | Parent                                               | Resume                                                                      |
| ------------- | ----------------------------------- | ---------------------------------------------- | ---------------------------------------------------- | --------------------------------------------------------------------------- |
| transient     | script exits 3                      | `SCRIPT_EXIT_CODE`, true                       | same code and resumability at `sub`, names the child | both succeed; the same child re-ran `work` (attempts 1, 2)                  |
| transient     | script times out                    | `SCRIPT_TIMEOUT`, true                         | same                                                 | both succeed                                                                |
| deterministic | expression decision throws          | `EVALUATION_EXPRESSION_FAILED`, false          | same, not resumable                                  | both refused (`INVALID_STATE`)                                              |
| deterministic | depth exceeded two children deep    | `SUBLOOP_DEPTH_EXCEEDED`, false                | every ancestor fails with it, not resumable          | refused                                                                     |
| provider      | harness quota exhausted             | `HARNESS_QUOTA_EXHAUSTED`, true                | same                                                 | both succeed; each continued its recorded harness session                   |
| provider      | classifier answers an undeclared id | `EVALUATION_INVALID_RESPONSE`, false           | same, not resumable                                  | both refused                                                                |
| bug           | mutation expression throws          | `INTERNAL_ERROR`, true                         | same                                                 | both fail again with `INTERNAL_ERROR`; nothing consumed, `after` never runs |
| cancellation  | input wait cancelled                | run `cancelled`                                | parent `cancelled`, request recorded from the child  | both refused                                                                |
| authored      | Failure exit returning data         | `failed` with `outcome: failure`, no `failure` | parent `succeeded`, child result as data             | not applicable                                                              |

Repeat and recovery: two parent resumes resume the same child twice until it succeeds (one child,
attempts 1 to 3, two parent `run.failed`); a child resumed directly lets the parent continue on
its own later resume; a nested failure reaches the root with the leaf's code and resuming the
root resumes the whole chain; a crash after the child's failure woke the parent fails the parent
exactly once at recovery without resuming the child. API (`subloop-failure.test.ts`): the same
through REST, `POST /runs/{id}/resume` of the parent resuming the child's harness session, and a
child cancelled through `POST /runs/{id}/cancel` cancelling its parent.

## Review round 2 (GPT-6.1 Sol review of `091314a`)

### P1: a stored Event destination executed, then wedged

Before the fix (`apps/api/src/retired-event-destination.test.ts`, all four failing on `1d7c46d`,
the round-1 code merged with `4958713`): loop detail, version, version-list and export reads
answered `500` (`RESPONSE_INVALID`); `POST /loops/{id}/runs` answered `202` and the run executed;
runs pinned to a published version or a draft-run snapshot holding the destination executed past
their wait and finished `succeeded` with `finalized_at` null (the delivery event failed
validation, so the run was never finalized and an awaiting parent never woke).

Fix: `retiredEventDestinations` (domain) finds every exit destination with `kind: "event"` in the
stored JSON; `definitionUpgradeRequired` and `assertCurrentDefinition` (engine) turn it into
`LoopUpgradeRequiredError` (a non-resumable `RunFailureError` with code `LOOP_UPGRADE_REQUIRED`
and `details: { loopId, versionId, version, paths }`, message naming the version and the repair).
It is checked at admission (`resolveVersion`, so manual, API, MCP, cron, event, poll, webhook and
subloop starts), on replay, at every executor start of a pinned run (the run fails before its next
node; an awaiting parent then fails with it under #251), and on every API read that serves a stored
definition (loop detail, versions, version, export, publish of the stored draft). The API error
handler answers 409 `LOOP_UPGRADE_REQUIRED` with `loopId`, `versionId`, `version` and `paths` as
problem extension members. Nothing is stripped or rewritten; `DELETE /loops/{id}` still works.
After the fix the four API tests and four engine tests (`stored-definition.test.ts`) pass.

### P2: the result variable was set before the variable merge

Before the fix (`awaited-children.test.ts`, "with a parent-wins/child-wins variable merge"): with
`vars.answer = "old result"` inherited by a child that returned no output, both strategies
restored `"old result"`; with `child-wins`, a child returning JSON `null` or data also ended with
`"old result"`. Fix: `resultTo.var` is assigned or removed after the merge. All six cases pass.
