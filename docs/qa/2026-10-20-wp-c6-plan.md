## #242 Enforce awaited parent-child execution

### Before-fix reproductions (base code, fake ports)

`packages/engine/src/awaited-children.test.ts`, run with the base `subloop.ts` and
`run-manager.ts` (the product files restored from `8589204`, the new tests kept):

| Test                                                                                             | Result on the base code                                                   |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| a stale child wake never answers a later input park of its parent                                | failed: parent `succeeded`, expected `waiting`                            |
| a stale child wake never reaches the next visit of the same subloop node                         | failed: parent `succeeded`, expected `waiting` on the second child        |
| a child that returns no output leaves the result absent in its parent                            | failed: summary carried `result: null`                                    |
| an unfinished child is never mapped: a parent woken before its child was resumed awaits it again | failed: parent mapped the running child and continued, expected `waiting` |

The constructed crossing (WP-C3 Opus review, `FOLLOWUPS.md`): the first child finishes after the
parent's park committed and before the parent's post-park check, so the child's own notification
and the check both observe the parent waiting on that child. The child's notification is held on
its single re-read of the parent inside `wake()` (one delayed read through the fake run port)
while the check wakes the parent, which runs on to its next park; then the held read returns.
Parent logs on the base code:

- Input park: `run.waiting` for `ask` at seq 13, then `run.woken {nodeId: ask, reason: child,
payload: {childRunId: <first child>}}` at seq 14; the wait node finished with
  `{wokeAt, reason: "child"}` and the parent succeeded without any input.
- Next visit: `child_run.started <second child>` at seq 16, `run.waiting` at seq 17, then
  `run.woken {reason: child, payload: {childRunId: <first child>}}` at seq 18 and
  `child_run.finished {childRunId: <second child>, status: "running"}` at seq 20; the parent
  succeeded while the second child stayed `waiting` (orphaned).

### Changes

- `RunManager.notifyParent` passes the `waitId` of the park it observed; `wake()` with reason
  `child` is accepted only by a park of kind `child` for that child run; any refusal is a no-op for
  the notifier (the paused case is reconciled on resume).
- The subloop handler takes the awaited child from its recorded park (or, before a park, from the
  visit's `child_run.started`) and never maps an unfinished child: it parks on it again.
- Absence: a child that returned no output leaves `result` out of the parent's summary and custom
  mapping bindings and removes `resultTo.var`; JSON `null` stays `null`.
- Exit-to-Event chaining retired: the exit `event` destination, `ReturnDeliveryPort.publishEvent`,
  the API's in-process event bus, the run-chain guard and `source: run:<id>` events are removed.
  External intake (`POST /events` to event triggers, inputs and signals to a run's observed wait)
  stays. Stored data is not rewritten; the CHANGELOG upgrade note has the detection queries.

### Tests

- Engine, `awaited-children.test.ts`: the four reproductions above; JSON `null` versus absence; a
  later visit without output removing an earlier result and a custom mapping seeing no `result`; a
  child exit (authored Exhausted) never finishing its parent, with the global append order child
  `run.finished` < parent `run.woken` < parent `after`; nested children; a leaf that finished while
  the process was down (finalization never ran) recovered with one continuation per ancestor; a
  parent interrupted between its durable wake and its status write recovered once, twice.
- API, `subloop-restart.test.ts` (built `dist/main.js`, disposable store, SIGKILL): eight kills at
  0 to 250 ms after a nested leaf's input (and one before the answer was confirmed), restart on the
  same store, one continuation per parent each time; the two constructed durable states above
  recovered by the built API and a second restart finding nothing to do. One run recorded where
  the kills landed: before the answer, during the leaf, during the middle run, during the top run,
  and after completion.
- API: exits with an `event` destination are refused (400); external Events still start every
  matching trigger, and finished runs record no Event.
- Domain: the format-3 converter refuses an exit with an Event channel (`V4_DEFINITION_INVALID`
  at the destination path).
