**Qualifications:**
- These are tracked samples. They support the targeted correction but are **not** whole-heap accounting, and I infer none. Complete accounting rests on source data flow, below.
- The pressure scenario uses the fixed seed `438`. In both baseline and candidate, its deterministic size sequence produced **no record larger than 65,536 bytes**, so the oversized-marker sub-stimulus named in the matrix scenario text was **not reached**. No row-2 predicate depends on it, and the 65,536-byte record edge was covered only by historical, non-repeated evidence. I report it as unreached, not as a failure.

**Source reasoning** (read-only, `apps/api/src/windows-log/gateway-log-writer.ts` lines 408–489):
- `takeBatch` splices the dequeued records out of the queue. For a single record it passes that record's own `bytes`; for several it makes one `Buffer.concat`. The `taken` array is local and goes out of scope on return, so across `verifyActiveName` and `handle.write` the writer holds one encoded copy of each in-flight record.
- A failed batch is discarded before `rollback` runs, so the rollback does not hold the bytes.
- This matches the measured single copies of R1–R3, including R2, which carries an acknowledgement. That means the acknowledgement closures do not retain the record bytes.

## 6. Adversarial observations and qualifications

None of these is a product defect.

1. **`rc3-facts-retained.statesNoLogChanged` is `false` on all three candidate routes (true in the baseline).** The harness regex `/no log file was changed/` does not match the new admitted wording "no **gateway** log file was changed". The predicate is informational, and exact-text equality (pass) is the oracle. The admitted final sentence is present verbatim. This is a harness wording artifact.
2. **`rc3-holder-released-before-positive` is a hard-coded `pass` in `f3-in-use-guidance.mjs`.** It relies on `holdExact` throwing otherwise. I verified the exit, close, EOF, birth absence and ordering independently from the raw V4 receipts (sections 3.6 and 3.7).
3. **`launcher-quiet-start` checks only the exit code.** I verified 0/0 stdout/stderr bytes from the raw launcher receipt.
4. **`decisiveWitness.observed: false` on the candidate is not a vacuous pass.** The head capture was observed, and the same op 8/9 hold points (196,608-byte pre-write `lstat` and write) were reached with full single copies of R1–R3.
5. **`rc2-retained-cap` peaks exactly at the 262,144-byte cap.** This is the moment R0 is in flight and R1–R3 are queued, matching logical pending. The pass condition is ≤ cap.
6. **The oversized-marker sub-stimulus in the pressure scenario was not reached** in either build (fixed seed 438; no record over 65,536 bytes). No predicate covers it.
7. **Logger-level locus unchanged.** A future code path that logs a raw Node parser error object directly through the managed logger would still serialize `rawPacket`. The correction is the managed `clientErrorHandler` only. Shell mode keeps Fastify's default by design.
8. **Request pairing.** In both builds, the chunked P2 request has an "incoming request" record without a "request completed" record (the socket is destroyed mid-body). `sink-records-complete` judges JSON-line completeness, not request pairing.
9. **Not exercised in this run** (plan §9): dialog presentation; native 408 and 431 client errors; other runtimes; cross-user or cross-session holders and races; fatal termination; nonlocal filesystems; real disk-full (ENOSPC was a seam). Native whole-process memory was not measured, and native rotation is sampled.
