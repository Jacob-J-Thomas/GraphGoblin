## Findings

1. **Observed: `/` means two different things.** The root type error and the unknown empty-named root key both report path `/`; only the message tells them apart. Under RFC 6901, `/` points to the member named `""`, and the whole document is `""`. This is the API's existing, deliberate root convention (`request-validation.ts:30`), and the driver expected it. So it's a design decision for the owner, not a regression from this patch.
2. **From the source only, not run: the same clash can occur in `errors.ts:133`.** The validator gives `/` for both the root (`[]`) and an empty-named root member (`[""]`), and the handler treats `/` as the root. An unknown key inside a strict object stored under an empty-named root member would therefore come out as `/key` instead of `//key`. That needs a request body schema whose top level allows arbitrary keys and holds strict objects. I didn't check whether any route has one, so it's unconfirmed.
