## Blocking findings

1. **B1 — P1: A parent's consent can retry a different, newly uncertain child script.** `packages/engine/src/run-manager.ts:3069` reads the parent's last `run.resumed` and forwards its boolean consent, while `resume()` obtains the child's _current_ sequence. `packages/engine/src/run-recovery.ts:47` stops requiring parent recovery as soon as the parent leaves `failed`. This opens a real scheduling interleaving: child script A fails uncertainly; the user consents to parent Resume; while the parent executor is pending, another client can Resume child A; A completes and child B fails uncertainly; the parent then resumes B with its old consent for A. The probe observed three script dispatches before releasing the parent and **four afterwards**, with both runs succeeding. The fourth dispatch is B's unreviewed retry. This violates #256's observation binding, #251's parent ownership and #321/ADR-0059's deliberate consent for uncertain work.

   Smallest fix: durably bind parent recovery to the exact child failure/visit observed when admitting the parent command, and refuse/propagate a changed child failure instead of capturing a new child observation when forwarding consent. Preserve parent ownership while that accepted recovery is pending. Add this two-client interleaving through the public ports/API; do not rely on a bare inherited boolean. Reproduction: `node docs/qa/2026-10-26-pr422-audit-r2/component-probes.mjs`; see the first record in [component-probes-timing.log.txt](component-probes-timing.log.txt). This is a controlled scheduler interleaving through injected public event/script ports with fake execution, not live-provider evidence. No manager private state is accessed or patched.

2. **B2 — P2: Every snapshot now scans and decodes the entire event history, regressing #418's bounded inspector path.** `packages/engine/src/run-manager.ts:1175` calls `events.read(runId)` without a boundary; `apps/api/src/routes/runs.ts:186` invokes it for every `GET /runs/:id`. The unchanged live refresher reads this endpoint after each coalesced batch. This reintroduces work proportional to all accumulated history on routine status reads, including every stored prompt/progress payload, although `docs/09-frontend-and-pwa.md:288` promises bounded work independent of history length.

   A real SQLite/built-API probe seeded valid unrelated signal events through the public event store. At 6 / 1,006 / 11,006 events, each GET decoded **all** 6 / 1,006 / 11,006 rows, respectively; the last read materialized **12,794,967 bytes**. With byte-count instrumentation disabled, the three GETs took approximately **6 / 37 / 206 ms**. The old public `getRun()` path performed zero history reads and took approximately 1 ms. These are local measurements, not a latency SLA; the decisive regression is the unbounded read. The earlier 529 ms capture includes byte-count instrumentation and is not presented as bare endpoint timing.

   Smallest fix: derive the recovery observation from bounded/indexed facts (lifecycle, reached-node identities, current consent and admitted intent), preserving the single policy. Keep full historical reconstruction for an admitted Replay command, outside routine live polling. Add a backend read-volume regression that increases old history without increasing snapshot work. Reproduction: the same component probe, with real SQLite and the built API; [timing and row counts](component-probes-timing.log.txt). Keeping #418's indexes alone does not preserve its behavior.

3. **B3 — P1: Required standalone acceptance callers were not migrated to the new Resume contract.** `apps/api/scripts/wait-restart.acceptance.mjs:241` sends `{}` and ignores the failed response, then times out waiting for the paused run to finish. `apps/api/scripts/prompt-restart.integration.mjs:257` also sends `{}` while expecting HTTP 409; both inherited-session cases now receive HTTP 400. The newly required `observedSeq` rejects these requests before the intended behavior is exercised. These are deterministic contract failures introduced by this PR, not the unrelated timing-failure class.

   Smallest fix: have each maintained acceptance caller read/review `recovery` and send that observation, preserving its original status/identity assertions and explicit script consent where applicable. Check the other remaining empty-body consumers in `apps/api/scripts/missing-session.integration.mjs:184` and `apps/api/scripts/failure-evidence/`; do not weaken the expected refusals. Verify the complete required acceptance chain afterwards. Reproduction: `pnpm.cmd test:wait-restart` fails at line 242 ([local log](wait-restart.log.txt)); `node --test --test-name-pattern='blocks unaccepted authored work' apps/api/scripts/prompt-restart.integration.mjs` fails **2/2**, `400 !== 409` ([log](prompt-restart-focused.log.txt)).
