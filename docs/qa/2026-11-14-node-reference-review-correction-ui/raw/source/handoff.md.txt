## Corrections

### U1: row identity across a reference-only remount

**Cause, confirmed.** The rename replaces the node's config object, and the `formEpoch` key remounts `SchemaForm`. Collection row ids are looked up in the dialog's `DisclosureIdentities` WeakMap by config object, and the repaired object had no entry. Fresh row ids broke the `#row:<id>` open-state keys and `keepFocusThrough`'s `data-row-id` match.

**Fix.** `forms/disclosures.ts::carryCollectionIdentities(identities, previous, next)` gives `next` the row snapshot recorded for `previous`. It does so only when every recorded collection path has the same list length in both values, `next` has no snapshot yet, and `previous` has one. Rows are never matched by content. `NodeEditorDialog.commitId` reads the exact pre-rename config from the store and calls `renameNode`. On success it carries the identities to the repaired config inside the `keepFocusThrough` action, before the batched remount renders. No store or new subsystem is involved. Existing remove, move, add and undo identity paths are unchanged.

### U2: review rows must prove the current field

**Fix.** `RenameReport` now carries `definition`, the draft as the rename left it (store `renameNode`). `RenameNotice` offers a row as an action only while the row's node has the same config object as in that definition. History restores the same immutable objects, so undo of later edits makes the rows actionable again. Otherwise the row is listed as information, and a sentence names the changed nodes: "`audit` changed after the rename. Its places show where they were then and no longer open a field." The summary counts, the number of places and the list are unchanged. Loop-level, script and deleted-node rows stay informational as before.

**Design choice.** This withdraws the action; it does not follow the moved row. It is conservative: any config edit to that node withdraws that node's links until undo restores the rename-time config, including a non-structural edit or a fix of the warned field itself. The store has no general path-rebasing mechanism, and adding one was outside the brief.

### U3: held section JSON is released only by the author

**Cause, confirmed.** `JsonText` derived `error = undefined` when a valid held candidate was `sameJson`-equal to the current section value. Its effect then reported the hold cleared. `setFieldError` treated that as an authored change, adding a step and erasing redo.

**Fix.** In `forms/fields/json.tsx`, a held valid candidate now always derives `PENDING_JSON` (`candidate.error ?? PENDING_JSON`). The hold ends only by the existing author paths:

- typing to equality (`onChange`), unchanged
- Apply
- Cancel
- discard, including an external discard from the validation panel

Re-reporting the identical entry is a no-op in `setFieldError`. A changed message on the same text is the existing message-only refresh, with no step. No confirmation workflow was added, and held text is never rewritten.

**Behavioural consequence.** A held buffer that a rename (or a sibling fix or remount) makes equal still blocks structured-editor switching and Publish until Apply or Cancel, as any held section JSON does. Applying it then is an ordinary step that clears the hold and leaves the definition object unchanged.

## Remaining facts and limits

- **Settings form.** Only the node dialog has caller-kept disclosure identities. `LoopSettingsPanel`'s settings `SchemaForm` keeps its own disclosure state, which restarts when a rename repairs settings (as on its other remounts). I did not change or verify that form's collection rows; the U1 finding concerned the node dialog.
- **Carry precondition.** The carry needs the store's pre-rename config to be the object the form last remembered. For decision configs normalized by the dialog, or another path where they differ, no snapshot is found and behaviour is as before (fresh rows), never content-matched.
- **U2 scope.** The withdrawal is per node and conservative, as described above. Following a moved row is not implemented.
- **U3 generality.** The change applies to all explicit section-JSON holds, not only renames. A sibling fix or remount that makes held text equal no longer auto-releases it. The existing JSON, parent-refresh, Apply/Cancel/confirmation and history tests stayed green in run 3.
- **Correction batches.** One evidence-based correction batch was used. The second permitted batch was not needed.
