**1. Parser-error privacy.** In managed mode only, `serve()` now gives Fastify its own handler for errors that Node reports before a request exists.
- **What it does:** it copies Fastify's default behaviour exactly: the 400/408/431 responses, the early return on a reset or already-closed socket, and closing the connection. The difference is the trace record, which now holds only `{ clientError: { statusCode, code } }`. `code` is included only if it looks like a Node error code (`^[A-Z][A-Z0-9_]{0,63}$`).
- **What is unchanged:** Pino's error serializer, so the private engine error name, message and stack stay in the log; the configured log level; and Fastify's default handler in shell mode and `createTestApp`.
- **First failure (unmodified code):** the managed log record held `err.message` and the whole 177-byte `rawPacket` as a list of numbers. Decoded, it contained all four canaries (path, query, bearer token, header).
- **After the fix:** a real malformed packet and a header-overflow packet each get Fastify's exact 400 or 431 response bytes, and the connection closes. A normal `/healthz` request afterwards returns 200. The client-error records contain only the allowed fields. No key, string or decoded byte array in any record contains a canary.
- **Control:** an app built the ordinary way still logs the raw packet at trace.
- **Unit tests:** they cover the 408, ECONNRESET, closed-socket, unwritable-socket and rejected-code cases, and info level.
- **Gap:** the 408 timeout is tested only with a fake socket.

**2. Encoded-data cap.** A new synchronous `takeBatch()` takes the records off the queue and joins them into one buffer before any await, so the original record buffers are released immediately. `writeBatch()` now holds only that one buffer and returns as soon as the write settles. A failed write hands its rollback position back to `cycle()` instead of waiting on the rollback while still holding the bytes. `cycle()` now keeps only the next record's length across rotation. Ordering, one write in flight, per-record acknowledgements, drops, limits, rollback and backoff are unchanged.
- **Test 1:** it reproduces the reviewer's example: records of 65,536, 65,437 and 100 bytes behind a held write. The record buffers are captured as weak references, the test waits one event-loop turn and forces a full garbage collection, then checks which buffers are still reachable. With the joined write held, the three record buffers are freed and only its own 131,073-byte buffer remains. The rest of the 256 KiB budget then fills exactly, and the next record is dropped.
- **Test 2:** a short multi-record write is followed by a held rollback. Neither the records nor the write buffer are still reachable.
- **Results:** on the old code both tests failed with `[true, true, true]`. On the new code both pass, and they passed in 5 of 5 repeated runs.
- **Reasoning, not tested:** that this holds at every other await point (rotation, recreating a removed file) is argued from the source. The brief moment during the synchronous join, Pino's temporary strings and allocator overhead are outside the contract.
- **Gap:** native throughput was not re-measured.
