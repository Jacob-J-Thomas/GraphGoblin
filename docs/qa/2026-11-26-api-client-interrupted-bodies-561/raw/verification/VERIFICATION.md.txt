## 3. Finding: MCP typecheck fails on DOM-only type names (FIX-IN-PR, production)

**Established by evidence:**
- `apps/mcp/tsconfig.json` extends `tsconfig.base.json`, which sets `customConditions: ["development"]`. It also sets `lib: ["ES2023"]` and `types: ["node"]`. So `tsc -p tsconfig.json` resolves `@graphgoblin/api-client` to `src/index.ts` and type-checks `body.ts` without the DOM library.
- The api-client and web configs both include `DOM`, which is why their checks pass.
- `@types/node@22.20.5` declares neither `ResponseType` nor `ReadableStreamReadResult` globally. In `undici-types` (the package `@types/node` uses for its fetch types), `ResponseType` is only a module export.
- Running the two halves of MCP's `typecheck` script separately (`diagnostics/`):
  - `tsc -b tsconfig.build.json` exits **0**. Project references substitute api-client's built declarations.
  - `tsc -p tsconfig.json` exits **2**, with the same three errors (stdout `2907dcf5…`, byte-identical to the stage log).
- After the merge, `pnpm typecheck --continue` shows 20/21 tasks succeeding. The only failure is `@graphgoblin/mcp#typecheck`, with the same three errors (section 5). CI's typecheck gate would fail.
- `apps/web` and `apps/mcp` are the only workspace consumers of `@graphgoblin/api-client`.

**Suggested correction (not applied; checked only in isolation):**
- In `body.ts`, type the set as `ReadonlySet<Response['type']>` and `new Set<Response['type']>(…)`.
- Type the chunk without the DOM alias, for example `let chunk: Awaited<ReturnType<typeof reader.read>>;`.
- A standalone probe (`diagnostics/type-name-probe/`) shows:
  - those forms compile under both `lib es2023` + `types node` and `lib es2023,dom,dom.iterable`;
  - the original forms fail under the Node-only library with the same three errors.

This was not compiled inside the real package. A correction needs its own author change, review, and a re-run of this verification from the start.
