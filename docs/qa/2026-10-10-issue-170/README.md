## Defects

### D1 — Major: incomplete number silently deletes the applied value and can publish

1. Open an inference node whose `timeoutSeconds` is `30`.
2. Open Advanced. Focus Timeout seconds, select all, and type a single `-` (do not intentionally clear it).
3. Move focus to Label and edit the label so persistence finishes. Close the dialog and Publish.

Expected: retain `30` in the definition and both drafts; preserve incomplete numeric input with a described error; refuse Publish until corrected or cancelled.

Actual: Edge reports native `validity.badInput === true`, while the control exposes an empty string. The form treats that as a valid optional-field deletion. There is no `aria-invalid`; server draft and IndexedDB both omit `timeoutSeconds`. Publish succeeds and published v1 also omits the timeout. The test separately asserts all four observations. This is silent loss of an authored watchdog.

Suspected location: `apps/web/src/forms/fields/text.tsx:199–211`, especially `text === '' ? undefined : Number(text)` before checking native `badInput`. The old main control also interpreted empty native values this way; this is an inherited edge case that the new last-valid-number guarantee still fails to address, not proven to be newly introduced by #170.

Recommended fix: distinguish intentional empty input from native bad input, retain the exact incomplete token in the held-input channel, and commit only a schema-valid number or an intentional optional clear. If native number inputs cannot supply the authored token reliably, use a text input with numeric input mode and explicit parsing. Verify both optional and defaulted numeric fields.

Evidence: `I6 incomplete optional numeric text…` (`test.fail`, D1), [numeric screenshot](numeric-incomplete-dark.png). Initial repro shows expected `30`, received `undefined` for both drafts and a published definition with no timeout.

### D2 — Minor: unselected tabs do not count hidden required answer/route controls

1. Open a valid provider decision with Choice/Noul routes and required evaluator fields.
2. Select Context.
3. Inspect Settings and the hidden answer editor.

Expected under the requested invariant: the tab that hides required answer/route controls carries a visible count or equivalent explicit counted summary.

Actual: Settings is simply `Settings`; its required answer controls are hidden. Likewise, valid configured context has no tab summary. Error counts appear correctly when problems exist. The invariant test narrows the failure to hidden required answer controls, not an assertion that optional context must always be counted.

Suspected location: `apps/web/src/forms/sections.tsx:206–217`; tab labels render `ProblemBadge` only, and it returns nothing for zero errors at line 238.

Recommended fix: add a concise count/summary for hidden required answer/route controls and meaningful configured Context state, separate from error counts. Keep the existing issue reveal/focus behaviour.

Evidence: `I2 required routes…` (`test.fail`, D2), [dark Context](dark-decision-1440-context.png), [light Context](light-decision-1440-context.png). This follows the QA brief’s stronger count requirement; the implementation’s narrower error-only count behaviour matches its current docs.

### D3 — Major: section JSON applies values that fail the parent node schema

1. Open a valid Claude inference node with read-only/never policy and no raw overrides or capabilities.
2. In Advanced, edit Config overrides as JSON: `{"raw":true}`. Alternatively edit Capabilities as JSON: `{"skills":["authored"]}`.
3. Click Apply JSON, then edit the node label and wait for the device draft.

Expected under invariant I4: use the parent schema’s Claude constraint before committing; retain the last applied valid config in the editor and IndexedDB, keeping invalid JSON as pending text with the schema’s message.

Actual: Apply is enabled, the invalid section replaces the applied value, and IndexedDB contains it. The full-form error is shown only after application. Observed output:

```text
Config overrides: Apply enabled=true; device={"raw":true}; server=undefined
Capabilities: Apply enabled=true; device={"skills":["authored"]}; server=undefined
```

The server draft remains valid and Publish correctly refuses. There is no evidence of invalid Claude configuration reaching a published version. The defect is the loss of the last-valid applied state and the invalid device draft at the JSON Apply boundary.

Suspected location: `apps/web/src/forms/fields/json.tsx:17–30` and `:147–160`, which validate only the supplied section schema, then `:250` commits it. Parent constraints are in `packages/contracts/src/nodes.ts:239–245` and `:357–358`.

Recommended fix: validate the merged candidate against applicable parent-node refinements before committing the section; project those errors onto the JSON editor while retaining its text. Keep the previous applied value until that candidate is valid or the user cancels. Do not rely on autosave/Publish to catch a failed Apply.

Evidence: both `I4 parent validation…` tests (`test.fail`, D3), [Claude JSON error](claude-json-parent-error-dark.png). This identifies a gap between the requested no-invalid-store invariant and ADR-0032’s narrower local-section validation.

## Design critique from the running form

- **Keep mounted Settings/Context panels and explicit Apply/Cancel.** Keyboard navigation, held text, issue reveal, conflict handling and normal history behaviour work. Preventing switch-back while text is pending makes the state understandable. Keep blocking Publish for valid unapplied text too, but call it **pending**, not “1 error”; a valid edit is not a schema failure.
- **Keep identity and Connections outside the tabs, and keep related values together.** “Settings” is a clear name. Atomic Answer JSON preserves rubric/band and route uniqueness checks; changing answer kind through the typed selector is clearer than silently changing it in pasted JSON. Optional objects should remain intact. Classifier thresholds and alternative recording are reasonable Advanced candidates, with useful summaries of customized values. The shared exit threshold treatment passed its regression suite. Error groups can remain collapsed when their counts and issue links work, subject to D2’s missing required-control summary.
- **Reverse inferred bulk renames by list length.** The observed single-route JSON renames preserve old edges. ADR-0032 extends this behaviour to pairing all unmatched rows in authored order whenever counts match, so a pasted replacement can inherit a connection despite all-new IDs. The docs make authors remove/apply and add/apply to express replacement. That pushes implementation bookkeeping onto loop authors. Preserve exact IDs automatically; provide an explicit rename mapping or a connection-change preview for unmatched IDs before Apply. This is a design objection to the documented rule, not an additional failing regression assertion.
- **Use the wider area, not just longer rows.** The 64rem dialog fits without clipping, but at 1440 px the initial Noul screen shows only the first side’s fields; False and Evaluation are below the fold. ID and label controls stretch almost the full width. I would use compact ID/label rows and side-by-side True/False groups at desktop widths, retaining the single-column sheet. The two desktop Settings screenshots show the wasted opportunity clearly.
- **Promote provider variable selection within Context.** Moving Context to its own tab is useful. Putting Vars behind another Advanced toggle makes a consequential choice two navigation steps away. The tested `vars: []` and absent-vars states have different meanings. Show that selection, or an explicit “all variables / none / N selected” summary, beside Messages and Include last output. Inference input mutations belong on Context; optional files can remain under Advanced with their counts.
- **Keep sandbox and session policy basic; improve the model summary.** These affect the kind of work a node performs. Optional model/effort overrides can stay Advanced, but the primary panel should summarize the effective/inherited selection so authors need not expand Advanced merely to understand the node. Required LLM model/effort selectors correctly remain visible on Settings.
- **Keep suggestions permissive and terminology honest.** Datalists correctly accept valid undeclared names and authored RFC6901 pointers; no resolved capability catalog exists in format 3. Do not invent capability options or imply that selecting a recorded slug resolves a tool. The unavailable notice is accurate, though its repeated per-list implementation detail can be consolidated.
- **Fix D1 and D3 before accepting the validation design.** Typed controls and section schemas are useful, but neither native input sanitization nor validation after Apply should make authors police the last-valid-value invariant. No compatibility layer, legacy input path or owner migration is needed to fix these frontend behaviours.
