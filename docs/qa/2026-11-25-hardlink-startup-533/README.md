# Hard-linked database startup refusal

[Issue #533](https://github.com/Jacob-J-Thomas/GraphGoblin/issues/533) removes the stack trace that foreground API startup printed when it refused a SQLite database with several hard links. Formal review 1 marked the candidate Ready with no findings. The separate actual-Claude Windows QA returned **PASS** on the reviewed component worktree. That QA did not run on the combined publication tree, so the publication worker ran a focused combined-tree check, recorded below. Opposite-family review of the combined branch, current-target hosted CI and the fresh independent Astra MAX final audit remain pending. [Source, projection and check binding](SOURCE-BINDING.json)

## The change

`acquireDatabaseLock` refuses a database whose link count exceeds one before it takes the database lock or a reclamation guard. That refusal now throws `HardLinkedDatabaseRefusedError`, which carries the canonical database path and the same message bytes as before: `database <canonical-path> has multiple hard links; use one ordinary SQLite file so GraphGoblin can establish exclusive ownership`. Foreground startup renders that class, like the existing ownership refusal, as one line with control characters and line separators escaped. Any other error, including a plain `Error` that repeats this text, keeps its error object and stack. The managed startup categories are unchanged, so the Windows launcher's managed gateway still records `store`/`store-unavailable` and exits 74. `--reset` and `--create-api-key` read only the unchanged message. [Refusal](../../../apps/api/src/data-dir-lock.ts) - [Foreground display](../../../apps/api/src/serve.ts) - [Distribution doc](../../../docs/11-security-and-distribution.md) - [Changelog](../../../CHANGELOG.md)

The display unit tests cover the typed rendering with its unchanged managed category, an impersonating plain `Error` that keeps its stack, a path containing the ownership message prefixes, control escaping that leaves the original message unchanged, and a real hard link refused under both names with no lock left. The new built-entry block in `main.test.ts` gives each child its own store and port, disables Ollama and points Codex and Claude at absent executables. Both spellings of a real SQLite store must exit 1 with one stderr line, empty stdout, unchanged bytes and no locks, and the same file must start and serve an authenticated request once the extra link is removed. An unexpected database filesystem failure must keep its stack. On Windows only, the managed entry must exit 74 with no output and one closed `store`/`store-unavailable` record that names neither the path nor the links. ## Limits

- Review and QA ran on the component worktree at `631d16e3` with the unstaged patch, not on the combined publication tree. The combined commit carries the same change projected onto `4e1037c9e9922ffa27237fe79850403b6b54fc70`. Five of the six paths differ in bytes from the reviewed files because the target advanced. Every added and removed line matches, except one `main.test.ts` import line, where the combined line keeps the target's `realpath` beside the reviewed `link` and `unlink`.
- The native evidence is Windows only. The unexpected-failure test accepts the different POSIX failure point but has never run there, and the managed test runs only on Windows. Current-target hosted CI, including its non-Windows jobs, is pending.
- The managed launcher keeps its generic `store`/`store-unavailable` record and exit 74, as the issue required. It does not show the hard-link remedy. The QA confirmed only that this category is preserved and carries no path.
- Neither refused path contained a control character, so escaping was exercised only by the unit test. The QA session did not recompute the wrapper's hashes. Byte equality across both spellings follows from their shared file identity. The reset database-stage label is asserted inside the reset test, not shown in its output.
- No coverage gate or full API suite has run on this change.
