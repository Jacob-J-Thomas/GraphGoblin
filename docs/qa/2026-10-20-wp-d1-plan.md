## #320 representation: the child and the parent's link commit in one transaction

Choice (proposal): the parent's `child_run.started { nodeId, childRunId }` is written by the admission port in the same SQLite transaction that creates the child run, its initial thread and its `run.queued` event. `RunAdmission` gains `parentNodeId`; storage appends the link to the parent's log (next sequence, `last_event_seq` updated) and notifies subscribers of both logs only after commit.

Why not an intent event or a table row recorded before the child: the brief allows either; both leave a window (intent durable, child missing) that recovery must then re-create from a re-derived admission, and an intent written before validation can name a child that never exists. One transaction removes the window instead of reconciling it: a child never exists without its parent's record of it and the record never names a missing child. The combinations then reduce to:

| Durable state at the crash                                              | Recovery                                                                                                               |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| neither child nor link (crash before commit, or the transaction failed) | the parent re-executes the subloop node and admits one child                                                           |
| child and link, no park                                                 | `childOfThisVisit` finds the link; the handler re-parks on that child or maps its outcome                              |
| child, link and park                                                    | the park is completed from `run.waiting`; `reconcileChild` wakes the parent if the child is terminal                   |
| all three and the child finished while the process was down             | the child is finalized first and wakes the parent (C6 test kept)                                                       |
| link without child, or child without link                               | impossible: one transaction (proved by fault injection inside the transaction, fake staged writes and SQLite triggers) |

`child_run.finished` is recorded once per observed child outcome, identified by child id plus the child's terminal-event sequence. `notifyParent` carries that sequence as `childFinishedSeq` in the existing child wake's JSON payload. The handler consumes an outcome only after a wake recorded that identity; an outcome that changed during the parent's interruption gets a fresh park/wake first. Its finish is associated with that preceding outcome identity. A parent output-mapping retry therefore reuses the existing finish; an independent child retry can produce a second observed finish even with the same status. Outcomes the parent never consumed are not backfilled (C6's existing requirement).

Continuation refinement and reason: the inherited parent-log boundary scan was insufficient. Retrying a parent output mapping recorded an unchanged outcome again (`before-engine.txt`); a child independently retried during its parent's interruption lost its second failed outcome (`before-independent-retry.txt`, expected two finish records, got one). Mirroring every child terminal event was rejected by the unchanged C6 test for an unconsumed failure followed by a resumed child: it requires only the final observed success. Outcome identity instead travels in the existing identity-bound child wake. The child outcome, terminal sequence and thread are read from one child-log snapshot, so an independently resumed mutable run row cannot pair old outcome fields with a new sequence. This requires a small change in the child-outcome reader as part of child bookkeeping, besides child start and `notifyParent`; finalisation/delivery remain untouched. There is no stored shape change: the wake payload remains ordinary JSON. The admission representation is unchanged. The in-memory admission also updates the parent's `lastEventSeq` with the link, matching SQLite.

Tests that must fail before the fix:

- engine/SQLite: a run manager over a real SQLite file whose admission port dies right after a child admission is acknowledged (the wrapper never returns); the handle is closed, the file reopened and a new manager recovers. Before: two children (the orphan and a second one). After: one.
- built API, real kill: concurrent parents; a read-only observer of the store kills the API (SIGKILL) the moment it sees a child row without its parent's `child_run.started`; after restart each parent has one child. Before: the observer sees the window and the restart duplicates the child. After: the window is never observed; kills at a sweep of delays leave one child per visit.
- engine: a crash between `child_run.finished` and the parent's next event records it twice before, once after.

## #321 classes and representation (proposal)

Named after WP-F4's submission vocabulary (`definitely-not-submitted`, `delivery-uncertain`, `submitted`):

| Class                    | Durable evidence                                                                                                                                                                   | Behaviour                                                                                                                                                    |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `definitely-not-started` | no `script.dispatched` on the visit, or the runner proved the process never started (spawn refused: missing command, `EINVAL` for `.cmd`, permissions; an already-aborted request) | ordinary rules: recovery runs it; a proven start failure fails with `SCRIPT_START_FAILED`, resumable                                                         |
| `outcome-uncertain`      | `script.dispatched` on the visit with no disposition after it (no `node.finished` of the node, no `run.failed`)                                                                    | recovery does not run it; the run fails with `SCRIPT_OUTCOME_UNCERTAIN`, resumable, message saying the previous attempt may already have produced its effect |
| `completed`              | the runner observed the process end and its result is recorded with the node's disposition                                                                                         | normal completion, or `SCRIPT_EXIT_CODE` with provenance; resume reruns knowingly                                                                            |

- `script.dispatched { nodeId, visitId, dispatchId }` is appended (durable) before the process runner is called. `visitId` follows WP-F4: `<runId>:<seq of the first node.started since the node last finished>`.
- Every script failure after preparation carries `failure.script = { visitId, dispatchId?, state, exitCode? }`.
- An explicit resume after `SCRIPT_OUTCOME_UNCERTAIN` reruns the script with a new dispatch (the `run.failed` is the disposition); Replay and Cancel stay available. No exactly-once claim: the docs say a resumed uncertain script can produce its effect twice.

Tests that must fail before the fix: a dispatched marker script interrupted by a real API kill is run again by recovery on the base (marker count 2); after the fix the marker count stays 1, the run is failed `SCRIPT_OUTCOME_UNCERTAIN`, and an explicit resume runs it once more (count 2, knowingly). Before dispatch and after completion the count stays 1 both before and after.
