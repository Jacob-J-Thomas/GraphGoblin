## Method

- **The built product.** Every scenario starts `node apps/api/dist/main.js` as its own process on a fresh store and restarts it on the same store to read the durable record.
  - The Ctrl+C check starts the gateway attached to a console of its own with acceptance C's `launcher2` (through PowerShell `Start-Process`, as a terminal window would).
  - A real `CTRL_C_EVENT` is then delivered to that console with acceptance C's `ctrlc` helper.
  - The three C# helpers are copied unchanged into [scripts/](scripts/) and compiled by [scripts/prepare.ps1](scripts/prepare.ps1).
  - Helpers: [scripts/lib.mjs](scripts/lib.mjs), patterned on the PR #417 QA helpers.
- **Live providers.** The product's own defaults: the SDK-bundled Codex CLI and the installed Claude CLI. No login, logout or configuration change was made.
  - The models were Codex `gpt-6-luna` at `low` and Claude `claude-haiku-5-5` at `low`. The exceptions are LP-4 (`max`) and LP-5 (`minimal`), as their checks require.
  - Prompts were one line. Only LP-1 and LP-2 asked for a shell command, because those checks need a turn that is still running.
- **Turn accounting.** Every real invocation is counted from the run's own durable `harness.turn` and LLM `decision.made` events, and the one direct CLI diagnostic is added. [turn-ledger.json](turn-ledger.json) lists each invocation with its run and node. Refused resumes count as invocations.
- **Dry runs.** Before any real turn, every live driver ran once against acceptance A's recording CLI, compiled as `codex.exe`/`claude.exe`, which makes no provider call. These runs only debugged the drivers and are kept in [dryrun/](dryrun/). They are not live evidence.
- **Provider-side history (LP-3, LP-4, LP-5).** I read only the Codex session-history file (`~/.codex/sessions/…/rollout-*-<thread>.jsonl`) of threads this QA created, found by thread ID in the file name. I recorded only entry types, the `turn_context` model and effort fields, and the turn's error message. Prompts, replies, instructions and account or rate-limit fields were not recorded.
- **L2 test action.** The provider must be asked to resume a conversation it does not know. While each run was parked at its input wait, I stopped the gateway (drain, exit 0) and replaced the worker's recorded native handle in the stopped disposable store's `harness_sessions` row with a random UUID the provider never issued. I then restarted the gateway and answered the wait. The real CLI then resumed that unknown handle. No provider-side file was touched.
- **Redaction.** Profile paths, the machine name and SIDs are replaced in every text file, and anything shaped like a token, key, email or account ID would be replaced too. The shell carries the owner's `JEV_API_KEY`; from the second gateway on it is removed from every gateway environment (O2).

## Defects

### D1 (Medium, #205 B43 under U16 #305): Codex `minimal` is offered and accepted for `gpt-6-luna`, but the provider refuses it

- **Reproduce.**
  1. On this build, with the installed Codex login, open a loop in the editor. Add an Inference node with harness `codex` and model GPT-6 Luna (`gpt-6-luna`).
  2. The Effort list offers `minimal`, `low`, `medium`, `high`, `xhigh` and `max`, and `GET /model-catalog` lists the same for every Codex model except GPT-5.5. Choose `minimal`.
  3. Publish, which is accepted, and start a run.
- **Expected** (#205: saved values match the actual provider request; U16: visible selections accurately describe what can execute). Only efforts the model can execute are offered, or an unsupported effort is refused before admission with `EFFORT_UNSUPPORTED`, as GPT-5.5 `max` and Claude `minimal` already are.
- **Actual.** The run fails every time. The CLI sends `model_reasoning_effort="minimal"`, and the provider answers HTTP 400 `invalid_request_error` / `unsupported_value` on `reasoning.effort`: "Unsupported value: 'minimal' is not supported with the 'gpt-6-luna' model. Supported values are: 'none', 'low', 'medium', 'high', 'xhigh', and 'max'." See [lp5-rollout-facts.log.txt](lp5-rollout-facts.log.txt) and [lp5-cli-diagnostic.log.txt](lp5-cli-diagnostic.log.txt).
- **Scope.** Only `gpt-6-luna` was tested. The other seeded GPT-6 and GPT-5.6 models also list `minimal`, and they were not tried. The provider names `none` as supported, and GraphGoblin does not offer it. That is a product decision (HQ-1).
- **Context.** The acceptance-fixes record for PR #417 (Task 4) left this exact question to this live check.

### D2 (Medium, #243 B45, with the classification rule of #244 B47): a provider refusal is recorded with an unrelated cause, as delivery-uncertain and resumable

- **Reproduce.** Run the D1 steps, then read `GET /runs/{id}`, the gateway log and the inspector.
- **Expected.** Provider and service failures stay external failures with truthful reasons (#243: "Provider/service limits remain external failures with truthful reasons"; "Other errors fail except positively identified transient failures"). The failure names the provider's refusal (HTTP 400, unsupported `reasoning.effort` `minimal`). A deterministic refusal of the request is not presented as uncertain delivery with Resume as the next step.
- **Actual.** `failure.code` is `HARNESS_DELIVERY_UNCERTAIN`, with `resumable: true`, `details.adapterCode: HARNESS_TURN_FAILED` and `inference.submission: delivery-uncertain`. The message is `harness turn failed: Codex Exec exited with code 1: Reading prompt from stdin...`. That stderr line is the CLI's banner, not the error. The gateway log says `codex turn failed: Codex Exec exited with code 1: Reading prompt from stdin...`. The inspector shows "Failed: HARNESS_DELIVERY_UNCERTAIN — harness turn failed: Codex Exec exited with code 1: Reading prompt from stdin... (resumable)" with an enabled **Resume** ([lp-effort-lp5-inspector.png](lp-effort-lp5-inspector.png)). Resuming would send the same pinned `minimal` effort; I did not exercise it.
- **What the CLI reported** ([lp5-cli-diagnostic.log.txt](lp5-cli-diagnostic.log.txt), the identical argv run directly against the SDK-bundled `codex.exe`):
  - The stream ran `thread.started`, `turn.started`, then `error` and `turn.failed`, both carrying the provider's full 400 message.
  - The CLI then exited with code 1, and its stderr was only `Reading prompt from stdin...`.
  - So the provider's reason reached the SDK's event stream and was then discarded.
- **Likely cause** (read from source, not traced at runtime).
  - `TurnAccumulator` folds the stream's `turn.failed` and the thrown process-exit error as evidence of equal rank (`HARNESS_TURN_FAILED`); see `packages/adapter-codex/src/events.ts:327-343`.
  - `mergeHarnessFailure` keeps the later evidence at equal rank: `harnessFailureRank(next) >= harnessFailureRank(previous) ? next : previous` (`packages/engine/src/handlers/inference-failure.ts:77`).
  - The generic "Codex Exec exited with code 1: <stderr>" therefore replaces the specific provider message. The `codex.turn.started` marker then makes the engine treat the failure as accepted work of uncertain delivery.
  - Whether quota (`429`) or authentication refusals are masked the same way depends on their rank. They were not observed in this session.
- **Severity.** Medium. Any Codex request the provider refuses is reported with a misleading cause, and the operator is steered to Resume a deterministic failure.
