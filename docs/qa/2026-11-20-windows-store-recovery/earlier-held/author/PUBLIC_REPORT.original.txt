# #471 author findings and candidate evidence

Candidate: `52bbab677117e8c7ded9953da1fa9c4bdba651dd`, based on
`8181f350028e284529c76b51927f32890afcb68a`. This is author evidence. Independent native QA,
cross-family review, hosted current-head/current-target CI and the final audit remain open.

Five native Windows processes deleting one synthetic stale UUID marker reproduced `EPERM`
from `unlink` after concurrent removal: 310 such errors in 400 trials, each followed by
independent `lstat: ENOENT` for that exact marker. A scheduling barrier immediately before
the unchanged baseline's real stale-marker unlink then reproduced eight `EPERM` errors across
five product trials: four matching seeded-marker unlinks and four guard-directory removals.
Each trial still had exactly one live writer acquisition,
matching final PID/token, clean release and an intact unrelated sentinel. This establishes a
native concurrent-deletion cause; it does not retroactively establish the exact syscall or
Windows kernel status of the historical CI failures, or prove a sharing violation.

The intermediate marker fix exposed three `rmdir` `EPERM` errors with independently observed
guard absence. The candidate therefore accepts Windows `EPERM` only after proving the exact
removed path absent. It never retries deletion, preserves successor markers and retains genuine
filesystem errors with operation/code. It rolls back the main lock if recovery cleanup fails,
reports retained ownership if rollback also fails, retains in-process holds on failed release,
and preserves original acquisition errors alongside cleanup failures. Native CI receipts now
retain bounded identities, final PID/token readback before refusal assertions, and cleanup checks.
