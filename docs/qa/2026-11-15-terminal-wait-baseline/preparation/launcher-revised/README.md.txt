# #410 native execution launcher preparation

The launcher wraps the reviewed native harness in the existing external suite directory. It passes the exact arguments that harness defines and retains its output paths. This preparation can be reviewed while #381 is active. The first execution requires the actual post-#381 main and a separate root admission. [Frozen harness](../runtime-410-native-preparation/README.md) · [Implementation brief](../runtime-410-implementation-brief.md)

## Bind one execution

1. For the baseline, use clean actual main after the #381 merge. For the candidate, use its frozen exact head on fresh actual main and a separate successful build receipt. Prepare the complete source, output and dependency file maps in the shape of build-binding.example.json. Use canonical absolute Windows paths for checkout, receipt and build log fields, and Git-style forward-slash relative keys for file maps. Record the project's Node executable hash and the exact checkout index hash. The complete binding stays outside the repository.
2. Populate admission-baseline.example.json or admission-candidate.example.json in a new external file. Bind its exact checkout, head, tree, actual main, merged #381 commit, build receipt hash and launch.ps1 hash. Set state to root-admitted only when the phase, slot and inputs have been reviewed. The evidence name is an unused basename scoped to the frozen harness. The wrapper's own receipt directory is an explicitly named, unused sibling under the batch.
3. Review the baseline W1–W4 observations before producing baseline-acceptance.example.json with state accepted-baseline. Bind the original summary bytes and its exact private-history-seed/graphgoblin.db transfer input, plus the old terminal parent ID. Candidate admission contains the explicit baseline evidence basename, summary, seed and root acceptance. The wrapper derives their fixed names only where the frozen harness does, and verifies the literal locations and hashes. Preserve the seed outside any public packet until the final admitted W4 run and first-evidence disposition.
4. Invoke launch.ps1 once from PowerShell 7.2 or later with the absolute admission file and its lowercase SHA-256. The wrapper verifies all five frozen harness files and the clean checkout, source, index, full bound output roots and the reviewed runtime dependency inventory before startup and after exit. The tracked map includes every Git index entry, and the output map includes every file in its listed output roots. The baseline requires actual main itself. Candidate admission separately identifies the old historical seed. The launcher does not create or repair a binding.

```powershell
$qaAdmissionHash = (Get-FileHash -LiteralPath $qaAdmission -Algorithm SHA256).Hash.ToLowerInvariant()
& $qaLaunchScript -AdmissionPath $qaAdmission -AdmissionSha256 $qaAdmissionHash
```

The exact Node process receives discrete ProcessStartInfo.ArgumentList entries and uses no shell. Its environment carries SystemRoot, WINDIR and an owned TEMP/TMP. The frozen gateway and MCP retain their own scrubbed environment. The supervisor works from the explicit receipt directory, and the harness continues to create fresh evidence and file stores under its own directory. The launcher writes no repository or harness source files.

## Read the independent dispositions

- child-exit.json records the supervisor's OS exit code immediately after exit, before transcript drains, hashing, JSON parsing, or case interpretation. stdout.log and stderr.log retain raw bytes. launch.json identifies the supervisor PID, creation time, executable and argv. A missing child-exit.json means the wrapper could not confirm an exit, so inspect the supervisor identity and any first error.
- The frozen harness preserves its own first-failure.json and summary.json. The wrapper preserves their bytes and hashes the W2 barrier and post-crash receipts when present. A successful wrapper outcome is a completed matrix for independent review. On baseline, the assertions expect the documented stale wait in W1 and W2. On candidate, they expect the new wait-free projections. W4 uses the already-terminal old row in both phases.
- The frozen run has its own 210-second watchdog. At the 240-second outer deadline the launcher records the exact supervisor PID and birth. Only an admission with stopExactSupervisorOnDeadline set to true allows stopping that exact process handle. The launcher never issues a process-tree stop. With the flag false, it reports the missed deadline and stays attached to the transcript streams until the owner resolves the supervisor. Either deadline outcome is incomplete. W2's deliberate gateway interruption is controlled solely by the frozen harness and its saved barrier proof.
- launch-result.json records the completed post-exit bind and phase result. A verification or reporting error has a separate receipt and leaves child-exit.json intact. The wrapper performs no runtime retry or filesystem deletion. Evaluate the harness's owned-store cleanup and the wrapper's temporary directory before releasing the slot. Retain any reported residue for an exact, separately admitted continuation.

The existing harness, completed run reports and accepted W4 history are the evidence. This launcher was parsed during preparation. Actual startup, teardown and W1–W4 behavior require the later admitted runs.
