## Editor revalidation performance (large supported graph)

Phase 1 measured the local validation that EditorPage runs on every definition change (`validateDraft`) in Node/Vitest. See `13-perf-results.json`, the script `perf-273.test.ts.txt` and the logs `09`–`14`. At 300 nodes with references, the median was 50.5 ms (p95 60.8 ms). `nodeReferenceIssues` alone had a median of 37.4 ms against 12.9 ms for the existing syntax checks. Without any node reference, the analysis still costs a median of 27.6 ms. Phase 2 should:

1. In Edge, load the 300-node fixture (the same generator) and the 300/600 routing fixture. Type 20 characters into one prompt field. Record input→paint latency (Event Timing `interactionId` durations, or a `performance.mark` around `validateDraft` via a temporary build flag) on the base `308c6285` and on the candidate.
2. Report median/p95 per keystroke on both. If the candidate exceeds the 16.7 ms frame budget where base did not, or doubles the median, treat it as a blocking regression for root to route. The likely fix is domain-side: cache per-field analysis by source text and share parsing with `syntaxIssues`. An editor-side fallback (deferred local validation) changes live-validation semantics and needs a decision.
3. Re-run `e2e/routing.spec.ts` performance (normal mode) to confirm drag routing is unaffected. Validation is not on the drag path, but moves do change the definition.
