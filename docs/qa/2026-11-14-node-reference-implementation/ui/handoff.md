## What changed and why (UI decisions)

1. **One atomic store write (`store.ts` `renameNode`).** The store calls the public `renameLoopNode(definition, oldId, nextId)` on the exact current draft. A `renamed` result goes through the existing `decisionRouteEdges` with the old/new ids. One `set()` then applies the complete definition and decision route ownership, and moves the node's held field input (`fieldErrors["node:<old>"]` becomes `"node:<new>"`). The same write updates the selection and a pending issue focus (`nodeFocus`), adds one history step (`rename <old> to <new>`, `renamed`), bumps the revision once and sets `saveState: 'pending'`. The old code did this in three separate `set()` calls, so subscribers could see intermediate states. Other forms' held text keeps its object identity. `renameNode` now returns a refusal message or `undefined`.
2. **Refusals keep existing feedback.** The voice-protection guard stays at the store entry, with the same `connectionError` and the same "Voice steps stay. Use Turn off voice messages." message, now also returned. The domain's `invalid-id` and `duplicate-id` map to the dialog's existing wording; the format message moved to a shared `ID_FORMAT_MESSAGE`. `missing-node` and `ambiguous-node` get new plain messages. Every refusal leaves the store object untouched. The dialog still checks `idProblem` first, so users see the same messages as before. A store refusal on close goes through the existing "stop once" path.
3. **Mounted forms cannot write old source back.** `SchemaForm` holds its values from mount, so its next change reports the whole stale config or settings. A new store map, `formEpochs`, is bumped per scope (`node:<id>`, `settings`) only where `renameLoopNode` changed that config or settings object. Structural sharing in `updateAtPointer` makes identity comparison exact. The node dialog's config form key and the loop settings form key include their scope's count. A form whose source was not repaired never remounts, and the variables form is never remounted, so unrelated buffers and held text survive. The renamed node's count moves with its id. History is not changed, and undo/redo still remount through `historyEpoch`.
4. **Focus through the remount.** Undo's existing focus-restoration code is now reusable as `keepFocusThrough(action, target)` in `useUndoShortcuts.ts`; `runHistory` calls it, and the existing body is unchanged. When the id field loses focus, the dialog passes `relatedTarget`, so a click or Tab into a control of the remounting form lands on the same control in the new form. Enter keeps focus in Node id, and closing the dialog returns focus to the canvas as before.
5. **Presentation: one notice, reusing existing patterns (`RenameNotice.tsx`).** No preview: the gesture applies immediately and Undo is the escape hatch, as the brief preferred. The store keeps a transient `renameReport` with `from`, `to`, `connections` (distinct edges), `references` (`repairedReferences` minus edge endpoints) and the domain `warnings`. It is not part of history. It is cleared by Dismiss, by undoing or redoing that rename's step (undoing a later fix keeps it), by the next rename and by load.
   - It renders as an `Alert` ("Renamed <old> to <new>"; info tone, or warn when there is something to review) above the canvas and at the top of the node dialog, as `ConflictNotice` does. That works because the page is inert while the modal is open.
   - Wording: "Updated N references in expressions, templates and mutation paths, and M connections. Plain text, JSON values and scripts are not changed." Then "Review one place / N places where <old> may remain:", and finally "Undo reverses the whole rename."
   - Review rows reuse `IssueList` with subject (Warning badge, code, message, node and path). Rows on a node still in the draft are buttons. In the dialog they focus a field of the open node in place, or `openNode(id, { field })` another node; on the page they open the node at the field. Loop-level, general (scripts and generated patches) and deleted-node rows only inform.
   - Dismiss returns focus to Node id in the dialog, and to the existing next dismiss control or save status on the page.
   - A rename that changed only connections and has nothing to review shows nothing, as before.
6. **Persistent diagnostics** (`NODE_REFERENCE_MISSING` error; `…_OPTIONAL_MISSING`, `…_OUTPUT_UNVERIFIED` and `…_UNCERTAIN` warnings) reach node badges, the indicator and Publish through the existing `validateDraft` → `validateLoop` path. No UI change was needed, and the backend's messages are shown unchanged.
7. **Docs:** a new docs09 "Renaming a node (#273)" subsection, plus a fix to the "Earlier node outputs" sentence that said renames are not repaired. Guide `02-build-a-loop.md` replaces "update references yourself". The CHANGELOG #273 bullet gains the editor sentence; its upgrade note is unchanged.

Not done, deliberately: no blind string replacement, no detection of old ids in held text, no compatibility, migration or runtime change, no domain/API edit, and no global redesign.

## Finding for root: per-edit validation cost on large graphs (backend-owned)

The editor runs `validateDraft` (which includes the new `nodeReferenceIssues`) on every definition change, so on every keystroke. Measured in Node/Vitest, 25 runs after 3 warm-ups (`13-perf-results.json`, script `perf-273.test.ts.txt`), on a 300-node chain with 2–4 references per node and 0 issues:

| Graph                                   | `validateDraft` median / p95 | `syntaxIssues` (pre-existing parsing) | `nodeReferenceIssues` (new) | `renameLoopNode` (one gesture) |
| --------------------------------------- | ---------------------------- | ------------------------------------- | --------------------------- | ------------------------------ |
| 100 nodes, with references              | 22.9 / 30.9 ms               | 4.9 ms                                | 11.8 ms                     | 9.4 ms                         |
| 300 nodes, with references              | 50.5 / 60.8 ms               | 12.9 ms                               | 37.4 ms                     | 33.4 ms                        |
| 300 nodes, no node references (control) | 44.2 / 49.2 ms               | 13.1 ms                               | 27.6 ms                     | 25.2 ms                        |

On large graphs the new analysis roughly triples per-keystroke validation, from about 13 ms (≈ `validateDraft` minus `nodeReferenceIssues`) to about 50 ms, which exceeds a 16.7 ms frame. It costs about 28 ms even when no field references a node, because it re-parses every authored field on every edit. A rename gesture itself (about 33 ms) is acceptable.

I did not mask this in the UI. Deferring local validation would change docs09's "surfaced live" semantics and needs a decision. The domain is frozen. Suggested backend direction: cache per-field analysis by (kind, scope, source) so a keystroke re-analyses only the changed field, and share the parse with `syntaxIssues`. Phase 2 must confirm in Edge with input→paint latency on base vs candidate. See `phase2-native-plan.md`.
