## Finding and cause (reproduced in source)

In a structured Codex override row, the JSON **Value** editor (`RecordValue` → `JsonControl` → `JsonText`) took a parsed value straight into the form. `JSON.parse` creates a member named `__proto__` as an own member. The form keeps values by assignment, so that member is lost in two places:

- react-hook-form's `_setValue` → `cloneObject` assigns `copy[key] = ...` (checked in installed `react-hook-form@7.89.0`).
- `stripUnset` assigns `out[key] = ...` on every watch report.

The form therefore reported a narrowed value that the contract accepted. That value was autosaved, and the editor rewrote the visible text to it. Only a rule outside the value, at the record level, refuses `__proto__`: the `CodexConfigOverridesSchema` intersection's raw-key check. A fix only in `stripUnset` would not be enough, because react-hook-form's own copy drops the member too. Preserving the member through RHF storage, the store and every copy would not be a bounded change.

## Correction (the architecture decision's refusal option)

The still-raw Value is refused at the existing JSON validation boundary, before anything can discard it. That boundary is `JsonText`'s `validateValue`, which already runs before any write. The check uses the record's existing public contract (the form's own record schema) and is scoped to the one entry.

- **`apps/web/src/forms/fields/structure.tsx`:** new `entryValueRefusal`, passed by `RecordField` → `RecordValue` → `JsonControl`.
  - If the form's copy (`stripUnset`) equals the parsed value (`sameJson`), the value is taken exactly as before.
  - Otherwise the record's schema checks `{ [key]: value }` for that entry alone, so other entries cannot mask it. If the schema refuses, the text is held with its messages:
    - A member inside the value: `<path from the value>: <message>`, for example `rows.0.__proto__: Codex config overrides require …`.
    - A record-level key check that stops at a refused key (the Codex check): `Key "<key>": <message>`. This becomes the member's message once the key is corrected.
  - Under a key that the record's key schema refuses (Zod `invalid_key`, value unchecked), the value schema decides.
  - A value the schema accepts is taken as before.
  - There is no Codex-specific code, no allowance for the reserved member, and no rewriting of submitted text.
- **`apps/web/src/forms/fields/json.tsx`:**
  - `JsonControl` passes `validateValue` through to `JsonText`.
  - A live (non-explicit) editor's derived re-check falls back to its own held message, not the section editor's "Apply JSON" prompt.
  - Its report effect only refreshes the message of the entry that still holds this render's text; it never creates or clears one. Typing, Discard, row removal and key rename already update held input synchronously. Explicit section editors are unchanged.
- The behavior of `stripUnset`, UNSET-marker removal, RHF storage, row identity (`rowIds`), the Key rules (including the `__proto__` Key refusal) and "Edit as JSON" section validation is unchanged.

### Resulting behavior

- The refused Value stays exactly as typed. It is `aria-invalid`, described by the message, and offers "Discard the unparsed text".
- The form reports nothing for that entry. The committed entry, neighbours, draft, revision, save state and server draft are unchanged, and no draft PUT is sent.
- The editor shows one blocking `FIELD_INPUT_INVALID` issue, and Publish refuses ("Some fields hold input that is not a valid value yet; complete or discard it first.").
- Renaming the member takes the whole value as typed, autosaves it and reloads it whole.
- Multi-level objects and objects inside arrays follow the same path.

## Residual observations (outside this slice)

1. **Admitted JSON elsewhere still loses `__proto__`.** A JSON field whose schema accepts a member named `__proto__` still loses it silently in the form. This is pre-existing and generic to RHF/`stripUnset` copying. Examples are a declared variable's JSON Schema and `unknown` JSON fields. The API's JSON body parser refuses such members anyway (the final audit observed 400 `MALFORMED_BODY`). The brief kept unrelated admitted JSON fields intact, so this is documented in docs/09 and suggested for separate tracking. It is not changed here.
2. **Mount-time loss of a stored member.** A form mounted on a stored definition that already contains such a member would also drop it through RHF's `defaultValues` copy. Stored invalid overrides are handled by #513's manual store recovery and publication check. This was not changed or exercised.
3. **One untaken defensive branch in `json.tsx`.** If no error is found on a later re-check, a live held editor keeps its last message until the next keystroke. No current contract reaches this: Codex refuses the member after a key fix, and Variables decide by the value schema either way. It is untaken in coverage.
4. **Separately tracked UX is unchanged.** The nested inline feedback for already-detected issues (#521) and the "Discard the unparsed text" wording for a parsed but refused value (it matches existing section refusals) are not changed here.
