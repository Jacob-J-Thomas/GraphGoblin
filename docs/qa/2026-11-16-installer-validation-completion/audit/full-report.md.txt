### Transaction and recovery

The publisher rereads each destination's canonical path and identity, plus its digest when present. It records an attempted entry before native I/O, which matters when a replacement partially progresses before throwing. Existing files use `File.Replace`; absent files use `File.Move`. A published destination must have the staged file's identity and digest.

Recovery traverses attempted entries in reverse, including the failing entry. It preserves an unchanged original; restores a verified backup into an absent destination or over the verified staged replacement; and deletes a new destination only when it remains the verified staged file. Unknown or changed state yields `recovery-required`, retaining stages. The user messages distinguish no replaced files, verified restoration and uncertain recovery. Created parent directories can remain after refusal; the messages make no directory-rollback promise.

I checked this reasoning against Microsoft's replacement semantics, including the backup-renamed partial-failure case, the replacement's resulting file ID, and the same-volume requirement. The implementation's per-output staging and recovery branches are consistent with those semantics. [Microsoft ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)

Cleanup is limited to stages whose current directory identity, path and non-reparse classification still match the owned stage. It deletes top-level files and the directory without recursive traversal. The code deliberately retains uncertain recovery material. Successful stage-removal regression coverage remains the known R1 follow-up; I do not infer comprehensive cleanup proof from artifact snapshots alone.
