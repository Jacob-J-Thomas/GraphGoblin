### Row notes

- **D4**: the offline apply opens one write transaction (`packages/infrastructure/src/sqlite/upgrade.ts:554`), runs the structural migrations inside it (`packages/infrastructure/src/sqlite/upgrade.ts:560`) and writes the marker before commit (`packages/infrastructure/src/sqlite/upgrade.ts:737`).
- **D7**: three separate gaps. (a) Timestamp webhooks reject a repeat only inside the endpoint's replay window (`apps/api/src/triggers/trigger-service.ts:431`), and the run start and `setRunIds` are separate writes. (b) `POST /events` deduplicates only when a dedupe key is supplied (`apps/api/src/triggers/trigger-service.ts:485`); a duplicate answers 202 with `duplicate: true` (`apps/api/src/routes/triggers.ts:175`, `apps/api/src/routes/triggers.ts:176`), and a retry without a key dispatches again. (c) Fan-out skips failed triggers after logging and links run ids in one final write (`apps/api/src/triggers/trigger-service.ts:533`), so a crash or partial failure loses linkage.
- **D21**: `packages/infrastructure/src/sqlite/event-read-benchmark.test.ts:1` measures validation overhead for a 10,000-event read, not the executor scan. Keep it as the read baseline. Add an executor scenario: one cycling loop to 5,000 node visits, timing `attemptFor` and `countEntries` (`packages/engine/src/run-manager.ts:229`, `packages/engine/src/run-manager.ts:240`).
- **D25**: repository reads do not parse `LoopDefinitionSchema`, so the startup parse is the only current-schema check of stored definitions; removing it without a replacement would let malformed rows reach the engine. Existing local stores can incur three runs; fresh stores and other configurations not necessarily.
- **D31 to D33** (rec 18): each needs a crash-boundary test that stops the process between the external effect and its recording event, restarts, and asserts the documented outcome: at most one child per subloop visit (D32); for returns and scripts, either exactly one effect via a stable id the receiver or script can deduplicate on, or an explicit at-least-once contract in docs/05 and the editor (D31, D33).
- **D37** (rec 22): the browser store appends and persists whole logs (`apps/web/src/runs/event-store.ts:49`, `apps/web/src/runs/event-store.ts:36`, `apps/web/src/runs/event-store.ts:74`).

20. **New - "Run finalization: signal completion through server, API client and inspector".** Scope: D35, across three layers. `finalized_at` is internal to the run repository and absent from the public run contract, and both the server SSE (`apps/api/src/sse.ts:83`) and the API client (`packages/api-client/src/sse.ts:222`) stop at the first terminal event, so neither a kept subscription nor one follow-up read can observe finalization; a single early read also misses returns delivered later. (a) Server/API: expose finalization in the run contract and keep the stream open after `run.finished` until finalization is recorded, then send an explicit completion signal. (b) API client: treat the terminal event as "terminal, finalizing" and end only on the completion signal; keep resume-from-cursor across reconnects. (c) Inspector: reconcile the snapshot and event log until finalized and show return evidence without reload. Bounded waiting: the stream and client wait at most a set time after the terminal event; past it the inspector marks finalization incomplete (pending recovery) and offers a refresh instead of claiming completion. Acceptance: tests for several returns delivered with delays, a failed return (`return.failed`), a reconnect between `run.finished` and finalization, an API restart during finalization (recovery finalizes, reopened inspector shows the outcome), and the timeout path showing incomplete finalization. Dependencies: 19. Decision: the wait bound.

Acceptance: cursor-continuity tests across pages and reconnects; a stalled reader is dropped at a set buffer size; per-run browser storage has a byte limit. Dependencies: none.
