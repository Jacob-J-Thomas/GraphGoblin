# ADR-0060: Explicit, revocable history deletion eligibility

Status: Accepted for #187 phase 1; extended for #322 phase 2.

## Context

The owner requires confirmation of particular history, individually or by explicit bulk selection. Age, outcome, terminal status and preferences for future history never confer consent. Active and required retained history must survive. The same rules apply to successful and failed runs.

## Decision

`runs.deletion_approval` records the authenticated confirming owner and actor (`kind`, `id`) and the server UTC time. Absence means retain. New runs always start without approval, including children and replay forks. Migration `0021_run_deletion_eligibility` adds this nullable field, a monotonic consent revision and an indexed replay-source identity backfilled once from existing threads; existing history remains retained. No reset or historical conversion is needed.

The explicit selection has a read-only preview and a confirmation command. Preview does not grant consent. The UI lists the exact IDs and the consequences before submitting `confirmed: true`, the same IDs, action and preview token. Cancelling, Escape, closing the dialog or a failed preview changes nothing. IDs are frozen while reviewing; later polling, paging and new runs cannot expand them. Filter controls clear selection. Selection never means all future matches.

Confirmation rechecks the selection inside the SQLite write transaction. An invalid, duplicate, empty, foreign or missing selection is refused. Protected records are reported with reasons; a bulk command changes all selected records or none. A SHA-256 token covers the sorted selected IDs and their relationship components, lifecycle state, event sequence, approvals and consent revisions. A competing confirmation, withdrawal or relevant activity makes it stale; the user must cancel and explicitly review again. Revisions prevent an approve/withdraw cycle from reviving a former token even with the same timestamp. There is no expiry interval: state equality and revisions establish freshness.

| History or event                                                                            | Protection and eligibility lifecycle                                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Queued, running, waiting or paused                                                          | Protected, regardless of outcome or age.                                                                                                                                                                                   |
| Terminal but not finalized                                                                  | Protected until terminal work completes, including return delivery handling.                                                                                                                                               |
| Parent/child or replay-source/fork references                                               | Treat the complete undirected dependency component as required history. Every member must be explicitly selected together or already approved. Missing dependencies refuse marking; foreign dependencies remain protected. |
| Terminal, finalized, dependency-complete selection                                          | May be marked only by explicit confirmation; all four terminal statuses use identical rules.                                                                                                                               |
| Resume, new child/replay dependency, changed relationship, new event or finalization change | SQLite triggers revoke approvals in the affected component in the same transaction, including the former parent/source when links change. No old consent returns when execution finishes again.                            |
| Withdrawal                                                                                  | Explicitly selected records and their related component become retained together. Withdrawal never deletes data and does not require selecting protected relatives.                                                        |
| Artifacts referenced by retained history                                                    | Always protected resources. Approval of one run never approves deleting a shared artifact or another run's copy/reference. Phase 1 removes no artifact references or bytes.                                                |

The component boundary deliberately conserves both sides of a recorded relationship, including replay provenance, rather than guessing which portions of historical evidence are dispensable. It is more restrictive than isolated row removal and is visible in preview reasons. Revoking related approvals on withdrawal is necessary to keep a retained member's dependencies safe. Each future cleanup batch must still recheck protection and resource references transactionally; an approval is consent, not a guarantee that every resource may be removed.

The maximum explicit selection is 500 IDs, matching the existing maximum history page size. This is an engineering request/UI bound that keeps review and atomic confirmation finite, not an owner-approved storage threshold. Larger unrelated selections can be reviewed in separate groups. A dependency component larger than the bound remains protected; no component is silently split. Malformed selection requests refuse rather than implying consent. Approved dependency components are complete: marking requires every member selected or already approved, withdrawal retains the whole component, and dependency/lifecycle changes revoke the affected component atomically. This invariant allows admission and relationship changes to gate traversal with indexed probes of just the directly involved records. `runs.replay_source_run_id` is written by the shared admission mapper in the same transaction as the initial thread; a thread relationship edit synchronizes just that row. The one-time migration parses existing threads; lifecycle traversal uses the primary key, `runs_parent_idx` and `runs_replay_source_idx`, never a materialized scan of every history edge. Former parent/source identities seed revocation too when a link is removed or redirected.

The event-append trigger tests only `OLD.deletion_approval` before doing anything. An ordinary append on an unapproved run (including a member of an unapproved component) performs no approval lookup elsewhere, JSON parsing or recursive walk even when unrelated approvals exist. An unexpected event/finalization change on an already approved row still revokes its component. No-op updates and unrelated metadata updates preserve component completeness. The reproducible SQLite progress-handler measurement in `docs/qa/2026-10-25-wp-e3-187/measure-append.py` counts actual VM instructions for the writer's `last_event_seq` update: 80 at both 100 and 10,000 history rows, versus 1,322 and 110,222 before this revision. This bounds trigger instruction work, not B-tree page I/O or end-to-end append latency.

Loop deletion is a separate explicit consent with its own in-product confirmation naming the loop's runs, history and artifact references. [ADR-0033](ADR-0033-loop-deletion-removes-runs.md) is unchanged: delete that loop's runs even if other loops reference them, retain other loops' history, clear a surviving child's live parent association, and explain a missing relative in the inspector. Keep the existing active-status, admission and pin guards; add neither a finalized-at guard nor a retained-relative refusal. No eligibility mark is required because the loop confirmation covers the history it removes. Loop deletion does not delete filesystem resources.

API run snapshots and list items expose the approval, as does the MCP `list_runs` summary. The browser offers the same confirmation for one inspected run or an explicit selection in Runs. MCP does not gain a history approval tool; listings cannot imply user consent.

## Consequences and phase boundary

Phase 1 introduced consent without automatic deletion. Phase 2 below consumes that consent under measured pressure. There is no delete-now command, automatic reset or promise of unlimited storage.

## Phase 2: pressure and scheduling (#322)

`StorageCapacityPort.read(path)` is a public dependency in `ContainerOverrides.storageCapacity`. Production composes `FsStorageCapacity`, using `fs.statfs` with bigint block counts and `bavail` (space available to this process). Data-directory and file-database-directory capacity are observed separately, including an external `GG_DB_URL`; in-memory SQLite has no database-volume observation. Invalid or unavailable readings fail closed and produce a visible unavailable status. Tests inject readings through this port, never patch filesystem internals or event writers.

Measure once at startup after migration/recovery, before listening, without reclaiming resources. After the HTTP listener accepts connections, start that observation's cleanup in the background and schedule measurements every 60 seconds, at most once per labeled observation per minute. Each pass reads the data path and, for file SQLite, the database directory once each; they may share a path or volume. Concurrent polls coalesce; API status reads return a cached observation and never start a pass. There is no after-write, after-confirmation or per-event cleanup hook. Stop cancels the timer, aborts removal between entries and awaits the active bounded operation; no further batch starts after stop. The production clock is real time; controlled tests use the public clock/capacity dependencies. A failed capacity attempt reports its own `checkedAt` and empty `volumes`, never an old reading as current.

Enter pressure if any observed volume has less than **min(1 GiB, 5% of total)** available. Leave pressure only when every observed volume has at least **min(2 GiB, 10%)**. These are engineering headroom and hysteresis parameters, not owner-approved retention thresholds: proportional bounds suit small volumes, absolute caps avoid unnecessary cleanup at tens of GiB free on large disks, and recovery headroom prevents oscillation. Adequate storage performs observation only and deletes nothing. Pressure never grants eligibility or broadens selection.

## Resource ownership and protection

Migration **0022_run_resource_ownership** adds `run_resources` (positive creation identity, producing run, resource kind/path, pending state and the copied confirming approval) and `run_resource_uses` (run/key/path use). Its unshipped definition also records the owned physical directory key, `workspace_references` and a singleton refresh epoch. Workspace references are live obligations, not ownership or consent. It does not infer ownership of existing files. The API composes `OwnedRunResources` around the workspace/artifact ports. Artifact publication receives the producing run ID; this changes `ArtifactStorePort.put` to require that argument. No event-log trigger or event-append statement changes.

| Resource                                 | Positive proof and cleanup boundary                                                                                                                                                                                                                                                                                                                                                                                  |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Run record and dependent rows            | Recheck owner, durable approval, terminal/finalized state and the entire parent/child/replay component inside the write transaction. Delete only those IDs, their events, sessions, timers, webhook receipts and usage rows. Prune their links from shared inbound deliveries; keep surviving deliveries. Remove only their now-unpinned draft snapshots, never unrelated orphan snapshots or published definitions. |
| Temporary workspace                      | Claim only a directory exclusively created by this process for that run. Store device, inode and birth time; a pre-existing run-shaped directory is unproven and never claimed. Record canonical uses for fixed/template directories too, without claiming ownership. Retained overlapping uses, configured fixed directories and unresolved retained template workspaces block removal.                             |
| Artifact file                            | Exclusively publish a complete synced temporary inode using a same-directory hard link, then remove the temporary name and record its identity/producing run. Existing untracked content-addressed bytes stay unproven. Shared puts record uses without transferring ownership. Verified repair of an owned corrupt artifact updates the stored identity, preserving its original owner.                             |
| Shared or retained-referenced resources  | Keep them. Recheck retained uses and initial/checkpoint threads, definition pins/definitions and event tails immediately before removal. Decode JSON values so escaped references count; damaged JSON or incomplete proof blocks removal.                                                                                                                                                                            |
| Links, substitutions and unrelated files | Never follow symbolic links/junctions for removal. Hard-linked files and workspaces containing links are preserved. Require the recorded creation identity and managed-root containment; replaced occupants, unrelated paths and unproven legacy resources stay. No broad directory sweep or path-name ownership inference.                                                                                          |

Admitted Event receipts stay with their retained inbound delivery source so deletion does not rewrite an admitted outcome as pending. Such immutable provenance can name a removed run; it is not a live parent/child dependency. Retained inbound payloads and Event/webhook admission intents are included in artifact-reference proof, including inputs whose execution has not started. Their retention does not confer deletion consent.

Artifact proof work is capped at 2,000 retained JSON documents and 2 MiB per resource. Exceeding either bound keeps the resource; it may become provable after other approved history is removed. This conservative budget avoids an unbounded JSON walk or a new per-event reference index. It does not grant consent to the retained history. Workspace checks also preserve actual canonical uses and any fixed-directory configuration; unresolved retained template usage is conservatively protected.

Explicit loop deletion remains ADR-0033's separate consent and database-only behavior. It removes its bookkeeping uses, but does not enqueue filesystem cleanup jobs. Resource ownership records left by that command do not become pressure eligibility merely because their run is absent.

## Batches, interruption and accounting

One pass examines at most 20 approved roots and deletes at most 500 run records, preserving complete components. Indexed traversal caps inspection at 501 component members; an oversized, incomplete, foreign, active or unfinished component is refused. Cursors rotate past protected work and reset safely on restart. Each selected component's rows, approvals and pending resource jobs commit atomically. Ordinary history paging uses surviving run IDs/timestamps; no partly deleted run is exposed. A large selected run's dependent SQL rows remain one atomic transaction, so the bounds are record/resource counts rather than a latency or WAL-size guarantee; storage errors roll back and warn.

Each pass reads at most 256 pending candidates and inventories/stages at most 32 resources. Referenced candidates do not consume the inventory budget, so blocked artifacts cannot starve workspaces later in the ordering. Both cursors wrap within a pass and advance only over considered work. Filesystem inventory streams entries outside every database transaction and publication gate, yields every 32 entries and admits at most 2,000 entries per resource. Larger or linked trees are preserved. The shared process gate serializes publication only against a short SQLite write transaction: reread the pending approval, owner and identity, recheck retained references, verify constant-size filesystem identities, rename into private quarantine, and durably change the journal key to the quarantined generation. No filesystem traversal or unlink runs inside that transaction or while holding the database statement lock. Workspace overlap probes use covering indexes over recorded physical directory keys; no retained-path resolution occurs inside this transaction. Replay admission also rechecks source existence in its own transaction.

After commit, remove only inventoried quarantine entries, checking realpath, creation identity, entry type and hard-link count again for each entry. Yield to the event loop after every entry, outside both locks; shutdown aborts between entries. An added or substituted entry refuses removal and retains the job. Bounds limit work counts, not filesystem-call latency or a large run's atomic SQL deletion time.

The original-key journal row is durable before rename. Quarantine paths hash the original key and creation identity. A staged job uses `quarantine:<generation hash>:<original key>` in the existing opaque journal key; its stored path, owner, identity and confirming approval stay unchanged. This separates a quarantined generation from a new publication at the original path. A crash after rename but before database commit is recovered by finding the same quarantine identity; if publication happens first, claiming the new inode durably moves the older pending generation to its quarantine key before recording the new generation. An interruption after commit or during unlink leaves a resumable quarantined job. Already missing bytes complete without extra credit. This is a journal state transition using migration 0022's existing columns, with no new migration, converter or historical ownership claim. Failed jobs retain their original consent; other jobs may proceed. There is no automatic eligibility restoration, reset, broad orphan collection or compaction.

`GET /system/storage` reports separate volume capacity, per-pass `deletedRuns` and `removedFileBytes`, current `reusableDatabaseBytes` (`freelist_count * page_size`), and whole-store pending/preserved resources. `preservedResources` counts every journaled resource currently kept, including shared, linked, unproven and deferred or queued resources, not just the current cursor window. Removed bytes are successfully unlinked file lengths, **not** a promise of physically freed blocks; sparse files, open handles, SQLite/WAL allocation and intervening writes can make OS free space differ. SQLite row deletion usually makes pages reusable without shrinking its OS file. Capacity is observed again only on the next scheduled sample. No `VACUUM` or unconditional compaction runs under pressure. An interrupted unlink whose commit/accounting is uncertain is not credited again on restart.

The web app shows a nonmodal, polite live status below the gateway notice: measured pressure cleaning only explicitly approved history, pressure with no eligible history that could be cleaned, or unavailable measurement/cleanup. It links to Runs for explicit review; observing it grants no consent. Preserved shared/linked/unproven/deferred resources are explained. Nothing eligible means warn and stop, never expand deletion. Warning placement/wording remain subject to owner product acceptance.

## Independent verification corrections (PR #412)

Artifact reads accept exactly the canonical form returned by `put`: `artifact:<lowercase kind>/<64 lowercase hex>`, where kind contains only lowercase ASCII letters, digits, `_` and `-`. Prefix/kind/hash case variants, alternate separators, extra path segments, encodings, whitespace and trailing newlines are missing references. The filesystem store enforces this boundary for the API download route and every engine consumer. Opaque run input can still contain arbitrary strings; a noncanonical string cannot resolve artifact bytes. Retained JSON proof decodes escapes and searches the same canonical key. There is no alternate-case compatibility path or stored rewrite.

Workspace physical identity is recorded when a workspace is claimed/used and when a fixed directory definition is created, saved or published. Native realpath resolves junctions, symbolic links, short names and case aliases; a missing suffix is appended to its deepest existing directory ancestor. Non-directory ancestors, non-missing errors and a 64-ancestor resolution bound produce unknown (`NULL`), never an unreferenced claim. Directory keys use platform case rules and end in a separator, preventing sibling-prefix confusion.

Migration 0022 maintains live source rows transactionally: version definition changes create/reset/remove fixed-directory obligations; workspace use insertion records a run obligation and resolves any template placeholder; deletion removes the matching source rows. A template run without recorded use has an unknown obligation. Draft snapshots get the same version trigger. Existing configurations are backfilled as unknown; old filesystem objects are not retroactively owned. Source triggers fire only on admission, version/relationship changes, use recording and deletion. No event/finalization/status append work is added.

A recorded path alone can become stale after an external alias change. Before workspace reclamation, a bounded sweep re-resolves at most **2,048 reference rows per pass**, outside every database transaction/publication gate, deduplicating equal path strings within the batch. Resolve at most 32 rows outside the lock, then apply one indexed, conditional SQL update for those observations and yield. This avoids a durable commit per reference while bounding every refresh statement to 32 rows; staging transactions are separate and contain no such refresh work. The epoch/index lets larger stores continue across passes; there is no maximum retained-path count. No workspace stages until that sweep completes. Unknown obligations still protect; an incomplete sweep retains pressure rather than claiming no eligible work. A restart begins a fresh epoch instead of trusting observations made before the process stopped. Updates compare source ID, path and prior epoch so a fresh recorded use is not overwritten by an older in-flight observation.

The staging transaction performs indexed unknown, ancestor-equality and descendant-range probes using the owned workspace's recorded physical key. The ancestor list depends on path depth, not history size. Null/equality/range probes use `workspace_references_physical_idx`; they do not load or JSON-parse retained runs or definitions. A final constant-size ownership/realpath check of the specific owned resource and managed roots still gates rename. Inventory and entry-by-entry purge remain outside the locks.

**Remaining filesystem race:** an external actor can create/retarget an alias after its row was observed and before quarantine rename. The data-directory lock serializes GraphGoblin, not arbitrary external filesystem changes, and Node offers no cross-tree filesystem snapshot. Refresh on every completed sweep and on each workspace use/definition publication detects changes before those observations; the next sweep detects later changes. The exposure is the current bounded sweep and reaping batch, rather than the lifetime of a saved definition. For more than 2,048 obligations a sweep spans multiple minute passes; this is a work bound, not a wall-clock freshness guarantee. The final owned-path identity check rejects substitutions of the candidate itself. We do not claim to eliminate an external mutation between observation and rename.

The 2,048-row sweep is an engineering throughput bound chosen to cover a 1,000-run store plus its fixed definitions in one pass while yielding for HTTP/execution work. Larger stores defer workspace staging until their sweep finishes, then can reclaim with the same indexed transaction. This replaces the round-2 32-path global refusal. The artifact budget remains 2,000 documents / 2 MiB and is independent of this workspace index.

Root traversal fills its bounded batch by wrapping within the same pass, so a newly approved older run is not deferred merely for falling before the last cursor. The 20-root / 500-record budgets remain. A concluding approved-candidate probe and whole-store pending count prevent `no-eligible` while approvals or potentially removable jobs remain, including new older approvals. A separate concluding reference census examines at most 256 pending jobs plus an overflow sentinel; unexamined work or concurrent writes make absence unproven and retain `pressure`. SQLite's existing `total_changes()`/`data_version` counters detect changes during this census without adding event hooks. Known protected or failed ownership proofs may remain with `no-eligible`; the notice still reports their full kept count. Counts do not alternate with cursor windows. This conservatively reports pressure rather than asserting absence when a bound prevents proof. No extra event/append hook or capacity measurement is introduced; the unshipped migration 0022 includes the workspace reference index.
