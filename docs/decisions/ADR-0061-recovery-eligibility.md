# ADR-0061 - Server-owned, observation-bound Resume and Replay

Date: 2026-10-27. Status: revised for the scan 3 known blockers on the capped path after integration with #412, #417 and #418 (#256, D-035).

## Context

The inspector needs current server eligibility, rather than guessing from a historical failure. #256 exposes main's recovery behavior; it does not prohibit deliberate Replay through effectful nodes or Resume after a completed resumable script failure. The orchestrator's scan 1 supersedes the earlier tightened interpretation.

## Decision

One engine policy computes the run read, Resume and Replay decisions. `GET /runs/{id}` and MCP expose the same `recovery`; HTTP and MCP commands require its reviewed `observedSeq`. A record advancing beyond the indexed evidence observation refuses as stale. The snapshot returns the decision record used by that read. Resume retains the validated status branch so a paused script failing during validation cannot become an unconsented retry.

Resume retains the run ID, definition, visit, thread and child identities, using main's status and recorded failure resumability. A completed `SCRIPT_EXIT_CODE` failure remains resumable after fixing the program. Non-resumable stop, deadline and unconfirmed-termination failures remain non-resumable. A failed parent owns recovery of its identified failed child and retries that exact child. Missing-session Resume uses #265's explicit fresh-session choice. Retrying an uncertain script requires explicit `retryUncertainScript: true`, recorded on `run.resumed`. A parent Resume durably records `childRecovery` with the exact child ID, immutable failure sequence (which identifies its script visit), child observation and any explicit script consent. The failure sequence comes from the child wake the parent actually consumed, rather than the child's later current failure. Already-admitted child work can advance before the parent command is admitted. The binding still names the older consumed failure; forwarding refuses its stale observation and the parent surfaces the newer outcome for fresh review instead of becoming stuck on its older failure. Ownership remains with that parent during pending execution, including after its status leaves `failed` and across restart. Forwarding uses only that stored observation. A changed observation refuses as `RECOVERY_STALE`; a newer child failure is propagated to the parent for a new review and fresh uncertain-script consent, never retried under the older consent.

Replay is available at a reached node in any source status, with usable pinned definition and state. It creates a new top-level run with a new ID and `replayOf`, seeded before the chosen node's first start. It keeps inherited values, counters and pinned subloop versions, starts new child runs and owns no source provider sessions. Source caller return defaults are dropped. A missing session may use deliberate Replay; a named-session policy may select the same missing session again.

Replay runs the path again for the new run: scripts, provider turns, child runs and deliveries after the selected node execute again if reached. The API/MCP description and inspector say this plainly. `recovery.replay[].effects` names knowable script, inference, subloop and delivery nodes on possible paths, including loopbacks. This is possible work, not a predicted branch. Selecting and confirming Replay provides ordinary consent. A path that re-executes the current uncertain script additionally requires explicit script consent, including when no dispatch marker survived and when Resume itself is non-resumable. The dedicated script dialog and the Replay picker's explicit checkbox provide that choice.

Neither action undoes or hides recorded effects. Replay leaves the source execution state, history, thread and result unchanged and never re-sends its own recorded deliveries. A fork that reaches its exit performs its own run's delivery. No exactly-once external-effect guarantee is claimed.

## Bounded recovery reads

A durable lifecycle event and its run-row projection can be acknowledged separately. Matching tail sequences alone do not establish a consistent failure. Recovery refuses as `RECOVERY_STALE` while the latest lifecycle status or failed payload disagrees with the row, without hiding the readable run. No script consent target is offered during that gap. The explanation is: "The recorded lifecycle and run status are still being synchronized. Refresh and review its current recovery choices." Both paused Resume paths atomically compare the reviewed event tail with their status claim; every Resume append also uses that exact expected tail. A failure committed after review or between claim and append therefore wins without a later `run.resumed` or a retry. Failed Resume uses the same reviewed-tail append guard.

Pinned-version reads decode stored JSON at the repository boundary. Malformed JSON is an unavailable definition; decoded but invalid shapes are refused by the same existing validation policy. Both keep run reads visible with `DEFINITION_UNAVAILABLE` and command refusals consistent. SQL and transport exceptions remain errors, rather than being caught as missing definitions.

Snapshots use `EventStorePort.recoveryFacts`: the latest lifecycle marker, latest failure, latest Resume and one reached-node existence check per node in the pinned definition. SQLite decodes at most three event payloads per examined run. Indexed MAX seeks use the existing `(run_id, type, seq)` index; migration 0025 adds the partial `run_events_reached_idx` on `(run_id, node_id, seq)` for `node.started`. Work is bounded by definition size and linked recovery depth, independently of accumulated history. Missing-session child proof and pending-parent ownership use the same bounded evidence. An event appended during the read cannot lend a newer sequence to older evidence. Full log reconstruction remains in admitted Replay and execution/restart, outside inspector polling. Unrelated damaged historical payloads are diagnosed when that history is read; current recovery evidence is always validated.

## Atomic fork admission

Migration 0024 reuses #412's indexed `replay_source_run_id` and adds only nullable `replay_intent_node_id` and `replay_intent_observed_seq` to the fork row. A unique index identifies `(source run, node, observedSeq)`, and a completeness CHECK requires both intent fields together with a non-null source and nonnegative sequence. Both intent fields may instead be null: main's existing/backfilled forks and lower-level source-only admissions have provenance without an observed recovery intent. Ordinary runs also have neither field. New REST, script-recovery and MCP Replay commands all use `RunManager.replay`, which always supplies the observed intent. There is one stored source fact; admission derives it from the initial thread, so #412's consent-revocation triggers see every fork. Additive ALTER statements preserve existing rows, columns, indexes and triggers; the generated snapshot records the same schema without relying on Drizzle Kit's table-rebuild/expression-index output.

The source observation is checked inside the transaction admitting the fork, alongside the fork row, initial state, queued event and pins. A failed transaction consumes nothing. If a commit acknowledgement is lost, storage finds the exact admitted fork and the original request returns it. A repeated caller receives `RECOVERY_STALE` with that `replayRunId`; the read and inspector link the existing fork. Adding the fork withdraws any affected deletion approvals through #412's relationship triggers; this changes consent metadata, not execution history. No source event is appended. Terminal event boundaries, SSE completion, finalization, delivery history and deletion readers require no new post-terminal event tolerance. The old consumed-intent-without-fork crash window is removed.

A node is part of the intent identity. Re-reading unchanged source history does not mint a second intent for the same node. New source execution events provide a new observation. Commands serialize per source run; the SQL uniqueness constraint also protects admission independently of that in-process lock. The existing one-manager-per-store ownership rule remains. The browser freezes dialog observations and uses native pointer click count to keep a multi-click in one intent; no debounce window is introduced.

## Refusal policy

Refusal codes equal HTTP and MCP codes. They are 409 except shutdown (503); missing/deleted/unowned runs use existing 404 `RUN_NOT_FOUND`.

Forwarding a changed child target uses the shared `RECOVERY_STALE` explanation: ?The run changed since it was shown. Refresh and review its current recovery choices.? An unidentifiable recorded child outcome explains: ?The recorded child failure cannot be identified. Review its history before recovering this parent.? An internal parent command with another observation explains: ?The parent recovery does not authorize this child observation. Review the current child failure through its parent.? Neither message retries work. Once the child has settled successfully or with an authored terminal outcome, normal child controls return even if its parent waits downstream. A historical Resume without a bound child intent does not invent consent; its child outcome is surfaced for review.

Historical corruption found during command reconstruction returns `STATE_UNAVAILABLE`: ?The recorded recovery history cannot be read. Repair or explicitly delete this history before recovering.? It does not require decoding unrelated history during polling.

## Consequences

Unavailable actions have visible text and associated accessible descriptions. A labelled Replay picker lets callers inspect every node's decision and possible repeated work. Errors refresh eligibility. Resume stays on the original ID and follows its next attempt (#116); Replay opens the exact new ID and links its source. Opening or cancelling dialogs dispatches nothing.

API/MCP clients must send the observed command contract and regenerate for the current snapshot/effect descriptions; no deprecated command shape is supported. Migrations 0024 and 0025 are data-preserving schema additions within the current store format, with no format reset or converter.
