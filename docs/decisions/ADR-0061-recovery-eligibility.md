# ADR-0061 - Server-owned, observation-bound Resume and Replay

Date: 2026-10-26. Status: revised for orchestrator scan 1 of 3 and integration with #412, #417 and #418 (#256, D-035).

## Context

The inspector needs current server eligibility, rather than guessing from a historical failure. #256 exposes main's recovery behavior; it does not prohibit deliberate Replay through effectful nodes or Resume after a completed resumable script failure. The orchestrator's scan 1 supersedes the earlier tightened interpretation.

## Decision

One engine policy computes the run read, Resume and Replay decisions. `GET /runs/{id}` and MCP expose the same `recovery`; HTTP and MCP commands require its reviewed `observedSeq`. A record advancing beyond the history read refuses as stale. The snapshot returns the decision record used by that read. Resume retains the validated status branch so a paused script failing during validation cannot become an unconsented retry.

Resume retains the run ID, definition, visit, thread and child identities, using main's status and recorded failure resumability. A completed `SCRIPT_EXIT_CODE` failure remains resumable after fixing the program. Non-resumable stop, deadline and unconfirmed-termination failures remain non-resumable. A failed parent owns recovery of its identified failed child and retries that exact child. Missing-session Resume uses #265's explicit fresh-session choice. Retrying an uncertain script requires explicit `retryUncertainScript: true`, recorded on `run.resumed` and propagated to children.

Replay is available at a reached node in any source status, with usable pinned definition and state. It creates a new top-level run with a new ID and `replayOf`, seeded before the chosen node's first start. It keeps inherited values, counters and pinned subloop versions, starts new child runs and owns no source provider sessions. Source caller return defaults are dropped. A missing session may use deliberate Replay; a named-session policy may select the same missing session again.

Replay runs the path again for the new run: scripts, provider turns, child runs and deliveries after the selected node execute again if reached. The API/MCP description and inspector say this plainly. `recovery.replay[].effects` names knowable script, inference, subloop and delivery nodes on possible paths, including loopbacks. This is possible work, not a predicted branch. Selecting and confirming Replay provides ordinary consent. A path that re-executes the current uncertain script additionally requires explicit script consent, including when no dispatch marker survived and when Resume itself is non-resumable. The dedicated script dialog and the Replay picker's explicit checkbox provide that choice.

Neither action undoes or hides recorded effects. Replay leaves the source execution state, history, thread and result unchanged and never re-sends its own recorded deliveries. A fork that reaches its exit performs its own run's delivery. No exactly-once external-effect guarantee is claimed.

## Atomic fork admission

Migration 0024 reuses #412's indexed `replay_source_run_id` and adds only nullable `replay_intent_node_id` and `replay_intent_observed_seq` to the fork row. A unique index identifies `(source run, node, observedSeq)`, and a completeness CHECK requires both intent fields together with a non-null source and nonnegative sequence. Both intent fields may instead be null: main's existing/backfilled forks and lower-level source-only admissions have provenance without an observed recovery intent. Ordinary runs also have neither field. New REST, script-recovery and MCP Replay commands all use `RunManager.replay`, which always supplies the observed intent. There is one stored source fact; admission derives it from the initial thread, so #412's consent-revocation triggers see every fork. Additive ALTER statements preserve existing rows, columns, indexes and triggers; the generated snapshot records the same schema without relying on Drizzle Kit's table-rebuild/expression-index output.

The source observation is checked inside the transaction admitting the fork, alongside the fork row, initial state, queued event and pins. A failed transaction consumes nothing. If a commit acknowledgement is lost, storage finds the exact admitted fork and the original request returns it. A repeated caller receives `RECOVERY_STALE` with that `replayRunId`; the read and inspector link the existing fork. Adding the fork withdraws any affected deletion approvals through #412's relationship triggers; this changes consent metadata, not execution history. No source event is appended. Terminal event boundaries, SSE completion, finalization, delivery history and deletion readers require no new post-terminal event tolerance. The old consumed-intent-without-fork crash window is removed.

A node is part of the intent identity. Re-reading unchanged source history does not mint a second intent for the same node. New source execution events provide a new observation. Commands serialize per source run; the SQL uniqueness constraint also protects admission independently of that in-process lock. The existing one-manager-per-store ownership rule remains. The browser freezes dialog observations and uses native pointer click count to keep a multi-click in one intent; no debounce window is introduced.

## Refusal policy

Refusal codes equal HTTP and MCP codes. They are 409 except shutdown (503); missing/deleted/unowned runs use existing 404 `RUN_NOT_FOUND`.

## Consequences

Unavailable actions have visible text and associated accessible descriptions. A labelled Replay picker lets callers inspect every node's decision and possible repeated work. Errors refresh eligibility. Resume stays on the original ID and follows its next attempt (#116); Replay opens the exact new ID and links its source. Opening or cancelling dialogs dispatches nothing.

API/MCP clients must send the observed command contract and regenerate for the current snapshot/effect descriptions; no deprecated command shape is supported. Migration 0024 is a data-preserving schema addition within the current store format, with no format reset or converter.
