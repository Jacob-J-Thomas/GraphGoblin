# ADR-0061 - Server-owned, observation-bound Resume and Replay

Date: 2026-10-25. Status: Accepted scope, implementation of #256.

## Context

Run status and the historical `failure.resumable` flag do not establish that an action is available now. A child can belong to a failed parent, a provider session may need an explicit fresh start, and an interrupted script may already have produced its effect. A stale tab must not turn an old recovery choice into a new attempt.

## Decision

The engine computes a read-only `RunRecovery` policy from the current run, its pinned definition, initial state and event log. `GET /runs/{id}` returns it as `recovery`; MCP `get_run` returns the same snapshot. The inspector renders these decisions and text. The Resume and Replay commands evaluate this same policy again. Stored failures remain historical facts; callers must use current eligibility instead of interpreting `failure.resumable` as permission.

Resume retains the run ID, thread, definition, visit and child identities. A paused park returns to the same wait. A supported failed node retries in place. When a failed parent's failure identifies its child, ordinary child recovery directs the caller to that exact parent; parent Resume recursively retries the same child. An interrupted parent which never durably adopted a failure does not own an independent child recovery. Missing-session fresh-start recovery remains a separate choice on the failed inference run (#265). An uncertain script needs `retryUncertainScript: true` from the deliberately opened recovery dialog; plain Resume refuses it. Consent is recorded on `run.resumed` and propagated through parent/child resumes. A completed failed script (including the typed `SCRIPT_EXIT_CODE` cause without optional provenance) cannot be resumed: repeating known external work requires a separately started execution.

Replay is available only on terminal execution history other than cancellation, at a node the source reached, with usable definition and state. It admits a separate top-level run with a new ID and `replayOf`, seeded just before that node's first start, retaining pinned definitions and inherited state. It does not undo external work. A conservative graph reachability check refuses a selection that can revisit recorded script dispatches, child admissions, submitted/uncertain provider work, or recorded webhook/file return deliveries, including paths through loopbacks. The recorded current script uncertainty also blocks paths into that script when no dispatch marker survived; an earlier Replay node cannot bypass consent. Proven pre-dispatch refusal is not a consumed effect. The current uncertain script has a dedicated explicit-consent Replay path, provided no other consumed work would repeat. A fork after external work retains its recorded output without dispatching that earlier work. Recorded deliveries are never resent by replaying their exit.

The recovery read fetches history before its decision record and returns that same record in the snapshot. It never attaches a newer history sequence to an older consent target. If the record advanced beyond the history read, all choices refuse as `RECOVERY_STALE`; there is no automatic read retry. Resume keeps the validated status branch, so a paused script failing during validation cannot become an unconsented failed-script retry.

Both commands require `observedSeq` from the reviewed read. The UI freezes this sequence while a dialog is open. A pointer multi-click is one intent even if a fresh eligible failure renders between clicks: the inspector uses the browser click count, with no custom debounce window. Keyboard activation can start a new deliberate choice. Commands serialize per source run; a second Resume of an observed failure is refused even if execution has already failed again. Replay first conditionally appends `run.replay_requested { nodeId, replayRunId, observedSeq }` on its source. This consumes the observed intent durably before fork admission, and compare-and-set protects against another caller. The fork's first event links back to the source. This audit changes the source event sequence, never its execution thread or result. A lost acknowledgement does not authorize resubmitting the old intent; inspect the requested run ID and review a fresh snapshot. A crash after the audit but before admission can leave a requested fork absent. A fresh deliberate decision is required; no automatic retry manufactures a second fork.

This is command deduplication, not an exactly-once external-effect guarantee. The existing one-manager-per-store lock remains required. No SQL migration or data reset is needed: the additional event fields are additive current-format facts. API and MCP callers must send the observed command contract; no legacy command shape is retained.

## Refusal policy

HTTP refusal codes equal the policy codes. Refusals are 409 except shutdown (503); an absent, deleted or unowned run is 404 `RUN_NOT_FOUND`. Reasons include visible explanatory text, not only disabled controls.

## Consequences

Unavailable Replay selections remain inspectable in a labelled node picker with text associated through `aria-describedby` and announced politely. Errors remain visible and refresh the run. Pending buttons disable further interaction after the pending render; server checks refuse duplicate requests from double-click races, multiple tabs and stale clients. A successful Resume stays on the original ID and uses the #116 attempt follower. A successful Replay navigates to its exact new ID and visibly links its source. Opening or cancelling either consent dialog makes no command.

The conservative policy can refuse useful debugging forks through effectful nodes; it does not invent effect rollback or recipient deduplication. Relaxing that rule would require a separate explicit repeat-effect contract. Product acceptance remains the owner's post-merge step; agent checks do not complete it.
